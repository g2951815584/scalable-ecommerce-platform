## 1. 引言

### 1.1 编写目的

本文档描述可扩展电子商务平台的业务需求与技术需求，作为后续概要设计、详细设计、开发、测试与验收的依据。文档面向：产品与业务方、开发工程师、测试工程师、运维工程师。

### 1.2 项目背景

平台以**微服务架构**构建，业务能力按领域拆分为独立服务，各服务可独立开发、部署与横向扩容。整体通过容器化（Docker / Docker Compose）编排，通过 API 网关统一对外暴露入口。

项目的核心价值在于以真实电商业务为载体验证分布式系统设计能力：服务拆分边界、服务间通信、数据一致性、服务发现、集中式日志与监控、CI/CD 自动化。

### 1.3 项目目标

| 编号 | 目标 | 达成判据 |
|---|---|---|
| G-1 | 支撑买家完成"浏览 → 加购 → 下单 → 支付 → 收货"完整闭环 | 端到端主流程可通过前端界面走通 |
| G-2 | 六大业务服务可独立部署与独立扩容 | 单个服务重新部署不影响其他服务可用性 |
| G-3 | 具备可观测能力 | 任一请求可跨服务追溯，异常可告警 |
| G-4 | 具备自动化交付能力 | 代码提交后自动完成构建、测试、镜像发布 |

### 1.4 术语表

| 术语 | 说明 |
|---|---|
| SKU | 库存量单位，商品的最小可售规格（如"某款T恤-M码-黑色"） |
| SPU | 标准化产品单元，一组 SKU 的聚合（如"某款T恤"） |
| 购物车 | 用户下单前的临时商品暂存区，不占用库存 |
| 订单 | 用户确认购买后生成的交易凭证，锁定价格快照 |
| 库存预占 | 下单时临时锁定库存，超时未支付则释放 |
| Saga | 分布式事务编排模式，通过一系列本地事务 + 补偿操作保证最终一致性 |
| 幂等 | 同一请求重复执行的结果与执行一次相同 |
| API 网关 | 所有外部流量的唯一入口，负责路由、鉴权、限流 |
| MVP | 最小可用版本 |

## 3. 项目范围

### 3.1 范围内（In Scope）

- 用户注册、登录、鉴权、个人资料与收货地址管理
- 商品目录：分类、SPU/SKU、商品详情、搜索与筛选
- 库存管理与库存预占/释放
- 购物车增删改查
- 订单创建、状态流转、取消、超时关闭
- 支付对接第三方网关（Stripe / PayPal）、支付回调、退款
- 通知：订单确认、支付成功、发货、退款结果的邮件/短信触达
- API 网关、服务注册发现、集中式日志、指标监控
- 容器化与编排、CI/CD 流水线
- 买家商城端 Web 界面、运营管理后台 Web 界面

### 3.2 范围外（Out of Scope）

- 个性化推荐算法、广告投放系统
- 自建仓储/物流调度系统（仅对接第三方物流单号）
- 直播带货、社区/内容板块
- 多租户 SaaS 化的商家入驻体系
- 自建支付网关（仅对接第三方）
- 移动原生 App（本期仅 Web）

> 范围外条目为明确排除项，如需纳入需走需求变更流程。

## 4. 功能性需求

### 4.1 用户服务（FR-US）

| 编号 | 需求名称 | 需求描述 | 优先级 |
|---|---|---|---|
| FR-US-001 | 用户注册 | 支持邮箱或手机号注册；校验唯一性；密码加密存储；注册后默认分配"注册买家"角色 | 高 |
| FR-US-002 | 邮箱/手机验证 | 注册后发送验证码，验证通过方可下单 | 高 |
| FR-US-003 | 用户登录 | 支持账号密码登录，返回访问令牌与刷新令牌 | 高 |
| FR-US-004 | 令牌刷新与登出 | 访问令牌过期前可用刷新令牌换取新令牌；登出使刷新令牌失效 | 高 |
| FR-US-005 | 密码找回 | 通过邮箱/短信验证码重置密码 | 高 |
| FR-US-006 | 个人资料维护 | 查看与修改昵称、头像、性别、生日等非关键信息 | 中 |
| FR-US-007 | 收货地址管理 | 增删改查收货地址，支持设置默认地址 | 高 |
| FR-US-008 | 角色与权限管理 | 管理员可为账号分配角色，角色决定后台可见菜单与可执行操作 | 高 |
| FR-US-009 | 账号状态管理 | 管理员可禁用/启用账号；禁用账号无法登录与下单 | 中 |
| FR-US-010 | 第三方登录 | 支持 Google / GitHub OAuth 登录 | 低 |

**异常流**：注册时账号已存在 → 提示"该账号已注册"；登录连续失败 5 次 → 锁定 15 分钟；令牌过期 → 返回 401 并由前端引导重新登录。

| FR-CAT-004 | 商品上下架 | 支持上架/下架；下架商品对买家不可见，但已生成的订单不受影响 | 高 |
| FR-CAT-005 | 商品列表 | 买家端按分类分页浏览商品，支持排序（销量、价格升降、上架时间） | 高 |
| FR-CAT-006 | 商品搜索 | 按关键词搜索商品标题与描述，支持分类/价格区间过滤 | 高 |
| FR-CAT-007 | 商品详情 | 展示商品主图、图集、描述、规格、价格区间、可售库存、评价数 | 高 |

| FR-CAT-010 | 库存预占 | 下单时预占库存；预占超时未支付自动释放 | 高 |

| FR-CAT-014 | 商品标签 | 支持为商品打标签（新品、热销、促销）并在列表页展示 | 低 |

**异常流**：下单时库存不足 → 返回"库存不足"并阻止下单；并发超卖 → 由预占机制保证不超卖；商品已下架 → 详情页提示且不可加购。

| FR-CART-005 | 选中结算 | 支持勾选部分商品进入结算流程 | 高 |
| FR-CART-006 | 失效商品处理 | 商品下架或库存为 0 时标记失效，结算时自动剔除 | 高 |

### 4.4 订单服务（FR-ORD）

| 编号 | 需求名称 | 需求描述 | 优先级 |
|---|---|---|---|
| FR-ORD-001 | 创建订单 | 由购物车选中项生成订单，快照商品名、规格、单价、数量 | 高 |
| FR-ORD-002 | 订单金额计算 | 计算商品总额、运费、优惠、应付金额 | 高 |
| FR-ORD-003 | 收货信息确认 | 下单时指定收货人、电话、地址，支持选择已有地址 | 高 |
| FR-ORD-004 | 订单状态流转 | 待支付 → 已支付 → 待发货 → 已发货 → 已收货 → 已完成；支持已取消/已关闭 | 高 |
| FR-ORD-005 | 超时未支付关闭 | 待支付订单超时（默认 30 分钟）自动关闭并释放库存 | 高 |
| FR-ORD-006 | 订单查询 | 买家查看本人订单列表与详情，支持按状态筛选 | 高 |
| FR-ORD-007 | 订单取消 | 未支付订单买家可自行取消；已支付订单需走退款流程 | 高 |
| FR-ORD-008 | 发货处理 | 仓储人员录入物流公司 + 单号，订单进入已发货 | 高 |
| FR-ORD-009 | 确认收货 | 买家确认收货后订单完成，触发可评价 | 高 |
| FR-ORD-010 | 自动确认收货 | 发货后超过 N 天未确认，系统自动确认收货 | 中 |
| FR-ORD-011 | 后台订单管理 | 订单运营按订单号/用户/状态/时间检索订单，支持改价、备注、强制关闭 | 高 |
| FR-ORD-012 | 订单备注 | 买家与客服均可添加备注，双方可见范围区分 | 低 |
| FR-ORD-013 | 订单列表导出 | 财务/运营按条件导出订单数据（CSV） | 中 |
| FR-ORD-014 | 超卖与异常订单处理 | 支付成功但库存扣减失败时进入异常队列，人工介入或自动退款 | 高 |

**异常流**：创建订单时库存预占失败 → 整单失败并提示具体缺货商品；支付成功但订单已关闭 → 自动发起退款；重复提交订单 → 通过幂等键去重。

## 5. 前端功能范围

前端划分为两个独立应用：**买家商城端**（面向 C 端消费者）与**运营管理后台**（面向内部角色）。

### 5.1 买家商城端

| 模块 | 页面 | 核心功能 |
|---|---|---|
| 账户 | 注册页 / 登录页 | 注册、登录、第三方登录、找回密码 |
| 账户 | 个人中心 | 资料修改、密码修改、收货地址管理 |
| 商品 | 首页 | 分类导航、推荐位（静态配置）、热销商品 |
| 商品 | 分类/列表页 | 分页浏览、排序、筛选（分类、价格区间） |
| 商品 | 搜索页 | 关键词搜索、结果排序与筛选 |
| 商品 | 商品详情页 | 图集、规格选择、库存显示、加购、立即购买、评价查看 |
| 购物车 | 购物车页 | 勾选、改数量、删除、失效商品提示、去结算 |
| 订单 | 结算页 | 收货地址选择/新增、商品清单确认、运费与金额展示、提交订单 |
| 订单 | 支付页 | 渠道选择（Stripe/PayPal）、跳转支付、支付结果展示 |

## 6. 非功能性需求

### 6.1 可扩展性（NFR-SC）

| 编号 | 需求 |
|---|---|
| NFR-SC-001 | 每个业务服务必须为无状态设计，会话与缓存外置，以支持多实例水平扩容 |
| NFR-SC-002 | 各服务可独立扩容，扩容某服务不得要求其他服务同步扩容 |
| NFR-SC-003 | 数据库按服务独占，禁止跨服务直连他人数据库 |
| NFR-SC-004 | 读多写少的场景（商品目录）需支持引入缓存层降低数据库压力 |
| NFR-SC-005 | 异步链路（通知、对账）需通过消息队列解耦，避免同步阻塞主流程 |

### 6.2 可用性与可靠性（NFR-AV）

| 编号 | 需求 |
|---|---|
| NFR-AV-001 | 单个业务服务实例故障不得导致平台整体不可用 |
| NFR-AV-002 | 服务依赖故障时需具备降级能力（如推荐位、评价数可缺失） |
| NFR-AV-003 | 关键数据（订单、支付流水）不得丢失，需有持久化与备份策略 |
| NFR-AV-004 | 支付、订单创建等关键操作必须幂等，重复请求不得产生重复业务结果 |
| NFR-AV-005 | 支付回调丢失需有补偿机制（定时查询 + 人工介入） |
| NFR-AV-006 | 所有服务需提供健康检查端点，供编排系统自动重启不健康实例 |

### 6.3 性能（NFR-PF）

| 编号 | 需求 |
|---|---|
| NFR-PF-001 | 商品浏览类读接口响应需明显快于下单类写接口，读接口应优先走缓存 |
| NFR-PF-002 | 下单链路中非必需步骤（通知、积分、统计）必须异步化，不得阻塞下单响应 |
| NFR-PF-003 | 数据库需对高频查询字段建立索引；订单、流水表需支持按时段归档 |
| NFR-PF-004 | 购物车等高频读写数据需存放于高性能存储，避免直接压主库 |

### 6.4 安全性（NFR-SE）

| 编号 | 需求 |
|---|---|
| NFR-SE-001 | 密码必须加盐哈希存储，禁止明文或可逆加密 |
| NFR-SE-002 | 全链路使用 HTTPS，服务间通信需有身份校验 |
| NFR-SE-003 | 鉴权在网关统一收口，后端服务需校验调用来源与用户身份 |
| NFR-SE-004 | 平台不得存储银行卡号、CVV 等支付敏感信息 |
| NFR-SE-005 | 需防范 OWASP Top 10 风险，重点覆盖注入、越权、XSS、CSRF |
| NFR-SE-006 | 越权访问必须拦截：买家只能访问本人购物车、订单与地址 |
| NFR-SE-007 | 密钥、数据库口令、第三方 API Key 必须通过环境变量或密钥管理注入，禁止入库入仓 |
| NFR-SE-008 | 支付回调必须验签，防止伪造回调 |
| NFR-SE-009 | 后台管理接口需独立鉴权并记录操作审计日志 |

### 6.5 可观测性与可维护性（NFR-OB）

| 编号 | 需求 |
|---|---|
| NFR-OB-001 | 日志格式统一结构化（含时间、服务名、追踪 ID、级别、消息） |
| NFR-OB-002 | 所有服务日志集中采集，支持按追踪 ID 跨服务检索 |
| NFR-OB-003 | 需采集接口 QPS、耗时分布、错误率、依赖健康度等指标 |
| NFR-OB-004 | 关键指标需配置告警阈值并支持通知到人 |
| NFR-OB-005 | 代码需有单元测试与接口测试，纳入 CI 自动化执行 |
| NFR-OB-006 | 各服务需提供自动生成的 API 文档 |

### 6.6 兼容性与合规（NFR-CP）

| 编号 | 需求 |
|---|---|
| NFR-CP-001 | 买家端需兼容主流浏览器最近两个大版本及移动端浏览器 |
| NFR-CP-002 | 金额计算需使用定点数，禁止浮点误差 |
| NFR-CP-003 | 金额与时间存储需明确时区与币种口径（本期单币种、UTC 存储） |
| NFR-CP-004 | 用户个人信息采集需最小化，支持账号注销与数据删除 |

| 购物车服务 | 购物车、购物车明细 |
| 订单服务 | 订单、订单明细、订单状态流转记录、收货信息快照、物流信息 |
| 支付服务 | 支付单、退款单、交易流水、对账差异记录 |
| 通知服务 | 通知模板、发送记录、用户通知偏好 |

### 7.2 核心实体清单

| 实体 | 归属 | 关键属性（概要） | 说明 |
|---|---|---|---|
| 用户 | 用户服务 | 账号、密码哈希、状态、角色 | 注册主体 |
| 角色/权限 | 用户服务 | 角色名、权限集合 | 后台鉴权基础 |
| 收货地址 | 用户服务 | 收货人、电话、地区、详细地址、是否默认 | 下单引用 |

| SKU | 商品目录 | 规格、价格、可售库存、预占库存 | 最小可售单位 |
| 库存流水 | 商品目录 | SKU、变更量、变更类型、关联单号、操作人 | 库存可追溯 |
| 商品评价 | 商品目录 | 用户、SKU、评分、内容、时间 | 已收货后产生 |
| 购物车项 | 购物车服务 | 用户、SKU、数量、选中状态 | 登录/游客均可有 |
| 订单 | 订单服务 | 订单号、用户、金额、状态、收货快照 | 交易主凭证 |
| 订单明细 | 订单服务 | 订单号、SKU、商品快照、单价、数量 | 价格快照防篡改 |
| 订单状态记录 | 订单服务 | 订单号、原状态、新状态、时间、操作人 | 状态流转可追溯 |
| 物流信息 | 订单服务 | 订单号、物流公司、单号、发货时间 | 发货环节产生 |
| 支付单 | 支付服务 | 订单号、渠道、金额、状态、第三方单号 | 一次支付对应一单 |
| 退款单 | 支付服务 | 订单号、支付单号、金额、状态、原因 | 支持部分退款 |
| 交易流水 | 支付服务 | 类型、金额、渠道、状态、时间 | 对账依据 |
| 通知模板 | 通知服务 | 编码、渠道、标题、正文、变量 | 可配置 |
| 发送记录 | 通知服务 | 收件人、渠道、模板、状态、失败原因 | 可追溯 |

### 7.3 数据一致性要求

- **强一致**：库存预占与扣减、支付状态更新 —— 必须保证不超卖、不重复扣款
- **最终一致**：订单状态与通知发送、库存扣减与销量统计、支付流水与对账数据 —— 允许秒级延迟，通过事件驱动达成
- **快照不可变**：订单明细中的商品名、规格、单价一经生成不得随商品变更而改变

## 9. 约束与假设

### 9.1 技术约束

- 后端服务使用 Python 实现，微服务框架以 FastAPI 为基础（详见概要架构设计）
- 全部服务容器化，本地与测试环境通过 Docker Compose 编排
- 服务间通过 REST（同步）与消息队列（异步）通信
- 必须包含 API 网关、服务注册发现、集中式日志三项平台能力

### 9.2 假设

- 第三方支付/邮件/短信服务在开发与测试阶段使用其沙箱环境
- 本期为单币种（人民币或美元二选一，实施前确定）、单时区口径
- 商品图片存放于对象存储，由商品运营上传
- 平台初期为单一自营商家，不涉及多商家结算分账

### 9.3 依赖

- 第三方支付、邮件、短信服务可用性
- 容器编排环境（本地为 Docker Desktop，生产为目标集群）

## 10. 验收标准

| 编号 | 验收项 | 通过判据 |
|---|---|---|
| AC-01 | 主流程闭环 | 买家从注册到确认收货全流程可在前端走通，无阻断性缺陷 |
| AC-02 | 服务独立性 | 服务清单中的各服务可单独构建镜像、单独启动、单独重启 |
| AC-03 | 网关收口 | 关闭网关后所有外部接口不可用；网关可正确路由至各服务 |
| AC-04 | 鉴权有效性 | 无令牌访问受保护接口返回 401；买家无法访问他人订单（越权返回 403） |
| AC-05 | 库存正确性 | 并发下单场景下不出现超卖；超时未支付订单可正确释放库存 |
| AC-06 | 支付幂等 | 重复回调不产生重复入账；退款重复请求被拒绝 |
| AC-07 | 异步解耦 | 通知服务不可用时，下单与支付主流程仍能成功，通知事后补偿 |
| AC-08 | 服务发现 | 扩容某服务实例后，网关无需重启即可将流量分发至新实例 |
| AC-09 | 可观测性 | 可通过追踪 ID 检索到一次下单请求在所有经过服务中的日志 |
| AC-10 | 自动化交付 | 提交代码后自动完成构建、测试、镜像发布，失败可定位原因 |
| AC-11 | 文档齐备 | 各服务提供可访问的自动生成 API 文档 |

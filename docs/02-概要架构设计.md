### 1.2 分层职责

| 层 | 组成 | 职责 |
|---|---|---|
| 接入层 | Traefik 网关 | 统一入口、路由转发、令牌校验、限流熔断、跨域处理 |
| 注册层 | Consul | 服务实例注册与健康探测，网关动态感知实例变化 |
| 业务层 | 六个微服务 | 各自领域的业务逻辑与数据管理 |
| 异步层 | RabbitMQ | 领域事件投递、主流程解耦、失败重试 |
| 数据层 | PostgreSQL × 6、Redis | 各服务独占库 + 共享缓存/会话存储 |
| 观测层 | ELK、Prometheus、Grafana | 日志聚合、指标采集、可视化告警 |

## 3. 服务边界与职责

### 3.1 服务划分

| 服务 | 端口（建议） | 核心职责 | 对外接口前缀 |
|---|---|---|---|
| 用户服务 user-service | 8001 | 注册、登录、令牌、资料、地址、角色权限 | `/api/v1/users`, `/api/v1/auth` |
| 商品目录服务 catalog-service | 8002 | 分类、SPU/SKU、库存、评价 | `/api/v1/products`, `/api/v1/categories` |
| 购物车服务 cart-service | 8003 | 购物车增删改查、结算前校验 | `/api/v1/cart` |
| 订单服务 order-service | 8004 | 订单创建、状态流转、发货、售后 | `/api/v1/orders` |
| 支付服务 payment-service | 8005 | 支付单、第三方对接、退款、对账 | `/api/v1/payments` |
| 通知服务 notification-service | 8006 | 模板管理、邮件短信发送、重试 | `/api/v1/notifications` |

每个服务内部统一采用分层结构：`api`（路由层）→ `service`（业务层）→ `repository`（数据访问层），外挂 `models`（ORM 实体）、`schemas`（Pydantic 契约）、`core`（配置、日志、异常）。

### 3.2 服务拆分依据

- **按业务能力拆分**：每个服务对应一个可独立演进的业务域，避免按技术分层拆成"订单表服务""订单接口服务"这类贫血切分。
- **数据所有权唯一**：一个实体只由一个服务写入，其他服务只能通过接口或事件读取，杜绝双写。
- **变更频率对齐**：商品目录变更频繁、支付逻辑稳定，拆开后互不干扰发布节奏。
- **故障隔离**：通知服务不可用不得影响下单（对应 AC-07）。

### 3.3 关键边界约定

| 事项 | 约定 |
|---|---|
| 商品详情展示库存 | 购物车与订单不复制库存字段，实时向商品目录服务查询 |
| 订单商品信息 | 下单瞬间快照至订单明细，之后不再回查商品库（满足快照不可变） |
| 用户信息引用 | 订单仅存 user_id 与收货信息快照，不跨库联表查用户 |
| 支付与订单 | 支付服务只认 order_no，订单状态由订单服务自身维护，靠事件驱动变更 |

## 4. 通信设计

### 4.1 同步通信（REST）

| 调用方 | 被调方 | 场景 | 说明 |
|---|---|---|---|
| 网关 | 全部服务 | 客户端请求转发 | 携带用户身份头 |
| 购物车服务 | 商品目录服务 | 校验 SKU 有效性与库存 | 结算前必查 |
| 订单服务 | 商品目录服务 | 库存预占 / 释放 / 扣减 | 下单关键路径，需超时与重试控制 |
| 订单服务 | 用户服务 | 校验收货地址归属 | 下单时一次 |
| 支付服务 | 订单服务 | 查询订单金额与状态 | 发起支付前校验 |
| 订单服务 | 支付服务 | 主动查询支付结果 | 回调丢失时补偿 |

**约定**：

- 统一 `/api/v1` 版本前缀，版本号变更才做不兼容调整
- 服务间调用必须设置连接与读取超时，禁止无超时调用
- 幂等：写操作需携带幂等键（`Idempotency-Key`），服务端按键去重
- 重试：仅对幂等读接口与超时类错误重试，采用指数退避
- 熔断：下游连续失败达阈值即熔断，返回降级结果而非阻塞

### 4.2 异步通信（事件）

| 事件名 | 生产者 | 消费者 | 用途 |
|---|---|---|---|
| `user.registered` | 用户服务 | 通知服务 | 发送欢迎/验证邮件 |
| `order.created` | 订单服务 | 支付服务、通知服务 | 生成支付单、发送下单确认 |
| `order.paid` | 订单服务 | 商品目录服务、通知服务 | 正式扣减库存、发送支付成功通知 |
| `order.cancelled` | 订单服务 | 商品目录服务、支付服务 | 释放预占库存、关闭支付单 |
| `order.shipped` | 订单服务 | 通知服务 | 发送发货通知含物流单号 |
| `payment.succeeded` | 支付服务 | 订单服务 | 驱动订单进入已支付 |
| `payment.failed` | 支付服务 | 订单服务、通知服务 | 标记支付失败、通知用户 |
| `payment.refunded` | 支付服务 | 订单服务、通知服务 | 更新订单状态、发送退款通知 |
| `stock.low` | 商品目录服务 | 通知服务 | 低库存预警给运营 |

**约定**：

- 事件信封统一包含：`event_id`、`event_type`、`occurred_at`、`trace_id`、`payload`
- 消费端必须幂等，按 `event_id` 去重（Redis 记录已处理事件）
- 消费失败进死信队列，达到重试上限后落库并告警，支持人工重放
- 事件只携带必要字段（通常是 ID + 关键状态），消费方按需回查，避免事件体膨胀

### 4.3 通信方式选择原则

| 场景 | 选择 | 原因 |
|---|---|---|
| 需即时结果（库存校验、地址校验） | 同步 REST | 结果决定下一步走向 |
| 通知、统计、对账 | 异步事件 | 与主流程无关，失败可重试 |
| 状态变更广播（订单/支付状态） | 异步事件 | 多消费方，避免生产者逐个同步调用 |

## 5. 数据设计

### 5.1 数据架构原则

- **一服务一库**：六个独立 PostgreSQL 库，账号权限隔离，禁止跨库访问
- **无共享表**：跨服务需要的数据通过接口获取或事件同步，必要时在本地建只读副本
- **快照隔离**：订单明细保存商品名、规格、单价快照，不受后续商品变更影响
- **读写分离预留**：商品目录等读密集服务预留只读副本接入能力

### 5.2 缓存策略

| 数据 | 存储 | 策略 |
|---|---|---|
| 商品详情 | Redis | 缓存旁路模式，商品变更时主动失效 |
| 分类树 | Redis | 长期缓存，变更时刷新 |
| 购物车 | Redis（主）+ PostgreSQL（持久化） | 热数据在 Redis，异步落库保证不丢 |
| 库存可售量 | Redis（预占计数）+ PostgreSQL（权威） | Redis 承担高并发预占，DB 为准 |
| 会话与令牌黑名单 | Redis | 设置与令牌同周期 TTL |
| 幂等键 | Redis | 按业务设置 TTL（下单 24 小时，支付 7 天） |

**缓存一致性**：采用"先写库、再删缓存"策略，避免脏数据长期驻留；对强一致场景（库存）不做纯缓存读，以数据库校验为准。

### 5.3 一致性设计

### 5.3.1 库存一致性

库存是最容易出问题的环节，采用**预占 + 确认 + 超时释放**三段式：

1. **预占**：下单时对每个 SKU 增加预占量，可售量 = 实际库存 − 预占量，任一 SKU 不足则整单回滚预占
2. **确认扣减**：收到 `payment.succeeded` 后，将预占转为实际扣减
3. **超时释放**：订单超时关闭或取消时，释放对应预占量

并发控制：数据库层面用条件更新（`WHERE available >= n`）保证不超卖，Redis 侧做前置拦截降低数据库压力。

### 5.3.2 下单 Saga 编排

订单创建跨越订单、商品目录两服务，采用**编排式 Saga**：

```
创建订单(待支付) 
  → 预占库存
      ├─ 成功 → 订单落库 → 发布 order.created → 返回支付凭据
      └─ 失败 → 取消订单 → 补偿释放已预占库存 → 返回"库存不足"
```

支付完成链路：

```
payment.succeeded 事件
  → 订单服务更新订单为已支付
  → 商品目录服务扣减库存
  → 通知服务发送通知
  任一步失败 → 事件重试 → 超限进死信队列 → 告警 + 人工处理
```

**补偿原则**：只做正向重试 + 最终人工兜底，不引入分布式事务框架；支付成功但扣减库存失败的订单进入异常队列（对应 FR-ORD-014）。

### 5.3.3 幂等实现

| 场景 | 幂等键 | 实现 |
|---|---|---|
| 创建订单 | 客户端生成的 request_id | Redis SETNX + 订单表唯一索引双保险 |
| 支付回调 | 第三方交易号 | 支付流水表唯一索引，重复回调直接返回成功 |
| 退款请求 | 退款单号 | 唯一索引 + 状态机校验（已退款不可再退） |
| 事件消费 | event_id | Redis 已处理集合 + TTL |

## 6. 平台能力设计

### 6.1 API 网关

- **路由**：按路径前缀转发至对应服务，服务地址从 Consul 动态解析
- **鉴权**：校验 JWT 签名与有效期，解析出 user_id 与角色，注入请求头传递下游
- **放行名单**：注册、登录、商品浏览、支付回调等无需登录的接口在白名单内
- **限流**：按 IP 与用户维度做令牌桶限流，登录与下单接口单独设置更严阈值
- **熔断降级**：下游服务不可用时快速失败，商品列表可降级为缓存快照
- **跨域与安全头**：统一处理 CORS，补齐安全响应头

### 6.2 服务发现

- 服务启动时向 Consul 注册 `服务名 + 实例地址 + 健康检查地址`
- Consul 按间隔探测 `/health`，连续失败则摘除实例
- 网关与调用方通过服务名获取健康实例列表，实例扩缩容无需重启上游
- 配置中心：非敏感配置存 Consul KV，按 `dev/test/prod` 环境区分

### 6.3 安全设计

| 层面 | 措施 |
|---|---|
| 传输 | 全链路 HTTPS，内网服务间启用 mTLS 或服务令牌 |
| 认证 | 用户侧 JWT（短期访问令牌 + 长期刷新令牌）；网关统一校验 |
| 授权 | 后端服务按 user_id 做数据归属校验，后台接口按角色校验 |
| 越权防护 | 所有涉及资源的接口强制校验归属，禁止仅凭 ID 查询（对应 NFR-SE-006） |
| 密码 | bcrypt/argon2 加盐哈希 |
| 支付 | 不落任何卡号与 CVV，回调强制验签，支付密钥独立存放 |
| 密钥管理 | 通过环境变量或密钥管理服务注入，代码库与镜像中不含明文 |
| 审计 | 后台管理操作记录操作人、时间、对象、变更前后值 |
| 输入校验 | Pydantic 全量校验请求体，ORM 参数化查询防注入 |

### 6.4 可观测性设计

| 维度 | 方案 |
|---|---|
| 日志 | 结构化 JSON 输出至 stdout，由 Filebeat/Logstash 采集进 Elasticsearch，Kibana 检索 |
| 追踪 | OpenTelemetry 埋点，`trace_id` 贯穿网关 → 服务 → 消息队列，写入日志字段 |
| 指标 | 每个服务暴露 `/metrics`，Prometheus 拉取；FastAPI 中间件采集 QPS、P95 耗时、错误率 |
| 业务指标 | 下单量、支付成功率、库存预占失败率、订单超时关闭数 |
| 告警 | 接口错误率、消息积压、死信队列长度、支付回调失败率超阈值即告警 |
| 健康检查 | 每个服务提供 `/health`（存活）与 `/ready`（就绪，含依赖探测） |

## 7. 前端架构

### 7.1 应用划分

| 应用 | 面向 | 技术 | 说明 |
|---|---|---|---|
| 买家商城端 | C 端消费者 | React + TypeScript + Vite | 移动端优先响应式，路由懒加载 |
| 运营管理后台 | 内部角色 | React + Ant Design Pro | 表格/表单密集，按角色渲染菜单 |

### 7.2 前端要点

- **统一请求层**：封装 axios/fetch，统一注入令牌、处理 401 静默刷新、统一错误提示转中文
- **状态管理**：买家端购物车与用户态用轻量 store；后台以服务端数据为主，配合请求缓存
- **权限控制**：后台菜单与按钮按角色权限动态渲染，前端隐藏仅为体验，真实拦截在后端
- **防重复提交**：提交类按钮点击后置灰并生成 request_id 幂等键
- **错误边界**：页面级错误边界避免白屏，列表页提供骨架屏与空态
- **构建产物**：两套应用独立构建镜像，由网关按路径（`/` 与 `/admin`）分发

## 8. 部署架构

### 8.1 环境划分

| 环境 | 编排方式 | 说明 |
|---|---|---|
| 本地开发 | Docker Compose | 单机拉起全部服务与中间件，支持只启动所需服务 |
| 测试环境 | Docker Compose / 单节点 K8s | 完整链路验证 |
| 生产环境 | Kubernetes | 多副本、自动扩缩容、滚动更新、自愈 |

### 8.2 Compose 编排要点

- 每个服务独立 Dockerfile，采用多阶段构建（构建层装依赖，运行层仅拷贝产物），镜像尽量精简
- 通过 `depends_on` + 健康检查控制启动顺序，避免服务先于数据库就绪启动
- 所有服务接入同一自定义网络，以服务名互相寻址
- 配置与密钥通过 `.env` 注入，`.env` 不入版本库
- 数据卷持久化数据库与中间件数据，避免容器重建丢数据

### 8.3 Kubernetes 生产要点

- 每个服务独立 Deployment + Service，副本数按负载配置
- 通过 HPA 按 CPU/内存或自定义指标自动扩缩容
- 配置 Liveness/Readiness 探针指向 `/health` 与 `/ready`
- 滚动更新策略保证发布过程零中断
- ConfigMap 存非敏感配置，Secret 存密钥与口令
- Ingress 承接外部流量，功能等价于本地环境的 Traefik

### 8.4 服务端口与依赖关系

| 服务 | 依赖中间件 | 依赖服务 |
|---|---|---|
| user-service | PostgreSQL、Redis | — |
| catalog-service | PostgreSQL、Redis | — |
| cart-service | PostgreSQL、Redis | catalog-service |
| order-service | PostgreSQL、RabbitMQ | catalog-service、user-service、payment-service |
| payment-service | PostgreSQL、RabbitMQ | order-service、Stripe、PayPal |
| notification-service | PostgreSQL、RabbitMQ | SendGrid、Twilio |

## 9. CI/CD 设计

### 9.1 流水线阶段

```
代码提交 / PR
  → 静态检查（ruff / mypy）
  → 单元测试（pytest）
  → 构建镜像（按变更服务选择性构建）
  → 集成测试（Compose 起全栈跑端到端用例）
  → 推送镜像仓库（打 git sha 与语义化标签）
  → 部署（测试环境自动 / 生产环境审批后）
  → 冒烟测试
```

### 9.2 关键设计

- **按服务触发**：依据变更路径只构建受影响服务，缩短流水线时长
- **镜像可追溯**：镜像标签包含 git commit，任一线上版本可回溯代码
- **迁移独立执行**：数据库迁移作为部署前置步骤单独执行，失败即中止发布
- **回滚能力**：保留历史镜像，支持一键回滚至上一版本
- **质量门禁**：测试不通过或覆盖率低于阈值禁止合并

## 10. 演进路线

对齐 roadmap.sh 的建议步骤，分阶段交付：

| 阶段 | 目标 | 产出 |
|---|---|---|
| 一 | 服务 MVP + 容器化 | 六个服务骨架、各自 Dockerfile、Compose 一键启动 |
| 二 | 业务闭环 | 购物车 → 下单 → 支付 → 通知 主链路打通，前端可用 |
| 三 | 网关与服务发现 | Traefik 接入，Consul 注册发现，客户端只依赖网关 |
| 四 | 异步解耦 | 引入 RabbitMQ，通知与库存扣减改为事件驱动 |
| 五 | 可观测性 | ELK 日志聚合、Prometheus + Grafana 监控、链路追踪 |
| 六 | 生产化部署 | Kubernetes 编排、自动扩缩容、负载均衡 |
| 七 | 自动化交付 | CI/CD 流水线打通，提交即自动构建测试发布 |

**迭代原则**：每个服务先交付最小可用版本，跑通主流程后再补全次要功能（评价、对账、标签等），避免一开始就追求全功能。

## 11. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 库存超卖 | 资损与客诉 | 预占机制 + 数据库条件更新 + 并发压测验证 |
| 支付回调丢失 | 订单状态不一致 | 定时主动查询补偿 + 对账发现差异 |
| 消息重复消费 | 重复扣减/重复通知 | 消费端按 event_id 幂等 |
| 分布式调试困难 | 排障耗时 | 全链路 trace_id + 集中日志 |
| 服务雪崩 | 局部故障放大 | 超时、重试上限、熔断、降级四件套 |
| 本地环境过重 | 开发效率下降 | Compose 支持按需启动子集服务 |
| 拆服务过早 | 复杂度高于收益 | 先 MVP 单体化实现各服务，验证边界后再拆分部署 |

## 1. 端到端业务流程

以下时序描述系统级协作，各服务内部实现见对应服务文档。

### 1.1 主流程总览

```
买家端          网关         购物车      商品目录      订单        支付        通知
  │              │            │           │           │           │           │
  │─浏览商品────▶│───────────▶│           │◀──────────│           │           │
  │─加购────────▶│───────────▶│───快照───▶│           │           │           │
  │─结算预览────▶│───────────▶│───校验───▶│           │           │           │
  │─提交订单────▶│────────────────────────▶│──预占───▶│           │           │
  │◀─支付凭据────│────────────────────────│           │           │           │
  │─发起支付────▶│────────────────────────────────────▶│───第三方──│
  │              │            │           │           │◀─回调─────│
  │              │            │           │◀─order.paid（扣减库存）│
  │◀─支付成功通知（通知服务异步发送）──────────────────────────────│
  │─查看订单────▶│────────────────────────▶│           │           │
  │─确认收货────▶│────────────────────────▶│───order.shipped/received──▶│
```

### 1.2 下单链路（含跨服务调用）

```
买家端  →  网关  →  订单服务
                      │
                      ├─(1) 幂等校验（Redis SETNX, Idempotency-Key）
                      ├─(2) → 购物车服务: 读取选中项
                      ├─(3) → 用户服务:   校验收货地址归属
                      ├─(4) → 商品目录服务: 批量查询 SKU 快照（价格、上架状态）
                      ├─(5) 计算金额（商品总额 + 运费 - 优惠）
                      ├─(6) → 商品目录服务: 批量预占库存
                      │        失败 → 回滚已预占项 → 返回"库存不足"
                      ├─(7) 本地事务：写订单 + 明细快照 + outbox 事件
                      └─(8) 返回订单号与待支付信息
```

**失败与补偿**：

| 步骤 | 失败处理 |
|---|---|
| (2) 购物车不可用 | 返回 `COMMON-7001`，不下单（购物车是下单的必要输入，无法降级） |
| (3) 用户服务不可用 | 返回 `COMMON-7001`；地址归属校验不可跳过（安全要求） |
| (4) 商品服务不可用 | 返回 `COMMON-7001`；不接受客户端传入的价格（防篡改） |
| (6) 部分 SKU 预占失败 | **反向补偿**：释放本次已成功的预占，整单失败 |
| (7) 落库失败 | 反向补偿：释放在 (6) 中预占的全部库存 |
| (8) 返回超时但订单已创建 | 客户端持同一 `Idempotency-Key` 重试，返回首次创建的订单 |

### 1.3 支付完成链路

```
支付服务  ──payment.succeeded──▶  MQ  ──┬──▶ 订单服务: 订单置为已支付
                                        │         └──order.paid──┐
                                        └──▶ 通知服务: 发送支付成功通知
                                                                 │
                      商品目录服务 ◀───────────────────────────────┘
                          正式扣减库存（预占转为实扣）
```

**关键约束**：订单状态更新与库存扣减**必须分两步**，分别由订单服务与商品目录服务在各自事务中完成。不合并的理由是数据所有权——订单状态归订单服务，库存归商品目录服务，跨库写入无法在一个事务中完成。

**异常路径**：库存扣减失败（如预占记录已过期被释放）→ 事件重试 5 次 → 进死信队列 → 告警 → 订单服务将订单标记为异常订单 → 人工介入或自动退款。

### 1.4 订单超时关闭与支付竞态

```
定时任务（每分钟）扫描 status=PENDING_PAYMENT AND expires_at < now()
  │
  ├─ 条件更新：SET status='CLOSING', version=version+1
  │            WHERE order_no=? AND status='PENDING_PAYMENT'
  │     影响行数=1 → 关闭成功 → 发 order.cancelled（释放预占库存）
  │     影响行数=0 → 订单状态已变（用户正在支付）→ 跳过，交由支付结果驱动
  │
  └─ 收到 payment.succeeded 时：
       若订单为 CLOSING → 改为 PAID，取消关闭流程（用户支付成功，必须认账）
       若订单已 CLOSED → 触发自动退款（对应 FR-ORD-014）
```

**设计要点**：不直接把订单置为终态 `CLOSED`，中间引入 `CLOSING` 过渡态，用条件更新（乐观锁）确保只有一个执行者生效。这是本系统最关键的竞态处理。

## 2. API 网关详细设计

### 2.1 路由规则

| 路径前缀 | 目标服务 | 鉴权 |
|---|---|---|
| `/api/v1/auth/*` | user-service | 白名单放行 |
| `/api/v1/users/*` | user-service | 强制 |
| `/api/v1/categories/*`、`/api/v1/products/*` | catalog-service | 读接口白名单，写接口强制 |
| `/api/v1/cart/*` | cart-service | 强制（游客车走 `X-Guest-Id` 特殊处理） |
| `/api/v1/orders/*` | order-service | 强制 |
| `/api/v1/payments/*` | payment-service | 强制；`/webhook` 子路径白名单 |
| `/api/v1/notifications/*` | notification-service | 强制 |
| `/internal/*` | **不路由** | 内部接口不暴露至网关，服务间直连 |
| `/admin/*` | 各服务 admin 路径 | 强制 + 角色校验 |
| `/health`、`/metrics` | — | 不对外暴露，仅内网可达 |

### 2.2 中间件链（按执行顺序）

| 顺序 | 中间件 | 职责 |
|---|---|---|
| 1 | `real-ip` | 解析客户端真实 IP 写入 `X-Client-Ip` |
| 2 | `trace` | 生成或继承 `X-Trace-Id`，透传 `X-Request-Id` |
| 3 | `security-headers` | 剥离外部传入的 `X-User-Id`、`X-User-Roles`、`X-Internal-Token`（**防伪造身份**） |
| 4 | `cors` | 跨域处理，仅允许配置的前端域名 |
| 5 | `rate-limit` | 按 IP / 用户维度限流 |
| 6 | `auth` | JWT 校验，解析出身份并注入 `X-User-Id`、`X-User-Roles` |
| 7 | `circuit-breaker` | 下游连续失败熔断 |
| 8 | `retry` | 仅对幂等读方法（GET）重试 |
| 9 | `forward` | 转发至目标服务 |

### 2.3 限流策略

| 维度 | 阈值 | 说明 |
|---|---|---|
| 全局 IP | 600 次/分钟 | 兜底防护 |
| 登录接口 | 10 次/分钟/IP | 防爆破 |
| 注册接口 | 5 次/小时/IP | 防刷号 |
| 验证码接口 | 5 次/小时/手机号 + 20 次/小时/IP | 防短信轰炸 |
| 下单接口 | 20 次/分钟/用户 | 防刷单与重复提交 |
| 支付发起 | 20 次/分钟/用户 | 防恶意创建支付单 |
| 商品读接口 | 1200 次/分钟/IP | 相对宽松，允许正常浏览 |

超限返回 `COMMON-6001`（HTTP 429）并在响应头带 `Retry-After`。

### 2.4 熔断与降级

| 下游服务 | 熔断条件 | 降级行为 |
|---|---|---|
| catalog-service | 10 秒内错误率 > 50%（且请求数 ≥ 20） | 商品列表返回 Redis 缓存快照；商品详情降级展示基础信息 |
| 其他服务 | 同上 | 快速失败返回 `COMMON-7001`，不做业务降级（宁可失败不可出错数据） |

熔断后进入 30 秒半开状态，放行少量探测请求；成功则恢复，失败则继续熔断。

## 3. 服务发现详细设计

### 3.1 注册

每个服务启动时向 Consul 注册：

```json
{
  "ID": "order-service-1726000000-1",
  "Name": "order-service",
  "Address": "10.0.1.15",
  "Port": 8004,
  "Tags": ["v1", "api"],
  "Check": {
    "HTTP": "http://10.0.1.15:8004/health",
    "Interval": "10s",
    "Timeout": "3s",
    "DeregisterCriticalServiceAfter": "1m"
  }
}
```

- 服务正常关闭时主动注销，避免流量打到已退出实例
- 异常退出由 Consul 按 `DeregisterCriticalServiceAfter` 自动摘除

### 3.2 健康检查端点

| 端点 | 用途 | 检查内容 |
|---|---|---|
| `/health` | 存活检查 | 进程存活即返回 200，**不探测依赖**（避免依赖抖动导致实例被误杀） |
| `/ready` | 就绪检查 | 探测数据库、Redis、MQ 连接；任一不可用返回 503 |

```json
{
  "status": "UP",
  "service": "order-service",
  "version": "1.0.0",
  "checks": [
    {"name": "database", "status": "UP", "latency_ms": 2},
    {"name": "redis", "status": "UP", "latency_ms": 1},
    {"name": "rabbitmq", "status": "UP", "latency_ms": 4}
  ]
}
```

### 3.3 配置中心

非敏感配置存 Consul KV，路径规范：

```
config/{env}/{service}/{key}
```

示例：`config/prod/order-service/order.timeout_minutes = 30`

服务启动时拉取并本地缓存，监听变更事件热更新；敏感配置（密钥、口令）不走 KV，由密钥管理服务注入。

## 4. 可观测性详细设计

### 4.1 日志管道

```
服务 stdout（结构化 JSON）
   → Filebeat / Logstash（采集、补充 host 与 container 元数据）
   → Elasticsearch（索引：logs-{service}-{yyyy.MM.dd}）
   → Kibana（按 trace_id / user_id / service 检索）
```

- 日志按服务分索引，按日期滚动，保留 30 天；订单与支付相关日志保留 180 天（对账与纠纷追溯需要）
- 必须可用的检索维度：`trace_id`、`user_id`、`order_no`、`error_code`、`status`
- 慢查询（>500ms）单独打标 `slow_query: true` 便于聚合分析

### 4.2 指标清单

每个服务暴露 `/metrics`，Prometheus 拉取。除通用指标外，需采集以下业务指标：

| 指标 | 类型 | 说明 |
|---|---|---|
| `http_requests_total{service,method,path,status}` | Counter | 请求量与错误率 |
| `http_request_duration_seconds{service,path}` | Histogram | 耗时分布，算 P50/P95/P99 |
| `db_query_duration_seconds{service,operation}` | Histogram | 数据库耗时 |
| `cache_hit_total` / `cache_miss_total` | Counter | 缓存命中率 |
| `orders_created_total` | Counter | 下单量 |
| `orders_closed_total{reason}` | Counter | 超时关闭量 |
| `inventory_reserve_failed_total` | Counter | 库存预占失败次数 |
| `payment_success_total{channel}` | Counter | 支付成功数 |
| `payment_callback_failed_total{reason}` | Counter | 回调失败数（验签/金额/未知单） |
| `mq_consume_total{event_type,result}` | Counter | 事件消费量与失败量 |
| `mq_dlq_size{queue}` | Gauge | 死信队列积压量 |
| `notification_send_total{channel,result}` | Counter | 通知发送量与失败量 |

### 4.3 告警规则

| 告警 | 条件 | 级别 |
|---|---|---|
| 服务不可用 | 实例健康检查连续 3 次失败 | P0 |
| 接口错误率高 | 5 分钟内 5xx 占比 > 5% | P1 |
| 接口耗时劣化 | P95 > 1s 持续 5 分钟 | P1 |
| 死信队列积压 | `mq_dlq_size > 10` | P1 |
| 支付回调失败 | 5 分钟内 `payment_callback_failed_total > 3` | P0 |
| 库存预占失败率 | 5 分钟内失败率 > 20% | P1 |
| 消息积压 | 队列深度 > 1000 且持续增长 | P1 |
| 对账差异 | 对账任务发现差异条数 > 0 | P1 |
| 低库存 | 收到 `stock.low` 事件 | P2（业务通知） |

### 4.4 链路追踪

- 采用 OpenTelemetry SDK，自动埋点 HTTP 入站/出站、数据库、Redis、MQ
- `trace_id` 全链路透传：HTTP 走 `X-Trace-Id` 头，MQ 走事件信封的 `trace_id` 字段
- 采样率：生产环境 10%，错误请求 100% 采样（保证异常可追）
- 追踪数据存 Jaeger，保留 7 天

### 5.2 Dockerfile 规范

统一采用多阶段构建：

```dockerfile
# 构建阶段
FROM python:3.12-slim AS builder
WORKDIR /build
COPY pyproject.toml uv.lock ./
RUN pip install --no-cache-dir uv && uv sync --frozen --no-dev

# 运行阶段
FROM python:3.12-slim
RUN useradd -m -u 1000 appuser
WORKDIR /app
COPY --from=builder /build/.venv /app/.venv
COPY app ./app
COPY alembic ./alembic
COPY alembic.ini ./
ENV PATH="/app/.venv/bin:$PATH" \
    PYTHONUNBUFFERED=1 \
    PYTHONDONTWRITEBYTECODE=1
USER appuser
EXPOSE 8004
HEALTHCHECK --interval=10s --timeout=3s --retries=3 \
    CMD python -c "import urllib.request; urllib.request.urlopen('http://localhost:8004/health')"
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8004", "--workers", "4"]
```

要点：非 root 用户运行、不写字节码、无构建工具残留、健康检查内置、单层依赖安装。

### 5.3 Compose 编排要点

| 配置项 | 说明 |
|---|---|
| `networks` | 自定义 bridge 网络 `ecommerce-net`，服务间以服务名互相寻址 |
| `volumes` | `postgres-data`、`redis-data`、`rabbitmq-data`、`es-data` 持久化 |
| `depends_on` | 配合 `condition: service_healthy`，确保中间件就绪后再启动业务服务 |
| `env_file` | 统一读 `.env`；`.env` 不入版本库，仓库只提交 `.env.example` |
| `restart` | 业务服务 `unless-stopped`，中间件 `always` |
| `deploy.resources` | 限制每个服务的内存与 CPU，防止单服务拖垮宿主机 |
| `logging` | 驱动为 `json-file`，限制单容器日志大小避免磁盘写满 |

**启动顺序**：`postgres` / `redis` / `rabbitmq` / `consul` → `elasticsearch` → `logstash` / `kibana` / `prometheus` / `grafana` → 六个业务服务 → 两个前端 → `gateway`。

**开发效率优化**：Compose 使用 profile 分组，开发者可只启动所需服务子集，例如仅启动 `catalog-service` 与其依赖进行单体调试，避免每次拉起全部 20 个容器。

### 5.4 Kubernetes 生产部署

| 资源对象 | 说明 |
|---|---|
| `Deployment` | 每服务一个，副本数按负载配置（网关与商品服务副本数较多） |
| `Service` | ClusterIP，供集群内互访 |
| `Ingress` | 承接外部流量，TLS 终止，功能等价于本地 Traefik |
| `ConfigMap` | 非敏感配置 |
| `Secret` | 数据库口令、JWT 密钥、第三方 API Key |
| `HPA` | 按 CPU 使用率（阈值 70%）与自定义指标（QPS）自动扩缩容 |
| `PodDisruptionBudget` | 保证滚动更新期间最小可用副本数 |
| `NetworkPolicy` | 限制服务间访问范围，如通知服务只允许被网关访问管理接口 |

**探针配置**：`livenessProbe` → `/health`（间隔 10s，失败 3 次重启）；`readinessProbe` → `/ready`（间隔 5s，失败即摘除流量）。

**滚动更新**：`maxSurge: 1`、`maxUnavailable: 0`，保证发布期间容量不缩减。数据库迁移以 `Job` 形式在更新前置执行。

## 6. CI/CD 详细设计

### 6.1 流水线定义

```yaml
触发：push 到 main / 提交 PR / 打 tag

阶段 1  变更检测      识别变更的服务目录，输出构建矩阵
阶段 2  静态检查      ruff（lint + format）、mypy（类型检查）
阶段 3  单元测试      pytest，覆盖率低于 70% 阻断
阶段 4  构建镜像      Docker build，标签 {service}:{git_sha} 与 {service}:latest
阶段 5  集成测试      Compose 拉起全栈，跑端到端用例（下单→支付→发货）
阶段 6  推送镜像      推送至镜像仓库
阶段 7  部署          测试环境自动部署；生产环境需人工审批
阶段 8  数据库迁移    执行 alembic upgrade head（失败即中止发布）
阶段 9  冒烟测试      健康检查 + 核心接口连通性验证
阶段 10 通知          成功/失败结果推送至团队渠道
```

### 6.2 关键设计

- **按服务触发**：依据变更路径只构建受影响服务，避免全量构建拖慢流水线
- **镜像可追溯**：标签含 git commit sha，任一线上版本可回溯到代码
- **迁移独立执行**：数据库迁移作为部署前置步骤单独执行。**迁移必须向后兼容**（先加字段后删字段，分两次发布），保证滚动更新期间新旧版本共存不报错
- **回滚**：保留最近 10 个版本镜像，支持一键回滚；回滚不执行反向迁移（除非明确写了 down 脚本）
- **质量门禁**：静态检查、单元测试、集成测试任一失败则阻断合并
- **密钥管理**：CI 中使用仓库 Secret，禁止在流水线文件中出现明文密钥

### 6.3 环境策略

| 环境 | 触发 | 部署方式 | 数据 |
|---|---|---|---|
| 开发 | 本地手动 | Compose | 本地数据卷，可用种子数据 |
| 测试 | 合入 main 自动 | Compose / 单节点 K8s | 独立数据库，每次集成测试前重建 |
| 预发 | 打 tag 自动 | K8s | 数据结构与生产一致，脱敏数据 |
| 生产 | 打 tag + 人工审批 | K8s 滚动更新 | 正式数据 |

## 7. 跨服务横切关注点

### 7.1 分布式事务边界

本系统**不使用**分布式事务框架（如 Seata、2PC），理由：跨服务强一致事务会带来严重的可用性耦合，且电商场景对"秒级最终一致"完全可接受。取而代之的组合手段：

| 手段 | 应用场景 |
|---|---|
| 编排式 Saga + 补偿 | 下单时多 SKU 库存预占 |
| 事务性发件箱（Outbox） | 所有跨服务事件发布 |
| 消费幂等 + 重试 + 死信 | 所有事件消费 |
| 对账兜底 | 支付与库存的最终校验 |

### 7.2 服务依赖与故障隔离

| 服务 | 被依赖程度 | 故障影响 | 隔离措施 |
|---|---|---|---|
| 用户服务 | 高 | 无法登录、无法下单 | 令牌校验在网关完成（不依赖用户服务）；地址查询失败即下单失败 |
| 商品目录服务 | 极高 | 无法浏览与下单 | 商品读接口走缓存降级；库存操作不可降级 |
| 购物车服务 | 中 | 无法加购与结算 | 无降级，直接报错（购物车是必要输入） |
| 订单服务 | 高 | 无法下单与查单 | 无降级 |
| 支付服务 | 中 | 无法支付，但不影响浏览与下单 | 下单成功但支付服务不可用时可稍后重试支付 |
| 通知服务 | 低 | 收不到通知 | **完全异步，不影响任何主流程** |

**设计原则**：只有通知服务可以被完全旁路。购物车与商品服务的库存能力位于关键路径，不可降级——**宁可让用户看到明确的错误，也不接受数据不一致**。

### 7.3 数据一致性校验任务

| 任务 | 周期 | 职责 |
|---|---|---|
| 库存校准 | 每小时 | 比对 Redis 预占计数与数据库预占量，不一致则以数据库为准修正 |
| 预占超时释放 | 每 5 分钟 | 扫描过期预占记录并释放（作为订单关闭的兜底） |
| 订单-支付对账 | 每日 | 比对支付流水与订单状态，发现"已支付但订单未更新"的遗漏 |
| 第三方对账 | 每日 | 拉取第三方账单与本地流水比对（详见支付服务文档） |
| 孤立数据清理 | 每周 | 清理无主购物车、过期验证码、过期令牌黑名单 |

### 7.4 版本兼容策略

- 接口使用 `/api/v1` 版本前缀，不兼容变更才升版本，旧版本至少保留 6 个月
- 事件信封含 `event_version`，消费端**只能新增可选字段，不得删除或改变字段语义**
- 服务部署支持"新老版本并存"，因此任何接口与事件的变更必须**向前兼容一个版本**

## 8. 安全加固清单

| 项 | 措施 |
|---|---|
| 传输加密 | 外部 HTTPS（TLS 1.2+），内部服务间启用 mTLS |
| 身份伪造防护 | 网关剥离外部传入的身份头（见 2.2 中间件链第 3 步） |
| 服务间认证 | `X-Internal-Token` 校验，密钥定期轮换 |
| 数据库 | 账号最小权限，仅授权本库；禁止生产直连公网 |
| 容器 | 非 root 运行，只读根文件系统，限制 capabilities |
| 依赖扫描 | CI 中集成依赖漏洞扫描，高危阻断发布 |
| 敏感信息 | 密钥不入代码库、不入镜像；日志脱敏见通用约定第 12.3 节 |
| 备份 | 数据库每日全量 + 实时 WAL 归档，备份异地存储并定期演练恢复 |

## 9. 容量与性能设计要点

需求文档未设定硬性容量指标，本设计以"可水平扩展、瓶颈可定位"为目标，具体要点：

- **无状态**：所有业务服务无状态，会话与缓存外置，可任意增减副本
- **缓存分层**：商品与分类走 Redis 缓存；购物车以 Redis 为主存储；热点 SKU 库存预占在 Redis 前置拦截
- **异步削峰**：通知、统计、对账全部异步，下单主链路只保留必要步骤
- **数据库**：订单与流水表按月分区或按时段归档；读密集服务预留只读副本
- **连接池**：每服务配置数据库连接池上限，避免服务副本数扩容后打爆数据库（**扩容服务前需先确认数据库承载能力**，这是最容易踩的坑）
- **压测基线**：上线前需对下单与支付链路做并发压测，重点验证不超卖、不重复扣款、连接池不耗尽

## 10. 测试策略

| 层次 | 范围 | 工具 | 要求 |
|---|---|---|---|
| 单元测试 | 服务内业务逻辑、状态机、金额计算 | pytest | 覆盖率 ≥ 70%，核心逻辑（状态流转、库存、金额）≥ 90% |
| 集成测试 | 单服务 + 真实数据库与 Redis | pytest + testcontainers | 覆盖所有写接口与异常分支 |
| 契约测试 | 服务间接口与事件 Schema | 基于 OpenAPI / JSON Schema 校验 | 确保生产消费双方契约一致 |
| 端到端测试 | 全栈主流程 | Compose + pytest | 覆盖 下单→支付→发货→收货 全链路 |
| 并发测试 | 库存预占、订单创建幂等、支付回调 | locust / JMeter | 验证不超卖、不重复入账 |
| 混沌测试 | 依赖故障时的降级与恢复 | 手动注入（停容器） | 验证通知服务不可用不影响下单、熔断生效 |

### 10.1 必须覆盖的关键用例

| 用例 | 验证点 |
|---|---|
| 同一 `Idempotency-Key` 并发提交 10 次下单请求 | 只创建一个订单，10 次返回同一订单号 |
| 100 并发抢购库存 10 的商品 | 恰好 10 单成功，预占量不超过库存 |
| 下单后不支付，等待超时 | 订单关闭，库存预占被释放，可被他人购买 |
| 超时关闭与支付成功同时发生 | 订单最终为已支付，不出现"已付款但订单关闭" |
| 同一支付回调重复投递 5 次 | 只入账一次，订单状态只更新一次 |
| 部分退款两次，合计超过支付金额 | 第二次被拒绝 |
| 通知服务停止后下单 | 下单成功，通知在恢复后补发 |
| 买家 A 访问买家 B 的订单 | 返回 403（`COMMON-3001`），不泄露资源是否存在 |
| 客户端篡改下单金额 | 服务端以商品服务返回价格为准，篡改无效 |
| 商品下架后访问其订单详情 | 订单正常展示（快照不可变） |

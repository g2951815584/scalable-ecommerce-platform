## 1. 服务概览

### 1.1 职责

用户服务是平台的**身份与访问管理（IAM）中心**，同时是**用户主数据（Party Data）的唯一写入方**。它承担三件事：

1. **身份认证**：账号注册、凭证校验、令牌签发与吊销、第三方 OAuth 登录。
2. **用户主数据**：账号状态、个人资料、收货地址。
3. **授权基础**：RBAC 角色与权限模型，为网关注入 `X-User-Roles` 与后台菜单渲染提供数据基础。

### 1.2 职责清单与需求映射

| 能力 | 说明 | 对应 FR |
|---|---|---|
| 注册 | 邮箱或手机号注册，唯一性校验，密码 argon2id 哈希，默认授予 `BUYER` 角色 | FR-US-001 |
| 账号验证 | 发送验证码、校验验证码；邮箱/手机验证状态写入主表 | FR-US-002 |
| 登录 | 账号密码登录，连续失败锁定，签发访问令牌与刷新令牌 | FR-US-003 |
| 令牌生命周期 | 刷新令牌轮换、重放检测、登出吊销、全端下线 | FR-US-004 |
| 密码找回 | 通过邮箱/短信验证码重置密码，重置后强制全端下线 | FR-US-005 |
| 个人资料 | 昵称、头像、性别、生日等非关键信息查看与修改 | FR-US-006 |
| 收货地址 | 地址增删改查、默认地址唯一、数量上限、归属校验 | FR-US-007 |
| 角色权限 | RBAC 模型，管理员分配角色与配置角色权限 | FR-US-008 |
| 账号状态 | 启用/禁用/锁定/注销，禁用即时阻断登录与下单 | FR-US-009 |
| 第三方登录 | Google / GitHub OAuth 授权码登录与绑定/解绑 | FR-US-010 |
| 账号注销 | 注销申请、数据匿名化、法定留存数据保留 | NFR-CP-004 |

### 1.3 边界（明确不做的事）

| 事项 | 归属 | 说明 |
|---|---|---|
| 购物车、订单、支付数据 | 各业务服务 | 用户服务不持有任何交易数据 |
| 用户通知的渠道发送 | 通知服务 | 用户服务只生成验证码并调用通知服务投递，不直接对接 SendGrid/Twilio |
| 令牌签名校验 | 网关 | 网关持有 `JWT_PUBLIC_KEY` 完成校验与身份头注入，业务服务不解析令牌 |
| 限流、熔断 | 网关 / 基础设施 | 用户服务只做登录、验证码等业务级频率控制 |
| 收货信息的订单快照 | 订单服务 | 订单在创建时快照地址，之后不再回查用户库（对应架构文档 3.3） |
| 权限的最终拦截 | 各业务服务 | 用户服务定义权限模型，业务服务按角色/权限自行拦截 |

### 1.4 上下游依赖

```
                    ┌──────────────────────────┐
   买家端 / 后台 ──▶ │ Gateway (Traefik)        │
                    │ 校验 JWT · 注入身份头     │──▶ user-service :8001
                    └──────────────────────────┘
                                  │
   order-service ────────────────┤  /internal/v1/users/*
   notification-service ◀────────┘  /internal/v1/notifications/send
                    ┌──────────────┴────────────┐
                    │ PostgreSQL  ·  Redis      │
                    └───────────────────────────┘
                              │
                     RabbitMQ │ ecommerce.events → user.registered
```

| 方向 | 对方 | 接口 / 事件 | 用途 | 失败处理 |
|---|---|---|---|---|
| 被调用 | order-service | `GET /internal/v1/users/{user_id}/addresses/{address_id}` | 下单时校验收货地址归属并取地址快照 | 依赖方按超时/熔断处理；本服务无状态、纯读 |
| 被调用 | order-service | `POST /internal/v1/users/batch` | 订单列表补全买家昵称、判断账号是否可下单 | 同上 |
| 被调用 | notification-service | `GET /internal/v1/users/{user_id}/profile` | 获取收件邮箱/手机号（FR-NOT-001~004） | 同上 |
| 主动调用 | notification-service | `POST /internal/v1/notifications/send` | 投递注册验证码、找回密码验证码 | 超时 1s/3s，失败返回 `USER-7001`，允许用户立即重试 |
| 发布事件 | notification-service（及任何订阅方） | `user.registered` | 触发欢迎邮件/通知记录 | 事务性发件箱，由定时任务重投 |
| 依赖中间件 | PostgreSQL / Redis / RabbitMQ | — | 主数据、令牌黑名单与限流、事件投递 | 见 §12 测试要点与告警项 |

> **设计取舍**：验证码投递采用**同步内部调用**而非事件，因为用户需要"验证码是否发出"的即时反馈；通知服务不可用时注册本身仍然成功，接口返回明确提示并允许绕过 60 秒冷却立即重试。渠道凭证、模板与重试策略集中在通知服务，用户服务不重复集成第三方（对应 FR-NOT-006）。
>
> 该依赖使 user-service 在部署依赖图中新增一条指向 notification-service 的边（原架构文档 8.4 中 user-service 依赖列为空），需同步更新部署文档；**该依赖不是关键路径**，仅验证码投递接口受影响。

### 1.5 与其他组件的令牌校验契约

令牌由本服务签发，校验在网关完成。本服务维护两个 Redis Key 供网关查询，构成**双方必须共同遵守的契约**（Redis 为平台共享基础设施）：

| Key | 语义 | 网关动作 |
|---|---|---|
| `user:auth:jwt:blacklist:{jti}` | 值存在即表示该访问令牌已被吊销 | 存在则拒绝，返回 `COMMON-2002` |
| `user:auth:revoke_after:{user_id}` | 值为 UTC 时间戳字符串，表示该用户在此时间之前签发的令牌全部失效 | 令牌 `iat` 早于该值则拒绝，返回 `COMMON-2002` |

无法协商该契约时，退化为"仅黑名单"方案，代价是禁用账号/重置密码后的访问令牌最长 30 分钟内仍可访问（刷新令牌已被吊销，无法续期）。

## 2. 数据库设计

### 2.1 表清单与关系

| # | 表名 | 说明 | 预估量级 | 软删除 | 乐观锁 |
|---|---|---|---|---|---|
| 1 | `users` | 用户主表（账号、状态、验证标记、登录计数） | 百万级 | 是 | 否 |
| 2 | `user_credentials` | 密码凭证（与用户 1:1） | 同 users | 否 | 否 |
| 3 | `user_profiles` | 资料扩展（与用户 1:1） | 同 users | 否 | 否 |
| 4 | `roles` | 角色 | 十级 | 否 | 否 |
| 5 | `permissions` | 权限点 | 百级 | 否 | 否 |
| 6 | `role_permissions` | 角色-权限关联 | 千级 | 否 | 否 |
| 7 | `user_roles` | 用户-角色关联 | 百万级 | 否 | 否 |
| 8 | `user_addresses` | 收货地址 | 千万级 | 是 | 是 |
| 9 | `verification_codes` | 验证码记录 | 千万级（定期清理） | 否 | 否 |
| 10 | `refresh_tokens` | 刷新令牌与轮换链 | 千万级（定期清理） | 否 | 否 |
| 11 | `oauth_bindings` | 第三方账号绑定 | 十万级 | 否 | 否 |
| 12 | `user_audit_logs` | 操作审计日志 | 千万级（定期归档） | 否 | 否 |
| 13 | `outbox_events` | 事务性发件箱（通用约定 §10.4） | 百万级（定期归档） | 否 | 否 |

> `idempotency_keys` 不建表：注册幂等以 `uk_users_email` / `uk_users_phone` 唯一索引兜底，其余写接口天然幂等或由状态机约束，幂等键统一存 Redis（通用约定 §6）。

关系（不使用物理外键，由应用层保证）：

```
users 1─1 user_credentials
users 1─1 user_profiles
users 1─N user_addresses
users 1─N user_roles N─1 roles 1─N role_permissions N─1 permissions
users 1─N refresh_tokens         (同一 token_family_id 构成一条轮换链)
users 1─N verification_codes     (按 account+scene 定位，弱关联)
users 1─N oauth_bindings
users 1─N user_audit_logs        (user_id 为被操作对象，operator_id 为操作者)
```

### 2.2 枚举字典

所有枚举使用 `VARCHAR(32)` + `CHECK` 约束，禁止数字编码（通用约定 §7.4）。

| 枚举 | 取值 | 说明 |
|---|---|---|
| `users.status` | `ACTIVE` / `DISABLED` / `LOCKED` / `DELETED` | 正常 / 管理员禁用 / 登录失败锁定 / 已注销 |
| `user_credentials.password_algo` | `argon2id` | 仅此一种，保留字段以便未来平滑迁移 |
| `user_profiles.gender` | `MALE` / `FEMALE` / `OTHER` / `UNKNOWN` | 默认 `UNKNOWN` |
| `roles.role_type` | `SYSTEM` / `CUSTOM` | 内置角色不可删除或改标识 |
| `user_addresses.source` | `MANUAL` / `ORDER_SNAPSHOT` | 下单时"新增地址"回写的来源标记（预留） |
| `verification_codes.account_type` | `EMAIL` / `PHONE` | 账号类型 |
| `verification_codes.scene` | `REGISTER` / `LOGIN` / `RESET_PASSWORD` / `BIND_EMAIL` / `BIND_PHONE` / `CLOSE_ACCOUNT` | 验证场景，场景隔离不可跨用 |
| `verification_codes.status` | `PENDING` / `USED` / `EXPIRED` / `LOCKED` | 待验证 / 已验证 / 已过期 / 错误次数超限失效 |
| `verification_codes.delivery_status` | `PENDING` / `SENT` / `FAILED` | 投递状态，失败可重发 |
| `refresh_tokens.status` | `ACTIVE` / `USED` / `REVOKED` / `EXPIRED` | 有效 / 已被轮换使用 / 主动吊销 / 自然过期 |
| `refresh_tokens.revoke_reason` | `LOGOUT` / `LOGOUT_ALL` / `ROTATED` / `REPLAY_DETECTED` / `PASSWORD_CHANGED` / `ADMIN_DISABLED` / `ACCOUNT_CLOSED` | 吊销原因，用于审计 |
| `oauth_bindings.provider` | `GOOGLE` / `GITHUB` | 第三方提供方 |
| `user_audit_logs.operator_type` | `USER` / `ADMIN` / `SYSTEM` | 操作者类型 |
| `outbox_events.status` | `PENDING` / `SENT` / `FAILED` | 待投递 / 已投递 / 超限失败待人工 |

典型审计动作 `user_audit_logs.action`（字符串，不设 CHECK，允许扩展）：`REGISTER`、`LOGIN`、`LOGIN_FAILED`、`LOGOUT`、`LOGOUT_ALL`、`PASSWORD_RESET`、`PASSWORD_CHANGED`、`REFRESH_REPLAY_DETECTED`、`PROFILE_UPDATED`、`ADDRESS_CREATED`、`ADDRESS_UPDATED`、`ADDRESS_DELETED`、`ADDRESS_SET_DEFAULT`、`ROLE_GRANTED`、`ROLE_REVOKED`、`ROLE_PERMISSION_UPDATED`、`USER_DISABLED`、`USER_ENABLED`、`ACCOUNT_CLOSE_REQUESTED`、`ACCOUNT_ANONYMIZED`、`OAUTH_BOUND`、`OAUTH_UNBOUND`。

### 2.4 索引设计

| 表 | 索引 | 类型 | 支撑场景 |
|---|---|---|---|
| users | `pk_users (id)` | 主键 | 按 ID 查询 |
| users | `uk_users_email (email) WHERE deleted_at IS NULL` | 唯一（部分） | 邮箱唯一性、邮箱登录 |
| users | `uk_users_phone (phone) WHERE deleted_at IS NULL` | 唯一（部分） | 手机唯一性、手机登录 |
| users | `idx_users_status_created_at (status, created_at DESC)` | 普通 | 后台按状态检索并按注册时间排序 |
| users | `idx_users_created_at (created_at DESC)` | 普通 | 后台默认列表、注册量统计 |
| users | `idx_users_locked_until (locked_until) WHERE locked_until IS NOT NULL` | 普通（部分） | 解锁任务扫描、锁定中账号检索 |
| user_credentials | `uk_user_credentials_user_id (user_id)` | 唯一 | 登录取凭证 |
| user_profiles | `uk_user_profiles_user_id (user_id)` | 唯一 | 资料读取 |
| roles | `uk_roles_code (code)` | 唯一 | 角色标识唯一性 |
| permissions | `uk_permissions_code (code)` | 唯一 | 权限标识唯一性 |
| permissions | `idx_permissions_module (module, code)` | 普通 | 后台按模块分组展示 |
| role_permissions | `uk_role_permissions_role_id_permission_id (role_id, permission_id)` | 唯一 | 防重复授权 |
| role_permissions | `idx_role_permissions_permission_id (permission_id)` | 普通 | 反查权限被哪些角色引用 |
| user_roles | `uk_user_roles_user_id_role_id (user_id, role_id)` | 唯一 | 防重复授角色 |
| user_roles | `idx_user_roles_role_id (role_id)` | 普通 | 按角色反查用户 / 删除角色前校验引用 |
| user_addresses | `idx_user_addresses_user_id_deleted_at (user_id, deleted_at)` | 普通 | 地址列表（最左前缀覆盖归属过滤） |
| user_addresses | `uk_user_addresses_default (user_id) WHERE is_default = TRUE AND deleted_at IS NULL` | 唯一（部分） | **默认地址唯一性兜底** |
| user_addresses | `idx_user_addresses_user_id_created_at (user_id, created_at DESC)` | 普通 | 列表排序（新建在前） |
| verification_codes | `idx_verification_codes_account_scene (account, scene, created_at DESC)` | 普通 | 取最近一条有效验证码 |
| verification_codes | `idx_verification_codes_expires_at (expires_at)` | 普通 | 清理任务扫描 |
| verification_codes | `idx_verification_codes_user_id (user_id)` | 普通 | 按用户追溯（风控） |
| refresh_tokens | `uk_refresh_tokens_token_hash (token_hash)` | 唯一 | 刷新时按哈希定位 |
| refresh_tokens | `idx_refresh_tokens_user_id_status (user_id, status)` | 普通 | 全端下线、登录设备列表 |
| refresh_tokens | `idx_refresh_tokens_token_family_id (token_family_id)` | 普通 | 按链吊销（重放检测） |
| refresh_tokens | `idx_refresh_tokens_expires_at (expires_at)` | 普通 | 清理任务扫描 |
| oauth_bindings | `uk_oauth_bindings_provider_provider_user_id (provider, provider_user_id)` | 唯一 | OAuth 登录定位用户 |
| oauth_bindings | `uk_oauth_bindings_user_id_provider (user_id, provider)` | 唯一 | 同用户同渠道仅一条绑定 |
| user_audit_logs | `idx_user_audit_logs_user_id_created_at (user_id, created_at DESC)` | 普通 | 用户操作轨迹 |
| user_audit_logs | `idx_user_audit_logs_operator_id_created_at (operator_id, created_at DESC)` | 普通 | 管理员操作轨迹 |
| user_audit_logs | `idx_user_audit_logs_action_created_at (action, created_at DESC)` | 普通 | 按动作检索（如重放检测告警） |
| user_audit_logs | `idx_user_audit_logs_created_at (created_at)` | 普通 | 归档任务扫描 |
| outbox_events | `uk_outbox_events_event_id (event_id)` | 唯一 | 消费方幂等追溯 |
| outbox_events | `idx_outbox_events_status_next_retry_at (status, next_retry_at)` | 普通 | 投递任务扫描 |
| outbox_events | `idx_outbox_events_created_at (created_at)` | 普通 | 归档任务扫描 |

> 单表索引均不超过 6 个（通用约定 §8.2）。`user_addresses` 的三个索引中，`idx_user_addresses_user_id_deleted_at` 与 `idx_user_addresses_user_id_created_at` 存在最左前缀冗余，保留前者是因为列表查询固定携带 `deleted_at IS NULL`、而 `created_at DESC` 排序在仅返回少量行时可用内存排序，实测后再决定是否合并。

### 2.5 完整 DDL

```sql
-- =============================================================================
-- 用户服务（user-service）完整 DDL
-- 目标库：ecommerce_user        数据库：PostgreSQL 16
-- 约定：雪花 ID 由应用层生成；时间统一 TIMESTAMPTZ（UTC）；不使用物理外键
-- 执行顺序：按本文件自上而下即可；初始化数据见文件末尾
-- =============================================================================

-- -----------------------------------------------------------------------------
-- 1. users 用户主表
-- -----------------------------------------------------------------------------
CREATE TABLE users (
    id                  BIGINT       NOT NULL,
    email               VARCHAR(254),
    phone               VARCHAR(20),
    status              VARCHAR(32)  NOT NULL DEFAULT 'ACTIVE',
    is_email_verified   BOOLEAN      NOT NULL DEFAULT FALSE,
    is_phone_verified   BOOLEAN      NOT NULL DEFAULT FALSE,
    failed_login_count  SMALLINT     NOT NULL DEFAULT 0,
    locked_until        TIMESTAMPTZ,
    last_login_at       TIMESTAMPTZ,
    last_login_ip       INET,
    registered_from     VARCHAR(32)  NOT NULL DEFAULT 'WEB',
    deleted_at          TIMESTAMPTZ,
    created_at          TIMESTAMPTZ  NOT NULL DEFAULT now(),
    updated_at          TIMESTAMPTZ  NOT NULL DEFAULT now(),
    CONSTRAINT pk_users PRIMARY KEY (id),
    CONSTRAINT ck_users_status CHECK (status IN ('ACTIVE', 'DISABLED', 'LOCKED', 'DELETED')),
    CONSTRAINT ck_users_account_present CHECK (email IS NOT NULL OR phone IS NOT NULL),
    CONSTRAINT ck_users_failed_login_count CHECK (failed_login_count >= 0),
    CONSTRAINT ck_users_email_format CHECK (email IS NULL OR email ~ '^[^@\s]+@[^@\s]+\.[^@\s]+$')
);

COMMENT ON TABLE  users IS '用户主表：账号标识、状态、验证标记与登录安全计数';
COMMENT ON COLUMN users.email IS '邮箱，统一小写存储；与 phone 至少一个非空';
COMMENT ON COLUMN users.phone IS '手机号，E.164 格式，如 +8613800138000';
COMMENT ON COLUMN users.status IS 'ACTIVE/DISABLED/LOCKED/DELETED';

COMMENT ON COLUMN users.locked_until IS '登录失败锁定截止时间，到期自动解锁';
COMMENT ON COLUMN users.deleted_at IS '注销时间，非空表示账号已注销';

-- 唯一性仅在未注销账号间生效；注销时邮箱/手机号被改写为匿名值，不占用原值
```

### 3.2 鉴权类接口

#### A1 `POST /api/v1/auth/register` — 用户注册

| 项 | 内容 |
|---|---|
| 鉴权 | 公开（网关白名单） |
| 幂等 | 可选 `Idempotency-Key`，重复请求返回首次结果（24 小时） |
| 限流 | 网关按 IP 限制；服务内按 IP 限制单日注册数（默认 20） |

请求体：

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| email | string | 条件 | ≤254，邮箱格式 | 与 `phone` 至少一个 |
| phone | string | 条件 | E.164，≤20 | 与 `email` 至少一个 |
| password | string | 是 | 8~64，见密码强度规则 | 明文仅用于计算哈希，不落日志 |
| nickname | string | 否 | 1~64 | 缺省则按账号生成脱敏昵称 |
| verification_code | string | 否 | 6 位数字 | 提供则先校验 `REGISTER` 场景验证码（支持"先验证后注册"） |
| registered_from | string | 否 | 枚举 | `WEB`（默认）/ `IOS` / `ANDROID` |

密码强度规则：长度 8~64；至少包含字母与数字；不含空白字符；不在常见弱口令字典内。

```bash
curl -X POST https://api.example.com/api/v1/auth/register \
  -H "Content-Type: application/json" \
  -H "X-Request-Id: 7f2c1a90-3b1e-4d55-9c88-0a1b2c3d4e5f" \
  -H "Idempotency-Key: reg-20260910-0001" \
  -d '{
    "email": "alice@example.com",
    "password": "Str0ngPass!2026",
    "nickname": "Alice"
  }'
```

响应 `201`：


#### A6 `POST /api/v1/auth/logout` — 登出

| 项 | 内容 |
|---|---|
| 鉴权 | 登录 |
| 幂等 | 是，重复登出返回 `204` |

请求体：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| refresh_token | string | 是 | 需吊销的刷新令牌 |

```bash
curl -X POST https://api.example.com/api/v1/auth/logout \
  -H "Authorization: Bearer eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9..." \
  -H "Content-Type: application/json" \
  -d '{"refresh_token": "3q2-7wB9kR1sT4uV6xY8zA0bC2dE4fG6hI8jK0lM2nO"}'
```

响应 `204 No Content`（无 body）。

服务端动作：
1. 按 `token_hash` 定位刷新令牌，置 `REVOKED` / `revoke_reason='LOGOUT'`；
2. 将当前访问令牌的 `jti` 写入 Redis 黑名单，TTL = 令牌剩余有效期；
3. 写审计日志 `LOGOUT`。

> **只吊销本次会话**，其他设备不受影响。`refresh_token` 缺失或不属于当前用户时同样返回 `204`（登出无副作用，不泄露信息）。

| 未绑定、第三方未提供已验证邮箱 | 返回 `409 USER-5016`，提示"请先用邮箱注册并登录后再绑定第三方账号" |
| 第三方邮箱已被其他本地账号占用且未验证 | 返回 `409 USER-5016` |
| 该第三方账号已绑定其他用户 | `409 USER-5008` |
| `state` 无效或过期 | `400 USER-1011` |
| 第三方接口不可用/超时 | `502 USER-7002` |

> OAuth 自动注册的账号**没有密码凭证**（`user_credentials` 无记录），登录只能通过该渠道；用户可在个人中心设置密码（`PUT /api/v1/users/me/password`，此时 `current_password` 可省略）。

| 项 | 内容 |
|---|---|
| 鉴权 | 登录 |
| 幂等 | 是；重复提交返回 `204` |
| 前置 | 需在请求中提供 `CLOSE_ACCOUNT` 场景验证码或 `verification_ticket` |

请求体：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| verification_ticket | string | 条件 | A3 校验 `CLOSE_ACCOUNT` 场景后返回的一次性凭证 |
| verification_code | string | 条件 | 与 `verification_ticket` 二选一 |
| reason | string | 否 | 注销原因，≤200，可空 |


响应 `204 No Content`。

错误码：`USER-1001` `USER-1011`（凭证无效或过期）`USER-3005`（账号未完成验证，无法注销）`USER-5014`（存在未完成订单，暂不能注销）。

注销语义（对应 NFR-CP-004）：
1. `users.status` 置 `DELETED`、`deleted_at` 置当前时间；
2. `email` / `phone` 立即改写为匿名值（`deleted+{user_id}@deleted.invalid` / `+00000000000`），释放原账号供他人注册；
3. 删除全部收货地址（`deleted_at` 置位，保留行以便历史订单可追溯）；
4. 吊销全部刷新令牌 + 写 `revoke_after`，令牌立即失效；
5. **保留** `user_id` 与审计日志：订单、支付流水按法规需留存交易记录，`user_id` 作为外部引用键不可回收；
6. 昵称/头像/生日等在 **30 天冷静期**后由 `account_purge` 任务彻底匿名化（昵称置 `已注销用户`，头像置空）；冷静期内运营可通过内部流程恢复账号。

> `DELETE` 携带请求体在部分代理上可能被丢弃，客户端如遇问题可改用 `POST /api/v1/users/me/close`（别名，行为一致）。本期同时注册两个路由。

## 4. 内部接口设计

内部接口统一置于 `/internal/v1` 命名空间，网关不对外暴露；调用方必须携带 `X-Internal-Token`（校验失败返回 `COMMON-2002`）、`X-Request-Id`、`X-Trace-Id`；超时连接 1s / 读取 3s；只读接口，遵循通用约定 §11.2 的重试规则（最多 2 次指数退避）。

### I1 `POST /internal/v1/users/batch` — 批量查询用户基本信息

**调用方**：order-service（订单列表补全买家昵称、判断账号是否可下单）、notification-service（通知记录补充昵称）。

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| user_ids | string[] | 是 | 1~100 个，字符串化雪花 ID | 超出 100 个返回 `USER-1001` |
| fields | string[] | 否 | 白名单枚举 | 需要返回的字段，缺省返回全部允许字段 |

## 5. 事件设计

### 5.1 发布事件

本期用户服务**只发布一个事件**：`user.registered`（通用约定 §10.3 标准事件目录）。

#### `user.registered`

| 项 | 内容 |
|---|---|
| Exchange | `ecommerce.events`（topic，持久化） |
| Routing Key | `user.registered` |
| 消费队列 | `notification.user.registered`（通知服务），DLX `ecommerce.events.dlx` → `notification.user.registered.dlq` |
| 触发时机 | 注册成功、OAuth 首次自动注册成功（同一本地事务内写入 outbox） |
| 投递方式 | 事务性发件箱 + `outbox_dispatch` 定时任务 |
| 幂等键 | `event_id`（UUID v4） |

事件体：

```json
{
  "event_id": "9f1c2b3a-4d5e-6f70-8192-a3b4c5d6e7f8",
  "event_type": "user.registered",
  "event_version": "1.0",
  "occurred_at": "2026-09-10T08:30:00.123Z",
  "producer": "user-service",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "payload": {
    "user_id": "8102394123456789",
    "account": "alice@example.com",
    "email": "alice@example.com",
    "phone": null,
    "nickname": "Alice"
  }
}
```

payload 字段：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| user_id | string | 是 | 用户 ID（字符串化雪花 ID） |
| account | string | 是 | 注册账号：有邮箱时为邮箱，否则为手机号 |
| email | string \| null | 是 | 邮箱，无则为 `null`；OAuth 注册时取第三方已验证邮箱 |
| phone | string \| null | 是 | 手机号，无则为 `null` |
| nickname | string | 是 | 昵称，缺省时按账号生成的脱敏昵称 |

> **隐私约束**：payload 中的邮箱与手机号属个人信息，队列与日志中不做明文脱敏（通知服务必须使用它们）。因此 **`outbox_events.payload` 与事件日志的采集侧需限制访问权限**；通知服务消费后不得将其写入自身日志（沿用通用约定 §12.3 脱敏清单）。

#### 未发布事件的场景（有意为之）

| 场景 | 为何不发事件 | 其他服务如何感知 |
|---|---|---|
| 账号被禁用（FR-US-009） | 唯一消费方是订单服务，且订单服务在下单时通过 I1 的 `can_place_order` 同步校验即可覆盖；广播会引入"事件丢失导致禁用未生效"的窗口 | 同步校验 + 令牌吊销 |
| 密码修改/重置 | 无跨服务语义 | 令牌吊销即时生效 |
| 资料修改 | 无跨服务语义（订单快照不依赖最新资料） | — |
| 账号注销 | 无消费方需要主动动作 | 订单服务通过 I1/I3 返回的 `missing_user_ids` / `can_place_order=false` 自然降级 |

若后续需要 `user.disabled`、`user.profile.updated` 等事件，须按通用约定 §10.3 的流程先登记到标准事件目录再实现。

### 5.2 订阅事件

**无。** 用户服务不消费任何事件，是纯生产者。这保证了它的可用性只依赖 PostgreSQL、Redis 与通知服务（仅验证码接口），不被消息积压影响。

### 5.3 事件投递与可靠性

| 环节 | 措施 |
|---|---|
| 生产 | 业务数据与 `outbox_events` 行在同一本地事务写入（`BEGIN ... INSERT users ... INSERT outbox_events ... COMMIT`），业务成功则事件不丢 |
| 投递 | `outbox_dispatch` 每 5 秒批量扫描 `status='PENDING' AND next_retry_at <= now()`，`FOR UPDATE SKIP LOCKED` 取行，发布至 RabbitMQ（publisher confirms），成功后置 `SENT` 并记录 `sent_at` |
| 重试 | 失败按 `1s / 5s / 30s / 2m / 10m` 指数退避重投，`retry_count` 达 5 次置 `FAILED` 并触发告警（P1） |
| 积压告警 | `PENDING` 且 `created_at` 早于 5 分钟的记录数 > 100 时告警 |
| 归档 | `outbox_dispatch` 投递成功后 30 天由 `outbox_cleanup` 任务删除 `SENT` 行 |
| 顺序性 | 本服务事件无顺序依赖（同一用户可能连续产生多个事件，消费方按 `event_id` 幂等处理即可），不设分区键 |

## 6. 核心业务流程

### 6.1 注册（FR-US-001 / FR-US-002）

```
客户端 ──POST /auth/register──▶ 用户服务
   1. 参数校验（账号、密码强度、幂等键）
   2. 唯一性预检（DB 查询，快速失败）
   3. 【本地事务】
      - INSERT users（status=ACTIVE）
      - INSERT user_credentials（argon2id）
      - INSERT user_profiles（默认昵称）
      - INSERT user_roles（BUYER，granted_by=NULL）
      - INSERT verification_codes（scene=REGISTER，若请求未带验证码）
      - INSERT outbox_events（user.registered）
   4. 提交事务
   5. 事务外：调通知服务投递验证码
   6. 签发访问令牌 + 刷新令牌，写入 refresh_tokens
   7. 返回 201（含令牌与投递状态）
```

```python
async def register(req, ctx) -> RegisterResult:
    validate_account(req.email, req.phone)          # 至少一个 + 格式校验
    validate_password_strength(req.password)        # USER-1004

    # 幂等：相同 Idempotency-Key 直接返回首次结果
    if req.idempotency_key:
        cached = await idem.get_or_none(req.idempotency_key)
        if cached:
            return cached

    # 唯一性预检（唯一索引兜底，见 except 分支）
    if req.email and await users.exists_active(email=req.email):
        raise BizError("USER-5001", "该邮箱已被注册")
    if req.phone and await users.exists_active(phone=req.phone):
        raise BizError("USER-5002", "该手机号已被注册")

    user_id = snowflake.next_id()
    try:
        async with uow.transaction():                       # 单库本地事务
            if req.verification_code:                       # 可选的"先验证后注册"
                await verification.consume(req.email or req.phone,
                                           "REGISTER", req.verification_code)
            user = await users.insert(
                id=user_id, email=lower(req.email), phone=req.phone,
                status="ACTIVE", registered_from=req.registered_from or "WEB",
                is_email_verified=bool(req.verification_code and req.email),
            )
            await credentials.insert(user_id=user_id,
                                     password_hash=argon2.hash(req.password))
            await profiles.insert(user_id=user_id,
                                  nickname=req.nickname or mask_as_nickname(user))
            buyer = await roles.get_by_code("BUYER")
            await user_roles.insert(user_id=user_id, role_id=buyer.id, granted_by=None)
            await audit.append(action="REGISTER", user_id=user_id,
                               operator_type="USER", client_ip=ctx.ip)
            if not req.verification_code:
                code = await verification.issue(user, "REGISTER", ctx.ip)
            # 事务性发件箱：与业务同事务，保证事件不丢
            await outbox.insert(event_type="user.registered", payload={
                "user_id": str(user_id), "account": user.account,
                "email": user.email, "phone": user.phone,
                "nickname": nickname,
            })
    except UniqueViolation as e:                            # 唯一索引兜底
        raise BizError("USER-5001" if "email" in str(e) else "USER-5002")

    # 事务外：投递失败不影响注册结果
    delivery = "NOT_REQUIRED"
    if not req.verification_code:
        delivery = await notify.send_verification_code(
            account=user.account, account_type=user.account_type,
            scene="REGISTER", code_plain=code.plain, biz_id=code.id)

    tokens = await token_service.issue_pair(user, ctx)      # 访问 + 刷新（新 family）
    result = RegisterResult(user, tokens, code, delivery)
    if req.idempotency_key:
        await idem.store(req.idempotency_key, result, ttl=24h)
    return result
```

**并发注册同一邮箱**：两个请求同时通过预检 → 后提交者触发 `uk_users_email` 唯一冲突 → 捕获异常转为 `USER-5001`。事务整体回滚，不产生孤儿凭证与角色关联。

### 6.2 登录与失败锁定（FR-US-003）

```
POST /auth/login
  ├─ 账号不存在 ──▶ 执行等价成本 dummy 哈希 ──▶ USER-2001
  ├─ status=DISABLED ──▶ USER-2003
  ├─ status=DELETED ──▶ USER-2004
  ├─ locked_until > now ──▶ USER-2002（含解锁时间）
  ├─ 密码错误 ──▶ failed_login_count += 1
  │     └─ 达到 5 次 ──▶ status=LOCKED? 不置 status，仅置 locked_until = now + 15min
  └─ 密码正确 ──▶ 清零计数 + 更新 last_login + 签发令牌对
```

**状态语义澄清**：`status='LOCKED'` 与 `locked_until` 的关系——**登录失败锁定不改 `status`**，只写 `locked_until`。`status='LOCKED'` 保留给"风控系统人工标记"的场景。这样管理员在后台看到的"锁定"过滤条件为 `locked_until > now()`，与 `status` 解耦，避免禁用与锁定互相覆盖。

```python
async def login(account, password, client_type, ctx) -> TokenPair:
    # IP 维度限流：15 分钟 30 次失败
    if await limiter.ip_login_fail_count(ctx.ip) >= 30:
        raise BizError("USER-6003", "请求过于频繁，请稍后重试")

    user = await users.find_by_account(account)         # email 或 phone
    if user is None:
        argon2.verify(DUMMY_HASH, password)             # 恒定耗时，防账号枚举
        await limiter.record_login_fail(ctx.ip)
        raise BizError("USER-2001", "账号或密码错误")

    if user.status == "DELETED":  raise BizError("USER-2004", "账号已注销")
    if user.status == "DISABLED": raise BizError("USER-2003", "账号已被禁用")
    if user.locked_until and user.locked_until > now():
        raise BizError("USER-2002", details={"locked_until": iso(user.locked_until)})

    cred = await credentials.get_by_user(user.id)
    ok = cred and argon2.verify(cred.password_hash, password)

    if not ok:
        async with uow.transaction():
            count = await users.incr_failed_login(user.id, for_update=True)
            if count >= settings.LOGIN_MAX_FAILURES:            # 默认 5
                await users.set_locked_until(
                    user.id, now() + timedelta(minutes=settings.LOGIN_LOCK_MINUTES))  # 15
                await limiter.set_login_fail_window(user.id, ttl=15min)
            await audit.append(action="LOGIN_FAILED", user_id=user.id,
                               operator_type="USER", client_ip=ctx.ip)
        await limiter.record_login_fail(ctx.ip)
        raise BizError("USER-2001", "账号或密码错误")

    # 密码正确：如哈希参数落后于当前配置则透明重哈希
    if argon2.needs_rehash(cred.password_hash):
        await credentials.update_hash(user.id, argon2.hash(password))

    async with uow.transaction():
        await users.reset_failed_login(user.id, now(), ctx.ip)
        await audit.append(action="LOGIN", user_id=user.id, client_ip=ctx.ip)

    if client_type == "ADMIN_CONSOLE" and not await rbac.has_console_access(user.id):
        raise BizError("COMMON-3001", "无权限登录管理后台")

    return await token_service.issue_pair(user, ctx)
```

**锁定与解锁**：`locked_until` 到期即自动可登录（无需任务）。管理员可通过 U4 启用账号顺带清零计数。解锁失败的审计日志保留，便于风控追溯。

### 6.3 刷新令牌轮换与重放检测（FR-US-004）

设计要点：
- **刷新令牌是不透明的随机串**（32 字节 CSPRNG → base64url，约 43 字符），不是 JWT。理由：轮换与重用检测必须依赖服务端状态，JWT 的自包含性在此没有收益；随机串更短、无签名开销、可即时吊销。
- **每次刷新都轮换**：旧令牌置 `USED` 并记录 `used_at`，新令牌继承 `token_family_id`，`parent_token_id` 指向旧令牌。
- **重放检测**：收到一个 `status='USED'` 的令牌，说明出现了令牌泄漏或客户端并发刷新。此时按 `token_family_id` 吊销整条链并强制该用户全端下线。

```
首次登录   T0(ACTIVE, family=F)
   │  刷新
   ▼
   T1(ACTIVE, family=F, parent=T0)   T0(USED)
   │  刷新
   ▼
   T2(ACTIVE, family=F, parent=T1)   T1(USED)

攻击者用 T0 刷新 ──▶ 命中 T0.status == USED ──▶ 吊销 F 全链 + 用户强制下线
```

```python
async def refresh(raw_token, ctx) -> TokenPair:
    digest = hmac_sha256(raw_token, settings.REFRESH_TOKEN_PEPPER)
    async with uow.transaction():
        row = await refresh_tokens.find_by_hash_for_update(digest)   # SELECT ... FOR UPDATE
        if row is None:
            raise BizError("USER-2005", "刷新令牌无效或已过期")

        # ---- 重放检测 ----
        if row.status == "USED":
            await refresh_tokens.revoke_family(
                row.token_family_id, reason="REPLAY_DETECTED")
            await auth_revocation.revoke_all(row.user_id)   # 写 revoke_after + 用户级下线
            await audit.append(action="REFRESH_REPLAY_DETECTED", user_id=row.user_id,
                               operator_type="SYSTEM", client_ip=ctx.ip,
                               after_value={"family_id": str(row.token_family_id)})
            logger.warning("refresh token replay detected", extra={"user_id": row.user_id})
            raise BizError("USER-2006",
                           "登录状态异常，出于安全已注销全部会话，请重新登录")

        if row.status != "ACTIVE":
            raise BizError("USER-2005", "刷新令牌无效或已过期")
        if row.expires_at <= now():
            await refresh_tokens.mark(row.id, status="EXPIRED")
            raise BizError("USER-2005", "刷新令牌无效或已过期")

        user = await users.get(row.user_id)
        if user is None or user.status in ("DISABLED", "DELETED"):
            await refresh_tokens.revoke_family(row.token_family_id, reason="ACCOUNT_CLOSED")
            raise BizError("USER-2003" if user else "USER-2004")

        # ---- 轮换 ----
        await refresh_tokens.mark(row.id, status="USED", used_at=now())
        new_tok = await token_service.issue_refresh(
            user, family_id=row.token_family_id, parent_id=row.id, ctx=ctx)
        await refresh_tokens.mark(row.id, revoke_reason="ROTATED")

    access = await token_service.sign_access(user)          # roles 实时查库
    return TokenPair(access, new_tok.plain)
```

**并发刷新（前端多标签页）**：后端不做宽限窗口——第二次请求携带的旧令牌已 `USED`，会触发重放检测。这是刻意的安全取舍，代价是要求前端请求层做**单飞刷新**（同一时刻只允许一个刷新请求，其余请求排队等待结果）。该要求已写入 §12 测试要点与前端接口约定。

**刷新令牌有效期**：每次轮换重新计时 14 天，即活跃用户不会被强制登出；长期不活跃则在最后一次刷新后 14 天失效（对应需求"刷新令牌 14 天"）。

### 6.4 令牌签发与吊销

```python
async def issue_pair(user, ctx) -> TokenPair:
    roles = await rbac.list_role_codes(user.id)             # 实时查 user_roles
    access_plain = jwt.sign(
        payload={
            "sub": str(user.id), "roles": roles,
            "jti": str(uuid4()), "iss": settings.JWT_ISSUER,
            "aud": settings.JWT_AUDIENCE,
        },
        private_key=settings.JWT_PRIVATE_KEY, algorithm="RS256",
        expires_delta=timedelta(seconds=settings.JWT_ACCESS_TTL_SECONDS),   # 1800
    )
    refresh_plain = generate_opaque_token()                  # 32B CSPRNG → base64url
    await refresh_tokens.insert(
        user_id=user.id, token_hash=hmac_sha256(refresh_plain, PEPPER),
        token_family_id=uuid4(), parent_token_id=None, status="ACTIVE",
        expires_at=now() + timedelta(seconds=settings.JWT_REFRESH_TTL_SECONDS),  # 14d
        client_ip=ctx.ip, user_agent=truncate(ctx.ua, 512),
    )
    return TokenPair(access_plain, refresh_plain)


async def revoke_access_jti(jti: str, exp: int) -> None:
    """登出：把访问令牌的 jti 写入黑名单，TTL 取令牌剩余有效期"""
    ttl = max(0, exp - epoch_now())
    if ttl > 0:
        await redis.set(f"user:auth:jwt:blacklist:{jti}", "1", ex=ttl)


async def revoke_all(user_id: int) -> int:
    """全端下线：吊销全部刷新令牌 + 写用户级吊销时间戳"""
    async with uow.transaction():
        n = await refresh_tokens.revoke_by_user(
            user_id, reason="LOGOUT_ALL")                    # ACTIVE → REVOKED
        await audit.append(action="LOGOUT_ALL", user_id=user_id, operator_type="USER")
    # 网关契约：iat < revoke_after 的访问令牌一律拒绝（见 §1.5）
    await redis.set(f"user:auth:revoke_after:{user_id}",
                    iso_utc(now()), ex=settings.JWT_REFRESH_TTL_SECONDS)
    return n
```

签名算法取 **RS256** 而非 HS256：网关与其他服务只需持有公钥即可验签，私钥只存在于用户服务，避免对称密钥在多服务间扩散造成伪造风险。

### 6.5 验证码发送与校验（FR-US-002）

```
发送：频率检查(Redis) → 生成 6 位随机码 → sha256 落库 → 调通知服务 → 写冷却 Key
校验：取最新 PENDING 记录 → 有效期检查 → 哈希比对 → 成功置 USED / 失败累加 attempts
```

```python
async def issue_code(account, account_type, scene, ctx) -> CodeRecord:
    # 1. 频率限制（Redis，先检查后写入）
    if await redis.exists(f"user:verify:send_lock:{scene}:{account}"):
        raise BizError("USER-6001", "验证码已发送，请 60 秒后重试")
    if await redis.incr_daily(f"user:verify:quota:{scene}:{account}", cap=10) > 10:
        raise BizError("USER-6002", "今日验证码发送次数已达上限")
    if await redis.incr_daily(f"user:verify:quota:ip:{ctx.ip}", cap=30) > 30:
        raise BizError("USER-6002", "今日验证码发送次数已达上限")

    # 2. 生成与落库（同场景旧码立即失效，避免多码并存被暴力枚举）
    plain = f"{secrets.randbelow(1_000_000):06d}"
    ttl = 600 if account_type == "EMAIL" else 300
    record = await verification_codes.insert(
        account=account, account_type=account_type, scene=scene,
        code_hash=sha256(f"{plain}{account}{scene}{PEPPER}"),
        channel="EMAIL" if account_type == "EMAIL" else "SMS",
        max_attempts=settings.VERIFY_CODE_MAX_ATTEMPTS,       # 5
        sender_ip=ctx.ip, expires_at=now() + timedelta(seconds=ttl),
    )
    await verification_codes.lock_active(account, scene, except_id=record.id)  # 旧码→EXPIRED

    # 3. 投递（失败则撤回冷却，允许立即重试）
    delivered = await notify.send_verification_code(
        to=account, channel=record.channel, code=plain,
        expire_minutes=ttl // 60, biz_id=record.id, scene=scene)
    if delivered:
        await verification_codes.mark(record.id, delivery_status="SENT")
        await redis.set(f"user:verify:send_lock:{scene}:{account}", "1", ex=60)
    else:
        await verification_codes.mark(record.id, delivery_status="FAILED", status="EXPIRED")
        raise BizError("USER-7001", "验证码发送失败，请稍后重试")

    # 4. 活跃验证码写入 Redis 供校验快速定位（含剩余尝试次数）
    await redis.set(f"user:verify:code:{scene}:{account}",
                    json.dumps({"id": record.id, "left": record.max_attempts}),
                    ex=ttl)
    return record


async def verify_code(account, scene, code, ctx) -> None:
    record = await verification_codes.find_latest(account, scene)
    if record is None:
        raise BizError("USER-4005", "验证码不存在或已失效")
    if record.status != "PENDING" or record.expires_at <= now():
        await verification_codes.mark(record.id, status="EXPIRED")
        raise BizError("USER-5004", "验证码已过期，请重新获取")

    # 原子累加尝试次数，超过上限立即失效（防暴力枚举）
    attempts = await verification_codes.incr_attempts(record.id)
    if attempts > record.max_attempts:
        await verification_codes.mark(record.id, status="LOCKED")
        raise BizError("USER-5005", "验证码错误次数过多，请重新获取")

    if not hmac_compare(sha256(f"{code}{account}{scene}{PEPPER}"), record.code_hash):
        left = max(0, record.max_attempts - attempts)
        raise BizError("USER-5003", "验证码错误",
                       details=[{"field": "code", "reason": f"还可尝试 {left} 次"}])

    await verification_codes.mark(record.id, status="USED", verified_at=now())
    await redis.delete(f"user:verify:code:{scene}:{account}")
```

**幂等消费**：`REGISTER` 场景在注册事务内调用 `consume()`，此时才写 `used_at`；`RESET_PASSWORD` / `CLOSE_ACCOUNT` 场景校验通过后签发一次性 `verification_ticket`（Redis 5 分钟），避免验证码被重复提交使用。

> 6 位数字验证码共 100 万种组合，配合"最长 10 分钟有效期 + 5 次尝试上限 + 60 秒发送间隔"，单个验证码被暴力猜中的概率 < 1e-5；叠加 IP 维度限流后风险可接受。

### 6.6 找回与重置密码（FR-US-005）

```
POST /auth/password/forgot
   ├─ 账号存在且 status=ACTIVE ──▶ 生成 RESET_PASSWORD 验证码 ──▶ 投递
   └─ 账号不存在/被禁用/未验证  ──▶ 不生成验证码，返回相同响应（防枚举）

POST /auth/password/reset
   1. 校验验证码（RESET_PASSWORD 场景，一次性）
   2. 强度校验新密码；与当前密码比对（argon2.verify 旧哈希），相同则 USER-5011
   3. 【本地事务】
      - UPDATE user_credentials（新哈希）
      - 吊销全部 refresh_tokens（reason=PASSWORD_CHANGED）
      - 审计 PASSWORD_RESET
   4. 事务外：写 user:auth:revoke_after:{user_id}（使所有访问令牌失效）
   5. 返回 200（不签发令牌）
```

重置后**不自动登录**：强制用户用新密码走一次登录，确保凭证校验链路被真实执行，同时使用户获得通知（登录成功邮件可由通知服务后续扩展）。

### 6.7 OAuth 登录（FR-US-010）

```
① GET /auth/oauth/{provider}/authorize
   → 生成 state + PKCE code_verifier
   → Redis user:oauth:state:{state} = {verifier, redirect_uri, bind, user_id?}  TTL 10min
   → 返回第三方 authorize_url

② 用户在第三方页面授权

③ POST /auth/oauth/{provider}/callback  { code, state }
   → Redis 取出并立即删除 state（一次性，防重放）→ 无记录则 USER-1011
   → 用 code + verifier 换第三方 access_token（超时 1s/3s，失败 USER-7002）
   → 拉取第三方用户信息（provider_user_id / email / email_verified）
   → 分支：
        a) oauth_bindings 存在 (provider, provider_user_id)
             ├─ user.status ACTIVE  → 直接签发令牌
             └─ user.status 非 ACTIVE → USER-2003 / USER-2004
        b) 不存在
             ├─ 第三方邮箱已验证 且 users.email 命中 ACTIVE 账号
             │     → 自动绑定（apply 审计 OAUTH_BOUND）→ 签发令牌
             ├─ 第三方邮箱已验证 且 无本地账号
             │     → 自动注册（user_roles=BUYER，is_email_verified=true，
             │                  不写 user_credentials）
             │     → outbox 写 user.registered → 签发令牌（is_new_user=true）
             └─ 第三方未提供已验证邮箱
                   → USER-5016「请先用邮箱注册并登录后再绑定第三方账号」
```

自动绑定的安全前提：**仅当第三方声明邮箱已验证**（Google `email_verified=true` / GitHub 主邮箱 `verified=true`）才允许按邮箱匹配本地账号。否则攻击者可在第三方注册一个未验证的受害者邮箱，从而接管本地账号。

```python
async def oauth_callback(provider, code, state, ctx) -> OAuthResult:
    state_data = await redis.getdel(f"user:oauth:state:{state}")   # 一次性
    if not state_data:
        raise BizError("USER-1011", "授权已过期或无效，请重新发起")

    info = await oauth_client.exchange(
        provider, code=code, code_verifier=state_data.verifier,
        redirect_uri=state_data.redirect_uri)                      # 第三方失败 → USER-7002

    binding = await oauth_bindings.find(provider, info.provider_user_id)
    if binding:
        user = await users.get(binding.user_id)
        if user.status == "DISABLED": raise BizError("USER-2003")
        if user.status == "DELETED":  raise BizError("USER-2004")
        await oauth_bindings.touch_login(binding.id, ctx.ip)
        return OAuthResult(await token_service.issue_pair(user, ctx), is_new_user=False)

    if not info.email_verified or not info.email:
        raise BizError("USER-5016", "该第三方账号未提供已验证邮箱，请先注册并登录后再绑定")

    local = await users.find_active_by_email(lower(info.email))
    if local:
        async with uow.transaction():
            await oauth_bindings.insert(user_id=local.id, provider=provider,
                                        provider_user_id=info.provider_user_id,
                                        provider_email=lower(info.email),
                                        is_email_verified_by_provider=True)
            await audit.append(action="OAUTH_BOUND", user_id=local.id,
                               operator_type="USER", client_ip=ctx.ip)
        return OAuthResult(await token_service.issue_pair(local, ctx), is_new_user=False)

    # 自动注册（无密码凭证）
    return OAuthResult(await register_via_oauth(provider, info, ctx), is_new_user=True)
```

### 6.8 收货地址新增与默认地址唯一性（FR-US-007）

并发风险：同一用户并发新增两个 `is_default=true` 的地址，或并发调用设默认接口，会短暂出现两条默认地址。防御三层：

1. **用户级咨询锁**：所有地址写操作先取 `pg_advisory_xact_lock(hashtext('user:address:' || user_id))`，在同一用户内串行化；
2. **部分唯一索引兜底**：`uk_user_addresses_default` 保证任何时刻最多一条默认地址，重复插入触发唯一冲突；
3. **乐观锁**：客户端携带 `version` 时校验版本，防"读取-修改-写入"覆盖。

```python
async def create_address(user_id: int, req) -> Address:
    async with uow.transaction():
        # 1. 用户级咨询锁，事务结束自动释放
        await db.execute("SELECT pg_advisory_xact_lock(hashtext(:k))",
                         {"k": f"user:address:{user_id}"})

        # 2. 数量上限（默认 20）
        count = await addresses.count_active(user_id)
        if count >= settings.ADDRESS_MAX_COUNT:
            raise BizError("USER-5007",
                           f"收货地址数量已达上限（{settings.ADDRESS_MAX_COUNT} 个）")

        # 3. 首个地址自动成为默认；否则按请求
        make_default = req.is_default or count == 0
        if make_default and count > 0:
            await addresses.clear_default(user_id)      # 先取消旧默认，再插入新默认

        try:
            addr = await addresses.insert(user_id=user_id, **req.dict(),
                                          is_default=make_default, version=1)
        except UniqueViolation:                          # uk_user_addresses_default
            raise BizError("USER-6004", "默认地址正在变更，请重试")

        await audit.append(action="ADDRESS_CREATED", user_id=user_id,
                           resource_type="ADDRESS", resource_id=str(addr.id),
                           operator_type="USER",
                           after_value=mask_address(addr))   # 日志只记录脱敏值

    await cache.delete(f"user:address:{user_id}:default")
    return addr


async def set_default(user_id: int, address_id: int) -> Address:
    async with uow.transaction():
        await db.execute("SELECT pg_advisory_xact_lock(hashtext(:k))",
                         {"k": f"user:address:{user_id}"})
        # 归属校验：条件里必须带 user_id，越权返回 USER-3001 而非 404
        addr = await addresses.get_for_user(address_id, user_id)
        if addr is None or addr.deleted_at:
            raise BizError("USER-3001", "收货地址不存在或无权访问")
        if addr.is_default:
            return addr                                   # 幂等：已是默认，直接返回

        previous = await addresses.get_default(user_id)
        await addresses.clear_default(user_id)
        await addresses.update(addr.id, is_default=True,
                               version=addr.version + 1, expected_version=addr.version)
        await audit.append(action="ADDRESS_SET_DEFAULT", user_id=user_id,
                           resource_type="ADDRESS", resource_id=str(addr.id),
                           operator_type="USER")

    await cache.delete(f"user:address:{user_id}:default")
    return addr
```

**删除默认地址**：不自动指定新默认地址（见 D5 说明）。下次下单时若用户未选地址，前端引导设置。

### 6.9 账号禁用（FR-US-009）

```python
async def set_status(admin_id: int, user_id: int, target: str, reason: str, ctx):
    if admin_id == user_id:
        raise BizError("USER-3006", "不能对本人账号执行该操作")

    async with uow.transaction():
        user = await users.get_for_update(user_id)
        if user is None:
            raise BizError("USER-4001", "用户不存在")
        if user.status == target:
            raise BizError("USER-5015", "账号已处于目标状态")

        if target == "DISABLED":
            if await rbac.is_last_admin(user_id):        # 保护：不允许禁用最后一个管理员
                raise BizError("USER-3004", "不允许禁用系统中最后一个管理员账号")
            await users.update(user_id, status="DISABLED")
            revoked = await refresh_tokens.revoke_by_user(
                user_id, reason="ADMIN_DISABLED")
            await audit.append(action="USER_DISABLED", user_id=user_id,
                               operator_id=admin_id, operator_type="ADMIN",
                               before_value={"status": user.status},
                               after_value={"status": "DISABLED", "reason": reason})
        else:
            await users.update(user_id, status="ACTIVE",
                               failed_login_count=0, locked_until=None)
            revoked = 0
            await audit.append(action="USER_ENABLED", user_id=user_id,
                               operator_id=admin_id, operator_type="ADMIN",
                               before_value={"status": user.status},
                               after_value={"status": "ACTIVE"})

    if target == "DISABLED":
        # 访问令牌立即失效（依赖 §1.5 网关契约）；TTL 取刷新令牌周期，覆盖所有存量访问令牌
        await redis.set(f"user:auth:revoke_after:{user_id}", iso_utc(now()),
                        ex=settings.JWT_REFRESH_TTL_SECONDS)
    await cache.delete(f"user:profile:{user_id}")
    return revoked
```

### 6.10 账号注销与数据删除（NFR-CP-004）

```
DELETE /users/me（需 CLOSE_ACCOUNT 验证码或 ticket）
   ├─ 存在未完成订单（PAYMENT_PENDING 等）──▶ 409 USER-5014（由 order-service 内部接口判定）
   └─ 通过
        1. status=DELETED, deleted_at=now()
        2. email → deleted+{id}@deleted.invalid；phone → +00000000000（释放原账号）
        3. 地址全部软删除
        4. 吊销全部刷新令牌 + revoke_after
        5. 审计 ACCOUNT_CLOSE_REQUESTED
   ── 30 天冷静期（可恢复）──▶ account_purge 任务
        6. 昵称 → 「已注销用户」；头像/bio/birthday/gender 清空
        7. oauth_bindings 物理删除
        8. user_credentials 物理删除（密码哈希不再保留）
        9. 审计 ACCOUNT_ANONYMIZED
   ── 保留 ──▶ user_id、user_audit_logs、地址行的 deleted 标记（供历史订单追溯）
```

```python
async def close_account(user_id: int, ticket: str, reason: str, ctx) -> None:
    # 1. 一次性凭证校验
    if not await redis.getdel(f"user:verify:ticket:{ticket}"):
        raise BizError("USER-1011", "验证已过期，请重新验证")

    user = await users.get(user_id)
    if user is None or user.status == "DELETED":
        return                                            # 幂等
    if not (user.is_email_verified or user.is_phone_verified):
        raise BizError("USER-3005", "请先完成邮箱或手机验证")

    # 2. 交易侧前置校验（同步内部调用 order-service）
    #    超时或订单服务不可用时不阻断注销？—— 阻断。避免用户带着未完成订单离场导致履约纠纷
    unfinished = await order_client.has_unfinished_orders(user_id)   # /internal/v1/orders/has-unfinished
    if unfinished is None:
        raise BizError("USER-7003", "服务繁忙，请稍后重试")
    if unfinished:
        raise BizError("USER-5014", "存在未完成的订单，请处理后再注销")

    anon_email = f"deleted+{user_id}@deleted.invalid"
    async with uow.transaction():
        await users.update(user_id, status="DELETED", deleted_at=now(),
                           email=anon_email if user.email else None,
                           phone="+00000000000" if user.phone else None,
                           failed_login_count=0, locked_until=None)
        await addresses.soft_delete_all(user_id)
        await refresh_tokens.revoke_by_user(user_id, reason="ACCOUNT_CLOSED")
        await audit.append(action="ACCOUNT_CLOSE_REQUESTED", user_id=user_id,
                           operator_type="USER", client_ip=ctx.ip,
                           after_value={"reason": reason})

    await redis.set(f"user:auth:revoke_after:{user_id}", iso_utc(now()),
                    ex=settings.JWT_REFRESH_TTL_SECONDS)
    await cache.delete(f"user:profile:{user_id}", f"user:address:{user_id}:default")
    logger.info("account closed", extra={"user_id": str(user_id)})
```

> **取舍说明**：注销后 `user_id` **不可回收**。订单、支付流水按《电子商务法》等要求需留存交易记录，指向已删除用户是正常的商业实践；若强行删除用户行会导致订单侧出现悬空 ID。因此采用"**匿名化保留**"而非"物理删除"，并在注销页面向用户明确告知（"交易记录将依法留存，个人信息将被匿名化处理"）。
>
> **接口依赖提示**：本流程需要 order-service 提供 `GET /internal/v1/orders/has-unfinished?user_id=`（订单服务详细设计中定义）。该接口未就绪时，`close_account` 的实现应降级为"跳过订单校验直接注销"，并在文档与配置中显式标记（`ACCOUNT_CLOSE_REQUIRE_ORDER_CHECK=false`）。

## 7. 缓存设计

Redis 为平台共享实例（架构文档 §1.2），Key 规范遵循通用约定 §9.1：`{服务名}:{实体}:{标识}`。

| Key | 类型 | TTL | 写入时机 | 失效 / 删除时机 | 用途 |
|---|---|---|---|---|---|
| `user:profile:{user_id}` | String(JSON) | 15 分钟 | 读未命中时回填 | 资料修改、账号禁用/注销后主动删除 | 个人资料读取加速（不含联系方式） |
| `user:address:{user_id}:default` | String(address_id) | 15 分钟 | 读未命中时回填 | 地址增删改、设默认、注销后主动删除 | 结算页默认地址 |
| `user:role:perms:{role_code}` | String(JSON) | 10 分钟 | 权限校验未命中时回填 | 角色权限变更（R6）、角色删除（R5）后主动删除 | 后台权限判定（§10.2） |
| `user:auth:jwt:blacklist:{jti}` | String | 访问令牌剩余有效期（≤1800s） | 登出、单会话吊销 | 自然过期 | 访问令牌吊销（网关读取，§1.5 契约） |
| `user:auth:revoke_after:{user_id}` | String(ISO8601) | 14 天（= 刷新令牌周期） | 全端下线、改密、重置密码、禁用、注销 | 自然过期 | 用户级令牌批量吊销（网关读取，§1.5 契约） |
| `user:verify:code:{scene}:{account}` | String(JSON) | 与验证码有效期一致（600s / 300s） | 验证码生成后 | 校验成功、验证码失效 | 校验时快速定位当前有效码 |
| `user:verify:send_lock:{scene}:{account}` | String | 60 秒 | 投递成功后 | 自然过期 | 发送频率限制（60 秒 1 次） |
| `user:verify:quota:{scene}:{account}:{yyyymmdd}` | Counter | 至次日 00:00 | 每次发送 | 自然过期 | 账号维度每日上限（10 次） |
| `user:verify:quota:ip:{ip}:{yyyymmdd}` | Counter | 至次日 00:00 | 每次发送 | 自然过期 | IP 维度每日上限（30 次） |
| `user:verify:ticket:{ticket}` | String(JSON) | 5 分钟 | 验证码校验通过（须票据的场景） | 消费即删（`GETDEL`） | 一次性验证凭证 |
| `user:login:fail:ip:{ip}` | Counter | 15 分钟 | 登录失败 | 自然过期 | IP 维度登录爆破限流（30 次） |
| `user:login:fail:user:{user_id}` | Counter | 15 分钟 | 登录失败 | 登录成功时删除 | 账号维度失败计数冗余（权威值在 `users.failed_login_count`） |
| `user:oauth:state:{state}` | String(JSON) | 10 分钟 | A10 发起授权 | 回调时 `GETDEL` | OAuth CSRF 防护与 PKCE verifier 暂存 |
| `user:idem:{key}` | String(JSON) | 24 小时 | 写接口成功后 | 自然过期 | 注册/新增地址幂等 |

设计说明：

- **不使用缓存加速登录**：登录涉及密码校验与安全计数，直接读主库，保证锁定状态与状态变更**强一致**（通用约定 §9.3：强一致场景不走缓存）。
- **`user:profile` 不含邮箱与手机号**：联系方式属高敏字段，仅从主库读取，避免"缓存中残留明文联系方式"扩大泄露面。
- **缓存穿透防护**：查询不存在的用户（如已注销的 `user_id`）时，缓存空值 `"__NULL__"` 并设 60 秒 TTL（通用约定 §9.3）。
- **缓存击穿防护**：`user:role:perms:{role_code}` 是热点 Key（后台每次写操作都读），采用逻辑过期 + 互斥重建（`SET NX` 抢锁），重建期间返回旧值。
- **一致性策略**：写操作统一"先写库、再删缓存"（通用约定 §9.3），删除失败时记录 WARN 日志并由 TTL 兜底收敛。
- **Redis 不可用降级**：令牌黑名单与限流依赖 Redis，不可用时按**失败关闭（fail-close）**处理——鉴权类接口返回 `502 COMMON-7001`，避免在失去吊销能力时放行已登出的令牌。

## 8. 定时任务

所有任务通过分布式锁（Redis `SET NX EX`）保证多实例下仅一个实例执行；执行间隔与锁 TTL 相等并留 20% 余量，任务异常退出后锁自然释放。

| 任务名 | 周期 | 职责 | 幂等要求 |
|---|---|---|---|
| `outbox_dispatch` | 每 5 秒 | 扫描 `outbox_events` 中 `PENDING` 且 `next_retry_at <= now()` 的记录，投递至 RabbitMQ，成功后置 `SENT` | **必须幂等**：`SELECT ... FOR UPDATE SKIP LOCKED` 取行，投递前后状态机严格单向（PENDING→SENT）；投递成功但更新失败时，重投靠 `event_id` 由消费方去重 |
| `refresh_token_cleanup` | 每日 03:10 | 删除 `expires_at < now() - 30 天` 的刷新令牌行（保留 30 天用于重放取证） | 幂等：按时间条件批量 `DELETE ... LIMIT 5000`，可重复执行 |
| `verification_code_cleanup` | 每小时 05 分 | 删除 `expires_at < now() - 24 小时` 的验证码记录；将仍为 `PENDING` 的过期记录置 `EXPIRED` | 幂等：条件更新 + 条件删除 |
| `account_purge` | 每日 04:00 | 对 `status='DELETED'` 且 `deleted_at < now() - 30 天` 的账号执行匿名化：昵称置「已注销用户」，清空头像/简介/生日/性别，物理删除 `oauth_bindings` 与 `user_credentials`，写 `ACCOUNT_ANONYMIZED` 审计 | **必须幂等**：以"昵称是否已是匿名值 + 关联表是否存在行"为判定条件，重复执行结果一致 |
| `audit_log_archive` | 每月 1 日 02:00 | 将 `created_at < now() - 180 天` 的审计日志导出至对象存储冷备后删除本地行 | 幂等：导出文件按 `yyyyMM` 命名，存在则跳过导出直接删除；删除按时间条件 |
| `outbox_cleanup` | 每日 03:30 | 删除 `status='SENT'` 且 `sent_at < now() - 30 天` 的 outbox 行 | 幂等：条件删除 |
| `stale_lock_cleanup` | 每 10 分钟 | 清理 `status='LOCKED'` 且 `locked_until < now() - 1 天` 的残留锁定（`LOCKED` 由人工风控标记，需到期复核） | 幂等：条件更新 |

任务与监控：

| 任务 | 关键监控指标 | 告警阈值 |
|---|---|---|
| `outbox_dispatch` | 待投递行数、投递失败率 | `PENDING` 且超 5 分钟未投递 > 100 行 |
| `refresh_token_cleanup` | 单次删除行数、执行耗时 | 耗时 > 60s |
| `account_purge` | 单次处理账号数、异常数 | 异常数 > 0 |
| `audit_log_archive` | 归档文件大小、失败次数 | 失败即告警 |

## 10. 安全与权限

### 10.1 鉴权要求

| 接口分组 | 网关 | 服务端 |
|---|---|---|
| `/api/v1/auth/register`、`/login`、`/token/refresh`、`/password/*`、`/verification-codes`（部分场景）、`/oauth/*` | 白名单放行，不校验令牌；按 IP 限流 | 按场景自行校验（如 `BIND_*` 场景要求 `X-User-Id` 非空） |
| `/api/v1/users/me/**` | 校验访问令牌，注入 `X-User-Id`、`X-User-Roles` | **以 `X-User-Id` 为唯一身份来源**，忽略查询参数/请求体中的任何 user_id |
| `/api/v1/admin/**` | 校验访问令牌，注入身份头 | 校验 `X-User-Roles` 含 `ADMIN`，或按 §10.2 校验权限码 |
| `/internal/v1/**` | **不暴露**（网关路由不匹配） | 校验 `X-Internal-Token` 与配置一致，失败返回 `COMMON-2002` |

服务端从请求头读取身份的代码约定（统一在 `app/core/deps.py` 提供依赖）：

```python
async def current_user(x_user_id: str = Header(None)) -> int:
    if not x_user_id:
        raise BizError("COMMON-2001", "缺少访问令牌")
    return int(x_user_id)          # 仅信任网关注入的头


async def require_roles(roles_header: str = Header(None, alias="X-User-Roles")):
    return set(filter(None, (roles_header or "").split(",")))
```

**信任边界**：服务只信任网关剥离并重新注入的头（通用约定 §4.3）。用户服务自身不做 JWT 解析——即使收到形似令牌的 `Authorization` 头也不解析，避免出现"两处验签逻辑不一致"的安全缺口。

### 10.2 RBAC 模型与网关 `X-User-Roles` 的配合

```
用户 ──N:M──▶ 角色 ──N:M──▶ 权限点
 user_roles      roles      role_permissions      permissions

JWT 载荷只携带 roles（角色码数组）
   │
网关验签后注入  X-User-Roles: BUYER,ORDER_OPERATOR
   │
业务服务按角色做粗粒度拦截（如 order-service 要求 ORDER_OPERATOR）
   │
用户服务对后台写操作额外做权限点校验（更细粒度，见下）
```

分层原因：**角色是稳定的、权限点可能频繁调整**。把权限点放进 JWT 会导致每次权限调整都需要用户重新登录；把角色放进 JWT 则使绝大多数业务拦截无需回查用户服务。因此：

- **JWT 与 `X-User-Roles` 只承载角色码**（`BUYER`、`ADMIN`、`ORDER_OPERATOR` ...）；
- **用户服务的后台接口用权限点做细粒度判定**（如 `PUT /admin/roles/{id}/permissions` 要求 `system:role:manage`），因为它是权限模型的所有者，可低成本读取 `user:role:perms:{role_code}` 缓存；
- **其他业务服务不做权限点判定**：它们只用角色码。若后续需要跨服务权限点校验，应在各服务本地维护"角色 → 业务动作"的静态映射，而不是把权限点塞进令牌。

```python
async def require_permission(code: str, user_id: int,
                             roles: set[str]) -> None:
    """后台接口细粒度校验：角色 → 权限，读缓存"""
    if "ADMIN" in roles:                     # 管理员直通，避免缓存未命中时误拒
        return
    perms: set[str] = set()
    for role in roles:
        cached = await cache.get(f"user:role:perms:{role}")
        if cached is None:
            rows = await rbac.list_permission_codes(role)     # 回源并回填（10 分钟）
            await cache.set(f"user:role:perms:{role}", rows, ex=600)
            cached = rows
        perms |= set(cached)
    if code not in perms:
        raise BizError("COMMON-3001", "无权限执行该操作")
```

接口与权限点映射：

| 接口 | 要求角色 | 要求权限点 |
|---|---|---|
| `GET /api/v1/admin/users` | 含任一后台角色 | `system:user:view` |
| `GET /api/v1/admin/users/{id}` | 含任一后台角色 | `system:user:view` |
| `PUT /api/v1/admin/users/{id}/roles` | `ADMIN` | `system:user:manage` |
| `PUT /api/v1/admin/users/{id}/status` | `ADMIN` | `system:user:manage` |
| `GET /api/v1/admin/roles`、`/admin/permissions` | `ADMIN` | `system:role:manage` |
| `POST/PUT/DELETE /api/v1/admin/roles/**` | `ADMIN` | `system:role:manage` |
| `GET /api/v1/admin/users`（含财务/客服等只读角色） | — | 由对应权限点决定可见字段 |

### 10.3 数据归属校验

| 场景 | 规则 |
|---|---|
| 个人资料读写 | `user_id` 一律取 `X-User-Id`；请求体/查询参数中的任何 user_id 被忽略 |
| 地址所有操作（D1~D6） | 查询条件强制 `WHERE user_id = :x_user_id`；目标地址不属于本人时返回 `USER-3001`（403），**不区分"不存在"与"无权"**，避免 ID 探测 |
| 内部接口（I1/I2/I3） | 不受 `X-User-Id` 约束（服务间调用），但必须携带 `X-Internal-Token`；I2 返回明文联系方式并**逐次审计**；I3 显式校验路径 `user_id` 与地址归属一致 |
| 管理后台 | 按角色 + 权限点校验；管理员可跨用户读取，但读取行为全部落审计日志 |
| 注销账号 | 严格控制：即使令牌有效，也要求 `CLOSE_ACCOUNT` 场景验证码（防止"盗用令牌即可注销"） |

### 10.4 脱敏

| 数据 | 存储 | 对外响应 | 日志 | 审计 |
|---|---|---|---|---|
| 密码 | argon2id 哈希 | 永不返回 | **完全不记录** | 不记录 |
| 访问令牌明文 | 不存储（JWT） | 仅签发时返回一次 | **完全不记录**（含 `Authorization` 头） | 不记录 |
| 刷新令牌明文 | 仅存 `sha256` 哈希 | 仅签发时返回一次 | **完全不记录** | 不记录 |
| 验证码明文 | 仅存 `sha256` 哈希 | 仅由通知服务投递 | **完全不记录** | 不记录 |
| 用户本人邮箱 | 明文 | 完整返回（本人视角） | 掩码 `a***e@example.com` | 掩码 |
| 用户本人手机号 | 明文 | 完整返回（本人视角） | 掩码 `+8613****8000` | 掩码 |
| 他人邮箱/手机号 | 明文 | 掩码（管理后台列表） | 掩码 | 掩码 |
| 收货地址 | 明文 | 完整返回（本人视角） | **只记录 address_id，不记录明细** | 只记录 address_id 与字段名 |
| OAuth 第三方令牌 | **不存储** | 不返回 | 不记录 | 不记录 |
| `X-Internal-Token` | 环境变量 | 不返回 | **完全不记录** | 不记录 |

实现方式：统一在 `app/core/logging.py` 注册日志过滤器，对 `email`/`phone`/`password`/`token`/`authorization`/`code` 等键名做键级掩码（而非字符串正则替换），确保结构化日志中不会因字段嵌套而漏掩。

### 10.5 其他安全措施

| 风险 | 措施 |
|---|---|
| 账号枚举 | 注册、找回密码、发送验证码接口对"账号不存在"返回与成功一致的响应；登录统一返回 `USER-2001`；响应时间做恒定化处理 |
| 暴力破解 | 账号维度 5 次锁定 15 分钟；IP 维度 15 分钟 30 次限流；验证码 5 次尝试上限 |
| 撞库 | 登录失败不区分"账号不存在/密码错误"；对同一 IP 的高频失败独立限流并触发告警 |
| 令牌泄漏 | 访问令牌仅 30 分钟；刷新令牌轮换 + 重放检测；异常时全端下线 |
| CSRF | 接口全部使用 `Authorization` 头承载令牌（非 Cookie），天然免疫 CSRF；OAuth 流程使用 `state` + PKCE |
| XSS | 昵称、简介等自由文本落库前 HTML 转义，输出时按纯文本渲染，不做 HTML 白名单 |
| 注入 | 全部通过 SQLAlchemy 参数化查询；`keyword` 模糊搜索使用 `ILIKE` 且对 `%`/`_` 转义 |
| 越权 | 见 §10.3；`X-User-Id` 为唯一身份来源 |
| 敏感配置 | 数据库口令、JWT 私钥、OAuth Client Secret、`INTERNAL_TOKEN`、验证码 pepper 全部经环境变量/密钥管理注入（NFR-SE-007） |
| 审计 | 后台所有写操作记录操作人、时间、对象、变更前后值（脱敏后），只追加不修改（NFR-SE-009） |
| 依赖第三方 | OAuth 回调仅信任 `HTTPS` 且校验 `iss`/`aud`/`nonce`（Google ID Token 场景）；不做第三方资料的可信来源 |

| 项 | 方法 | 通过标准 |

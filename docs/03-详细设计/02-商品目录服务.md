## 1. 服务概览

### 1.1 职责

商品目录服务是平台的**商品与库存权威数据源**（System of Record），承担四类职责：

| 职责域 | 内容 |
|---|---|
| 商品域 | 分类树、SPU、SKU、图片、属性规格、标签的维护与查询 |
| 库存域 | 库存权威数据的维护、预占/确认/释放全生命周期、库存流水追溯、低库存预警 |
| 评价域 | 商品评价与回复的写入、查询 |
| 查询域 | 买家端商品列表、搜索、详情；为购物车与订单服务提供 SKU 快照与库存原子操作 |

### 1.2 边界（明确不做的事）

| 不做 | 归属 | 说明 |
|---|---|---|
| 订单状态、订单明细快照 | 订单服务 | 本服务只按 `order_no` 操作库存，不感知订单状态机 |
| 购物车数据 | 购物车服务 | 本服务只提供校验所需的库存与 SKU 快照 |
| 支付、金额结算 | 支付服务 | 本服务只存储 SKU 售价 |
| 用户资料 | 用户服务 | 评价表只存 `user_id`，展示昵称由前端向用户服务获取或使用下单时的匿名标识 |
| 商品销量统计 | 订单服务（本期） | 列表页按销量排序时取订单服务提供的只读统计接口；本期未接入前该排序项对该服务不可用时保持稳定退化（见 6.6） |
| 商品图片存储 | 对象存储 | 本服务只存 URL |
| 推荐、广告 | 范围外 | — |

**关键边界约定**：商品详情展示的库存由本服务实时提供；购物车与订单服务**不复制**库存字段。

### 1.3 上下游依赖

| 方向 | 对象 | 方式 | 场景 |
|---|---|---|---|
| 上游 | API 网关（Traefik） | HTTP | 全部对外接口经网关，注入 `X-User-Id`/`X-User-Roles` |
| 下游调用 | order-service | HTTP `/internal/v1/orders/can-review` | 发表评价前校验"该用户对该 SKU 有已完成订单" |
| 下游调用 | order-service | HTTP `/internal/v1/orders/stats/sales` | 列表页按销量排序（本期可选，见 6.6） |
| 被调用 | order-service | HTTP `/internal/v1/inventory/*` | 库存预占、释放、确认扣减（下单关键路径） |
| 被调用 | cart-service | HTTP `/internal/v1/skus/batch` | 加购与结算前校验 SKU 有效性与库存 |
| 被调用 | cart-service / 前端 SSR | HTTP `/api/v1/products/*` | 商品列表与详情 |
| 消息 | RabbitMQ | 发布 `stock.low` | 低库存预警 |
| 消息 | RabbitMQ | 订阅 `order.paid`、`order.cancelled` | 正式扣减库存、释放预占 |
| 中间件 | PostgreSQL 16、Redis 7 | — | 权威数据 + 缓存/预占计数 |

**不依赖**：user-service（分类/商品/库存不涉及用户归属）、payment-service。本服务在 user-service 或 payment-service 故障时仍可完整工作，保证买家浏览链路可用。

### 1.5 领域模型

```
Category (树, ≤3 级)
   │ 1:N
   ▼
 SPU ──1:N──▶ SKU ──1:1──▶ Inventory ──1:N──▶ InventoryTransaction (流水, 只增不改)
  │             │                 │
  │             │                 └──1:N──▶ StockReservation (预占记录, 按 order_no+sku_id 唯一)
  │             ├──1:N──▶ ProductImage (SPU 级图集 / SKU 级主图)
  │             ├──1:N──▶ ProductAttribute (SPU 级属性 + SKU 级规格值)
  │             └──1:N──▶ Review (评价, 关联 order_no) ──1:N──▶ ReviewReply
  ├──N:M──▶ Tag (product_tag_rel)
  └──1:N──▶ ProductChangeLog (变更留痕)
                    Inventory ──1:N──▶ LowStockAlert (预警记录)
```

### 2.2 categories（分类）

存储方案：**邻接表（`parent_id`）+ 物化路径（`path`）+ `depth`**，见 6.1 的取舍说明。

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | PK | — | 雪花 ID |
| `parent_id` | BIGINT | NULL | `NULL` | 父分类 ID，根节点为 `NULL`；不建物理外键 |
| `name` | VARCHAR(64) | NOT NULL | — | 分类名称 |
| `slug` | VARCHAR(64) | UNIQUE NOT NULL | — | URL 友好标识，小写 kebab-case |
| `path` | VARCHAR(255) | NOT NULL | — | 物化路径，形如 `/1/12/135/`（含自身 ID，前后带 `/`） |
| `depth` | SMALLINT | NOT NULL, CHECK 1..3 | — | 层级，从 1 起，最多 3 级 |
| `level_name` | VARCHAR(16) | NOT NULL | — | 层级中文名：`LEVEL_1`/`LEVEL_2`/`LEVEL_3`，仅用于后台展示 |
| `sort_order` | INTEGER | NOT NULL | `0` | 同级排序，升序；相同值按 `id` 兜底 |
| `icon_url` | VARCHAR(512) | NULL | `NULL` | 分类图标 |
| `is_enabled` | BOOLEAN | NOT NULL | `TRUE` | 停用后买家端不可见，其子树一并隐藏 |
| `product_count` | INTEGER | NOT NULL | `0` | 该分类下（**不含子分类**）在架 SPU 数，异步刷新 |
| `deleted_at` | TIMESTAMPTZ | NULL | `NULL` | 软删除；仅允许删除无子分类且无在架商品的分类 |
| `created_at` | TIMESTAMPTZ | NOT NULL | `now()` | — |
| `updated_at` | TIMESTAMPTZ | NOT NULL | `now()` | — |

**索引**

| 索引名 | 类型 | 字段 | 用途 |
|---|---|---|---|
| `pk_categories` | PK | `id` | — |
| `uk_categories_slug` | UNIQUE | `slug` | 唯一性 |
| `idx_categories_parent_id_sort_order` | BTREE | `parent_id, sort_order` | 同级子节点查询与排序 |
| `idx_categories_path` | BTREE | `path varchar_pattern_ops` | 子树前缀查询 `path LIKE '/1/12/%'` |
| `idx_categories_enabled_depth` | BTREE | `is_enabled, depth`（部分索引，`WHERE deleted_at IS NULL`） | 买家端分类树一次性加载 |

### 2.6 product_attributes（商品属性 / SKU 规格值）

单表承载两级属性，用 `scope` 区分，避免 SPU 属性与 SKU 规格值分散在两套结构里。

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | PK | — | 雪花 ID |
| `spu_id` | BIGINT | NOT NULL | — | 所属 SPU |
| `sku_id` | BIGINT | NULL | `NULL` | `scope='SKU'` 时必填；`scope='SPU'` 时为空 |
| `scope` | VARCHAR(16) | NOT NULL, CHECK | — | `SPU`（描述性属性，如"材质:纯棉"）\| `SKU`（规格维度，如"颜色:黑色"） |
| `attr_name` | VARCHAR(64) | NOT NULL | — | 属性名/规格维度名 |
| `attr_value` | VARCHAR(255) | NOT NULL | — | 属性值/规格值 |
| `sort_order` | INTEGER | NOT NULL | `0` | 详情页展示顺序；同 `attr_name` 的 `sort_order` 决定规格维度顺序 |
| `created_at` | TIMESTAMPTZ | NOT NULL | `now()` | — |
| `updated_at` | TIMESTAMPTZ | NOT NULL | `now()` | — |

**约束与索引**

| 索引名 | 类型 | 字段 | 用途 |
|---|---|---|---|
| `pk_product_attributes` | PK | `id` | — |
| `uk_product_attributes_sku_attr` | UNIQUE（部分，`WHERE scope='SKU'`） | `sku_id, attr_name` | 同一 SKU 的同一维度只有一个值 |
| `uk_product_attributes_spu_attr` | UNIQUE（部分，`WHERE scope='SPU'`） | `spu_id, attr_name` | 同一 SPU 的描述性属性不重复 |
| `idx_product_attributes_spu_id_scope` | BTREE | `spu_id, scope, sort_order` | 详情页属性区 |
| `ck_product_attributes_scope_sku` | CHECK | `(scope='SKU' AND sku_id IS NOT NULL) OR (scope='SPU' AND sku_id IS NULL)` | 结构一致性 |

### 2.7 inventories（库存，SKU 维度）

**本表是全库并发最高的表，只做单行条件更新，不存放派生计算的历史值。**

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | PK | — | 雪花 ID |
| `sku_id` | BIGINT | UNIQUE NOT NULL | — | SKU，一 SKU 一行 |
| `stock` | INTEGER | NOT NULL, CHECK ≥ 0 | `0` | **总库存**（物理可售总量口径，调整唯一入口） |
| `reserved` | INTEGER | NOT NULL, CHECK ≥ 0 | `0` | **预占量**，下单后支付前占用 |
| `sold` | INTEGER | NOT NULL, CHECK ≥ 0 | `0` | **实扣量**，支付成功后累计；仅统计口径，不参与可售计算 |
| `low_stock_threshold` | INTEGER | NOT NULL | 由配置 `LOW_STOCK_DEFAULT_THRESHOLD` 初始化 | 低库存阈值，可按 SKU 覆盖 |
| `version` | INTEGER | NOT NULL | `0` | 乐观锁版本号，通用约定第 8.1 节要求 |
| `last_reconciled_at` | TIMESTAMPTZ | NULL | `NULL` | 最近一次 Redis/DB 校准时间，用于校准任务挑行 |
| `created_at` | TIMESTAMPTZ | NOT NULL | `now()` | — |
| `updated_at` | TIMESTAMPTZ | NOT NULL | `now()` | — |

**核心约束（必须存在）**

```sql
CONSTRAINT ck_inventories_reserved_not_exceed_stock CHECK (reserved <= stock)
```
该约束是**防超卖的最后一道防线**。所有预占都通过条件更新 `WHERE stock - reserved >= n` 完成，即使应用层出现逻辑缺陷，违反该 CHECK 的写入会被数据库拒绝（`23514`），应用层捕获后转为 `CAT-5003`。

**索引**

| `pk_inventories` | PK | `id` | — |
| `uk_inventories_sku_id` | UNIQUE | `sku_id` | 一 SKU 一行；条件更新的定位索引 |
| `idx_inventories_low_stock` | BTREE（部分，`WHERE stock - reserved <= 0`） | `sku_id` | 零库存排查 |
| `idx_inventories_last_reconciled_at` | BTREE | `last_reconciled_at NULLS FIRST` | 校准任务扫描"最久未校准"的行 |

```sql

  ON inventory_transactions (sku_id, ref_no, txn_type)

```

-- 触发器：维护 spus.search_vector
--   中文分词说明：PostgreSQL 无内置中文分词器。本服务将搜索向量按字符级切分
--   （to_tsvector('simple', ...) 用空格切分，中文文本落库为连续串时被整体视为一个词元，
--    故在应用层写入 title 等字段时保留原始文本，由 search_vector 生成函数按 CJK 字符逐个插入空格），
--   保证"无线耳机"可切分为 无/线/耳/机 四个词元，与查询侧同规则匹配（详见 6.4）。
CREATE OR REPLACE FUNCTION catalog_build_spu_search_vector(
    p_title VARCHAR, p_subtitle VARCHAR, p_brand VARCHAR, p_description TEXT
) RETURNS TSVECTOR AS $$
DECLARE
    v_text TEXT;
BEGIN
    -- 将 CJK 字符之间插入空格，实现字符级切分；ASCII 词按原样保留
    v_text := regexp_replace(
                  COALESCE(p_title,'') || ' ' || COALESCE(p_subtitle,'') || ' ' ||
                  COALESCE(p_brand,'') || ' ' || COALESCE(p_description,''),
                  '([一-龥])', ' \1 ', 'g');
    RETURN setweight(to_tsvector('simple', COALESCE(p_title,'')), 'A')
        || setweight(to_tsvector('simple', COALESCE(p_subtitle,'')), 'B')
        || setweight(to_tsvector('simple', COALESCE(p_brand,'')),    'B')
        || setweight(to_tsvector('simple', v_text),                  'D');
END;
$$ LANGUAGE plpgsql IMMUTABLE;

CREATE OR REPLACE FUNCTION trg_spus_search_vector() RETURNS trigger AS $$
BEGIN
    NEW.search_vector := catalog_build_spu_search_vector(
        NEW.title, NEW.subtitle, NEW.brand, NEW.description);
    NEW.updated_at := now();
    RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_spus_before_write
    BEFORE INSERT OR UPDATE OF title, subtitle, brand, description ON spus
    FOR EACH ROW EXECUTE FUNCTION trg_spus_search_vector();

| `tag_code` | string | 否 | — | 标签编码，如 `NEW`；可重复传多个，取交集 |
| `brand` | string | 否 | — | 品牌精确匹配 |
| `min_price_cents` | integer | 否 | — | 价格下限（分），与 SPU `max_price_cents` 比较 |
| `max_price_cents` | integer | 否 | — | 价格上限（分），与 SPU `min_price_cents` 比较 |
| `sort` | enum | 否 | `NEWEST` | `NEWEST`\|`PRICE_ASC`\|`PRICE_DESC`\|`SALES_DESC` |
| `page` | integer | 否 | `1` | 偏移分页；`sort != NEWEST` 时使用 |
| `page_size` | integer | 否 | `20` | 最大 100 |
| `cursor` | string | 否 | — | 游标分页；`sort = NEWEST` 时使用，与 `page` 互斥 |
| `limit` | integer | 否 | `20` | 游标分页每页条数，最大 100 |

**分页选择规则（重要）**

| 排序 | 分页方式 | 原因 |
|---|---|---|
| `NEWEST`（默认，首页/无限滚动） | **游标分页**（`cursor` + `limit`） | 商品列表是买家端最高频的深翻页场景。游标基于 `(published_at, id)` 稳定排序键，翻页不随新上架商品插入而漂移，且 `WHERE (published_at, id) < (?, ?)` 可走索引直达，深翻页无 `OFFSET` 线性代价 |
| `PRICE_ASC` / `PRICE_DESC` / `SALES_DESC` | **偏移分页**（`page` + `page_size`） | 价格排序下用户几乎不会翻过第 3 页，深翻页风险低；排序键非唯一（价格相同），游标需附加 `id` 且 `SALES_DESC` 的 `sales_count` 会频繁变动导致游标失效，收益不抵复杂度 |

> 同一接口按 `sort` 二选一分页方式，符合通用约定 2.3 的"偏移与游标二选一，不得混用"——此处"混用"指同一请求内混用，服务端通过 `sort` 参数强制唯一路径，收到 `cursor` 与 `page` 同时存在时返回 `CAT-1005`。

**B-10 / B-11 上下架**

| 接口 | 前置校验 | 副作用 |
|---|---|---|

## 4. 内部接口设计

内部接口是本服务的**重点**。订单服务在下单关键路径上同步调用，接口的幂等性、并发安全与失败语义直接决定平台是否超卖。

### 4.1 通用约定

| 项 | 约定 |
|---|---|
| 路径前缀 | `/internal/v1/*`，网关不暴露；仅接受内网来源 |
| 认证 | 必须携带 `X-Internal-Token`，校验失败返回 `COMMON-2002` |
| 请求头 | 必须携带 `X-Request-Id`、`X-Trace-Id` |
| 超时 | 调用方连接 1s / 读取 3s（通用约定 11.1）；本服务 P99 目标 < 150ms |
| 重试 | 调用方对写操作**默认不重试**；本服务所有写接口自身强幂等，允许调用方在超时后**带同一业务键重试**（见 4.4 超时语义） |
| 错误语义 | 区分"业务失败"（4xx，调用方不应重试，需走补偿）与"系统失败"（5xx/超时，调用方可重试） |

### 4.3 I-02 库存预占

`POST /internal/v1/inventory/reserve`，调用方 order-service（下单核心路径）。

**请求**

```json
{
  "order_no": "SO20260910000001",
  "expires_at": "2026-09-10T09:00:00.000Z",
  "items": [
    { "sku_id": "2002", "quantity": 2 },
    { "sku_id": "2003", "quantity": 1 }
  ]
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `order_no` | string | 是 | 订单号，作为幂等业务键，长度 ≤ 32 |
| `items` | array | 是 | 1~50 项；同一 `sku_id` 不得重复（重复返回 `CAT-1007`） |
| `items[].sku_id` | string | 是 | — |
| `items[].quantity` | integer | 是 | 1~999 |
| `expires_at` | string(ISO8601) | 否 | 预占过期时间；缺省取 `now() + ORDER_RESERVE_TTL_SECONDS`；**上限** `now() + 2h`，超出则截断，防止调用方传入过长 TTL 阻塞库存 |

**响应**（`200`，全部成功）

```json
{
  "code": "OK",
  "message": "success",
  "data": {
    "order_no": "SO20260910000001",
    "expires_at": "2026-09-10T09:00:00.000Z",
    "items": [
      { "sku_id": "2002", "quantity": 2, "reserved_after": 14, "available_after": 286 },
      { "sku_id": "2003", "quantity": 1, "reserved_after": 1,  "available_after": 9 }
    ],
    "idempotent_replay": false
  },
  "trace_id": "...",
  "timestamp": "..."
}
```

**失败响应（整单失败，全有或全无）**——HTTP `409`：

```json
{
  "code": "CAT-5002",
  "message": "库存不足，无法下单",
  "details": [
    { "field": "items[0].sku_id", "reason": "可售库存不足，当前可售 1 件，需 2 件", "sku_id": "2002" }
  ],
  "data": null,
  "trace_id": "...",
  "timestamp": "..."
}
```

**幂等语义**（核心）

| 情况 | 行为 |
|---|---|
| Redis 幂等键 `catalog:reserve:idem:{order_no}` 命中 | 直接返回首次结果（缓存的响应体），`idempotent_replay=true` |
| Redis 未命中，但 `stock_reservations` 已有该 `(order_no, sku_id)` 且状态 `RESERVED` | 视为重复调用，返回当前预占结果，`idempotent_replay=true`；不重复累加 |
| `(order_no, sku_id)` 已 `CONFIRMED` 或 `RELEASED`/`EXPIRED` | 返回 `CAT-5011`（订单状态与预占状态不一致），调用方需告警人工介入 |
| 全新请求 | 正常执行三步：Redis 前置扣减 → DB 条件更新 → 写预占记录与流水 |

**原子性**：多 SKU 的预占在**单个数据库事务**内完成，任一 SKU 条件更新影响行数为 0 则整个事务回滚（`ROLLBACK`），Redis 侧已扣减的计数由事务外补偿回补。为避免长事务，SKU 按 `sku_id` 升序处理，减少多订单交叉时的死锁概率。

**错误码**

| 错误码 | HTTP | 场景 | 调用方应否重试 |
|---|---|---|---|
| `CAT-1001` | 400 | `items` 为空/超 50/数量越界 | 否 |
| `CAT-1007` | 400 | 同一请求内 `sku_id` 重复 | 否 |
| `CAT-4006` | 404 | 部分 SKU 不存在 | 否 |
| `CAT-5002` | 409 | 库存不足（含 `details` 明细） | 否，走整单失败 |
| `CAT-5003` | 409 | 数据库 CHECK 约束被触发（`reserved > stock`），防超卖兜底生效 | 否，告警 |
| `CAT-5011` | 409 | 订单已有终态预占记录，状态不一致 | 否，告警人工 |
| `CAT-6003` | 429 | 预占并发冲突，条件更新失败可重试一次（内部自动重试 1 次） | 是，最多 1 次 |
| `COMMON-8001` | 500 | 数据库故障 | 是（带同一 `order_no`） |

### 4.4 I-03 释放预占

`POST /internal/v1/inventory/release`，调用方 order-service（用户取消、下单补偿、支付超时关闭）。

**请求**

```json
{
  "order_no": "SO20260910000001",
  "reason": "USER_CANCELLED",
  "items": [{ "sku_id": "2002", "quantity": 2 }, { "sku_id": "2003", "quantity": 1 }]
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `order_no` | string | 是 | 幂等业务键 |
| `reason` | string | 是 | `USER_CANCELLED`\|`ORDER_TIMEOUT`\|`ORDER_ROLLBACK`\|`MANUAL`；写入预占记录 `release_reason` 与流水 `reason` |
| `items` | array | 否 | 省略时释放该订单**全部** `RESERVED` 记录（推荐用法，避免调用方漏传） |

**响应**（`200`）

```json
{
  "code": "OK",
  "message": "success",
  "data": {
    "order_no": "SO20260910000001",
    "released": [
      { "sku_id": "2002", "quantity": 2, "status": "RELEASED", "reserved_after": 12, "available_after": 288 },
      { "sku_id": "2003", "quantity": 1, "status": "RELEASED", "reserved_after": 0,  "available_after": 10 }
    ],
    "skipped": [],
    "idempotent_replay": false
  }
}
```

**幂等与状态迁移**：只处理 `status='RESERVED'` 的记录，条件更新 `WHERE status='RESERVED'` 并检查影响行数。

| 当前状态 | 行为 |
|---|---|
| `RESERVED` | 正常释放，`status='RELEASED'`，`reserved -= quantity`，写 `RELEASE` 流水 |
| `RELEASED` / `EXPIRED` | 幂等跳过，计入 `skipped`，返回 200 |
| `CONFIRMED` | **拒绝释放**，返回 `CAT-5012`（已支付扣减的库存不可释放，调用方须走退款流程） |

**错误码**：`CAT-5012`（预占已确认扣减）、`CAT-4007`（订单无任何预占记录；返回 200 且 `released=[]`、`skipped=[]`，视为幂等成功，避免订单服务重试风暴）、`COMMON-2002`。

### 4.5 I-04 / I-05 确认扣减

**I-04 `POST /internal/v1/inventory/confirm`**（单 SKU，用于人工补偿与单条重放）

```json
{ "order_no": "SO20260910000001", "sku_id": "2002", "quantity": 2, "event_id": "9f1c2b3a-..." }
```

**I-05 `POST /internal/v1/inventory/batch-confirm`**（批量，`order.paid` 消费失败后由订单服务或运维补偿调用）

```json
{
  "order_no": "SO20260910000001",
  "event_id": "9f1c2b3a-4d5e-6f70-8192-a3b4c5d6e7f8",
  "paid_at": "2026-09-10T08:35:00.000Z",
  "items": [{ "sku_id": "2002", "quantity": 2 }, { "sku_id": "2003", "quantity": 1 }]
}
```

**响应**（`200`）

```json
{
  "code": "OK",
  "message": "success",
  "data": {
    "order_no": "SO20260910000001",
    "confirmed": [
      { "sku_id": "2002", "quantity": 2, "status": "CONFIRMED", "reserved_after": 12, "sold_after": 42, "available_after": 288 }
    ],
    "skipped": [],
    "idempotent_replay": false
  },
  "trace_id": "...",
  "timestamp": "..."
}
```

**确认扣减的语义（必须精确）**：确认扣减**只做预占量的转移，不再校验可售量**。

```
reserved -= quantity      -- 预占转为已售
sold     += quantity
-- stock 不变！因为下预占时 stock 未减少，可售量已通过 reserved 扣减
-- 可售量 available = stock - reserved，确认后 reserved 减少 → available 回升，但 sold 增加 → 净效果是"已卖出"
```

这是三段式设计的关键：**预占时只增加 `reserved`（不动 `stock`），确认时只做 `reserved → sold` 的转移**。因此确认阶段**不可能**因库存不足而失败，只会因预占记录状态不对而失败。这也意味着 `order.paid` 的消费**天然不会失败于库存**，极大提高了支付后链路的一次成功率。

**幂等**：条件更新 `UPDATE stock_reservations SET status='CONFIRMED', confirmed_at=now() WHERE order_no=? AND sku_id=? AND status='RESERVED'`，影响行数为 0 且记录已是 `CONFIRMED` → 幂等返回成功；记录不存在 → `CAT-4007`（返回 200 + `skipped` 明细，事件消费场景视为已处理）；记录为 `RELEASED`/`EXPIRED` → **`CAT-5013`（严重不一致：支付成功但库存已释放）**，调用方须告警并走 FR-ORD-014 的异常订单人工处理流程。

**错误码**

| 错误码 | HTTP | 场景 |
|---|---|---|
| `CAT-5013` | 409 | 支付成功但预占已释放/过期——**超卖风险**，最高优先级告警 |
| `CAT-4008` | 404 | `order_no` 无任何预占记录且非幂等重放（事件早于预占到或调用错误） |
| `CAT-1001` | 400 | `items` 与预占记录数量不一致（`quantity` 与预占量不符） |
| `COMMON-2002` | — | 内部令牌无效 |

**补充说明**：`I-04`/`I-05` 与事件消费共用同一段业务逻辑（`services/inventory.confirm_reservation`），避免"接口能扣、事件能扣"两套实现产生分歧。事件路径额外做 `event_id` 幂等（Redis 已处理集合）。

## 5. 事件设计

### 5.1 发布事件

#### 5.1.1 `stock.low`

| 项 | 内容 |
|---|---|
| `event_type` | `stock.low` |
| `event_version` | `1.0` |
| `producer` | `catalog-service` |
| 消费方 | notification-service |
| Routing Key | `stock.low` |
| 消费队列 | `notification.stock.low` |
| 死信 | `notification.stock.low.dlq` |
| 触发时机 | 库存变动（预占/确认/调整/入库）后，`stock - reserved <= low_stock_threshold` 且该 SKU 无 `OPEN` 预警记录时 |

**Payload**

```json
{
  "sku_id": "2002",
  "spu_id": "2001",
  "spu_title": "降噪无线蓝牙耳机 Pro",
  "sku_code": "ACME-EARPRO-BLK",
  "spec_name": "颜色:黑色",
  "available": 3,
  "threshold": 20,
  "trigger": "RESERVE",
  "occurred_at": "2026-09-10T08:30:00.123Z"
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `sku_id` | string | 是 | 告警 SKU |
| `spu_id` | string | 是 | 所属 SPU |
| `spu_title` | string | 是 | 商品标题快照，便于通知文案直接使用（通用约定 10.3 的 payload 核心字段） |
| `sku_code` | string | 是 | SKU 编码，便于运营定位 |
| `spec_name` | string | 是 | 规格摘要（通用约定 10.3 要求字段名 `spec_name`） |
| `available` | integer | 是 | 触发时可售量 |
| `threshold` | integer | 是 | 触发阈值 |
| `trigger` | enum | 是 | `RESERVE`\|`CONFIRM`\|`ADJUST`\|`INBOUND`，说明由哪种变动触发 |
| `occurred_at` | string | 是 | 触发时间 |

> 事件信封（`event_id`/`event_type`/`event_version`/`occurred_at`/`producer`/`trace_id`）由 outbox 投递层统一封装，此处只描述 `payload`。`payload` 中的 `occurred_at` 与信封字段重复，保留是为了让通知服务在不解析信封时也能拿到时间；消费端以信封为准。

**发布流程**：库存变更事务内 `INSERT INTO outbox_events (status='PENDING')`，由 `publish-outbox-events` 任务（第 8 章）扫描投递。**不在业务事务内直接发 MQ**，避免"业务回滚但事件已发"。

### 5.2 订阅事件

#### 5.2.1 `order.paid`（正式扣减库存）

| 项 | 内容 |
|---|---|
| `event_type` | `order.paid` |
| `producer` | order-service |
| 本服务队列 | `catalog.order.paid` |
| 分区 | 按 `order_no` 路由，同订单事件有序 |
| 幂等 | `event_id` Redis 已处理集合（TTL 7 天）+ `stock_reservations` 状态条件更新 |
| 重试 | 指数退避 `1s/5s/30s/2m/10m`，5 次后进 DLQ 并告警 |

**消费逻辑**

```
1. payload 取 order_no、items[].sku_id、items[].quantity
2. 幂等检查：Redis SISMEMBER / SETNX catalog:event:order.paid:{event_id}
   ├─ 已处理 → 记录 debug 日志，ACK 退出
3. 对每个 item 执行 confirm_reservation(order_no, sku_id, quantity, event_id)
   ├─ 预占记录 status='RESERVED' → 条件更新为 CONFIRMED，reserved -= q，sold += q，写 CONFIRM 流水
   ├─ 已是 'CONFIRMED' → 幂等跳过
   ├─ 是 'RELEASED'/'EXPIRED' → 【严重】支付成功但库存已释放
   │      → 写 product_change_logs? 否。写低优先级"异常订单"告警日志 + 发送运维告警
   │      → 返回失败，让事件重试；重试耗尽进 DLQ，由运维按 FR-ORD-014 处理
   └─ 记录不存在 → 返回失败重试（可能是 reserve 的请求还未提交，属罕见乱序）
4. 全部成功 → 标记 event_id 已处理 → ACK
5. 任一失败 → 不 ACK，按退避重试
```

**注意事项**
- **不做整单事务回滚**：若 5 个 SKU 中 3 个成功、2 个失败，重试时成功的 3 个走幂等跳过，最终收敛。这是"幂等 + 重试"优于"分布式事务"的体现。
- 消费成功后触发低库存检查（`stock.low` 可能在此时才触发）。
- 消费耗时记录到 `catalog_event_consume_duration_seconds` 指标。

#### 5.2.2 `order.cancelled`（释放预占库存）

| 项 | 内容 |
|---|---|
| `event_type` | `order.cancelled` |
| `producer` | order-service |
| 本服务队列 | `catalog.order.cancelled` |
| 触发来源 | 用户取消、超时未支付关闭、支付失败关闭 |

**消费逻辑**

```
1. 幂等检查（同 5.2.1）
2. 取 order_no；items 可能为空（订单服务未提供明细）
   ├─ items 非空 → release_reservation(order_no, sku_id, quantity, reason=payload.reason)
   └─ items 为空 → 查询 stock_reservations WHERE order_no=? AND status='RESERVED' 全部释放
3. 每条：条件更新 status='RESERVED' → 'RELEASED'，reserved -= quantity，写 RELEASE 流水
4. 已是 'RELEASED'/'EXPIRED' → 幂等跳过
5. 是 'CONFIRMED'【严重】→ 订单已支付却取消（应走退款不与库存释放混淆）
       → 告警，不释放，进 DLQ
6. 全部处理完 → ACK
```

**`reason` 映射**：payload `reason` 为 `TIMEOUT` 时，预占记录 `status` 置 `EXPIRED`（区分"系统超时"与"用户主动取消"），否则置 `RELEASED`；两者都回补 `reserved` 并写 `RELEASE` 流水（`ref_type='ORDER'`，超时场景额外记录 `release_reason`）。

#### 5.2.3 订阅汇总

| event_type | 队列 | 幂等键 | 处理摘要 | 失败处理 |
|---|---|---|---|---|
| `order.paid` | `catalog.order.paid` | `event_id` + 预占状态 | 预占转实扣（`reserved -= n; sold += n`） | 退避重试 → DLQ → 告警 → 人工按 FR-ORD-014 处理 |
| `order.cancelled` | `catalog.order.cancelled` | `event_id` + 预占状态 | 回补预占（`reserved -= n`） | 同上 |

**未订阅的事件**：`order.created`、`order.shipped`、`payment.*` 与 `user.registered` 本服务不消费。库存预占由**同步调用** `I-02` 完成而非订阅 `order.created`，原因：下单需即时知道预占结果以决定整单成败（概要架构 4.3 的通信选择原则）。

### 5.3 超时释放的职责边界

预占超时释放由**本服务的定时任务**（`release-expired-reservations`，扫描 `expires_at`）与**订单服务的超时关闭任务**双路径覆盖：

| 路径 | 触发者 | 说明 |
|---|---|---|
| 主路径 | order-service 超时关闭订单 → 发 `order.cancelled` → 本服务释放 | 有订单上下文，`reason` 准确 |
| 兜底路径 | 本服务 `release-expired-reservations` 任务 | 订单服务故障或事件丢失时，保证库存最终释放 |

兜底路径执行时**同时**投递一条 `catalog.reservation.expired` 内部告警日志（**不**跨服务发事件，避免新增未登记的事件类型），并在响应中暴露计数供监控告警；是否需通知订单服务由运维判断（订单服务的订单若仍挂待支付，会自行超时关闭）。

## 6. 核心业务流程

### 6.1 分类树：存储方案取舍

| 方案 | 优点 | 缺点 | 本服务取舍 |
|---|---|---|---|
| 仅 `parent_id` + 递归 CTE | 结构最简，无冗余 | 每次查树需递归，无法一次查询取子树全部商品；深层递归代价随层级增长 | ✗ |
| 仅物化路径 | 子树查询一次 `LIKE` 完成 | 移动节点需重写整棵子树路径 | ✗ |
| **邻接表 + 物化路径（采用）** | `parent_id` 保证写入正确性与简单的同级查询；`path` 让"某分类及全部子分类的商品"一次查询完成（列表页核心查询） | 分类移动/改名需级联更新子树 `path` | ✓ 分类变更频率极低（运营手工操作），读远多于写，值得为读优化 |
| 闭包表 | 查询最灵活 | 表体积 O(n²)，3 级树收益不明显，写入维护复杂 | ✗ |

**路径维护规则**

```
创建：path = parent.path + self.id + '/'      depth = parent.depth + 1
根节点：path = '/' + self.id + '/',  depth = 1
移动：更新自身 parent_id/depth/path，并 var 子树
      UPDATE categories
         SET path = <new_parent_path> || substring(path from length(<old_parent_path>)+1),
             depth = depth + <delta>,
             updated_at = now()
       WHERE path LIKE <old_parent_path> || '%'
```

**深度限制**：`depth <= 3` 由 CHECK 约束强制（FR-CAT-001"建议不超过 3 级"落地为硬约束，避免前端分类导航无限嵌套）。创建第 4 级时返回 `CAT-5014`。

**列表页按分类查询**（含子分类）：

```sql
-- 应用层先取目标分类的 path（命中 uk/idx），拼前缀
SELECT ... FROM spus s
WHERE s.status = 'ON_SALE' AND s.deleted_at IS NULL
  AND s.category_id IN (
      SELECT c.id FROM categories c
      WHERE c.path LIKE '/1001/1012/%' AND c.is_enabled AND c.deleted_at IS NULL
  )
```

**缓存**：整棵树序列化后存 `catalog:category:tree`（TTL 30 分钟，变更主动删除）。树规模在百级以内，单 Key 存储开销可忽略。

### 6.2 库存三段式

#### 6.2.1 预占（下单）

```
def reserve(order_no, items, expires_at=None):
    # 步骤 0：入参校验与去重
    assert 1 <= len(items) <= 50
    assert len({i.sku_id for i in items}) == len(items)   # 否则 CAT-1007
    expires_at = min(expires_at or now() + cfg.ORDER_RESERVE_TTL,
                     now() + timedelta(hours=2))

    # 步骤 1：Redis 幂等键抢占（第一道幂等）
    cache_key = f"catalog:reserve:idem:{order_no}"
    if not redis.set(cache_key, "IN_PROGRESS", nx=True, ex=cfg.RESERVE_IDEM_TTL):
        cached = redis.get(f"catalog:reserve:result:{order_no}")
        if cached: return replay(cached)            # 已完成，返回首次结果
        raise RetryableError(CAT-6003)              # 另一请求正在执行，调用方重试

    try:
        # 步骤 2：Redis 前置扣减（降低 DB 压力，非权威）
        #   对每个 SKU 用 Lua 原子判断并扣减，不足则整体回补
        ok = redis.eval(RESERVE_LUA, keys=[inv_key(i.sku_id) for i in items],
                                     args=[i.quantity for i in items])
        if not ok:
            raise BusinessError(CAT-5002, details=...)   # 快速失败，不触达 DB

        # 步骤 3：数据库条件更新（权威，防超卖）
        with db.transaction():
            reservations = []
            for item in sorted(items, key=sku_id):        # 升序，降低死锁概率
                # 3.1 条件更新：可售量足够才更新，检查影响行数
                rows = db.execute("""
                    UPDATE inventories
                       SET reserved = reserved + :q,
                           version  = version + 1,
                           updated_at = now()
                     WHERE sku_id = :sku
                       AND stock - reserved >= :q
                """, {"q": item.quantity, "sku": item.sku_id})
                if rows == 0:
                    raise BusinessError(CAT-5002, sku_id=item.sku_id)   # 触发事务回滚

                # 3.2 写预占记录（唯一约束为幂等兜底）
                try:
                    db.insert_stock_reservation(
                        order_no=order_no, sku_id=item.sku_id,
                        quantity=item.quantity, status="RESERVED",
                        expires_at=expires_at)
                except UniqueViolation:
                    # 订单服务重试但 Redis 幂等键已过期：转为幂等返回
                    existing = db.get_reservation(order_no, item.sku_id)
                    if existing.status != "RESERVED":
                        raise BusinessError(CAT-5011)     # 状态不一致，告警
                    rollback_and_return_replay(existing)

                # 3.3 写库存流水（带快照值）
                inv = db.get_inventory(item.sku_id)
                db.insert_txn(sku_id=item.sku_id, txn_type="RESERVE",
                              quantity=item.quantity,
                              stock_after=inv.stock, reserved_after=inv.reserved,
                              available_after=inv.stock - inv.reserved, sold_after=inv.sold,
                              ref_type="ORDER", ref_no=order_no)
                reservations.append(...)

            # 步骤 4：低库存检查（同事务写 outbox，保证不漏发）
            for item in items:
                maybe_raise_low_stock_alert(item.sku_id, trigger="RESERVE")

        # 步骤 5：写幂等结果缓存，供重放
        redis.set(f"catalog:reserve:result:{order_no}", serialize(result), ex=cfg.RESERVE_IDEM_TTL)
        return result

    except Exception:
        # 步骤 6：失败补偿——回补 Redis 计数（DB 已随事务回滚）
        redis.eval(RELEASE_LUA, keys=..., args=...)
        redis.delete(cache_key)          # 允许调用方带同一 order_no 重试
        raise
```

**为什么 Redis 与 DB 要配合（关键取舍）**

| 层 | 角色 | 作用 | 失效后果 |
|---|---|---|---|
| Redis | 前置拦截 | 用 Lua 原子判断 + 扣减，在**高并发秒杀**场景挡住绝大多数注定失败的请求，避免全部压到 DB 行锁上造成排队 | 拦截失效 → 请求全打到 DB，DB 条件更新仍能正确防超卖（只是慢） |
| PostgreSQL 条件更新 | **权威** | `WHERE stock - reserved >= n` + 检查影响行数，在行锁下保证原子性 | 失效 → 超卖（因此还有 CHECK 约束兜底） |

**因此：Redis 计数与 DB 不一致不会导致超卖，只会导致"误判"（拦截了本可成功的请求，或放行了注定失败的请求，后者被 DB 拒绝）。** 这是本方案最重要的性质，也是可接受 Redis 计数为"近似值"的前提。

**不一致的来源与校准**

| 来源 | 说明 | 校准方式 |
|---|---|---|
| 事务回滚后补偿失败 | DB 回滚了但 Redis 回补失败（网络抖动） | 校准任务 |
| 实例崩溃 | Redis 已扣减、事务未提交 | 校准任务 |
| 人工调整库存 | B-19 直接改 DB，未同步 Redis | 写库后**主动删除** `catalog:inventory:{sku_id}`，下次读取时按 DB 重建 |
| 预占超时释放 | 定时任务改 DB | 同上，删除 Key |

```
def reconcile_inventory(sku_id):
    """以 DB 为权威重建 Redis 计数。可在校准任务中批量执行，也可在读到异常时单点触发。"""
    inv = db.query_one("SELECT stock, reserved FROM inventories WHERE sku_id = :s", {"s": sku_id})
    available = inv.stock - inv.reserved
    # 用 SET 而非 INCRBY，纠正漂移
    redis.set(f"catalog:inventory:{sku_id}", available, ex=cfg.INVENTORY_COUNTER_TTL)
    db.execute("UPDATE inventories SET last_reconciled_at = now() WHERE sku_id = :s", {"s": sku_id})
    metrics.incr("catalog_inventory_reconcile_total")
    return available
```

**Redis 计数的使用边界（重要约束）**

| 场景 | 是否用 Redis 计数 |
|---|---|
| 商品详情页 `available` 展示 | **否**，直接读 DB（强一致，通用约定 9.3） |
| `batch-query` / `skus/batch` 的 `available` | **否**，读 DB |
| 预占接口的前置拦截 | **是**，仅用于"要不要真的去尝试 DB"，不作为最终答案 |
| 后台库存查询 | **否**，读 DB |

即：**Redis 只出现在写路径的入口，绝不出现在读路径的出口。** 这样即使 Redis 完全清空，系统行为也完全正确，只是预占接口的 DB 压力上升。此约束使 Redis 成为纯粹的**性能优化层**而非正确性依赖。

#### 6.2.2 确认扣减（支付成功后）

```
def confirm_reservation(order_no, sku_id, quantity, event_id=None):
    with db.transaction():
        # 条件更新：只允许从 RESERVED 迁移到 CONFIRMED
        rows = db.execute("""
            UPDATE stock_reservations
               SET status = 'CONFIRMED',
                   confirmed_at = now(),
                   updated_at = now()
             WHERE order_no = :o AND sku_id = :s
               AND status = 'RESERVED'
        """, {"o": order_no, "s": sku_id})

        if rows == 0:
            res = db.get_reservation(order_no, sku_id)
            if res is None:
                raise BusinessError(CAT-4008)                       # 预占记录缺失
            if res.status == "CONFIRMED":
                return replay_ok()                                  # 幂等
            raise BusinessError(CAT-5013)                           # 已释放却要扣减 → 超卖风险，告警

        # 只做 reserved → sold 的转移，stock 不变
        db.execute("""
            UPDATE inventories
               SET reserved = reserved - :q,
                   sold     = sold + :q,
                   version  = version + 1,
                   updated_at = now()
             WHERE sku_id = :s
        """, {"q": quantity, "s": sku_id})

        inv = db.get_inventory(sku_id)
        db.insert_txn(sku_id=sku_id, txn_type="CONFIRM", quantity=+quantity,
                      stock_after=inv.stock, reserved_after=inv.reserved,
                      available_after=inv.stock - inv.reserved, sold_after=inv.sold,
                      ref_type="ORDER", ref_no=order_no, event_id=event_id)

        maybe_raise_low_stock_alert(sku_id, trigger="CONFIRM")     # available 回升，一般不触发，但保留统一入口
    redis.delete(f"catalog:inventory:{sku_id}")                    # 使 Redis 计数下次按 DB 重建
```

#### 6.2.3 释放预占

```
def release_reservation(order_no, sku_id, quantity, reason, expired=False):
    with db.transaction():
        target = "EXPIRED" if expired else "RELEASED"
        rows = db.execute("""
            UPDATE stock_reservations
               SET status = :t, released_at = now(), release_reason = :r, updated_at = now()
             WHERE order_no = :o AND sku_id = :s AND status = 'RESERVED'
        """, {"t": target, "r": reason, "o": order_no, "s": sku_id})

        if rows == 0:
            res = db.get_reservation(order_no, sku_id)
            if res is None:                  return skip()      # 幂等：无记录视为已释放
            if res.status in ("RELEASED","EXPIRED"): return skip()
            raise BusinessError(CAT-5012)                        # CONFIRMED 不可释放

        db.execute("""
            UPDATE inventories
               SET reserved = reserved - :q, version = version + 1, updated_at = now()
             WHERE sku_id = :s
        """, {"q": quantity, "s": sku_id})

        inv = db.get_inventory(sku_id)
        db.insert_txn(sku_id=sku_id, txn_type="RELEASE", quantity=-quantity,
                      stock_after=inv.stock, reserved_after=inv.reserved,
                      available_after=inv.stock - inv.reserved, sold_after=inv.sold,
                      reason=reason, ref_type="ORDER", ref_no=order_no)
    redis.delete(f"catalog:inventory:{sku_id}")
```

#### 6.4.2 关键词搜索方案

**本期方案：PostgreSQL 全文检索（`tsvector` + GIN）+ `pg_trgm` 兜底**

**中文分词问题的处理（关键）**：PostgreSQL 的 `to_tsvector('simple', ...)` 按空格切词，中文连续文本会被视为**一个词元**，导致"无线耳机"只能整体匹配。本服务的处理：在 `catalog_build_spu_search_vector` 中把 CJK 字符逐个用空格隔开，使"无线耳机"变为 `无 线 耳 机` 四个词元，索引与查询侧**同规则**处理，从而实现字符级匹配。

```
查询侧归一化：
  q_norm = regexp_replace(trim(keyword), '([一-龥])', ' \1 ', 'g')
  查询：... WHERE search_vector @@ to_tsquery('simple', <以 & 连接的词元串>)
```

**检索主查询**

```sql
WITH q AS (SELECT to_tsquery('simple', :ts_query) AS tsq)
SELECT s.id, s.title,
       ts_rank_cd(s.search_vector, q.tsq, 32) AS relevance,
       ts_headline('simple', s.title, q.tsq, 'StartSel=<em>,StopSel=</em>,MaxFragments=1') AS title_hl
  FROM spus s, q
 WHERE s.status = 'ON_SALE' AND s.deleted_at IS NULL
   AND s.search_vector @@ q.tsq
   AND (:cat_path IS NULL OR s.category_id IN (<子树>))
   AND (:min_price IS NULL OR s.max_price_cents >= :min_price)
   AND (:max_price IS NULL OR s.min_price_cents <= :max_price)
 ORDER BY relevance DESC, s.sales_count DESC, s.id DESC
 LIMIT :page_size OFFSET :offset;
```

权重设计（见 DDL 触发器）：标题 `A`、副标题/品牌 `B`、描述 `D`，`ts_rank_cd` 的权重数组 `{0.1, 0.2, 0.4, 1.0}` 让标题命中显著加权。

**兜底路径**：当主查询返回结果数 < 3（短词、错字、品牌名），追加一次 `pg_trgm` 相似度查询（走 `idx_spus_title_trgm`）：

```sql
SELECT id, title, similarity(title, :keyword) AS sim
  FROM spus
 WHERE status='ON_SALE' AND deleted_at IS NULL
   AND title % :keyword                    -- pg_trgm 相似度阈值（默认 0.3）
 ORDER BY sim DESC LIMIT 10;
```
与主查询结果按 `id` 去重合并，兜底结果排在主结果之后。

**为什么本期不引入 Elasticsearch**

| 维度 | PostgreSQL FTS + trgm | Elasticsearch |
|---|---|---|
| 中文分词质量 | 字符级匹配，无词边界、无同义词/拼音/繁简 | IK 分词、同义词、拼音、纠错，质量显著更好 |
| 相关度排序 | `ts_rank_cd`，较粗糙 | BM25 + 多路召回 + 自定义打分 |
| 运维成本 | 零额外组件，随库备份 | 独立集群、索引同步、双写一致性、监控告警 |
| 数据一致性 | 同库同事务，天然一致 | 需异步同步（Canal/双写/定时），存在延迟与漏数据 |
| 规模 | 十万级 SPU 检索延迟 < 50ms，完全够用 | 百万级以上才有明显优势 |

**取舍结论**：本期 SPU 量级在十万以内，搜索质量要求为"关键词能搜到"，**运维复杂度与一致性风险远大于分词质量收益**，故采用 PostgreSQL。同时**预留接入点**：

- 搜索逻辑集中在 `services/search.py` 单一模块，接口层只调用 `SearchService.search(...)`，返回统一 DTO；
- 商品写路径（创建/编辑/上下架）在事务提交后调用 `SearchService.index(product_id)`，本期实现为"空操作"（`tsvector` 由触发器维护）；
- 接入 ES 时改为向 ES 写索引，读路径切换为 `EsSearchService`；`search_vector` 列与触发器保留作为降级路径（ES 不可用时回退 PG 检索，符合通用约定 11.3 的降级精神）。
- 引入 ES 的**触发条件**写入本文档作为决策记录：① 单表 SPU 超 100 万；② 需要拼音/同义词/纠错；③ 搜索结果 P95 > 300ms。

**结果集上限**：`SEARCH_MAX_RESULT`（默认 10000）。搜索结果排序不稳定（相关性分数相同者顺序不定），**不适合游标分页**，故统一用偏移分页；当 `offset + page_size > SEARCH_MAX_RESULT` 时返回 `CAT-5007` 提示缩小范围。

### 6.5 上下架对已生成订单无影响

```
上架/下架只改 spus.status 与缓存，不触碰任何订单数据，也不校验库存。

已生成订单不受影响的保证链：
  1. 下单瞬间，order-service 通过 I-06 取 SKU 快照（标题/规格/单价/图片）写入订单明细；
  2. 订单明细为不可变快照（需求 7.3"快照不可变"）；
  3. 支付成功后的 order.paid → confirm_reservation 只校验 stock_reservations.status，
     完全不读 spus.status / skus.status；
  4. 因此即使是"下单后商品立即下架"，该订单仍可正常支付、扣减库存、发货。

反例（必须避免的实现）：若 confirm 阶段校验 "SKU 是否仍在架"，则下架商品会导致
已支付订单扣减失败 → 进入 FR-ORD-014 异常队列。本设计明确禁止该校验。
```

**下架的真实影响面**：买家端列表/搜索不再返回；详情页返回 `CAT-4002`；购物车中标记失效（FR-CART-006）；不可加购。**不影响的**：已生成的订单与已预占的库存。

### 6.6 销量排序

列表页 `sort=SALES_DESC` 使用 `spus.sales_count`（冗余字段）。本期该字段的更新有两种可选数据源，实现时按可用性择一：

| 方案 | 说明 | 本期取舍 |
|---|---|---|
| 订单服务提供只读统计接口 `GET /internal/v1/orders/stats/sales?spu_ids=...` | 权威、实时 | **需要 order-service 提供该接口**；若未提供，用方案 B |
| 本服务在 `order.paid` 消费成功后 `sales_count += quantity` | 本服务内闭环，秒级最终一致 | **采用**，实现简单且不新增跨服务依赖 |

采用方案 B 时，`sales_count` 的语义为"经本服务确认扣减的件数"，与订单服务的口径在极端情况下（`order.paid` 重试中）可能有短暂差异，可接受（销量仅用于排序展示，不参与任何计算）。**一致性补偿**：`reconcile-sales-count` 任务（第 8 章）在接入订单服务统计接口后按周校准；未接入前该任务空转。

### 6.7 价格聚合字段与更新时机

SPU 的价格由其 SKU 聚合而来。列表页与搜索页必须按价格排序/过滤，若每次实时聚合，需要 JOIN + `MIN/MAX` 分组，代价高且无法走索引。

**冗余字段**：`spus.min_price_cents` / `spus.max_price_cents`。

**聚合口径**：仅统计 `skus.status='ENABLED' AND skus.deleted_at IS NULL` 的 SKU。若无启用 SKU，两字段为 `NULL`（该商品在买家端不可见，因为列表查询要求至少一个 `ENABLED` SKU）。

**更新时机**（**必须覆盖全部路径，任一遗漏都会导致价格显示错误**）

| 触发 | 处理 |
|---|---|
| `B-13` 新增 SKU | 事务内重算该 SPU 的聚合 |
| `B-14` 编辑 SKU（价格或 `status`） | 事务内重算 |
| `B-15` 删除/停用 SKU | 事务内重算 |
| 商品软删除后恢复 | 重算 |
| 定时兜底 | `recalc-spu-price-range` 任务每日按 `(sku_id, price, status)` 抽样校验，发现漂移则修正并告警 |

```
-- 事务内统一调用（放在 SKU 变更之后）
UPDATE spus s
   SET min_price_cents = agg.min_p,
       max_price_cents = agg.max_p,
       updated_at = now()
  FROM (SELECT MIN(price_cents) AS min_p, MAX(price_cents) AS max_p
          FROM skus
         WHERE spu_id = :spu AND status = 'ENABLED' AND deleted_at IS NULL) agg,
       (SELECT :spu AS spu) _
 WHERE s.id = :spu;
```
因 `agg` 恒返回一行（无匹配时 `MIN/MAX` 为 `NULL`），该语句在无启用 SKU 时会把两字段置 `NULL`，行为正确。

**与缓存的关系**：价格聚合变更后删除 `catalog:product:{spu_id}`；列表结果缓存（若启用）按分类维度整体失效。

### 6.8 低库存预警

```
def maybe_raise_low_stock_alert(sku_id, trigger):
    """在库存变更的同一事务内调用，保证"库存变了但预警丢了"不会发生"""
    inv = db.get_inventory(sku_id)                 # 已加行锁
    available = inv.stock - inv.reserved
    open_alert = db.query_one("SELECT id FROM low_stock_alerts WHERE sku_id=:s AND status='OPEN'", {"s": sku_id})

    if available <= inv.low_stock_threshold:
        if open_alert is None:
            # 新预警：插入记录 + 同事务写 outbox（发布 stock.low）
            alert_id = db.insert_low_stock_alert(
                sku_id=sku_id, spu_id=..., available=available,
                threshold=inv.low_stock_threshold, status="OPEN")
            db.insert_outbox_event(
                event_type="stock.low", event_version="1.0",
                payload={"sku_id": str(sku_id), "spu_id": str(spu_id),
                         "spu_title": spu.title, "sku_code": sku.sku_code,
                         "spec_name": sku.spec_text, "available": available,
                         "threshold": inv.low_stock_threshold,
                         "trigger": trigger, "occurred_at": iso_now()})
        else:
            db.execute("UPDATE low_stock_alerts SET available=:a, updated_at=now() WHERE id=:i",
                       {"a": available, "i": open_alert.id})    # 更新当前值，不重复发事件
    else:
        if open_alert is not None:
            db.execute("UPDATE low_stock_alerts SET status='RESOLVED', resolved_at=now(), updated_at=now() WHERE id=:i",
                       {"i": open_alert.id})
```

**告警抑制**：`uk_low_stock_alerts_sku_open` 保证同一 SKU 同时只有一条 `OPEN`。阻止了"每次库存变动都发 `stock.low`"导致的告警风暴——这是本设计中最容易踩的坑：若不做抑制，一个热销 SKU 在清仓阶段会发出上千条 `stock.low` 事件。

### 6.9 评价与订单的交互（跨服务校验）

评价的前置条件"该用户对该 SKU 有已完成订单"，而订单数据在订单服务。本服务**不复制**订单数据。

| 方案 | 评价 |
|---|---|
| 本服务建订单完成记录的只读副本（订阅 `order.completed` 事件） | 需新增未登记的事件类型（通用约定 10.3 的标准事件目录中无"订单完成"事件，只有 `order.shipped`）；副本会滞后，用户在确认收货后立刻评价可能失败 |
| **同步调用订单服务内部接口（采用）** | 实时、权威；订单服务不可用时拒绝评价（可接受：评价非关键路径，用户稍后重试） |

**调用契约（需 order-service 提供）**

```
GET /internal/v1/orders/can-review?user_id=1024&order_no=SO20260908000042&sku_id=2002
Header: X-Internal-Token, X-Request-Id, X-Trace-Id

200 {
  "code": "OK",
  "data": {
    "can_review": true,
    "order_status": "COMPLETED",
    "received_at": "2026-09-07T04:00:00.000Z"
  }
}
```

**本服务侧处理**

```
def create_review(user_id, product_id, payload):
    # ① 本地校验：商品、SKU 归属
    spu = get_spu(product_id)
    if spu is None or spu.status != "ON_SALE": raise BusinessError(CAT-4003)
    sku = get_sku(payload.sku_id)
    if sku is None or sku.spu_id != spu.id: raise BusinessError(CAT-4004)

    # ② 本地查重（快速失败，避免无谓的跨服务调用）
    if db.exists_review(order_no=payload.order_no, sku_id=sku.id, user_id=user_id):
        raise BusinessError(CAT-5008)

    # ③ 跨服务校验（不可跳过）
    try:
        resp = order_client.can_review(user_id=user_id,
                                       order_no=payload.order_no,
                                       sku_id=sku.id,
                                       timeout=(1.0, 3.0))
    except (Timeout, ConnectionError):
        raise BusinessError(CAT-7010)          # 502，拒绝评价，不降级放行
    if resp.code != "OK":            raise BusinessError(CAT-7001)
    if not resp.data.can_review:     raise BusinessError(CAT-5009)

    # ④ 落库（唯一约束兜底并发重复提交）
    try:
        review = db.insert_review(spu_id=spu.id, sku_id=sku.id, user_id=user_id,
                                  order_no=payload.order_no, rating=payload.rating,
                                  content=payload.content, images=payload.images,
                                  is_anonymous=payload.is_anonymous,
                                  status="PUBLISHED",
                                  sku_spec_text=sku.spec_text)   # 规格快照
    except UniqueViolation:
        raise BusinessError(CAT-5008)

    # ⑤ 异步重算商品评分与评价数
    enqueue_recalc_rating(spu.id)
    return review
```

**熔断与降级**：对 order-service 的调用走 `clients` 层统一封装，连续失败 5 次熔断 30s（通用约定 11.2）。熔断期间评价接口快速返回 `CAT-7010`（502）。**不做降级放行**——放行会产生未购买的评价，是内容可信度问题，比"暂时不能评价"危害大得多。

**越权防护**：`user_id` 取自 `X-User-Id`，请求体不接受 `user_id`。校验时把 `user_id` 传给订单服务，由订单服务确认该订单属于该用户——即"这个用户对这笔订单有权评价"。若订单不属于该用户，订单服务返回 `can_review=false` 或 404，本服务统一返回 `CAT-5010`（而非 `COMMON-3001`，避免泄露订单是否存在；此处 UX 优先于安全惯例，因为订单号本身不是密钥，而 `CAT-5010` 与 `CAT-5009` 对攻击者的信息量相同）。

### 6.10 商品编辑留痕

```
def update_product(spu_id, patch, operator, version, remark):
    with db.transaction():
        spu = db.get_spu_for_update(spu_id)          # SELECT ... FOR UPDATE
        if spu.version != version:
            raise BusinessError(CAT-6001)            # 乐观锁冲突

        changed = {}
        before, after = {}, {}
        for field, new_val in patch.items():
            old_val = getattr(spu, field)
            if old_val != new_val:
                changed[field] = True
                before[field] = old_val
                after[field] = new_val

        if not changed:
            return spu                                # 无变更，不写留痕（避免噪声）

        # 在架商品禁止改分类（会破坏分类计数与列表缓存一致性）
        if spu.status == "ON_SALE" and "category_id" in changed:
            raise BusinessError(CAT-5005)

        db.apply_patch(spu_id, patch, version_bump=True)
        db.insert_change_log(
            entity_type="SPU", entity_id=spu_id, spu_id=spu_id, action="UPDATE",
            changed_fields=list(changed.keys()),
            before_value=before, after_value=after,
            operator_id=operator.id, operator_name=operator.name,
            remark=remark, client_ip=operator.client_ip, trace_id=operator.trace_id)

    # 事务提交后失效缓存（先写库、再删缓存）
    redis.delete(f"catalog:product:{spu_id}")
    redis.delete(cache.list_key_for_category(spu.category_id))   # 分类列表缓存
    return result
```

## 7. 缓存设计

### 7.1 Key 清单

| Key 模板 | 内容 | TTL | 失效时机 |
|---|---|---|---|
| `catalog:product:{spu_id}` | 商品详情（SPU + 图片 + 属性 + SKU 列表 + 标签），**不含库存** | 30 分钟 | 商品编辑、上下架、SKU 增删改、图片/属性/标签变更、分类变更 |
| `catalog:product:null:{spu_id}` | 空值占位（防穿透） | 60 秒 | 商品创建时（按 ID 删除） |
| `catalog:category:tree` | 启用分类树完整结构 | 30 分钟 | 分类增删改、排序、启停 |
| `catalog:category:path:{category_id}` | 分类到根节点的路径数组（面包屑） | 30 分钟 | 分类改名/移动 |
| `catalog:sku:snapshot:{sku_id}` | SKU 快照（标题/规格/价格/图片/上下架状态），**不含库存** | 5 分钟 | SKU 编辑、SPU 上下架、SPU 标题变更 |
| `catalog:inventory:{sku_id}` | 可售量计数（预占前置拦截用） | 10 分钟（仅作漂移兜底，主要靠主动校准） | 预占/释放/确认/人工调整后主动删除；每 5 分钟校准任务刷新 |
| `catalog:reserve:idem:{order_no}` | 预占幂等锁 | 30 分钟 | 业务完成后保留至 TTL 自然过期 |
| `catalog:reserve:result:{order_no}` | 预占成功响应体（幂等重放） | 30 分钟 | 随幂等锁过期 |
| `catalog:event:{event_type}:{event_id}` | 已消费事件标记 | 7 天 | 自然过期 |
| `catalog:tag:list` | 启用标签字典 | 30 分钟 | 标签增删改 |
| `catalog:list:{category_id}:{sort}:{filters_hash}` | 列表页首页结果缓存（可选） | 60 秒 | 该分类下商品上下架/编辑 |
| `catalog:review:summary:{spu_id}` | 评价统计（均分、各星分布） | 5 分钟 | 新评价、评价隐藏、评价删除 |

> 库存**不做详情缓存内嵌**、**不做纯缓存读**（通用约定 9.3 与 5.3.1 一致性要求）。`catalog:inventory:{sku_id}` 只用于写路径前置拦截，不用于任何读接口的输出。

### 7.2 失效策略

**模式**：Cache-Aside，**先写数据库，再删除缓存**（通用约定 9.3）。禁止先删缓存。

**集中失效入口**：所有失效在 `services/cache_invalidator.py` 中集中声明，避免"某个接口改了商品但忘了删缓存"——这是缓存方案最常见的线上问题。声明形式（示意）：

```
INVALIDATION_RULES = {
    "spu.updated":           ["catalog:product:{spu_id}", "catalog:category:tree_count:{category_id}", "catalog:list:*"],
    "spu.status_changed":    ["catalog:product:{spu_id}", "catalog:list:*", "catalog:sku:snapshot:*:{spu_id}"],
    "sku.updated":           ["catalog:product:{spu_id}", "catalog:sku:snapshot:{sku_id}", "catalog:list:*"],
    "category.changed":      ["catalog:category:tree", "catalog:category:path:*", "catalog:list:*"],
    "tag.changed":           ["catalog:tag:list", "catalog:product:*"],
    "review.created":        ["catalog:review:summary:{spu_id}", "catalog:product:{spu_id}"],
}
```

**通配删除的实现**：不使用 `KEYS`（阻塞 Redis）。改为**版本号法**——为列表缓存维护一个命名空间版本键：

```
catalog:list:ver:{category_id}      -- 整数版本号
列表缓存 Key = catalog:list:{category_id}:v{ver}:{sort}:{filters_hash}
失效时 INCR catalog:list:ver:{category_id} → 旧 Key 自然不可达，靠 TTL 回收
```

**延迟双删**：对"先写库再删缓存"仍可能出现"删除后并发读回填旧值"的窗口（读请求在删除前已从 DB 读到旧值、删除后才回填）。本服务对详情缓存采用**延迟双删**：删除后 `sleep 200ms` 再删一次（通过异步任务执行，不阻塞请求）。商品详情缓存 30 分钟 TTL 是最坏情况的兜底。

**缓存击穿防护**：商品详情、分类树为热点 Key，采用逻辑过期：缓存值内嵌 `logical_expire_at`，读取时若已逻辑过期则返回旧值并异步触发刷新（单飞锁 `SETNX` 保证只有一个请求回源）。

**缓存降级**：Redis 不可用时，所有缓存读写捕获异常并降级为"直接读 DB"（`services/cache.py` 统一封装，异常不外抛）。这保证 Redis 故障不会导致商品浏览不可用（NFR-AV-002）。库存前置拦截在 Redis 不可用时直接跳过，全部压力落到 DB 条件更新（正确性不受影响，见 6.2.1）。

### 7.3 缓存与强一致的边界（汇总）

| 数据 | 读走缓存 | 写后处理 | 理由 |
|---|---|---|---|
| 商品详情（基本信息） | 是 | 删缓存 | 变更低频，可容忍 1 次请求的旧值 |
| 分类树 | 是 | 删缓存 | 变更极低频 |
| SKU 快照（价格/标题） | 是 | 删缓存 | 下单快照由订单服务负责，此处容忍 5 分钟 |
| **可售库存** | **否** | **写库后删 Redis 计数** | 强一致要求（需求 7.3） |
| 评价统计 | 是 | 删缓存 | 统计口径，容忍 5 分钟 |
| 商品上下架状态 | 随详情缓存 | 删缓存 | 下架需尽快生效，TTL 30 分钟为兜底 |

## 8. 定时任务

所有任务基于分布式锁 `SET catalog:task:{name}:lock <instance_id> NX EX {lock_ttl}` 选主，多实例部署时同一时刻只有一个实例执行；实例数与锁 TTL 的关系：`lock_ttl >= 预估最长执行时间 × 2`。

| # | 任务名 | 周期 | 职责 | 幂等要求 | 锁 TTL |
|---|---|---|---|---|---|
| 8.1 | `publish-outbox-events` | 每 5 秒 | 扫描 `outbox_events` 中 `PENDING`/`FAILED` 且 `next_retry_at <= now()` 的记录，投递至 RabbitMQ（`ecommerce.events`，Routing Key = `event_type`），成功后置 `PUBLISHED`，失败按 `1s/5s/30s/2m/10m` 更新 `next_retry_at` 与 `retry_count`，5 次后置 `FAILED` 并告警 | 投递后发送成功才置 `PUBLISHED`；极端情况下重复投递由消费端 `event_id` 幂等兜底 | 30s |
| 8.2 | `release-expired-reservations` | 每分钟 | 兜底释放超时未支付的预占（6.2.4）；单批 200 条，循环至无可处理 | 依赖 `UPDATE ... WHERE status='RESERVED'` 的条件更新，天然幂等；重复执行不会重复回补 | 120s |
| 8.3 | `reconcile-inventory-counters` | 每 5 分钟 | 以 DB 为权威重建 Redis 可售量计数：扫描 `idx_inventories_last_reconciled_at` 中 5 分钟前未校准的行，逐批（500 行）执行 `reconcile_inventory` | 覆盖式 `SET`（非 `INCRBY`），重复执行结果相同 | 300s |
| 8.4 | `scan-low-stock-alerts` | 每 10 分钟 | 补扫阈值穿越：找出 `stock - reserved <= low_stock_threshold` 且无 `OPEN` 预警的 SKU 并补发（覆盖"变更路径遗漏"与"直接改库"场景）；同时把 `available > threshold` 的 `OPEN` 记录置 `RESOLVED` | 依赖 `uk_low_stock_alerts_sku_open` 唯一约束 + 存在性检查，重复执行不重复发事件 | 300s |
| 8.5 | `expire-product-tags` | 每 10 分钟 | 删除 `product_tag_rel.expires_at < now()` 的关联（促销活动到期自动摘标签），并递增对应分类的列表缓存版本号 | `DELETE` 幂等 | 120s |
| 8.6 | `recalc-spu-price-range` | 每日 03:00 | 抽样/全量校验 `spus.min_price_cents`/`max_price_cents` 与实际 SKU 聚合是否一致，不一致则修正、修正数量超阈值（> 100）时告警 | 幂等（重算为覆盖写） | 600s |
| 8.7 | `recalc-spu-rating` | 每 5 分钟 | 重算 `reviews` 变更（新增/隐藏/删除）影响的 SPU 的 `rating_avg` 与 `review_count`（基于 `reviews.updated_at > 上次执行时间` 的增量集合） | 覆盖写，幂等 | 300s |
| 8.8 | `refresh-category-product-count` | 每小时 | 重算 `categories.product_count`（直接挂载的在架 SPU 数） | 覆盖写，幂等 | 300s |
| 8.9 | `reconcile-sales-count` | 每日 04:00 | 若已接入 order-service 销量统计接口，则按周校准 `spus.sales_count`；否则空转并输出提示日志 | 覆盖写，幂等 | 600s |
| 8.10 | `archive-inventory-transactions` | 每日 02:30 | 将 `created_at < now() - 180 天` 的库存流水与变更留痕迁移至归档表（`inventory_transactions_archive` / 同名结构），迁移在单事务内 `INSERT ... SELECT` + `DELETE`，每批 10000 行 | 按 `id` 范围分批，`INSERT ... ON CONFLICT (id) DO NOTHING` 保证重复执行安全 | 1800s |
| 8.11 | `cleanup-expired-idempotency-keys` | 每小时 | 清理已过期但未被 Redis TTL 回收的幂等键残留（`catalog:reserve:*` 前缀中 `idem` 与 `result` 不匹配的孤儿键），以及对账 `stock_reservations` 与幂等键的一致性 | `DEL` 幂等 | 300s |

**任务执行的可观测性**：每个任务记录结构化日志（含任务名、耗时、处理条数、失败条数、`trace_id`）并上报指标 `catalog_task_duration_seconds{task}`、`catalog_task_processed_total{task}`、`catalog_task_failed_total{task}`；`release-expired-reservations` 与 `reconcile-inventory-counters` 的失败数 > 0 时告警（前者代表库存释放受阻，后者代表 Redis/DB 漂移）。

**关于 `release-expired-reservations` 与订单服务超时关闭的关系**：两者并行不冲突（见 5.3）。若订单服务正常，其 `order.cancelled` 事件会先触发释放，本任务扫描时该记录已是 `RELEASED`，直接跳过。为避免"订单还在待支付但库存已被本任务释放"造成的用户困惑，`ORDER_RESERVE_TTL_SECONDS` 必须 **≥ 订单服务的订单超时时间 + 5 分钟缓冲**（配置约束，见第 11 章），保证订单服务总是先关闭订单。

## 10. 安全与权限

### 10.1 鉴权矩阵

| 接口组 | 网关校验 | 服务内校验 | 失败返回 |
|---|---|---|---|
| 买家端商品浏览（A-01~A-05） | 白名单放行，不校验令牌 | 无（公开数据） | — |
| 发表评价（A-06） | 校验令牌 | 校验 `X-User-Id` 存在；`user_id` 只取请求头 | `COMMON-2001` |
| 后台接口（B-01~B-27） | 校验令牌 | 校验 `X-User-Roles` 含 `ADMIN` 或 `CATALOG_OPERATOR` | `COMMON-3001` |
| 内容治理（B-27） | 校验令牌 | 校验 `X-User-Roles` 含 `ADMIN` | `COMMON-3001` |
| 内部接口（I-01~I-06） | 网关**不路由** | 校验 `X-Internal-Token` 与配置一致 | `COMMON-2002` |

**强制要求**：
- 服务**不解析 JWT**，只信任网关注入的 `X-User-Id` / `X-User-Roles`（通用约定 4.3）。
- 所有写操作涉及 `user_id` 的（评价、库存调整操作人、标签打标人、留痕操作人）一律取自 `X-User-Id`，**请求体中的任何 `user_id`/`operator_id` 字段必须被忽略**（若 Pydantic 模型声明了该字段则直接拒绝为 `CAT-1001`）。
- `/internal/*` 路由在网关路由表中显式排除（不允许外部访问）；即便被访问到，`X-Internal-Token` 校验会拦截。

### 10.2 数据归属校验

| 数据 | 归属 | 校验方式 |
|---|---|---|
| 商品、分类、标签、库存 | 平台公共数据 | 后台角色校验即可 |
| 评价（写） | 买家本人 | ① `user_id` 取 `X-User-Id`；② 调 order-service 确认订单属于该用户 |
| 评价（改/删） | 评价作者本人 | 查询时校验 `reviews.user_id == X-User-Id`，不匹配返回 `COMMON-3001` |
| 评价回复（买家追评） | 评价作者本人 | 同上 |
| 评价回复（运营回复） | 后台角色 | 角色校验 |

**越权返回 `COMMON-3001` 而非 404**（通用约定 4.4）：买家删除他人评价时返回 403 而非 404，避免通过响应码枚举评价 ID。

### 10.3 后台操作审计

NFR-SE-009 要求后台管理接口记录操作审计日志。本服务通过两条路径落地：

| 路径 | 覆盖范围 | 存储 |
|---|---|---|
| `product_change_logs` | 有业务语义的变更：商品/分类/SKU/标签/库存 | 业务库，长期保留（归档后移至归档表） |
| 结构化访问日志 | 全部写接口（含未产生留痕的，如评价隐藏） | ELK，含 `operator_id`、`path`、`method`、`status`、`client_ip`、`trace_id` |

**审计日志必含字段**：操作人（`operator_id` + `operator_name` 快照）、时间、对象（`entity_type` + `entity_id`）、变更前后值（`before_value`/`after_value`）、客户端 IP、`trace_id`。日志中不含任何密钥类内容（通用约定 12.3）。

### 10.4 输入与输出安全

| 风险 | 措施 |
|---|---|
| SQL 注入 | 全部走 SQLAlchemy 参数化；排序字段**白名单映射**（`sort` 枚举 → 列名映射表），禁止拼接 |
| XSS（商品描述） | 富文本白名单标签（`p/br/strong/em/ul/ol/li/img` 等），落库前用 `bleach` 清洗；`img` 的 `src` 仅允许 `https://` 且限定 CDN 域名 |
| XSS（评价内容） | 纯文本存储，输出时由前端转义；服务端在写入前去除控制字符 |
| XSS（搜索高亮） | `ts_headline` 输出的 `highlight` 中，除 `<em>` 外的 HTML 已转义 |
| 图片 URL 注入 | 校验协议为 `https`、长度 ≤ 512、域名在白名单内（`IMAGE_ALLOWED_DOMAINS`） |
| 越权访问 | 见 10.2 |
| 内部接口伪造 | `X-Internal-Token` 校验；该令牌由密钥管理注入，非硬编码（通用约定 13） |
| 批量查询滥用 | `sku_ids` / `items` 长度上限（100 / 50），单请求体大小上限 64KB |
| 搜索型 DoS | `keyword` 长度上限 64；`SEARCH_MAX_RESULT` 截断；网关对本服务搜索接口按 IP 限流 |

### 10.5 脱敏

| 字段 | 处理 | 说明 |
|---|---|---|
| 评价者昵称 | 本服务**不存储**昵称 | 响应只回 `user_id`；展示昵称由前端向 user-service 获取。匿名评价前端统一显示"匿名用户" |
| 评价者 `user_id` | 对买家端**不回显完整 ID** | `A-05` 中 `user.user_id` 仅用于前端关联，若产品要求隐藏则替换为评价维度哈希；匿名评价不回 `user_id` |
| `operator_name` | 完整存储 | 后台账号名，属内部标识，非个人敏感信息 |
| `client_ip` | 完整存储于留痕表 | 仅后台可见，买家端接口不返回 |
| 手机号/邮箱/银行卡 | **本服务不涉及** | 本服务不存储任何用户联系方式或支付信息 |

## 1. 服务概览

### 1.1 职责

通知服务是**纯消费型终端服务**，不参与任何交易主链路，负责把平台内的领域事件转化为对用户的触达动作：

| 职责域 | 具体内容 |
|---|---|
| 事件消费 | 订阅 8 类领域事件，映射到模板，渲染并投递 |
| 渠道适配 | 邮件统一走 SendGrid、短信统一走 Twilio，渠道实现可替换、可开关、可降级 |
| 模板管理 | 模板的版本化维护、变量契约定义、变量校验、预览与测试发送 |
| 发送执行 | 收件人解析、偏好判定、渲染、第三方调用、结果记录 |
| 失败处理 | 本地有限重试 + MQ 退避重试 + 死信落库告警 + 人工重发 + 降级补发 |
| 发送记录 | 全量发送记录与送达状态，供排障、审计与统计 |
| 用户偏好 | 营销类通知可退订，交易类通知不可关闭 |
| 同步触达 | 为极少数需要"用户立即收到"的场景（验证码）提供同步接口 |

### 1.2 边界（本服务不做什么）

| 不做的事 | 原因 |
|---|---|
| 不生成验证码、不校验验证码 | 身份验证归属用户服务（FR-US-002）；通知服务只做投递，接收并投递明文验证码后立即丢弃，不落库不落日志 |
| 不判断交易是否成功 | 只消费事件，事件即事实；不主动查订单/支付服务确认状态 |
| 不保存商品、订单的业务数据 | 模板变量只取事件 payload 与收件人信息，不复制业务数据；需要跳转明细时只渲染订单号并引导用户到订单页 |
| 不参与主流程 | 通知服务宕机时，订单、支付、库存链路必须不受影响（AC-07、NFR-AV-001） |
| 不发布领域事件 | 终端服务，无下游（关于"通知发送失败"事件的取舍见 5.4） |
| 不负责消息文案的多语言 | 本期单语言（`zh-CN`），`Accept-Language` 仅透传不参与渲染 |

### 1.3 上下游依赖

```
                      ┌────────────────────────────────────────┐
   RabbitMQ ─────────▶│                                        │
   ecommerce.events   │        notification-service            │
                      │                                        │
   用户服务 ◀─────────│  事件消费 · 模板渲染 · 渠道适配 · 重试   │─────────▶ SendGrid（邮件）
   (收件人查询)        │                                        │─────────▶ Twilio（短信）
                      │                                        │
   PostgreSQL ◀───────│                                        │─────────▶ 告警通道（Alertmanager / Webhook）
   Redis ◀────────────│                                        │
                      └────────────────────────────────────────┘
```

| 方向 | 对象 | 用途 | 失败影响 |
|---|---|---|---|
| 上游（事件） | RabbitMQ `ecommerce.events` | 9 个事件中的 8 个由本服务消费 | 事件堆积，恢复后继续消费，不丢 |
| 上游（同步） | 用户服务 | 调用 `/api/v1/notifications/verification-code` | 用户服务提示"验证码发送失败"，用户可重试 |
| 上游（同步） | 其他服务 | 极少数场景调用 `/internal/v1/notifications/send` | 调用方按 11 章降级处理 |
| 下游 | 用户服务 `/internal/v1/users/{user_id}/contact` | 事件 payload 只有 `user_id` 时解析收件人 | 可重试错误，MQ 退避重试，超限死信 |
| 下游 | SendGrid | 邮件投递 | 降级/补发，见 6.5 |
| 下游 | Twilio | 短信投递与状态回调 | 降级为邮件，见 6.5 |
| 下游 | 告警通道 | 发送失败超限、渠道熔断、死信堆积告警 | 记录日志，下轮重试 |

### 1.4 对应需求编号

| 需求编号 | 需求名称 | 本服务实现要点 | 对应章节 |
|---|---|---|---|
| FR-NOT-001 | 订单确认通知 | `order.created` → `ORDER_CREATED_EMAIL` / `ORDER_CREATED_SMS` | 5.3、6.2 |
| FR-NOT-002 | 支付成功通知 | `order.paid` → `ORDER_PAID_*`，渲染订单号与支付时间 | 5.3、6.2 |
| FR-NOT-003 | 发货通知 | `order.shipped` → `ORDER_SHIPPED_*`，渲染物流公司与单号 | 5.3、6.2 |
| FR-NOT-004 | 退款通知 | `payment.refunded` → `REFUND_SUCCEEDED_*`，渲染退款金额与到账预期 | 5.3、6.2 |
| FR-NOT-005 | 模板管理 | 模板 + 版本两张表、变量契约、校验/预览/测试发送、发布流程 | 2、3.2、6.3 |
| FR-NOT-006 | 渠道适配 | `notification_channel_configs` 表 + SendGrid / Twilio 适配器 + 渠道开关 | 2.7、6.4、11 |
| FR-NOT-007 | 失败重试 | 本地有限重试 → MQ 退避重试 → 死信落库告警 → 人工重发/补发 | 5.5、6.5、8 |
| FR-NOT-008 | 发送记录 | `notification_records` 全量记录 + 游标分页查询 + 详情 + 重发 | 2.3、3.3 |
| FR-NOT-009 | 用户偏好 | `notification_preferences` + 交易类不可关闭的服务端强制校验 | 2.4、3.4、6.6 |
| FR-US-002 | 邮箱/手机验证（上游） | 验证码同步发送接口与限流 | 3.6、6.7 |
| NFR-PF-002 | 通知异步化 | 全部交易类通知走事件，主流程零阻塞 | 5 |
| NFR-SE-005/007 | 输入安全、密钥外置 | 最小渲染器 + 模板注入防护 + 密钥注入 | 10 |
| AC-07 | 通知服务不可用不影响主流程 | 无同步反压、纯消费、失败只影响自身 | 1.2、5.5 |

### 1.5 关键设计决策速览

| 决策点 | 结论 | 理由 | 详见 |
|---|---|---|---|
| 模板版本 | 模板主表 + 不可变版本表，发送记录冗余 `template_code` + `template_version` | 已发送记录可精确追溯当时使用的模板内容 | 2.2、2.3 |
| 重试 | 第三方失败先本地有限重试（2 次，≤2s），仍失败抛异常交 MQ 按 `1s/5s/30s/2m/10m` 退避重试 5 次，最终死信 | 短时抖动就地消化，长时故障不阻塞消费线程 | 6.5、5.5 |
| 补发队列 | 超出 MQ 重试时间窗（分钟~小时级）的场景落 `notification_retry_tasks`，由定时任务补发 | MQ 重试上限 10 分钟，覆盖不了短信配额恢复、渠道长期熔断 | 2.5、8 |
| 模板引擎 | 自研最小渲染器（仅 `{{var}}` 与 `{{var\|default}}`），不启用完整模板引擎求值 | 从语法层面杜绝模板注入与表达式执行 | 6.3、10.4 |
| 变量缺失 | required 变量缺失 → 拒绝发送并落 SKIPPED 记录；optional 变量缺省用模板声明的默认值 | 绝不发出半截内容 | 6.3 |
| 收件人 | 事件无联系方式时调用户服务内部接口，Redis 缓存 15 分钟且**缓存加密值** | 降低跨服务调用，同时避免明文联系方式驻留 Redis | 6.8、7 |
| 收件人落库 | AES-256-GCM 加密 + HMAC 盲索引 + 掩码列 | 兼顾"按收件人查询"能力与最小化明文暴露 | 2.3、10.3 |
| 验证码 | 由用户服务生成与校验，通知服务同步投递、不落明文、60 秒冷却 + 日限 + IP 限流 | 立即送达需求无法异步；明文不落库降低泄露面 | 3.6、6.7 |
| 依赖 | 通知服务不依赖订单/支付/商品服务 | 保持单向依赖，任何业务服务故障都不阻塞通知消费 | 1.3 |

## 2. 数据库设计

数据库 `ecommerce_notification`，PostgreSQL 16，时区 UTC。公共字段（`id`、`created_at`、`updated_at`）、命名规范、无物理外键等约定见通用约定第 8 章。

### 2.1 表清单

| 序号 | 表名 | 用途 | 预估量级 | 保留策略 |
|---|---|---|---|---|
| 1 | `notification_templates` | 模板逻辑主表（渠道、事件、类别、启用状态、当前版本） | 数十行 | 长期 |
| 2 | `notification_template_versions` | 模板版本快照（不可变） | 数百行 | 长期 |
| 3 | `notification_records` | 发送记录（核心表） | 百万级/年 | 18 个月在线，历史归档 |
| 4 | `notification_preferences` | 用户通知偏好 | 与用户数同量级 | 长期 |
| 5 | `notification_retry_tasks` | 延迟补发任务队列（DB 侧重试） | 万级 | 完成后 30 天清理 |
| 6 | `notification_channel_configs` | 渠道配置（开关、优先级、配额、降级目标） | 数行 | 长期 |
| 7 | `notification_dead_letters` | 死信落库（人工重放依据） | 千级 | 90 天 |
| 8 | `notification_stats_daily` | 发送统计日汇总 | 千级/年 | 长期 |

### 2.2 `notification_templates` — 模板主表

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | PK | — | 雪花 ID，应用层生成 |
| `template_code` | VARCHAR(64) | NOT NULL | — | 模板编码，全局唯一，大写 snake_case，如 `ORDER_CREATED_EMAIL` |
| `channel` | VARCHAR(32) | NOT NULL, CHECK | — | 渠道：`EMAIL` / `SMS` |
| `event_type` | VARCHAR(64) | NULL | NULL | 触发事件类型，如 `order.created`；为 NULL 表示非事件触发（如验证码） |
| `category` | VARCHAR(32) | NOT NULL, CHECK | `TRANSACTIONAL` | 通知类别：`TRANSACTIONAL` / `MARKETING` / `OPERATIONAL` |
| `name` | VARCHAR(128) | NOT NULL | — | 中文名称，如"下单确认邮件" |
| `description` | VARCHAR(512) | NULL | NULL | 用途说明 |
| `is_enabled` | BOOLEAN | NOT NULL | FALSE | 启用状态，停用后不再发送（不删除历史记录） |
| `current_version` | INTEGER | NOT NULL, CHECK ≥ 0 | 0 | 当前生效版本号，0 表示尚未发布 |
| `deleted_at` | TIMESTAMPTZ | NULL | NULL | 软删除；被记录引用的模板只允许停用，不允许删除 |
| `created_by` | VARCHAR(64) | NOT NULL | `system` | 创建人（管理员 ID） |
| `updated_by` | VARCHAR(64) | NOT NULL | `system` | 最后修改人 |
| `created_at` / `updated_at` | TIMESTAMPTZ | NOT NULL | `now()` | 通用字段 |

唯一约束 `uk_notification_templates_event_type_channel` 建立在 `(event_type, channel)` 上：**一个事件在同一渠道下只允许一个模板**，避免消费端选不出模板。若后续要做 A/B 变体或多语言，需去掉该约束并在消费端增加模板选择策略（本期不做）。

### 2.3 `notification_template_versions` — 模板版本表

版本一经发布即**不可修改**，只能新建下一版；这是"已发送记录可追溯"的基础。

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | PK | — | 雪花 ID |
| `template_id` | BIGINT | NOT NULL | — | 关联 `notification_templates.id`，应用层保证 |
| `template_code` | VARCHAR(64) | NOT NULL | — | 冗余编码，便于按编码直查版本 |
| `version` | INTEGER | NOT NULL, CHECK ≥ 1 | — | 版本号，同模板内自增 |
| `status` | VARCHAR(32) | NOT NULL, CHECK | `DRAFT` | `DRAFT` / `PUBLISHED` / `ARCHIVED` |
| `title_template` | VARCHAR(255) | NULL | NULL | 标题模板（邮件主题）；SMS 渠道必须为 NULL |
| `body_template` | TEXT | NOT NULL | — | 正文模板，支持 `{{var}}` 占位符 |
| `variables_schema` | JSONB | NOT NULL | `[]` | 变量契约数组，结构见 6.3 |
| `change_note` | VARCHAR(255) | NULL | NULL | 变更说明，审计用 |
| `published_at` | TIMESTAMPTZ | NULL | NULL | 发布时间 |
| `published_by` | VARCHAR(64) | NULL | NULL | 发布人 |
| `created_at` / `updated_at` | TIMESTAMPTZ | NOT NULL | `now()` | 通用字段 |

约束与索引：

- `uk_notification_template_versions_template_version` UNIQUE `(template_id, version)` — 同模板版本号唯一
- `idx_notification_template_versions_code_version` `(template_code, version DESC)` — 按编码取最新版本（消费链路高频）

**版本状态机**：`DRAFT` →（发布）→ `PUBLISHED` →（模板更新时自动归档）→ `ARCHIVED`。同一 `template_id` 下最多一个 `PUBLISHED` 版本，由 `notification_templates.current_version` 指向。发布新版本时，在同一事务中把旧 `PUBLISHED` 置为 `ARCHIVED` 并更新 `current_version`。

### 2.4 `notification_records` — 发送记录表

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | PK | — | 雪花 ID，天然按时间递增，兼作游标分页键 |
| `record_no` | VARCHAR(32) | NOT NULL | — | 通知单号，格式 `NT` + `YYYYMMDD` + 8 位序列，如 `NT20260910000001` |
| `event_id` | UUID | NULL | NULL | 来源事件 ID；同步接口触发时为 NULL |
| `event_type` | VARCHAR(64) | NULL | NULL | 触发事件类型 |
| `trigger_source` | VARCHAR(16) | NOT NULL, CHECK | `EVENT` | `EVENT` / `SYNC_API` / `MANUAL` / `SCHEDULED` |
| `parent_record_no` | VARCHAR(32) | NULL | NULL | 重发场景指向原记录，构成审计链 |
| `user_id` | BIGINT | NULL | NULL | 收件用户；运营类通知为 NULL |
| `template_id` | BIGINT | NOT NULL | — | 模板主键 |
| `template_code` | VARCHAR(64) | NOT NULL | — | 模板编码（冗余） |
| `template_version` | INTEGER | NOT NULL | — | **发送时使用的模板版本**，追溯关键字段 |
| `channel` | VARCHAR(32) | NOT NULL, CHECK | — | `EMAIL` / `SMS` |
| `provider` | VARCHAR(32) | NULL | NULL | `SENDGRID` / `TWILIO` |
| `recipient_cipher` | TEXT | NOT NULL | — | 收件人密文（AES-256-GCM，Base64） |
| `recipient_masked` | VARCHAR(128) | NOT NULL | — | 收件人掩码，展示与日志用 |
| `recipient_hash` | CHAR(64) | NOT NULL | — | 归一化后 HMAC-SHA256（hex），用于按收件人精确查询 |
| `recipient_key_id` | SMALLINT | NOT NULL | 1 | 加密密钥版本，支持轮换 |
| `subject` | VARCHAR(255) | NULL | NULL | 渲染后的标题 |
| `rendered_content` | JSONB | NULL | NULL | 渲染结果的 `{subject, body}` 快照，受 `NOT_RECORD_RENDERED_CONTENT` 控制；验证码类永不写入 |
| `render_variables` | JSONB | NOT NULL | `{}` | 渲染所用变量（验证码类中 `code` 以 `******` 存储） |
| `status` | VARCHAR(32) | NOT NULL, CHECK | `PENDING` | 见下方状态字典 |
| `retry_count` | SMALLINT | NOT NULL | 0 | 已重试次数（本地 + MQ 累计） |
| `max_retry_count` | SMALLINT | NOT NULL | 5 | 重试上限 |
| `next_retry_at` | TIMESTAMPTZ | NULL | NULL | 下次补发时间，补发任务扫描依据 |
| `last_error_code` | VARCHAR(64) | NULL | NULL | 最近一次失败错误码（`NOT-xxxx` 或第三方错误码） |
| `last_error_message` | VARCHAR(512) | NULL | NULL | 最近一次失败原因（已脱敏，截断） |
| `provider_message_id` | VARCHAR(128) | NULL | NULL | 第三方消息 ID，用于回执对账 |
| `sent_at` | TIMESTAMPTZ | NULL | NULL | 第三方受理时间 |
| `delivered_at` | TIMESTAMPTZ | NULL | NULL | 送达确认时间（回执） |
| `trace_id` | VARCHAR(64) | NULL | NULL | 链路追踪 ID |
| `created_at` / `updated_at` | TIMESTAMPTZ | NOT NULL | `now()` | 通用字段 |

索引设计（含主键共 6 个，符合单表索引预算）：

| 索引名 | 类型 | 字段 | 用途 |
|---|---|---|---|
| `pk_notification_records` | PK | `id` | 主键 |
| `uk_notification_records_record_no` | UNIQUE | `record_no` | 单号唯一、详情查询 |
| `uk_notification_records_event_template_channel` | UNIQUE（部分） | `(event_id, template_code, channel)` WHERE `event_id IS NOT NULL` | **事件消费幂等的数据库兜底** |
| `idx_notification_records_created_at` | 普通 | `(created_at DESC, id DESC)` | 后台列表游标分页主索引 |
| `idx_notification_records_user_id_created_at` | 普通 | `(user_id, created_at DESC)` | 按用户查发送历史 |
| `idx_notification_records_status_retry` | 普通 | `(status, next_retry_at)` WHERE `status = 'PENDING'` | 补发任务扫描 |
| `idx_notification_records_recipient_hash` | 普通 | `(recipient_hash, created_at DESC)` | 按收件人查询 |

> 索引预算说明：以上含主键为 7 个，略高于"建议不超过 6"的约定，是因为 `recipient_hash` 索引承载"客服按收件人查记录"这一刚需查询。若后续需要更多筛选维度（如 `event_type + status`），优先将统计类查询下沉到 `notification_stats_daily`，而不是继续加索引。

### 2.5 `notification_preferences` — 用户通知偏好表

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | PK | — | 雪花 ID |
| `user_id` | BIGINT | NOT NULL, UNIQUE | — | 用户 ID |
| `marketing_email_enabled` | BOOLEAN | NOT NULL | TRUE | 营销类邮件开关 |
| `marketing_sms_enabled` | BOOLEAN | NOT NULL | TRUE | 营销类短信开关 |
| `unsubscribed_at` | TIMESTAMPTZ | NULL | NULL | 一键退订时间（邮件退订链接触发） |
| `unsubscribe_reason` | VARCHAR(128) | NULL | NULL | 退订原因（可空） |
| `source` | VARCHAR(16) | NOT NULL, CHECK | `DEFAULT` | 记录来源：`DEFAULT` / `USER` / `ADMIN` / `SYSTEM` |
| `last_modified_by` | VARCHAR(32) | NULL | NULL | 最后修改者（用户 ID 或 `ADMIN:{id}`） |
| `created_at` / `updated_at` | TIMESTAMPTZ | NOT NULL | `now()` | 通用字段 |

**无记录即默认全开**，读取时若不存在返回默认值，不强制写库（避免注册时写放大）。交易类通知不受本表影响——表中**刻意不提供**交易类开关字段，从数据结构上杜绝误关闭。

### 2.6 `notification_retry_tasks` — 延迟补发任务表

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
|---|---|---|---|---|

### 2.10 枚举字典

| 枚举 | 取值 | 含义 |
|---|---|---|
| `channel` | `EMAIL` / `SMS` | 投递渠道。IN_APP、PUSH 不在本期范围，新增需同步修改 CHECK 约束与本文档 |
| `provider` | `SENDGRID` / `TWILIO` | 渠道供应商 |
| `category` | `TRANSACTIONAL` / `MARKETING` / `OPERATIONAL` | 交易类（不可关闭）/ 营销类（可关闭）/ 运营类（发给内部人员，不受用户偏好约束） |
| `template_version.status` | `DRAFT` / `PUBLISHED` / `ARCHIVED` | 版本状态 |
| `record.status` | `PENDING` / `SENDING` / `SENT` / `DELIVERED` / `FAILED` / `SKIPPED` | 记录状态 |
| `record.trigger_source` | `EVENT` / `SYNC_API` / `MANUAL` / `SCHEDULED` | 触发来源 |
| `retry_task.task_type` | `RETRY_SEND` / `FALLBACK_CHANNEL` / `REPLENISH` | 补发任务类型 |
| `retry_task.status` | `PENDING` / `PROCESSING` / `DONE` / `CANCELLED` | 补发任务状态 |
| `dead_letter.status` | `PENDING` / `REPLAYING` / `REPLAYED` / `IGNORED` | 死信处理状态 |
| `preference.source` | `DEFAULT` / `USER` / `ADMIN` / `SYSTEM` | 偏好记录来源 |

`record.status` 状态机：

```
                 ┌──────────── 本地重试 / MQ 重试 ────────────┐
                 ▼                                            │
  (创建) ──▶ PENDING ──▶ SENDING ──▶ SENT ──▶ DELIVERED        │
                 │           │         │                      │
                 │           │         └─(回执失败/bounce)─▶ FAILED
                 │           └─(不可重试错误)──────────────▶ FAILED
                 └─(前置校验不通过)───────────────────────▶ SKIPPED
```

说明：`FAILED` 为终态，表示"不可重试错误"或"重试次数耗尽"，必须落库并触发告警；`SKIPPED` 为终态，表示因模板停用、渠道关闭、收件人缺失、偏好退订、变量缺失等原因**主动不发送**，也必须落库（FR-NOT-007 要求"超限后落库"，FR-NOT-005 异常流要求"变量缺失拒绝发送并记录"）。`DELIVERED` 仅邮件渠道可达（依赖 SendGrid 回执）；短信无回执时 `SENT` 即视为结束态。

### 3.2 模板管理接口

#### T1 GET `/api/v1/admin/notification-templates`

查询参数（偏移分页，模板数量少，不使用游标）：

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| `event_type` | string | 否 | — | 按事件类型筛选，如 `order.created` |
| `channel` | string | 否 | — | `EMAIL` / `SMS` |
| `category` | string | 否 | — | `TRANSACTIONAL` / `MARKETING` / `OPERATIONAL` |
| `is_enabled` | boolean | 否 | — | 启用状态 |
| `keyword` | string | 否 | — | 在 `template_code` 与 `name` 上模糊匹配 |
| `page` | int | 否 | 1 | 页码 |
| `page_size` | int | 否 | 20 | 每页条数，最大 100 |

响应 `data.items[]` 字段：`template_code`、`channel`、`event_type`、`category`、`name`、`is_enabled`、`current_version`、`published_at`、`updated_by`、`updated_at`。

错误码：`COMMON-1001`（参数非法）、`COMMON-3001`（非管理员）。

#### T2 POST `/api/v1/admin/notification-templates`

请求体：

```json
{
  "template_code": "ORDER_SHIPPED_EMAIL",
  "channel": "EMAIL",
  "event_type": "order.shipped",
  "category": "TRANSACTIONAL",
  "name": "发货通知邮件",
  "description": "订单发货后通知买家物流公司与单号",
  "draft_version": {
    "title_template": "您的订单 {{order_no}} 已发货",
    "body_template": "<p>{{buyer_nickname}} 您好，您购买的订单 {{order_no}} 已于 {{shipped_at}} 发货。</p><p>物流公司：{{carrier}}，运单号：{{tracking_no}}</p>",
    "variables_schema": [
      {"name": "buyer_nickname", "type": "STRING", "required": false, "source": "CONTACT", "max_length": 32, "default": "顾客"},
      {"name": "order_no", "type": "STRING", "required": true, "source": "EVENT", "max_length": 32},
      {"name": "carrier", "type": "STRING", "required": true, "source": "EVENT", "max_length": 64},
      {"name": "tracking_no", "type": "STRING", "required": true, "source": "EVENT", "max_length": 64},
      {"name": "shipped_at", "type": "DATETIME", "required": true, "source": "EVENT"}

    "change_note": "初始版本"

```

行为：模板与 `version=1` 的 `DRAFT` 版本在同一事务内创建；`is_enabled` 固定为 `false`，需显式调用 T6 启用，且启用前 `current_version` 必须 ≥ 1（即至少发布一个版本）。

响应 `201`：

```json
{
  "code": "OK",
  "message": "success",
  "data": {
    "template_code": "ORDER_SHIPPED_EMAIL",
    "is_enabled": false,
    "current_version": 0,
    "draft_version": 1
  },
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "timestamp": "2026-09-10T08:30:00.123Z"
}
```

错误码：`NOT-5001`（编码已存在）、`NOT-1002`（变量定义非法）、`NOT-1003`（正文引用了未声明变量）、`NOT-1006`（渠道不支持）。

#### T3 GET `/api/v1/admin/notification-templates/{template_code}`

响应 `data` 同时包含模板元信息与当前生效版本内容；若 `current_version = 0`，`current_version_detail` 为 `null`。

#### T4 PUT `/api/v1/admin/notification-templates/{template_code}`

可更新字段：`name`、`description`、`category`、`event_type`。**不允许**修改 `template_code` 与 `channel`（改渠道等价于新建模板）。

> `event_type` 变更后需满足唯一约束（见 2.2）；变更会影响事件到模板的映射，因此接口在响应中返回 `{"mapping_changed": true}` 提示调用方确认。映射关系由数据库 `event_type` 驱动（见 5.3），无需改代码。

#### T5 DELETE `/api/v1/admin/notification-templates/{template_code}`

- 若模板存在任一发送记录（含 `SKIPPED`）→ 返回 `NOT-5005`（409），提示改用停用
- 否则软删除（写 `deleted_at`），同时把其版本置为 `ARCHIVED`
- 成功返回 `204 No Content`

#### T6 PUT `/api/v1/admin/notification-templates/{template_code}/status`

请求体 `{"is_enabled": true}`。

启用前置校验：`current_version >= 1` 且对应版本状态为 `PUBLISHED`，否则返回 `NOT-5002`。停用后消费链路遇到该模板直接落 `SKIPPED` 记录（`last_error_code = NOT-5002`）。

#### T7–T8 版本管理

- T7 GET `.../versions`：偏移分页，返回 `version`、`status`、`change_note`、`published_at`、`published_by`、`created_at`。**不返回** `body_template` 全文，仅返回前 200 字符摘要，避免列表响应过大。
- T8 POST `.../versions`：请求体为 `title_template`、`body_template`、`variables_schema`、`change_note`。版本号 = 该模板 `max(version) + 1`，状态 `DRAFT`。仅允许基于当前最新版本追加，不允许插入历史版本。

#### T9 POST `.../versions/{version}/validate`

请求体可为空（校验已存版本）或携带待校验内容：

```json
{
  "title_template": "您的订单 {{order_no}} 已发货",
  "body_template": "<p>{{carrier}} / {{tracking_no}}</p>"
}
```

响应 `data`：

```json
{
  "is_valid": false,
  "declared_variables": ["order_no", "carrier", "tracking_no"],
  "used_variables": ["order_no", "carrier", "tracking_no", "courier_phone"],
  "errors": [
    {"field": "body_template", "reason": "变量 courier_phone 未在 variables_schema 中声明"},
    {"field": "variables_schema[0].default", "reason": "必填变量 buyer_nickname 不应设置默认值"}
  ],
  "warnings": [
    {"field": "variables_schema[2]", "reason": "变量 tracking_no 未在模板中被引用"}
  ]
}
```

校验规则（与发布接口共用同一套校验器）：变量名符合 `^[a-z][a-z0-9_]{0,31}$`；占位符必须能在 `variables_schema` 中找到声明；声明为 `required` 的变量不得设置 `default`；`default` 为空的 optional 变量会告警；SMS 渠道不得有 `title_template`；正文渲染后的预估长度不超过渠道上限（邮件正文 512KB、短信 500 字符，超出告警）。

#### T10 POST `.../versions/{version}/publish`

事务内完成：校验通过 → 该版本置 `PUBLISHED`、`published_at`/`published_by` → 同模板其他 `PUBLISHED` 版本置 `ARCHIVED` → 更新 `notification_templates.current_version` → 删除模板缓存 `notification:template:{template_code}:*`。

错误码：`NOT-5007`（版本状态不允许发布，如已归档）、`NOT-1002`/`NOT-1003`（校验失败，`details` 返回明细）。

#### T11 POST `/api/v1/admin/notification-templates/{template_code}/preview`

请求体：`{"version": 2, "variables": {"order_no": "SO20260910000001", "carrier": "顺丰速运", "tracking_no": "SF1234567890"}}`（`version` 省略时用 `current_version`）。

响应 `data`：

```json
{
  "template_code": "ORDER_SHIPPED_EMAIL",
  "version": 2,
  "channel": "EMAIL",
  "subject": "您的订单 SO20260910000001 已发货",
  "body": "<p>顾客 您好，您购买的订单 SO20260910000001 已于 2026-09-10 09:15 发货。</p><p>物流公司：顺丰速运，运单号：SF1234567890</p>",
  "missing_variables": [],
  "used_defaults": ["buyer_nickname"]

```

预览**不会**发送、不落发送记录、不消耗配额。若存在 required 变量缺失，返回 `NOT-1004`（400），`details` 逐条列出缺失变量。

#### T12 POST `/api/v1/admin/notification-templates/{template_code}/test-send`

请求体：

```json
{
  "version": 2,
```

### 3.3 发送记录接口

#### R1 GET `/api/v1/admin/notification-records`

**固定使用游标分页**（通用约定 2.3：偏移分页与游标分页二选一，数据量可能极大的列表必须支持游标分页）。

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `cursor` | string | 否 | 上一页返回的 `next_cursor`，base64 编码的 `id`；不传表示从最新开始 |
| `limit` | int | 否 | 每页条数，默认 20，最大 100 |
| `record_no` | string | 否 | 精确匹配通知单号 |
| `recipient` | string | 否 | 邮箱或手机号**明文**，服务端归一化后计算 HMAC 并按 `recipient_hash` 匹配 |
| `user_id` | string | 否 | 收件用户 ID |
| `event_type` | string | 否 | 事件类型 |
| `template_code` | string | 否 | 模板编码 |
| `channel` | string | 否 | `EMAIL` / `SMS` |
| `status` | string | 否 | 记录状态，多值用逗号分隔 |
| `trigger_source` | string | 否 | 触发来源 |
| `start_time` / `end_time` | string | 否 | ISO 8601 时间范围，默认最近 7 天，跨度上限 90 天 |

响应 `data`：

```json
{
  "items": [
    {
      "record_no": "NT20260910000001",
      "event_id": "9f1c2b3a-4d5e-6f70-8192-a3b4c5d6e7f8",
      "event_type": "order.shipped",
      "trigger_source": "EVENT",
      "user_id": "1024",
      "template_code": "ORDER_SHIPPED_EMAIL",
      "template_version": 2,
      "channel": "EMAIL",
      "provider": "SENDGRID",
      "recipient_masked": "b***@example.com",
      "subject": "您的订单 SO20260910000001 已发货",
      "status": "DELIVERED",
      "retry_count": 0,
      "provider_message_id": "sg_msg_8f2c1a",
      "sent_at": "2026-09-10T09:15:02.310Z",
      "delivered_at": "2026-09-10T09:15:07.882Z",
      "created_at": "2026-09-10T09:15:01.900Z"
    }
  ],
  "next_cursor": "MTgwMDAwMDAwMDAwMDAwMDAwMQ==",
  "has_more": true
}
```

排序固定为 `id DESC`（雪花 ID 时间有序）。查询实现：`WHERE id < :cursor AND ... ORDER BY id DESC LIMIT :limit + 1`，返回条数 > `limit` 时截断并置 `has_more = true`。

> 收件人一律返回掩码。若客服确需查看完整收件人，本期不支持，需另立带审计的接口（NFR-SE-009）。

#### R2 GET `/api/v1/admin/notification-records/{record_no}`

在列表字段基础上追加：`render_variables`（验证码类已脱敏）、`rendered_content`（若开启落库且非验证码类）、`last_error_code`、`last_error_message`、`next_retry_at`、`parent_record_no`、`trace_id`、`template_snapshot`（发送时模板版本的标题/正文，用于回答"当时发了什么"）。

错误码：`NOT-4003`（记录不存在，404）。

#### R3 POST `/api/v1/admin/notification-records/{record_no}/resend`

请求体：

```json
{
  "channel": "EMAIL",
  "recipient": "buyer@example.com",
  "reason": "用户反馈未收到发货通知",
  "async": false
}
```

语义：

- **不修改原记录**，而是新建一条记录（`trigger_source = MANUAL`、`parent_record_no` 指向原记录），保留完整审计链
- `channel` 省略时沿用原渠道；显式指定可换渠道（如原短信失败改发邮件）
- `recipient` 省略时使用原记录解密后的收件人；显式指定时以请求为准
- `async = false`：同步执行，最长等待 3 秒；`async = true`：建 `REPLENISH` 补发任务，立即返回 `202`

状态限制：原记录状态为 `SENDING` 时返回 `NOT-5006`（409）；`SENT` / `DELIVERED` 允许重发（用户可能确实没收到），但需在 `reason` 中说明。

响应：`202` 与 `{"record_no": "NT20260910000012", "status": "PENDING", "parent_record_no": "NT20260910000001"}`。

#### R4 GET `/api/v1/admin/notification-records/statistics`

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `start_date` / `end_date` | date | 是 | 日期范围，跨度上限 366 天 |
| `channel` | string | 否 | 渠道 |
| `event_type` | string | 否 | 事件类型 |
| `group_by` | string | 否 | `date`（默认）/ `channel` / `event_type` |

数据源为 `notification_stats_daily`（T+1）。若查询范围包含当日，当日数据由实时聚合补充，响应中标注 `is_realtime: true`。

### 3.4 用户通知偏好接口

#### P1 GET `/api/v1/users/me/notification-preferences`

鉴权：登录即可，`user_id` 一律取 `X-User-Id`，忽略任何请求参数中的用户标识。

响应 `data`：

```json
{
  "marketing_email_enabled": true,
  "marketing_sms_enabled": true,
  "unsubscribed_at": null,
  "transactional_notice": "交易类通知（订单、支付、发货、退款）不可关闭",
  "updated_at": "2026-09-10T08:00:00.000Z"
}
```

用户无偏好记录时返回默认值（`true` / `true`），不写库。

#### P2 PUT `/api/v1/users/me/notification-preferences`

请求体：

```json
{
  "marketing_email_enabled": false,
  "marketing_sms_enabled": true
}
```

规则：

- 只接受上述两个字段；请求体中出现任何交易类字段（如 `order_email_enabled`）→ `COMMON-1001`（400），`details` 说明"交易类通知不可关闭"
- 显式传入 `unsubscribe_all: true` → 一次性将两个营销开关置 false 并写 `unsubscribed_at`、`source = USER`
- upsert 语义：无记录则插入，有记录则更新
- 写库后立即删除缓存 `notification:pref:{user_id}`（先写库、再删缓存）
- 返回 `200` + 更新后的完整偏好对象

### 3.5 验证码接口

#### V1 POST `/api/v1/notifications/verification-code`

**调用方**：用户服务（注册 FR-US-002、找回密码 FR-US-005、绑定手机）。验证码由用户服务生成与校验，通知服务只做同步投递。

鉴权（二选一，满足其一即可）：

| 调用路径 | 凭证 | 说明 |
|---|---|---|
| 服务间直连 | `X-Internal-Token` | 用户服务内网调用，网关不暴露；无需风控令牌 |
| 网关转发 | `X-Captcha-Token` | 前端先通过风控（图形验证码/行为验证）获得的一次性令牌，60 秒有效，用后失效 |

请求体：

```json
{
  "scene": "REGISTER",
  "channel": "SMS",
  "recipient": "+8613800138000",
  "code": "483921",
  "user_id": "1024",
  "expires_minutes": 5,
  "idempotency_key": "user-service:register:+8613800138000:202609100830"
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `scene` | string | 是 | `REGISTER` / `RESET_PASSWORD` / `BIND_PHONE` / `LOGIN_2FA`，用于选择模板与限流策略 |
| `channel` | string | 是 | `SMS` / `EMAIL` |
| `recipient` | string | 是 | 手机号（E.164）或邮箱 |
| `code` | string | 是 | 验证码明文，4~8 位数字；**不落库、不落日志** |
| `user_id` | string | 否 | 注册场景可空；为空时按收件人维度限流 |
| `expires_minutes` | int | 否 | 有效期，仅用于渲染文案，默认 5 |
| `idempotency_key` | string | 否 | 幂等键，60 秒内重复请求返回首次结果 |

响应 `200`：

```json
{
  "code": "OK",
  "message": "success",
  "data": {
    "record_no": "NT20260910000031",
    "channel": "SMS",
    "provider": "TWILIO",
    "status": "SENT",
    "degraded": false,
    "provider_message_id": "SM0a1b2c3d",
    "expires_at": "2026-09-10T08:35:00.000Z"
  },
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "timestamp": "2026-09-10T08:30:00.123Z"
}
```

降级场景：短信渠道不可用或配额耗尽但邮件可用（且 `scene` 允许）→ 返回 `200` 且 `channel = "EMAIL"`、`degraded = true`，并在 `message` 中提示"短信通道繁忙，已通过邮件发送"。若两渠道均不可用 → 返回 `NOT-7001`/`NOT-7002`（502），调用方必须向用户提示失败而不是静默成功。

错误码：`NOT-6002`（60 秒内重复请求）、`NOT-6003`（收件人当日超限）、`NOT-6004`（IP 维度超限）、`NOT-1005`（收件人格式非法）、`NOT-2001`（风控令牌无效）、`NOT-7001`/`NOT-7002`（渠道不可用）。

安全约束：

- 响应中**不得**区分"该手机号已注册/未注册"，避免账号枚举
- 明文验证码只存在于单次请求内存中，禁止写日志、禁止进 `render_variables`、禁止进 `rendered_content`
- 该路径在网关单独配置更严格的限流（见 6.7）

### 3.6 SendGrid 回执回调

#### E1 POST `/api/v1/notifications/webhooks/sendgrid`

鉴权：PUBLIC（网关白名单），但必须校验 SendGrid 事件回调签名（`X-Twilio-Email-Event-Webhook-Signature` + `X-Twilio-Email-Event-Webhook-Timestamp`），签名无效或时间戳超出 5 分钟窗口则拒绝（`COMMON-2002`），防止伪造回执。

请求体为 SendGrid 事件数组（平台只消费以下事件）：`delivered` → 置 `DELIVERED` 并写 `delivered_at`；`bounce` / `dropped` / `spamreport` → 置 `FAILED`，`last_error_code = NOT-7001`，原因截断写入 `last_error_message`，并触发告警；其余事件忽略。

匹配规则：用事件中的 `sg_message_id`（取其 `xxx.filter` 前的部分）匹配 `notification_records.provider_message_id`。

幂等：置位操作带状态前置条件（`WHERE status = 'SENT'`），重复回执不改变已终态记录，直接返回 `200`。

响应：恒返回 `200`（`{"code":"OK"}`），避免 SendGrid 重试风暴；处理失败记录日志与告警。

### 3.7 内部接口

#### I1 POST `/internal/v1/notifications/send`

**这是例外通道，不是常规通道。** 主流程一律发事件，理由见 4.1。

请求体：

```json
{
  "template_code": "ORDER_CREATED_EMAIL",
  "recipient": {"user_id": "1024", "email": "buyer@example.com"},
  "variables": {"order_no": "SO20260910000001", "total_amount": "199.00", "currency": "CNY"},
  "idempotency_key": "order-service:SO20260910000001:created",
  "requires_immediate": true
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `template_code` | string | 是 | 模板编码，决定渠道 |
| `recipient` | object | 是 | 至少给出 `user_id`、`email`、`phone` 之一；给 `user_id` 时由本服务回查用户服务补齐 |
| `variables` | object | 是 | 变量键必须覆盖模板的 required 变量 |
| `idempotency_key` | string | 是 | 调用方生成的幂等键，24 小时内重复请求返回首次结果 |
| `requires_immediate` | boolean | 否 | `true` 时同步等待第三方受理（预算 2 秒）；`false` 时立即返回 `202` 并异步发送 |

响应：同步成功返回 `200` + `{"record_no": "...", "status": "SENT", "channel": "SMS", "degraded": false}`；超时预算则返回 `202` + `{"record_no": "...", "status": "PENDING"}`，由补发任务兜底。

错误码：`NOT-4001`（未知模板编码）、`NOT-1004`（变量缺失）、`NOT-5002`（模板未启用）、`NOT-7001`/`NOT-7002`（渠道不可用且无法降级）、`COMMON-2002`（内网令牌无效）。

## 4. 内部接口设计

### 4.1 为什么主流程应该发事件而不是调用 `/internal/v1/notifications/send`

| 维度 | 发事件（推荐） | 同步调 `/internal/v1/notifications/send` |
|---|---|---|
| 主流程阻塞 | 不阻塞，发件箱投递与业务同事务，响应时间不受通知服务影响 | 阻塞，通知服务或第三方慢会直接抬高下单/支付耗时（违反 NFR-PF-002） |
| 可用性耦合 | 通知服务宕机只造成事件堆积，恢复后补消费（AC-07） | 通知服务宕机导致调用方失败或需自行降级，故障跨服务传播 |
| 事务边界 | 与业务数据同库同事务，保证"业务成功则事件不丢" | 业务事务已提交后调用，调用失败即通知丢失，需要额外补偿 |
| 重试与死信 | 由 MQ 统一退避重试 + 死信 + 人工重放 | 调用方必须自己实现重试、超时、熔断，每个服务重复一遍 |
| 语义 | 事件即事实，"订单已发货"这件事必然发生 | 命令式调用，把通知服务的内部实现暴露给调用方 |

**结论**：`/internal/v1/notifications/send` 只服务于**必须立即知道投递结果**的极少数场景：

1. 用户服务注册/找回密码时同步发验证码（V1 接口，见 6.7）——这个走 `/api/v1/notifications/verification-code`，不走 I1
2. 后台客服在售后页面即时补发一次通知，且需要当场看到成功/失败
3. 运维脚本按用户投诉补发历史通知

其余场景（尤其订单、支付）**必须发事件**。若发现某服务频繁调用 I1，应在评审中要求其改为发事件，必要时补充标准事件目录。

### 4.2 本服务依赖的内部接口

以下接口由用户服务提供，本服务为调用方，契约需与用户服务详细设计对齐：

#### GET `/internal/v1/users/{user_id}/contact`

| 项 | 内容 |
|---|---|
| 用途 | 事件 payload 只有 `user_id` 时解析收件人联系方式与昵称 |
| 鉴权 | `X-Internal-Token` |
| 超时 | 连接 1s、读取 3s（通用约定 11.1） |
| 重试 | 最多 2 次指数退避（只读查询），仍失败则抛 `TransientError` 交 MQ 重试 |
| 缓存 | 本服务侧缓存 15 分钟，见 7.1 |

响应 `data`：

```json
{
  "user_id": "1024",
  "email": "buyer@example.com",
  "phone": "+8613800138000",
  "nickname": "小明",

  "email_verified": true,
```

字段缺失（如 `phone` 为 `null`）表示用户未绑定该联系方式，属正常业务返回，不算调用失败。用户不存在返回 `COMMON-4001`，本服务按"收件人缺失"处理（落 `SKIPPED` 记录并缓存空值 60 秒防穿透）。

## 5. 事件设计

### 5.1 概述

- **发布事件**：无（终端服务）。关于是否新增"通知发送失败"事件的讨论见 5.4
- **订阅事件**：8 个，全部来自通用约定 10.3 标准事件目录
- **队列声明**：`notification.{event_type}`，如 `notification.order.shipped`
- **死信**：每队列 DLX `ecommerce.events.dlx`，死信队列 `notification.{event_type}.dlq`

### 5.2 队列与绑定

| 队列名 | Routing Key | Prefetch | 说明 |
|---|---|---|---|
| `notification.user.registered` | `user.registered` | 10 | 欢迎/验证邮件 |
| `notification.order.created` | `order.created` | 10 | 下单确认 |
| `notification.order.paid` | `order.paid` | 10 | 支付成功 |
| `notification.order.cancelled` | `order.cancelled` | 10 | 订单取消 |
| `notification.order.shipped` | `order.shipped` | 10 | 发货通知 |
| `notification.payment.failed` | `payment.failed` | 10 | 支付失败 |
| `notification.payment.refunded` | `payment.refunded` | 10 | 退款通知 |
| `notification.stock.low` | `stock.low` | 5 | 低库存预警（运营） |

所有队列均可配置 `x-dead-letter-exchange: ecommerce.events.dlx`，绑定到 `ecommerce.events`（topic），持久化队列。

**顺序性说明**：通用约定要求"同一订单的事件保证顺序，按 `order_no` 作为分区键路由到同一队列"。本服务为终端服务，通知之间无状态依赖，即使 `order.paid` 先于 `order.created` 到达也各自独立发送；因此本服务**不依赖**顺序性，队列不设置单活消费者（允许并发消费提升吞吐）。同一消息内的多模板分发（如邮件 + 短信）在同一消费线程内**串行执行**，保证单事件内的处理顺序可预期。

### 5.4 关于"发布事件"的说明（建议暂不新增）

本服务当前不发布任何事件。是否新增 `notification.send_failed`（通知发送失败）事件，分析如下：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. 不新增（**推荐本期采用**） | 失败落 `notification_records`（`status = FAILED`），超限进 DLQ 表，通过 Alertmanager 告警通道与 `notification_stats_daily` 暴露 | 不扩大事件目录；告警是通知服务自己的职责，不需要绕一圈 MQ；避免新增事件带来的版本与消费方协商成本 | 告警体系需能读取通知服务的指标/表，而非订阅事件 |
| B. 新增 `notification.send_failed` | 生产者通知服务，消费者告警服务/运营服务；payload 含 `record_no`、`template_code`、`channel`、`recipient_masked`、`error_code`、`failed_at` | 与现有事件驱动告警体系一致 | 需要同步更新通用约定 10.3 事件目录；增加一个消费方；告警链路本身就依赖 MQ，MQ 故障时告警失效 |

**本期决策**：采用方案 A，不新增事件，因此**无需修改通用约定**。若后续确需方案 B，必须走以下流程，不得在实现中擅自投递未登记的事件：

1. 在 `00-通用约定.md` 10.3 节"标准事件目录"中新增一行：

   | event_type | 生产者 | 消费者 | payload 核心字段 |
   |---|---|---|---|
   | `notification.send_failed` | 通知服务 | 告警服务 | `record_no`、`template_code`、`channel`、`error_code`、`failed_at` |

2. 在通用约定 10.4 节说明通知服务需要引入事务性发件箱（`outbox_events` 表）
3. 同步更新本文档的 2.1 表清单（新增发件箱表）与本章
4. 与告警服务确认消费幂等与告警去重策略

另有一项**消费侧**建议（同样需走变更流程）：本服务依赖 15 分钟 TTL 兜底用户联系方式变更，若需要即时失效，建议由用户服务新增 `user.contact_updated` 事件（payload：`user_id`、字段名、变更时间，**不含联系方式明文**）。该事件需同步登记进通用约定 10.3。

### 5.5 消费幂等与重试编排

**幂等**（三层，逐层兜底）：

| 层级 | 机制 | 作用 |
|---|---|---|
| 第一层 | Redis `notification:event:{event_id}`（SET NX EX 7 天） | 快速拦截重复投递，命中即 ack 并记 debug 日志 |
| 第二层 | `notification_records` 部分唯一索引 `(event_id, template_code, channel)` | 数据库层保证同事件同模板同渠道不重复落库 |
| 第三层 | 消费前检查已有记录状态 | 已 `SENT`/`DELIVERED` 直接短路；`FAILED`/`PENDING` 则继续重试 |

第一层的写入时机是**处理成功之后**：处理失败时删除该键，使 MQ 重试能重新进入处理流程（否则重试会被自己误判为重复）。第二层才是真正的幂等保底。

**重试编排**（三段式，与通用约定 10.4 的 `1s/5s/30s/2m/10m` 对齐）：

```
[第三方调用失败]
   │
   ├─ 可重试错误（超时 / 5xx / 429）
   │     ├─ 本地重试：最多 2 次，退避 0.5s、2s（含 ±30% 抖动）
   │     │     └─ 成功 → 结束
   │     └─ 本地重试耗尽 → 记录置 PENDING，抛出异常，nack 不 ack
   │           └─ 重发布到 ecommerce.events.retry，routing key = retry.{n}.{event_type}
   │                 └─ 落到 notification.retry.{1s|5s|30s|2m|10m}（TTL 队列）
   │                       └─ TTL 到期 DLX 回 ecommerce.events → 回到主队列重试
   │                             └─ 第 5 次仍失败 → 进 notification.{event_type}.dlq
   │                                   └─ DLQ 消费者落 notification_dead_letters + 告警
   │
   ├─ 不可重试错误（收件人格式非法 / 退订 / 模板渲染失败 / 模板停用）
   │     └─ 直接落 FAILED 或 SKIPPED（带错误码），不重试，必要时告警
   │
   └─ 依赖不可用（用户服务超时 / 渠道熔断 / 配额耗尽）
         └─ 抛 TransientError 交 MQ 重试；若判断恢复时间超出 MQ 时间窗
               └─ 落 notification_retry_tasks（scheduled_at = 未来时间），由定时任务补发
```

**MQ 重试队列拓扑**（每个消费队列一组）：

```
ecommerce.events (topic)
   │  routing key = event_type
   ▼
notification.order.shipped  ──失败nack/重发布──▶  ecommerce.events.retry (topic)
   ▲                                                   │ routing key = retry.1.order.shipped
   │                                                   ▼
   │                                       notification.retry.1s  (TTL 1s,  DLX=ecommerce.events)
   │                                       notification.retry.5s  (TTL 5s)
   │                                       notification.retry.30s (TTL 30s)
   │                                       notification.retry.2m  (TTL 2m)
   │                                       notification.retry.10m (TTL 10m)
   │                                                   │ TTL 到期
   └───────────────────────────────────────────────────┘
   │ x-dead-letter-exchange: ecommerce.events.dlx
   ▼
notification.order.shipped.dlq  ──▶ DLQ 消费者 ──▶ notification_dead_letters + 告警
```

重试次数从消息头 `x-death`（RabbitMQ 自动累积）或自定义头 `x-retry-count` 读取，二者取大值。选择"应用层重发布 + TTL 队列"而不是 `x-delayed-message` 插件，是为了不引入额外插件依赖，Docker Compose 与生产环境行为一致；队列数量为 `5 × 8 = 40` 个，可接受。若后续队列数继续增长，可改用 quorum queue 的 `x-delivery-limit` + 固定退避，或将 8 个通知队列合并为 1 个（以 `event_type` 分发）——本期不做。

**DLQ 消费者**：独立部署的消费者进程订阅 `notification.*.dlq`，职责是把消息落 `notification_dead_letters` 并触发告警，**不直接重放**——重放必须由人工在看清楚根因后通过 D2 接口触发，避免故障期间自动重放造成二次雪崩。

### 5.6 逐事件处理说明

#### `user.registered`

- payload：`user_id`、`account`、`email`、`phone`、`nickname`
- 处理：收件人**直接取 payload**，不调用户服务（避免刚注册完调用用户服务读不到数据的时序问题）
- 变量：`buyer_nickname`（payload.nickname，可空，默认"顾客"）、`account`、`registered_at`（取信封 `occurred_at`）、`verify_url`（由配置 `NOT_SITE_BASE_URL` + `user_id` 拼接；**URL 模板来自配置，不由事件字段拼接**，防 SSRF/开放重定向）
- 渠道：邮件必发；短信仅在 `USER_WELCOME_SMS` 启用时发送
- 注意：本事件通常与用户服务发出的验证码邮件（V1）并存，二者不冲突

#### `order.created`

- payload：`order_no`、`user_id`、`total_amount_cents`、`currency`、`expires_at`、`items[]`（`sku_id`、`quantity`）
- 处理：收件人经 `user_id` → 用户服务；变量 `total_amount` = `total_amount_cents / 100` 格式化（`199.00`）、`currency`、`expires_at`（本地化展示）、`item_count` = `sum(items[].quantity)`
- **不渲染商品名称**：事件中只有 `sku_id`，若为展示商品名而回查商品目录，会引入新依赖与新的失败点。本期只渲染订单号、金额、件数与支付截止时间，正文附订单页链接

#### `order.paid`

- payload：`order_no`、`user_id`、`paid_at`、`items[]`
- 变量：`order_no`、`paid_at`、`pay_amount`（若后续需要金额，需订单服务在事件中补充——本期不补充，正文只写"支付成功"并给订单页链接）
- 说明：`payment.succeeded` 由订单服务消费并发出 `order.paid`，本服务只消费 `order.paid`，避免重复通知

#### `order.cancelled`

- payload：`order_no`、`user_id`、`reason`、`items[]`
- 变量：`order_no`、`cancel_reason`（`reason` 为后端枚举/文案，直接渲染；**若该字段可能含用户输入，必须经 HTML 转义**）、`cancelled_at`
- 预占库存释放失败导致取消失败时不会有该事件，本服务无需判断

#### `order.shipped`

- payload：`order_no`、`user_id`、`carrier`、`tracking_no`、`shipped_at`
- 变量：`order_no`、`carrier`（物流公司名）、`tracking_no`（**必须完整渲染，不可截断**）、`shipped_at`、`tracking_url`（当 `carrier` 命中配置的物流公司→查询 URL 模板映射时生成；未命中则不渲染 URL，模板中用 optional 变量处理）
- 物流公司与单号均为发货人员录入的**用户可控内容**，必须转义（见 10.4）

#### `payment.failed`

- payload：`payment_no`、`order_no`、`reason`、`failed_at`
- 变量：`order_no`、`fail_reason`（第三方返回的原因需映射为可展示文案；未映射到则使用通用文案"支付未完成"）、`retry_payment_url`
- 语义：这是"支付尝试失败"，不是订单关闭；正文需引导用户重新支付

#### `payment.refunded`

- payload：`refund_no`、`payment_no`、`order_no`、`amount_cents`、`refunded_at`
- 变量：`order_no`、`refund_amount`（格式化）、`refunded_at`、`arrival_expectation`（配置文案，如"1-7 个工作日"）
- 注意：可能是部分退款，正文措辞需避免"全额退回"

#### `stock.low`

- payload：`sku_id`、`spu_title`、`spec_name`、`available`、`threshold`
- 收件人：配置项 `NOT_OPS_ALERT_EMAILS` / `NOT_OPS_ALERT_PHONES`，**不调用户服务**
- 变量：`spu_title`、`spec_name`、`sku_id`、`available`、`threshold`、`alert_time`
- 该事件的去重：同一 SKU 在短时间内可能反复触发，本服务对 `stock.low` 增加**告警抑制窗口**（Redis `notification:suppress:stock_low:{sku_id}`，TTL 30 分钟），窗口内重复事件只落一条 `SKIPPED` 记录（`last_error_code = NOT-6005`），避免打扰运营
- 该事件频率可能很高，故队列 prefetch 设为 5，且不发送短信（默认停用）

## 6. 核心业务流程

### 6.1 主链路：事件消费 → 发送

```
MQ 投递 → 信封校验 → 幂等抢占 → 逐模板分发
   ├─ 模板解析（缓存）
   ├─ 渠道开关检查 → 停用则落 SKIPPED
   ├─ 收件人解析（payload 或用户服务 + 缓存）
   ├─ 用户偏好判定（仅 MARKETING 受影响）
   ├─ 变量构建 + required 校验 → 缺失则落 SKIPPED（拒绝发送）
   ├─ 记录落库（幂等 upsert）
   ├─ 渲染 → 发送（本地重试 + 降级）
   └─ 结果落库（SENT / FAILED / SKIPPED）
```

### 6.2 消费主链路伪代码

```python
# app/events/consumers/notification_consumer.py
import asyncio, logging
from app.core.errors import TransientError, PermanentError

log = logging.getLogger(__name__)

@consumer(queue="notification.{event_type}", prefetch=10, manual_ack=True)
async def handle_message(envelope: dict, delivery) -> None:
    """事件消费入口。抛异常 = 触发 MQ 退避重试；正常返回 = ack。"""
    event_id = envelope.get("event_id")
    event_type = envelope.get("event_type")
    payload = envelope.get("payload") or {}
    occurred_at = envelope.get("occurred_at")
    trace_id = envelope.get("trace_id")
    ctx = {"trace_id": trace_id, "event_id": event_id, "event_type": event_type}

    # ---- 1. 信封校验（结构非法属不可重试错误，直接落死信并 ack，避免毒消息阻塞队列）----
    if not event_id or not event_type or not isinstance(payload, dict):
        await dead_letter_service.save_raw(
            queue_name=delivery.queue, envelope=envelope,
            error_code="NOT-8002", error_message="invalid event envelope",
        )
        await delivery.ack()
        return

    # ---- 2. 幂等抢占（第一层）----
    claimed = await idempotency.claim(event_id, ttl=7 * 24 * 3600)
    if not claimed:
        log.debug("duplicate event skipped", extra=ctx)
        await delivery.ack()
        return

    try:
        # ---- 3. 逐模板串行分发（一个事件可能对应邮件 + 短信）----
        template_codes = await template_router.resolve(event_type)  # 读缓存，见 7.1
        if not template_codes:
            log.warning("no template bound to event, ignored", extra=ctx)
            await idempotency.mark_done(event_id)
            await delivery.ack()
            return

        for template_code in template_codes:
            #  不可重试的业务性跳过在内部消化，不向上抛
            #  可重试的依赖故障向上抛，中断本次消费
            await dispatch_one(template_code, envelope, delivery)

    except TransientError as exc:
        # 关键：删除幂等键，使 MQ 重试可以重新进入处理；DB 唯一索引仍是最终兜底
        await idempotency.release(event_id)
        log.warning("transient failure, hand over to MQ retry",
                    extra={**ctx, "error": str(exc), "retry_count": delivery.retry_count})
        raise                       # 不 ack → 重发布到 retry exchange
    except Exception as exc:
        await idempotency.release(event_id)
        log.exception("unexpected failure", extra=ctx)
        raise

    await idempotency.mark_done(event_id)
    await delivery.ack()


async def dispatch_one(template_code: str, envelope: dict, delivery) -> None:
    event_id = envelope["event_id"]
    event_type = envelope["event_type"]
    payload = envelope["payload"]
    trace_id = envelope.get("trace_id")
    occurred_at = envelope.get("occurred_at")
    ctx = {"trace_id": trace_id, "event_id": event_id, "template_code": template_code}

    # ---- 3.1 模板解析（含缓存；模板不存在/未启用 → 终态，不重试）----
    template = await template_service.get_enabled_template(template_code)
    if template is None:
        await record_service.create_terminal(
            event_id=event_id, event_type=event_type, template_code=template_code,
            channel=await template_service.guess_channel(template_code),
            status="SKIPPED", error_code="NOT-5002",
            error_message="模板不存在或未启用", trace_id=trace_id,
        )
        return

    # ---- 3.2 渠道开关（FR-NOT-006）----
    if not await channel_service.is_enabled(template.channel):
        await record_service.create_terminal(
            event_id=event_id, event_type=event_type, template=template,
            status="SKIPPED", error_code="NOT-5002",
            error_message=f"渠道 {template.channel} 已停用", trace_id=trace_id,
        )
        return

    # ---- 3.3 收件人解析（payload 优先，其次用户服务；失败抛 TransientError）----
    contact = await recipient_resolver.resolve(event_type, payload, template.channel)
    if contact is None:
        # 用户未绑定该联系方式 / 用户不存在：业务性缺失，终态并告警（交易类通知缺失需要人工介入）
        await record_service.create_terminal(
            event_id=event_id, event_type=event_type, template=template,
            user_id=payload.get("user_id"), status="SKIPPED",
            error_code="NOT-5004", error_message="收件人联系方式缺失", trace_id=trace_id,
        )
        await notifier.alert(
            title="通知收件人缺失",
            detail=f"event={event_type} template={template_code} user_id={payload.get('user_id')}",
            level="warning" if template.category == "TRANSACTIONAL" else "info",
        )
        return

    # ---- 3.4 用户偏好判定（仅 MARKETING 受影响；交易类永不受影响）----
    if not await preference_service.is_allowed(
        category=template.category, channel=template.channel, user_id=contact.user_id
    ):
        await record_service.create_terminal(
            event_id=event_id, event_type=event_type, template=template,
            user_id=contact.user_id, recipient=contact.recipient_for(template.channel),
            status="SKIPPED", error_code="NOT-5003",
            error_message="用户已关闭该营销类通知", trace_id=trace_id,
        )
        return

    # ---- 3.5 告警抑制窗口（目前仅 stock.low 使用）----
    suppression_key = template.suppression_key(payload)   # 如 stock_low:{sku_id}
    if suppression_key and await suppressor.is_suppressed(suppression_key):
        await record_service.create_terminal(..., status="SKIPPED",
                                             error_code="NOT-6005",
                                             error_message="命中告警抑制窗口")
        return

    # ---- 3.6 变量构建 + required 校验（缺失 → 拒绝发送，绝不发半截内容）----
    try:
        variables = variable_builder.build(
            template=template, payload=payload, contact=contact,
            occurred_at=occurred_at, event_type=event_type,
        )
    except VariableMissingError as exc:
        await record_service.create_terminal(
            event_id=event_id, event_type=event_type, template=template,
            user_id=contact.user_id, recipient=contact.recipient_for(template.channel),
            status="SKIPPED", error_code="NOT-5004",
            error_message=f"必填变量缺失: {','.join(exc.missing)}", trace_id=trace_id,
            render_variables=exc.partial_variables,
        )
        await notifier.alert(title="通知模板变量缺失，已拒绝发送",
                             detail=f"template={template_code} missing={exc.missing}",
                             level="error")
        return

    # ---- 3.7 记录落库（幂等：唯一索引 + 状态判定）----
    record, created = await record_service.get_or_create(
        event_id=event_id, event_type=event_type, template=template,
        channel=template.channel, user_id=contact.user_id,
        recipient=contact.recipient_for(template.channel),
        render_variables=variables, trace_id=trace_id,
    )
    if not created:
        if record.status in ("SENT", "DELIVERED", "SKIPPED"):
            log.debug("record already settled, short-circuit",
                      extra={**ctx, "record_no": record.record_no, "status": record.status})
            return                      # 部分成功后的重试，短路已完成的那条
        if record.retry_count >= record.max_retry_count:
            await record_service.mark_failed(record, "NOT-7001", "重试次数耗尽")
            await notifier.alert(title="通知重试次数耗尽", detail=record.record_no, level="error")
            return

    # ---- 3.8 渲染（渲染器为最小实现，见 6.3）----
    try:
        rendered = renderer.render(template, variables)      # -> RenderedContent(subject, body)
    except (VariableMissingError, TemplateSyntaxError) as exc:
        # 渲染失败属不可重试错误（模板内容问题，重试无意义）
        await record_service.mark_skipped(record, "NOT-8001", f"渲染失败: {exc}")
        await notifier.alert(title="通知模板渲染失败", detail=record.record_no, level="error")
        return

    await record_service.mark_sending(record, rendered)

    # ---- 3.9 发送（本地重试 + 降级；可重试失败向上抛给 MQ）----
    await send_executor.execute(record, rendered, template)
```

### 6.3 模板渲染与变量校验

**变量契约**（`variables_schema`，JSONB 数组）：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `name` | string | 是 | 变量名，`^[a-z][a-z0-9_]{0,31}$` |
| `type` | string | 是 | `STRING` / `NUMBER` / `MONEY` / `DATETIME` / `URL` |
| `required` | boolean | 是 | 为 true 时缺失即拒绝发送 |
| `source` | string | 是 | `EVENT`（取 payload）/ `CONTACT`（收件人信息）/ `CONFIG`（配置项）/ `SYSTEM`（系统生成，如 `site_name`） |
| `max_length` | int | 否 | 渲染后长度上限，超出则截断并告警（`tracking_no` 等关键字段不允许截断，见下） |
| `default` | string | 否 | optional 变量的默认值；`required = true` 时禁止设置 |
| `description` | string | 否 | 说明，供后台展示 |

**占位符语法**（刻意保持最小集合）：

| 语法 | 含义 |
|---|---|
| `{{var}}` | 变量替换 |
| `{{var\|default:文本}}` | 变量缺失或为空时使用默认文本（等价于 optional 变量） |

**不支持的语法**（会直接判定为模板语法错误，发布时即拒绝）：表达式运算、函数调用、属性/下标访问（`{{a.b}}`、`{{a[0]}}`）、过滤器管道（除 `default` 外）、`{% %}` 语句块、`{# #}` 注释、`include`/`extends`、任何形式的循环与条件。

**渲染器实现选型**：使用自研最小渲染器（正则匹配 `{{name}}` / `{{name|default:...}}` 后按白名单变量名查表替换），**不使用 Jinja2 等通用模板引擎的求值能力**。

| 方案 | 注入风险 | 灵活性 | 结论 |
|---|---|---|---|
| Jinja2 `SandboxedEnvironment` + 白名单过滤器 | 低（沙箱已被多次绕过） | 高 | 不采用 |
| 自研最小渲染器 | 极低（语法上不存在可执行结构） | 仅占位符替换，足够 | **采用** |
| `str.format` / f-string | 高（可访问对象属性与 `__globals__`） | 低 | 禁止 |

**变量缺失处理**（对应 FR-NOT-005 异常流"模板变量缺失 → 拒绝发送并记录"）：

```python
def build_and_validate(template: TemplateVersion, payload: dict, contact: Contact,
                       occurred_at: str, event_type: str) -> dict:
    variables, missing, defaults_used = {}, [], []
    for spec in template.variables_schema:
        raw = RESOLVERS[spec.source](spec.name, payload, contact, occurred_at, event_type)
        if raw is None or raw == "":
            if spec.required:
                missing.append(spec.name)
                continue
            if spec.default is not None:
                variables[spec.name] = spec.default
                defaults_used.append(spec.name)
            else:
                variables[spec.name] = ""     # optional 且无默认值 → 空串（模板需自行容错）
            continue
        variables[spec.name] = coerce(spec.type, raw, spec.max_length)
    if missing:
        raise VariableMissingError(missing=missing, partial_variables=variables)
    return variables
```

规则：

- **required 变量缺失 → 抛 `VariableMissingError` → 不发送，落 `SKIPPED` 记录（`last_error_code = NOT-5004`）+ 告警**。绝不发送含未替换占位符或半截内容的消息
- optional 变量缺失 → 使用 `default`；无 `default` 则渲染为空串
- 渲染完成后做**兜底断言**：结果中不得残留 `{{` 或 `}}`，否则判为渲染失败并按不可重试错误处理（这是防御性检查，正常流程不会触发，用于兜住意外语法）
- `type` 转换：`MONEY` 由分为单位的整数转 `"199.00"`；`DATETIME` 由 ISO 8601 UTC 转 `"2026-09-10 17:15"`（按 `NOT_DISPLAY_TIMEZONE` 配置，默认 `Asia/Shanghai`）；`NUMBER` 转十进制字符串；`URL` 校验 scheme 必须为 `https`，且域名必须在配置白名单内（防 SSRF 与开放重定向）
- **关键字段不可截断**：`max_length` 超出时，若该变量在模板中标为 `TRUNCATE_FORBIDDEN`（`logistics` 类字段预置），则判为渲染失败并拒绝发送，避免发出错误单号

**模板版本管理**：

- 每次修改都产生新版本（T8），发布后（T10）版本内容在数据库层与应用层均不允许修改
- 发送记录冗余 `template_id` + `template_code` + `template_version`，R2 详情接口据此返回 `template_snapshot`，回答"这条通知当时用的什么模板"
- 模板缓存 Key 带版本号或整体失效（见 7.1），保证发布后立即生效
- 记录一旦生成，模板后续再改也不影响历史记录的追溯结果

### 6.4 收件人解析

```python
# app/services/recipient_resolver.py
class RecipientResolver:

    async def resolve(self, event_type: str, payload: dict, channel: str) -> Contact | None:
        # 路径一：事件 payload 直接带联系方式（user.registered）
        if direct := self._from_payload(payload, channel):
            return direct

        user_id = payload.get("user_id")
        if not user_id:
            return None

        # 路径二：查缓存（缓存的是加密值，取出后解密）
        cached = await self._get_cached(user_id)
        if cached is not None:
            if cached.is_not_found:              # 负缓存：用户不存在
                return None
            return cached.contact

        # 路径三：调用户服务内部接口
        try:
            data = await user_client.get_contact(user_id)     # 超时 1s/3s，内部重试 2 次
        except InternalServiceError as exc:
            # 可重试错误：抛给上层 → MQ 退避重试。
            # 绝不因取不到联系方式就把通知"静默丢弃"：交易类通知必须送达。
            raise TransientError(f"user contact lookup failed: {exc}") from exc
        except UserNotFoundError:
            await self._cache_not_found(user_id)      # TTL 60s，防穿透
            return None

        contact = Contact(
            user_id=user_id,
            email=data.get("email"),
            phone=data.get("phone"),
            nickname=data.get("nickname"),
        )
        await self._cache(user_id, contact)           # TTL 15 分钟
        return contact

    def _from_payload(self, payload, channel) -> Contact | None:
        if channel == "EMAIL" and payload.get("email"):
            return Contact(user_id=payload.get("user_id"), email=payload["email"], phone=None)
        if channel == "SMS" and payload.get("phone"):
            return Contact(user_id=payload.get("user_id"), email=None, phone=payload["phone"])
        return None
```

**调用失败的处理结论**：

| 失败类型 | 处理 | 理由 |
|---|---|---|
| 用户服务超时 / 5xx / 连接拒绝 | 抛 `TransientError`，MQ 退避重试（1s/5s/30s/2m/10m） | 联系方式是发送的必要条件，不能放弃；用户服务通常是短暂故障 |
| 用户服务返回 404（用户不存在） | 负缓存 60 秒 + 落 `SKIPPED` 记录 + 告警 | 重试无意义；用户被注销或数据异常需要人工确认 |
| 用户存在但未绑定手机号/邮箱 | 落 `SKIPPED` 记录，不重试 | 业务性缺失；交易类通知需告警（可能说明用户资料不完整影响触达） |
| 重试 5 次仍失败 | 进死信，人工重放（D2） | 通用约定 10.4 死信策略 |

**收件人缓存**：Key `notification:user_contact:{user_id}`，TTL 15 分钟（对齐通用约定 9.2 用户资料 TTL），值为加密后的联系方式（`{email_cipher, phone_cipher, nickname, key_id}`）。缓存的是密文而非明文，即使 Redis 被未授权访问也无法直接读取联系方式，代价是每次读取多一次对称解密（微秒级，可忽略）。

缓存失效：本期**无** `user.contact_updated` 事件，只能靠 15 分钟 TTL 自然失效。这意味着用户刚改完手机号后 15 分钟内到达的通知可能发到旧号码。对交易类通知，这个窗口可接受（用户在改号瞬间不会正好下单）；若要消除，需推动新增 `user.contact_updated` 事件（见 5.4 建议）。此外，管理端可提供运维级的缓存清除手段（`notification:user_contact:{user_id}` 直接 DEL）。

### 6.5 发送执行、错误分类与降级

```python
# app/services/send_executor.py
TRANSIENT_STATUS = {408, 425, 429, 500, 502, 503, 504}

class SendExecutor:

    async def execute(self, record, rendered, template) -> None:
        channel = template.channel

        # ---- 1. 渠道可用性：熔断 / 配额 / 全局开关 ----
        if await circuit.is_open(channel) or await quota.is_exhausted(channel):
            await self._handle_channel_unavailable(record, rendered, template, channel)
            return

        # ---- 2. 本地有限重试（短时抖动就地消化，避免把 MQ 重试额度浪费在小抖动上）----
        for attempt in range(1, settings.NOT_LOCAL_RETRY_MAX_ATTEMPTS + 1):   # 默认 2
            try:
                result = await self._provider_call(channel, record, rendered)
                await record_service.mark_sent(record, provider_message_id=result.message_id,
                                               provider=result.provider)
                await quota.increment(channel)
                await circuit.record_success(channel)
                return
            except TransientProviderError as exc:
                await circuit.record_failure(channel)
                if attempt < settings.NOT_LOCAL_RETRY_MAX_ATTEMPTS:
                    await asyncio.sleep(backoff(attempt) + jitter())   # 0.5s / 2s
                    continue
                # 本地重试耗尽 → 交 MQ
                await record_service.mark_pending(record, error_code=exc.code,
                                                  error_message=exc.message,
                                                  incr_retry=True)
                log.warning("local retry exhausted, escalate to MQ",
                            extra={"record_no": record.record_no, "channel": channel})
                raise TransientError(str(exc)) from exc        # 不 ack，触发 MQ 退避重试
            except PermanentProviderError as exc:
                # 2xx 但业务被拒（收件人非法、退订、内容被拒）→ 重试无意义
                await circuit.record_success(channel)
                await record_service.mark_failed(record, exc.code, exc.message)
                await notifier.alert(title="通知发送被第三方拒绝",
                                     detail=f"{record.record_no} {exc.code}", level="warning")
                return
            except Exception as exc:                            # 兜底：未知异常按可重试处理一次
                await record_service.mark_failed(record, "NOT-8002", str(exc)[:500])
                await notifier.alert(title="通知发送未知异常", detail=record.record_no, level="error")
                return

    async def _handle_channel_unavailable(self, record, rendered, template, channel) -> None:
        """渠道不可用：按 降级 → 补发队列 的顺序处理。"""
        fallback = await channel_service.get_fallback(channel)

        # 交易类通知：允许降级到备用渠道
        if fallback and template.category == "TRANSACTIONAL" \
                and await channel_service.is_enabled(fallback):
            await record_service.mark_skipped(record, "NOT-7004",
                                              f"渠道 {channel} 不可用，已降级至 {fallback}")
            await self._send_via_fallback(record, template, fallback)
            await notifier.alert(
                title="通知渠道降级",
                detail=f"{channel} → {fallback}，影响记录 {record.record_no}", level="warning")
            return

        # 降级不可用 → 落补发队列，等渠道恢复后重发（超过 MQ 重试时间窗的场景）
        await retry_task_service.schedule(
            record=record, task_type="RETRY_SEND",
            scheduled_at=utcnow() + timedelta(minutes=settings.NOT_CHANNEL_RETRY_DELAY_MINUTES),
        )
        await record_service.mark_pending(record, error_code="NOT-7004",
                                          error_message="渠道不可用，已进入补发队列")
        await notifier.alert(title="通知渠道不可用，已进入补发队列",
                             detail=f"channel={channel} record={record.record_no}", level="warning")

    async def _send_via_fallback(self, record, template, fallback: str) -> None:
        """降级发送：新建一条记录（保留双渠道审计链），复用同一组渲染变量换模板渲染。"""
        fallback_template = await template_service.get_enabled_by_event(
            event_type=template.event_type, channel=fallback)
        if fallback_template is None:
            await retry_task_service.schedule(record, "FALLBACK_CHANNEL",
                                              scheduled_at=utcnow() + timedelta(minutes=30))
            return
        contact = await contact_service.get(record.user_id)
        recipient = contact.recipient_for(fallback)
        if not recipient:
            await record_service.create_terminal(..., status="SKIPPED",
                                                 error_code="NOT-5004",
                                                 error_message="降级渠道收件人缺失")
            return
        new_record, _ = await record_service.get_or_create(
            event_id=record.event_id, template=fallback_template, channel=fallback,
            user_id=record.user_id, recipient=recipient,
            render_variables=record.render_variables, parent_record_no=record.record_no,
            trigger_source="SCHEDULED")
        rendered = renderer.render(fallback_template, record.render_variables)
        await self.execute(new_record, rendered, fallback_template)     # 递归一次，不会无限下降
```

**错误分类表**（实现时落到 `clients/error_classifier.py`，供所有渠道适配器复用）：

| 分类 | 判定条件 | 处理 | 举例 |
|---|---|---|---|
| 可重试 | 连接超时、读超时、HTTP 408/425/429/500/502/503/504、渠道客户端抛出的限流错误 | 本地重试 2 次 → MQ 退避重试 | SendGrid 502、Twilio 连接超时、HTTP 429 限流 |
| 不可重试 | HTTP 400/401/403/404/422、收件人格式非法、`unsubscribed`、`invalid_email`、内容被拒、模板渲染失败、required 变量缺失 | 直接落 `FAILED`/`SKIPPED`，不重试，告警 | Twilio 错误码 21211（收件人号码非法）、SendGrid 400 `invalid_email` |
| 依赖不可用 | 熔断开启、配额耗尽、渠道全局停用 | 降级 → 补发队列 → 告警 | 短信日配额耗尽 |
| 内部错误 | 本服务 DB/Redis 异常、渲染器抛出未预期异常 | 记录 + 告警；DB 异常向上抛触发 MQ 重试 | 连接池耗尽 |

**降级链**（对应 FR-NOT-006 异常流"第三方短信额度耗尽 → 降级为邮件并告警"）：

```
[交易类通知需要发送]
        │
        ├─ 首选渠道（模板定义的 channel）
        │     ├─ 可用 → 发送
        │     └─ 不可用（熔断 / 配额耗尽 / 全局停用 / 供应商 5xx 持续）
        │           ├─ 有降级渠道且模板支持（SMS → EMAIL）→ 换渠道发送，告警"渠道降级"
        │           └─ 降级渠道不可用
        │                 ├─ 邮件也不可用（SendGrid 故障）→ 落 notification_retry_tasks
        │                 │      （scheduled_at = now + NOT_CHANNEL_RETRY_DELAY_MINUTES）
        │                 │      → 定时任务在渠道恢复后补发（6.9 / 第 8 章）
        │                 └─ 通知告警"通知渠道全面不可用"，人工介入
        │
        └─ 营销类通知：不降级，直接跳过并落 SKIPPED（可接受的业务损失）
```

降级只改变送达渠道，**不改变渲染内容**（同一组 `render_variables` 换模板渲染），且降级产生的记录通过 `parent_record_no` 与原记录关联，两个渠道的送达情况都可追溯。

### 6.6 用户偏好判定

```python
# app/services/preference_service.py
async def is_allowed(category: str, channel: str, user_id: int | None) -> bool:
    # 交易类与运营类通知不受用户偏好约束（FR-NOT-009：交易类不可关闭）
    if category != "MARKETING":
        return True
    if user_id is None:
        return True

    pref = await get_cached(user_id)          # Key: notification:pref:{user_id}，TTL 30 分钟
    if pref is None:
        pref = await repo.find_by_user_id(user_id) or DEFAULT_PREF   # 无记录 = 全开
        await cache.set(user_id, pref, ttl=1800)

    if pref.unsubscribed_at is not None:
        return False
    return pref.marketing_email_enabled if channel == "EMAIL" else pref.marketing_sms_enabled
```

强制约束（服务端，不可绕过）：

- 交易类通知的判定依据是**模板的 `category` 字段**，而不是渠道或用户设置。`category = TRANSACTIONAL` 时 `is_allowed` 恒为 `True`
- 偏好接口（P2）不暴露交易类字段，请求体中出现即报错
- 数据库中不存在交易类开关列，即使有人直接改库也无法关闭交易类通知（只能停用模板或关闭渠道，后者会触发告警）
- 邮件底部附带退订链接（仅营销类模板渲染，由 `category = MARKETING` 决定是否渲染该区块），退订链接带签名参数，落地到退订接口后写 `marketing_*_enabled = false`

### 6.7 验证码同步链路

```
用户服务（注册/找回密码）
   │  生成验证码 + 存入自己的校验存储（用户服务独占）
   │
   ▼
POST /api/v1/notifications/verification-code    （同步，超时预算 3 秒）
   │
   ├─ 鉴权：X-Internal-Token 或 X-Captcha-Token
   ├─ 参数校验：scene / channel / recipient 格式 / code 长度
   ├─ 幂等：idempotency_key（Redis，60 秒）命中则返回首次结果
   ├─ 限流四道闸（见下表）——任一不过即 429，不发送
   ├─ 渲染 VCODE_SMS / VCODE_EMAIL 模板（code 只参与渲染，不落库）
   ├─ 渠道选择：SMS 不可用 → EMAIL（degraded = true）
   ├─ 落发送记录（render_variables.code 替换为 ******，rendered_content 恒为 NULL）
   └─ 调用第三方 → 返回 {record_no, status, provider_message_id}
```

**为什么会话式同步而不是事件**：用户点击"获取验证码"后必须在 1~3 秒内收到，且用户服务需要知道发送结果以决定是否提示"验证码已发送 / 发送失败请重试"。异步事件会使用户看到"已发送"但实际失败，破坏验证流程体验。这是通用约定 4.3 通信选择原则中"需即时结果"的典型场景，因此**允许**走同步。

**可靠性保障**：

| 措施 | 说明 |
|---|---|
| 本地重试 | 第三方超时/5xx 时在接口内部立即重试 1 次（不 sleep），总预算控制在 3 秒内 |
| 降级 | 短信不可用 → 邮件（`degraded = true`），返回成功 |
| 失败可见 | 两渠道均失败 → 返回 `NOT-7001`/`NOT-7002`（502），用户服务必须提示失败，**不得静默成功** |
| 不重试落库 | 若请求方已断开（客户端超时），发送记录仍保留，`status` 反映真实结果，便于排查"用户说没收到"的投诉 |
| 熔断保护 | 渠道连续失败熔断 30 秒，期间直接走降级，避免每个验证码请求都等超时 |

**限流设计**（四道闸，全部基于 Redis 原子计数；对应 FR-NOT-007 的可靠性边界与防刷要求）：

| 层级 | Key | 阈值 | TTL | 超限错误码 |
|---|---|---|---|---|
| L1 冷却 | `notification:vcode:cooldown:{recipient_hash}` | 同一收件人 60 秒 1 条 | 60 秒 | `NOT-6002` |
| L2 收件人日限 | `notification:vcode:daily:{recipient_hash}:{yyyymmdd}` | 10 条/日 | 至次日 00:00 + 1h | `NOT-6003` |
| L3 用户日限 | `notification:vcode:user:{user_id}:{yyyymmdd}` | 20 条/日 | 至次日 00:00 + 1h | `NOT-6003` |
| L4 IP 限流 | `notification:vcode:ip:{ip}:{yyyymmdd}` / `:hour:{yyyymm}` | 20 条/小时、50 条/日 | 对应周期 | `NOT-6004` |
| L5 渠道配额 | `notification:quota:SMS:{yyyymmdd}` | `channel_configs.daily_quota` | 至次日 00:00 + 1h | 走降级而非报错 |

实现要点：

- L1 用 `SET key 1 NX EX 60`，抢占失败即超限——**先抢占再发送**，防止并发重复请求都通过校验
- 若 L2/L3/L4 校验失败，需要把 L1 的抢占**回滚**（DEL），避免用户被"限流失败"后再等 60 秒
- L2/L3/L4 用 `INCR` + `EXPIRE`（首次设置 TTL），Redis 不可用时按"放行 + 告警"处理（可用性优先，因为网关与风控令牌已有一层防护），但 L1 在 Redis 不可用时降级为"放行"
- 收件人一律先归一化（手机号转 E.164、邮箱转小写）再计算 `recipient_hash`，避免通过 `Buyer@Example.com` 绕过限流
- 网关侧对该路径额外配置按 IP 的令牌桶限流（更外层的一道闸）

**安全约束**：

- `code` 明文只存在于本次请求的内存变量中，进程内不得写入任何日志（日志中间件对该字段做字段级脱敏，见 10.2）
- 落库时 `render_variables.code = "******"`，且**强制** `rendered_content = NULL`（不受 `NOT_RECORD_RENDERED_CONTENT` 配置影响）
- 接口响应不区分"手机号已注册/未注册"，防止账号枚举
- 若 `scene` 为 `RESET_PASSWORD`，短信正文中的验证码与场景文案由模板决定，**不得**回显用户提交的可控内容

### 6.8 手动重发流程

```
管理员点击"重发"
   │
   ├─ 校验：原记录存在？状态允许（非 SENDING）？
   ├─ 解密原记录收件人（或使用请求指定的收件人）
   ├─ 取当前生效模板版本重新渲染（或复用原记录的 render_variables）
   ├─ 新建记录：trigger_source = MANUAL, parent_record_no = 原 record_no
   ├─ 同步执行发送（async=false，预算 3 秒）或建 REPLENISH 任务（async=true）
   └─ 返回新记录信息；原记录保持不变
```

关键点：**不修改原记录**。重发产生新记录，审计链通过 `parent_record_no` 串联，避免"重发成功后原失败记录消失"导致对账困难。重发复用原 `render_variables`（而不是重新拉取业务数据），保证重发内容与首次一致；若原记录无 `render_variables`（历史数据或验证码类），则拒绝重发并提示改用测试发送。

### 6.9 补发任务执行流程

```python
# app/tasks/retry_pending_notifications.py
async def run_once() -> None:
    if not await lock.acquire("notification:lock:retry_scan", ttl=60):   # 多实例互斥
        return

    # 1) DB 补发队列：抢占一批到期任务（SKIP LOCKED 支持多实例并行）
    tasks = await retry_task_repo.claim_due(limit=200, now=utcnow())
    for task in tasks:
        try:
            record = await record_repo.get(task.record_id)
            if record.status in ("SENT", "DELIVERED", "SKIPPED"):
                await retry_task_repo.mark_done(task)               # 已被其他路径处理
                continue
            if task.task_type == "FALLBACK_CHANNEL":
                await send_executor.send_via_fallback(record, task.target_channel)
            else:
                template = await template_service.get_version(
                    record.template_code, record.template_version)   # 用原版本重发，内容一致
                rendered = renderer.render(template, record.render_variables)
                await send_executor.execute(record, rendered, template)
            await retry_task_repo.mark_done(task)
        except TransientError as exc:
            # 任务级退避：attempt 递增，scheduled_at 指数后移；超 max_attempts 置 CANCELLED + 告警
            await retry_task_repo.reschedule_or_cancel(task, str(exc))

    # 2) 悬挂记录回收：SENDING 超时（进程崩溃）的记录回退为 PENDING
    await record_repo.reset_stuck(status="SENDING",
                                  updated_before=utcnow() - timedelta(minutes=15))
```

## 7. 缓存设计

### 7.1 Key 清单

Key 命名遵循 `{服务名}:{实体}:{标识}[:{子标识}]`。

| Key | 值 | TTL | 写入时机 | 失效时机 | 用途 |
|---|---|---|---|---|---|
| `notification:event:{event_id}` | `"1"` | 7 天 | 事件消费成功后 | 消费失败时主动 DEL | 消费幂等第一层（通用约定第 6 章） |
| `notification:user_contact:{user_id}` | 加密 JSON `{email_cipher, phone_cipher, nickname, key_id}` | 15 分钟 | 首次调用用户服务成功后回填 | TTL 自然过期；运维可手动清除 | 收件人解析，降低跨服务调用 |
| `notification:user_contact:miss:{user_id}` | `"1"` | 60 秒 | 用户服务返回 404 | TTL | 负缓存防穿透（通用约定 9.3） |
| `notification:pref:{user_id}` | 偏好 JSON `{marketing_email_enabled, marketing_sms_enabled, unsubscribed_at}` | 30 分钟 | 首次查询后回填 | 用户修改偏好时**先写库再 DEL** | 偏好判定，避免每封通知查库 |
| `notification:template:{template_code}` | 启用模板 + 当前生效版本内容（含 `variables_schema`） | 1 小时 | 消费链路首次读取 | 模板创建/更新/发布/启停时 DEL | 模板解析（消费链路高频） |
| `notification:template_route:{event_type}` | 该事件对应的模板编码数组 | 1 小时 | 首次解析后回填 | 模板增删改时 DEL | 事件→模板映射，避免每事件查库 |
| `notification:quota:{channel}:{yyyymmdd}` | 当日已发送计数 | 至次日 00:30 | 每成功发送一次 INCR | TTL | 日配额控制与告警（80% 阈值） |
| `notification:vcode:cooldown:{recipient_hash}` | `"1"` | 60 秒 | 验证码请求抢占 | TTL / 限流失败时 DEL | 验证码 60 秒冷却 |
| `notification:vcode:daily:{recipient_hash}:{yyyymmdd}` | 计数 | 至次日 01:00 | INCR | TTL | 收件人日限 |
| `notification:vcode:user:{user_id}:{yyyymmdd}` | 计数 | 至次日 01:00 | INCR | TTL | 用户日限 |
| `notification:vcode:ip:{ip}:{yyyymmdd}` / `:hour:{yyyymm}` | 计数 | 对应周期 | INCR | TTL | IP 维度限流 |
| `notification:suppress:stock_low:{sku_id}` | `"1"` | 30 分钟 | 首次发送 `stock.low` 通知后 | TTL | 告警抑制窗口，防重复打扰运营 |
| `notification:circuit:{channel}` | 熔断状态机数据（失败计数、开启时间） | 30 秒（开启态） | 第三方调用成功/失败后 | TTL 到期自动半开 | 渠道熔断（通用约定 11.2） |
| `notification:idem:{idempotency_key}` | 首次响应摘要 | 24 小时 | I1 接口首次处理成功 | TTL | I1 与验证码接口的请求幂等 |
| `notification:lock:{task_name}` | 实例标识 | 与任务周期匹配 | 定时任务开始 | 任务结束主动 DEL，或 TTL 兜底 | 定时任务多实例互斥 |

### 7.2 缓存策略要点

- **一致性**：全部采用 Cache-Aside + "先写库、再删缓存"（通用约定 9.3）。模板与偏好的写路径统一在服务层调用 `cache.delete()`
- **不使用 `KEYS` 扫描**：模板按编码逐键删除（`notification:template:{code}` 与 `notification:template_route:{event_type}` 显式列出），避免生产环境阻塞 Redis
- **缓存穿透**：用户联系方式与偏好查询均提供负缓存（60 秒）
- **缓存击穿**：模板与路由 Key 是热点 Key，采用逻辑过期 + 单飞（singleflight）回源：缓存值内嵌 `expire_at`，读到逻辑过期时由一个协程回源，其余协程短暂等待（最长 200ms）后使用旧值
- **缓存雪崩**：同类 Key 的 TTL 加 ±10% 抖动
- **敏感数据**：`user_contact` 缓存存密文；偏好缓存无敏感数据可直接存明文；Redis 启用 ACL，通知服务使用独立账号，仅授权本服务 Key 前缀
- **Redis 不可用时的降级**：模板/路由/偏好缓存不可用 → 直接回源数据库并放行；幂等 Key 不可用 → 依赖数据库唯一索引兜底；配额 Key 不可用 → 放行并告警（可用性优先，配额是成本控制而非正确性约束）

## 8. 定时任务

任务由独立的调度进程（或单实例副本的 APScheduler/Celery Beat）触发，全部要求**多实例安全**（Redis 分布式锁 + 数据库行级锁）。

| 任务名 | 周期 | 职责 | 幂等要求 |
|---|---|---|---|
| `retry_pending_notifications` | 每 30 秒 | 扫描 `notification_retry_tasks` 中 `status = PENDING AND scheduled_at <= now()` 的任务并执行补发；同时把 `SENDING` 超过 15 分钟的记录回退为 `PENDING` | 抢占式（`FOR UPDATE SKIP LOCKED` + `locked_by`），任务置 `DONE` 前崩溃可由 `locked_at` 超时回收；发送本身由 `record_no` 与状态机保证不重复发送（`SENT`/`DELIVERED` 短路） |
| `scan_undelivered_records` | 每 10 分钟 | 扫描 `status = SENT AND delivered_at IS NULL AND sent_at < now() - NOT_DELIVERY_TIMEOUT_MINUTES` 的邮件记录，按渠道与模板聚合后告警（"长时间未送达"） | 只读 + 告警去重（同批次 30 分钟内只告警一次，用 Redis Key 去重），可重复执行 |
| `aggregate_notification_stats` | 每日 02:00（汇总前一日）与每小时（汇总当日） | 按 `(stat_date, channel, event_type)` 聚合 `notification_records` 写入 `notification_stats_daily`（UPSERT） | 按唯一键 UPSERT，可重复执行；重跑同一天结果一致 |
| `refresh_preference_cache` | 每 30 分钟 | 把近 7 日有偏好变更的用户（`updated_at` 在窗口内）批量刷新进缓存，降低读放大 | 只读 + 覆盖写，可重复执行 |
| `warm_template_cache` | 每 30 分钟 | 预加载全部启用模板与事件路由映射，避免消费高峰期的首次回源抖动 | 覆盖写，可重复执行 |
| `scan_stale_dead_letters` | 每小时 | 扫描 `notification_dead_letters` 中 `status = PENDING AND created_at < now() - 1 小时` 的记录，重复告警提醒人工处理 | 只读 + 告警去重；不自动重放 |
| `cleanup_expired_data` | 每日 03:30 | 清理 `DONE`/`CANCELLED` 超过 30 天的补发任务；把超过 `NOT_RECORD_RETENTION_DAYS`（默认 540 天）的发送记录归档（导出后删除，或迁移到归档表）；清理 `REPLAYED`/`IGNORED` 超过 90 天的死信 | 按主键分批 DELETE（每批 ≤ 5000 行），可重复执行；归档前需先落对象存储成功再删除 |
| `report_quota_usage` | 每小时 | 统计各渠道当日配额使用率，超过 `quota_alert_percent` 时告警 | 只读 + 告警去重 |

任务实现约束：

- 每个任务执行前抢 `notification:lock:{task_name}`（`SET NX EX`，TTL 为周期的 1.5 倍），未抢到直接退出，避免多副本重复执行
- 任务执行记录指标（耗时、处理条数、失败条数）到 `/metrics`，供 Prometheus 采集
- 任务自身的异常不得导致进程退出：捕获后记录日志与告警，等待下个周期重试

## 10. 安全与权限

### 10.1 鉴权要求

| 接口组 | 鉴权 | 服务端校验内容 |
|---|---|---|
| `/api/v1/admin/notification-templates/*` | 登录 + `ADMIN` | `X-User-Roles` 含 `ADMIN`，否则 `COMMON-3001`；所有写操作记录 `updated_by` 与审计日志 |
| `/api/v1/admin/notification-records/*`、`/api/v1/admin/notification-dead-letters/*` | 登录 + `ADMIN` | 同上；查询结果收件人一律掩码 |
| `/api/v1/users/me/notification-preferences` | 登录 | `user_id` 一律取 `X-User-Id`，**忽略**请求参数与请求体中的任何用户标识（通用约定 4.4） |
| `/api/v1/notifications/verification-code` | 服务间 `X-Internal-Token` 或网关 `X-Captcha-Token` | 二者居其一；两者都缺失返回 `COMMON-2001` |
| `/api/v1/notifications/webhooks/sendgrid` | 免登录（白名单）+ 回执签名 | 校验签名与时间戳（±5 分钟）；非法请求返回 `COMMON-2002` 并告警 |
| `/internal/v1/notifications/send` | `X-Internal-Token` | 校验失败返回 `COMMON-2002`；网关不暴露 `/internal/*` |

网关职责：剥离外部传入的 `X-User-Id`、`X-User-Roles`、`X-Internal-Token`（通用约定 4.3），并保证 `/api/v1/users/me/notification-preferences` 被正确路由到本服务（3.1 路由归属声明）。

### 10.2 脱敏

| 场景 | 处理 |
|---|---|
| 日志中的手机号 | 保留前 3 后 4：`138****8000`（通用约定 12.3） |
| 日志中的邮箱 | 保留首字符与域名：`b***@example.com` |
| 日志中的验证码 | **完全不记录**；日志中间件对 `code`、`verification_code` 等字段名做强制过滤 |
| 日志中的 `X-Internal-Token`、SendGrid/Twilio 密钥 | 完全不记录 |
| 日志中的收件人 | 统一使用 `recipient_masked` 列，禁止打印解密后的明文 |
| 接口响应 | 收件人一律返回掩码；`render_variables` 中 `code` 返回 `******` |
| 异常堆栈 | 异常信息写入 `last_error_message` 前先经过脱敏函数（正则替换手机号/邮箱/token）并截断至 512 字符 |
| MQ 死信落库 | `payload` 原样保留（含 `user_id` 等 ID，不含联系方式），`message_headers` 剔除凭证类头 |

实现方式：统一在日志处理器中挂一个 `RedactingFilter`，按字段名与正则双重过滤；集成测试中需有专门用例断言"日志中不出现明文手机号/邮箱/验证码"。

### 10.3 收件人存储：加密与查询的取舍

| 方案 | 可查询性 | 安全性 | 结论 |
|---|---|---|---|
| 明文存储 | 最佳（任意模糊查询） | 差（一次库泄露即批量泄露联系方式，违反 NFR-CP-004 数据最小化） | 不采用 |
| 单向哈希存储 | 只能精确匹配 | 最佳 | 不可用（发送时需要真实收件人） |
| **加密存储 + HMAC 盲索引 + 掩码列** | 精确匹配（邮箱/手机号完全相等）；模糊查询不可用 | 较好（需同时拿到密钥与库才可解密） | **采用** |
| 直接放 Redis 不落库 | — | — | 不采用（发送记录必须可追溯，FR-NOT-008） |

具体实现：

- 加密算法 AES-256-GCM，密钥与密钥版本（`key_id`）由密钥管理服务注入，落库字段 `recipient_cipher` 采用 `Base64(key_id ‖ nonce ‖ ciphertext ‖ tag)`
- 盲索引 `recipient_hash = HMAC-SHA256(normalize(recipient), index_key)`（hex，64 字符）。归一化规则：邮箱转小写并去除首尾空白；手机号转 E.164（无国家码时按 `NOT_DEFAULT_COUNTRY_CODE` 补全）。**索引密钥与加密密钥分离**，便于只轮换其一
- 掩码列 `recipient_masked` 在写入时计算并落库，所有展示与日志读这一列，不触达解密逻辑
- 密钥轮换：新增 `key_id`，新写入使用新密钥，解密按密文自带的 `key_id` 选择密钥，历史数据无需重写
- 保留策略：发送记录的归档与删除（`cleanup_expired_data`）同时清除密文；`NOT_RECORD_RENDERED_CONTENT = false` 时 `rendered_content` 不落库，进一步减少 PII 面积

### 10.4 模板注入防护

风险面：模板正文由管理员编写、变量值来自事件 payload（部分字段是用户可控内容，如昵称、取消原因、物流单号）。防护分三层：

**第一层 — 语法层（见 6.3）**：不使用通用模板引擎的求值能力，渲染器只支持 `{{var}}` 与 `{{var|default:文本}}`。不存在表达式、函数调用、属性访问、语句块，因此"通过变量内容注入模板语法执行代码"这条路径在语法上不成立。用户可控内容**永不作为模板源**（只在渲染时作为值参与替换，不做二次解析——渲染结果不做递归渲染，杜绝 `{{a}}` 的值里再含 `{{b}}` 被解析）。

**第二层 — 转义层**：邮件正文为 HTML，渲染时对变量值执行 HTML 转义（`& < > " '`），防止 XSS 与结构破坏；短信正文为纯文本，做长度校验不转义；`subject`（邮件主题）做换行符与头注入字符过滤（`\r`、`\n`），防止邮件头注入。

**第三层 — 值域层**：

| 变量来源 | 校验 |
|---|---|
| `URL` 类型变量 | scheme 必须为 `https`；域名必须在配置白名单 `NOT_ALLOWED_URL_HOSTS` 内；不接受 `javascript:`、`data:`、`file:` 等 |
| 邮件正文中的图片 | `<img src>` 只允许来自模板中硬编码的、经配置的静态资源域名；不允许用变量拼接图片地址 |
| `STRING` 类型变量 | 单变量长度上限 512（可配），超出按 `max_length` 截断或拒绝（关键字段拒绝） |
| 变量值中的 HTML | 一律转义，不允许模板使用 `|raw` 之类的"不转义"标记（语法层面也不存在该过滤器） |

补充约束：

- 模板 CRUD 接口仅对 `ADMIN` 开放，且所有变更记入审计日志（操作人、变更前后内容摘要）
- 管理端预览接口（T11）返回的 HTML 由后台前端在 iframe 中使用 sandbox 渲染，避免管理员在预览时被自己的模板 XSS 攻击
- 发布前校验器会拒绝包含 `<script>`、`<iframe>`、`on*=` 事件的邮件正文（白名单标签集：`p`、`br`、`a`、`strong`、`em`、`ul`、`ol`、`li`、`table`、`td`、`tr`、`h1`-`h3`、`img`），超出白名单的标签在发布时告警，在渲染时剥离

### 10.5 其他安全要求

- **第三方密钥**：SendGrid / Twilio 密钥仅通过环境变量或密钥管理服务注入，禁止入库（`channel_configs.config` 只存非敏感参数）、禁止入日志、禁止入镜像
- **出站调用**：全部走 HTTPS，设置连接 1s / 读取 3s 超时（SendGrid 与 Twilio 的读取超时可放宽到 5s，通过 `NOT_SEND_TIMEOUT_MS` 配置）；出站调用记录日志（含耗时、状态码、脱敏后的目标）
- **回执验签**：E1 接口必须验签，防止伪造送达/退信回执污染发送记录
- **审计**：后台的模板增删改、启停、发布、测试发送、记录重发、死信重放全部记录审计日志（操作人、时间、对象、变更摘要），仅追加不可修改
- **防刷**：验证码接口四道限流闸 + 网关 IP 限流 + 风控令牌；`stock.low` 告警抑制窗口防止事件风暴放大成短信费用

### 12.3 测试环境与工具

- 第三方渠道在测试环境一律使用 Mock Server（本地容器），通过环境变量切换真实/模拟实现；**禁止**在 CI 中调用真实的 SendGrid/Twilio
- 事件驱动测试：用 testcontainers 或 Compose 起真实 RabbitMQ，测试内直接向 `ecommerce.events` 投递构造的事件信封，避免依赖上游服务的实现进度
- 消费链路测试建议封装 `publish_event(event_type, payload)` 与 `wait_for_records(n)` 两个辅助函数，避免用 `sleep` 断言
- 覆盖率门禁：与本服务其他模块一致纳入 CI（概要架构设计 9.2"质量门禁"）；渲染器、错误分类器、限流器、加密模块要求分支覆盖率 ≥ 90%

## 1. 服务概览

### 1.1 职责

支付服务是平台的**资金侧唯一记录者**，负责把"订单需要收多少钱"转化为"平台上真实到账的钱"，并对每一笔资金的流入流出留下可审计的痕迹。核心职责：

| 职责 | 说明 | 对应需求 |
|---|---|---|
| 发起支付 | 校验订单状态与金额后创建支付单，调用第三方创建支付意图，返回凭据/跳转链接 | FR-PAY-001 |
| 渠道适配 | 抽象 Stripe 与 PayPal 两种渠道，对上提供统一的创建、查询、退款、验签能力 | FR-PAY-002 |
| 回调处理 | 接收第三方异步回调，验签、落原始记录、幂等入账、驱动订单状态 | FR-PAY-003 |
| 支付结果查询 | 主动向第三方查询支付状态，作为回调丢失的补偿手段 | FR-PAY-004 |
| 支付幂等 | 同一订单同一渠道只存在一个进行中的支付单；重复回调只入账一次 | FR-PAY-005 |
| 退款 | 全额与部分退款，多次部分退款累计不超过支付金额，退款结果异步回调更新 | FR-PAY-006 |
| 交易流水 | 支付与退款统一记账，成为对账与财务查询的唯一数据来源 | FR-PAY-007 |
| 对账 | 按日拉取第三方账单与本地流水比对，输出差异清单并告警 | FR-PAY-008 |
| 支付超时 | 支付单到期未完成则关闭，与订单超时关闭联动 | FR-PAY-009 |
| 敏感信息隔离 | 不接触、不存储卡号与 CVV，凭证完全由第三方托管 | FR-PAY-010 |

### 1.2 服务边界

**做什么**：

- 支付单生命周期管理（创建、进行中、成功、失败、关闭）
- 与 Stripe / PayPal 的支付、退款、查询、验签对接
- 退款单生命周期管理（申请、审核、执行、结果落定）
- 交易流水记账与每日对账
- 面向财务/客服的后台查询与操作接口

**不做什么**：

| 不做的事 | 归属 | 原因 |
|---|---|---|
| 订单状态流转 | 订单服务 | 支付服务只认 `order_no` 并发 `payment.succeeded`，订单状态由订单服务自身维护（架构 3.3） |
| 订单金额计算 | 订单服务 | 金额是一次交易的权威口径，支付服务只做校验不做计算 |
| 优惠、改价、运费 | 订单服务 | 与资金渠道无关，属于订单域 |
| 库存释放与扣减 | 商品目录服务 | 由 `order.cancelled` / `order.paid` 驱动 |
| 用户身份与令牌 | 用户服务 + 网关 | 支付服务只信任网关注入的身份头 |
| 退款业务依据（是否该退） | 订单服务 | 支付服务只负责"退得对不对"，不负责"该不该退" |
| 卡号、CVV 的采集与存储 | 第三方（Stripe/PayPal） | PCI 边界，见第 10 章 |

### 1.3 上下游依赖

**同步依赖（出站）**：

| 被调方 | 场景 | 接口 | 超时 |
|---|---|---|---|
| order-service | 发起支付前校验订单状态与金额 | `GET /internal/v1/orders/{order_no}/payment-check` | 连接 1s / 读取 3s |
| order-service | 发起退款前校验订单可退性 | `GET /internal/v1/orders/{order_no}/refund-check` | 连接 1s / 读取 3s |
| Stripe | 创建支付意图、查询、退款、拉取账单 | HTTPS API（沙箱/生产） | 连接 2s / 读取 10s |
| PayPal | 创建订单、查询、退款、拉取账单、回调验签 | HTTPS API（沙箱/生产） | 连接 2s / 读取 10s |

> 服务间调用统一遵守通用约定第 11 章；第三方调用策略见 6.10。

**同步被依赖（入站）**：

| 调用方 | 场景 | 接口 |
|---|---|---|
| order-service | 查询订单的支付状态（展示/补偿/异常订单判定） | `GET /internal/v1/payments/by-order/{order_no}` |

**异步依赖**：

| 方向 | 事件 | 说明 |
|---|---|---|
| 订阅 | `order.created` | 预创建支付单（可选，见 5.2.1） |
| 订阅 | `order.cancelled` | 关闭进行中的支付单 |
| 发布 | `payment.succeeded` / `payment.failed` / `payment.refunded` | 驱动订单服务与通知服务 |
| 发布 | `order.paid` 由订单服务发出 | 本服务不发布该事件 |

## 2. 数据库设计

数据库 `ecommerce_payment`，PostgreSQL 16，一服务一库，不设物理外键。所有 `id` 为应用层生成的雪花 ID（BIGINT），JSON 中序列化为字符串。

### 2.1 表清单

| # | 表名 | 职责 | 主要写入方 |
|---|---|---|---|
| 1 | `payments` | 支付单主表，一次支付尝试一行 | 发起支付、回调处理、定时任务 |
| 2 | `refunds` | 退款单，支持多次部分退款 | 退款接口、回调处理、定时任务 |
| 3 | `payment_transactions` | 交易流水，支付与退款统一记账 | 回调处理、退款处理 |
| 4 | `payment_callback_logs` | 第三方回调原始报文与处理轨迹 | Webhook 入口 |
| 5 | `reconciliation_batches` | 对账批次，一次渠道单日对账一行 | 对账定时任务 |
| 6 | `reconciliation_differences` | 对账差异明细 | 对账定时任务 |
| 7 | `outbox_events` | 事务性发件箱 | 所有需要发事件的业务事务 |

**为什么支付单与退款单分表**：支付单与退款单的生命周期、状态机、唯一性与幂等键完全不同（支付单按"订单 + 渠道"防重，退款单按客户端幂等键防重，且一个支付单对应 N 个退款单）。合表会让唯一索引与状态机互相污染。

**为什么交易流水与支付/退款单不合并**（明确取舍）：支付单与退款单是**业务状态表**，随状态流转反复 `UPDATE`；交易流水是**记账表**，只 `INSERT` 不 `UPDATE`。分开的理由有三：

1. **对账需要一张不可变的流水账**。对账的语义是"本地流水 vs 第三方账单"，如果对账对象是会被后续状态覆盖的业务表，历史批次的结果将无法复现。
2. **支付与退款需要共用一条时间线**。第三方账单是把收款与退款按时间混排的，流水表用 `transaction_type = PAYMENT/REFUND` + 统一字段承载两者，比对逻辑只有一套；若分开，对账代码要写两遍再归并。
3. **可追加列**。手续费、结算批次号这类只有财务关心的字段加在流水表上，不必污染支付单。

代价是同一笔金额在两处出现，需保证**同一事务内写入**（见 6.3），并由每日对账（6.7）与巡检任务（8.6）兜底校验两者一致性。

**为什么回调网络日志要有独立表**：Webhook 是免登录入口，是攻击面；验签失败、重放、伪造的报文都需要可追溯。业务表只保留"处理结果"，而签名头、原始报文体、处理耗时、处理结论这些排查依据必须原样留存，且要能回答"这条回调是第一次见还是重放"。

| `order_no` | VARCHAR(32) | NOT NULL | — | 关联订单服务订单号，不存订单其他字段 |

| `expires_at` | TIMESTAMPTZ | NOT NULL | — | 支付单过期时间，取自订单 `expires_at` |
| `paid_at` | TIMESTAMPTZ | NULL | NULL | 支付成功时间（第三方口径，UTC） |
| `failed_at` | TIMESTAMPTZ | NULL | NULL | 失败时间 |
| `closed_at` | TIMESTAMPTZ | NULL | NULL | 关闭时间 |
| `last_synced_at` | TIMESTAMPTZ | NULL | NULL | 最近一次主动同步第三方状态的时间 |
| `version` | INT | NOT NULL DEFAULT 0 | 0 | 乐观锁版本号 |
| `created_at` | TIMESTAMPTZ | NOT NULL | now() | — |
| `updated_at` | TIMESTAMPTZ | NOT NULL | now() | 应用层维护 |

**唯一索引设计（本表关键）**：

```sql
-- ① 支付单号全局唯一
CREATE UNIQUE INDEX uk_payments_payment_no ON payments (payment_no);

-- ② 同一订单同一渠道，只允许一个"进行中"的支付单
CREATE UNIQUE INDEX uk_payments_order_channel_active
    ON payments (order_no, channel)
    WHERE status IN ('PENDING', 'PROCESSING');

-- ③ 第三方支付号唯一：重复回调只入账一次的最终兜底
CREATE UNIQUE INDEX uk_payments_third_party_payment_id
    ON payments (channel, third_party_payment_id)
    WHERE third_party_payment_id IS NOT NULL;
```

三个索引各自解决的问题不同：

- **①** 是主键之外的对外标识，所有接口按 `payment_no` 寻址。
- **②** 是**并发发起支付的闸门**。它是**部分唯一索引**而非全表唯一索引，这是刻意的：`PENDING`/`PROCESSING` 之外的状态（`SUCCEEDED`/`FAILED`/`CLOSED`）不参与约束，因此"同一订单先失败、再换渠道重试"或"支付单关闭后用户重新发起"都是合法的，而"同一订单同一渠道同时存在两个进行中的支付"会被数据库直接拒绝。业务层捕获唯一键冲突异常后，转查询返回既有支付单（见 6.1）。
- **③** 是**回调幂等的最终防线**。它与通用约定第 6 章"第三方交易号 + 支付流水表唯一索引"配合：应用层用流水表唯一索引做第一道拦截，本索引保证即使拦截失效，也不会出现两个支付单指向同一笔第三方交易。

> **与通用约定的对照说明**：通用约定 6 章定义支付幂等键为"订单号 + 渠道"。本服务把该语义落成"Redis 幂等键（`pay:{order_no}:{channel}`，TTL 7 天）+ 索引 ②"。区别在于 Redis 键在支付单进入终态后被显式删除（见 7.1），而索引 ② 只覆盖进行中状态——二者结合，既阻止了"同时两个进行中"，又允许终态后的合法重试。

**其他索引**：

```sql
CREATE INDEX idx_payments_order_no              ON payments (order_no);
CREATE INDEX idx_payments_user_created          ON payments (user_id, created_at DESC);
CREATE INDEX idx_payments_status_expires        ON payments (status, expires_at)
    WHERE status IN ('PENDING', 'PROCESSING');   -- 超时关闭与回调补偿扫描
CREATE INDEX idx_payments_channel_paid_at       ON payments (channel, paid_at)
    WHERE status = 'SUCCEEDED';                  -- 对账与流水查询
CREATE INDEX idx_payments_status_created        ON payments (status, created_at);
```

索引总数 8 个（含 3 个唯一索引），略高于通用约定建议的 6 个上限。取舍说明：`idx_payments_user_created` 与 `idx_payments_status_created` 服务于后台流水查询的不同过滤维度，若后续写入压力成为瓶颈，优先合并/删除 `idx_payments_status_created`（其查询可退化为全表扫描 + 时间过滤，后台接口可接受）。

**索引**：

```sql
CREATE UNIQUE INDEX uk_refunds_refund_no         ON refunds (refund_no);
-- 退款幂等：同一客户端幂等键全局唯一（唯一索引为最终兜底，Redis 为前置拦截）
CREATE UNIQUE INDEX uk_refunds_idempotency_key   ON refunds (idempotency_key);
CREATE UNIQUE INDEX uk_refunds_third_party_id    ON refunds (channel, third_party_refund_id)
    WHERE third_party_refund_id IS NOT NULL;
CREATE INDEX idx_refunds_payment_no              ON refunds (payment_no);
CREATE INDEX idx_refunds_order_no                ON refunds (order_no);
CREATE INDEX idx_refunds_status_updated          ON refunds (status, updated_at)
    WHERE status = 'PENDING';                     -- 退款状态同步任务扫描
CREATE INDEX idx_refunds_user_created            ON refunds (user_id, created_at DESC);
```

**关于 `idempotency_key` 的唯一性**：通用约定第 6 章规定退款幂等键"由客户端生成"。但客户端可能在不同场景复用一个 key（如前端 bug），因此**唯一索引必须是 `UNIQUE(idempotency_key)`，而非 `UNIQUE(idempotency_key, payment_no)`**——后者会让同一个 key 在另一笔支付上生效，幂等失效。为降低 key 撞车风险，服务端在校验通过后把 key 与 `payment_no` 绑定写入 Redis（`pay:idem:refund:{key}` → `{payment_no, refund_no}`），命中但 `payment_no` 不符时返回 `PAY-1002`。

### 2.4 payment_transactions（交易流水）

**只 INSERT，不 UPDATE，不 DELETE。** 流水记账后不可变；若需更正，追加一条反向流水并注明原因（本期未开放该操作，仅保留字段）。

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | PK | — | 雪花 ID |
| `transaction_no` | VARCHAR(32) | NOT NULL, UNIQUE | — | 流水号，`TX` + yyyyMMdd + 10 位序列 |
| `transaction_type` | VARCHAR(16) | NOT NULL, CHECK | — | `PAYMENT` / `REFUND` |
| `payment_no` | VARCHAR(32) | NOT NULL | — | 关联支付单号 |
| `refund_no` | VARCHAR(32) | NULL | NULL | 退款流水时关联退款单号 |

### 2.10 数据库层金额约束

除应用层校验外，关键金额约束下沉到数据库，作为最后一道防线：

```sql
ALTER TABLE payments ADD CONSTRAINT ck_payments_refunded_amount
    CHECK (refunded_amount_cents >= 0 AND refunded_amount_cents <= amount_cents);

ALTER TABLE refunds ADD CONSTRAINT ck_refunds_amount_positive
    CHECK (amount_cents > 0 AND amount_cents <= payment_amount_cents);

ALTER TABLE payments ADD CONSTRAINT ck_payments_amount_positive CHECK (amount_cents > 0);
```

`ck_payments_refunded_amount` 的价值：即使应用层出现 bug 或并发绕过，也**不可能**把累计退款额推过支付金额。它是 6.6 中条件更新之外的第二重保护。

> 注意：`CHECK` 约束作用于**单行**。refunds 表只能约束"单笔退款不超过支付金额"，"多笔退款累计不超过支付金额"必须靠条件更新（6.6）+ payments 表 CHECK 共同保证，这一点在 6.6.3 中详述。

### 3.2 发起支付

**`POST /api/v1/payments`**

- 鉴权：买家登录（`X-User-Id` 必填）
- 请求头：`Idempotency-Key`（必需，客户端生成 UUID）、`X-Request-Id`、`X-Trace-Id`
- 限流：20 次/分钟/用户（网关，见平台文档 2.3）

**请求体**：

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| `order_no` | string | 是 | `^SO\d{14,}$` | 订单号 |
| `channel` | string | 是 | `STRIPE` / `PAYPAL` | 支付渠道 |
| `return_url` | string | 否 | 合法 URL，长度 ≤ 512 | 支付完成后前端跳回页；渠道支持时透传 |
| `cancel_url` | string | 否 | 合法 URL，长度 ≤ 512 | 用户取消支付后跳回页 |
| `client_context` | object | 否 | — | 前端环境信息（`ua_platform`、`locale`），仅透传第三方，不落库 |

> **注意**：请求体中**没有金额字段**。金额一律以订单服务返回值为准（见 6.1），这是本接口最重要的安全设计。若客户端尝试传入 `amount_cents`，服务端忽略且不报错（向后兼容），但会记录 WARN 日志与指标 `payments_client_amount_injected_total`。

**成功响应** `201 Created`：

```json
{
  "code": "OK",
  "message": "success",
  "data": {
    "payment_no": "PA20260910000001",
    "order_no": "SO20260910000001",
    "channel": "STRIPE",
    "status": "PENDING",
    "amount_cents": 19900,
    "currency": "CNY",
    "expires_at": "2026-09-10T09:00:00.000Z",
    "pay_type": "CLIENT_SECRET",
    "pay_payload": {
      "publishable_key": "pk_test_****",
      "client_secret": "pi_3Nx****_secret_****",
      "payment_intent_id": "pi_3Nx****"
    },
    "created_at": "2026-09-10T08:30:00.123Z"
  },
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "timestamp": "2026-09-10T08:30:00.130Z"
}
```

PayPal 渠道的 `pay_type` 为 `REDIRECT`，`pay_payload` 形如：

```json
{
  "pay_type": "REDIRECT",
  "pay_payload": {
    "pay_url": "https://www.sandbox.paypal.com/checkoutnow?token=5O190127TN364715T",
    "third_party_intent_id": "5O190127TN364715T"
  }
}
```

**重复请求（幂等命中）**：返回 `200 OK`，`data` 与首次创建完全一致（含原 `payment_no`），并在 `data` 中追加 `"idempotent_replay": true`。

**错误码**：

| 错误码 | HTTP | 场景 |
|---|---|---|
| `COMMON-1001` | 400 | 参数校验失败（订单号格式、渠道非法、URL 非法） |
| `COMMON-2001` | 401 | 缺少令牌 |
| `PAY-1001` | 400 | 缺少 `Idempotency-Key` 请求头 |
| `PAY-4001` | 404 | 订单不存在（订单服务返回 404） |
| `PAY-3001` | 403 | 订单不属于当前用户 |
| `PAY-5001` | 409 | 订单状态不允许支付（非待支付，如已支付/已取消/已关闭） |
| `PAY-5003` | 409 | 支付单已过期 |
| `PAY-5005` | 409 | 该订单该渠道已存在进行中的支付单（返回既有支付单号于 `details`） |
| `PAY-5006` | 409 | 订单金额与预期不符（第三方/本地不一致，防篡改触发） |
| `PAY-7001` | 502 | 订单服务不可用 |
| `PAY-7002` | 502 | 第三方渠道调用失败（创建支付意图失败/超时） |
| `PAY-7004` | 502 | 该渠道当前不可用（熔断中） |

### 3.4 按订单查询支付单

**`GET /api/v1/payments/by-order/{order_no}`**

- 鉴权：买家登录 + 归属校验（按 `order_no` 查出的支付单 `user_id` 必须与 `X-User-Id` 一致）
- 用途：支付页展示"该订单的历史支付尝试"，以及"换渠道重付"

**响应** `200 OK`：`data.items` 为支付单摘要数组（按 `created_at DESC`），字段裁剪为 `payment_no`、`channel`、`status`、`amount_cents`、`refunded_amount_cents`、`expires_at`、`paid_at`、`fail_reason`、`created_at`。无记录时 `items` 为空数组，HTTP 仍为 200（订单存在但从未发起支付是正常状态，不返回 404）。

订单是否存在由订单服务判定：本接口不校验订单存在性，只按 `order_no` 查本地支付单。若同一订单号查不到任何支付单，仍返回空列表。

**错误码**：`COMMON-1001`、`COMMON-2001`、`COMMON-3001`。

### 3.5 主动同步支付结果

**`POST /api/v1/payments/{payment_no}/sync`**

- 鉴权：买家登录 + 归属校验
- 语义：向第三方查询该支付单的最新状态并落库，与定时任务（8.2）共用同一段业务逻辑（`PaymentSyncService.sync_one`）
- 频率限制：**同一支付单 60 秒内最多一次**，超限返回 `PAY-6002`（Redis 计数）

**请求体**：无（`Content-Type` 可省略）

**响应** `200 OK`：

若第三方返回的状态无法映射到本服务状态（如未知枚举值），返回 `data.status_after` 为原状态、`changed` 为 `false`，并记录 `PAY-8004` 级别的告警日志与第三方原始状态字样。

|---|---|---|---|

| 找不到支付单 | 200 | `{"received": true, "unmatched": true}` | 记 `IGNORED` + 告警 |
| 内部错误（DB 不可用等） | 500 | `{"error": "internal error"}` | 记 `FAILED`，**依赖第三方重试**，见 6.3.5 |

### 3.8 发起退款

**`POST /api/v1/payments/{payment_no}/refunds`**

- 鉴权：买家登录（仅能对自己订单的支付单发起，且仅能申请，见下）或客服角色
- 请求头：`Idempotency-Key`（必需）
- 权限细节：
  - `BUYER`：只能对本人支付单发起退款申请；金额不得超过 `refundable_amount_cents`；申请进入 `audit_status='PENDING'`（是否需审核由配置阈值决定，低于阈值直接执行）

| `refund_application_no` | string | 否 | 长度 ≤ 32 | 订单服务的售后退款申请单号，用于跨服务关联 |

**成功响应** `201 Created`：

当 `audit_status='PENDING'` 时，`status` 为 `PENDING` 但不会调用第三方，需等审核通过（3.12）后才执行。

**错误码**：

| 错误码 | HTTP | 场景 |
|---|---|---|
| `COMMON-1001` | 400 | 参数校验失败 |

| `PAY-7002` | 502 | 第三方退款调用失败（已创建退款单，状态置 `FAILED`，可通过 8.3 重试） |

### 3.12 退款审核

**`POST /api/v1/admin/payments/refunds/{refund_no}/audit`**

- 鉴权：`ORDER_OPERATOR` / `CUSTOMER_SERVICE` / `ADMIN`
- 请求体：

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| `action` | string | 是 | `APPROVE` / `REJECT` | 审核动作 |
| `reject_reason` | string | 条件必填 | `action=REJECT` 时必填，长度 1~255 | 驳回原因 |
| `note` | string | 否 | 长度 ≤ 255 | 审核备注 |

**响应** `200 OK`：返回更新后的退款单（结构同 3.9），`action=APPROVE` 时若第三方调用已完成则 `status` 直接为 `SUCCEEDED`，否则为 `PENDING`。

**幂等性**：由状态机保证——已审核（`audit_status IN ('APPROVED','REJECTED')`）的退款单再次提交返回 `PAY-5010`（409）。不支持"撤回复审"。

**错误码**：`COMMON-1001`、`COMMON-3001`、`PAY-4003`、`PAY-5010`（退款单已审核过）、`PAY-7002`（审核通过但第三方退款调用失败，退款单转 `FAILED` 并告知审核人）。

### 3.13 退款重试（人工介入）

**`POST /api/v1/admin/payments/refunds/{refund_no}/retry`**

- 鉴权：`FINANCE` / `ADMIN`
- 语义：用于定时任务重试超限（`retry_count >= PAYMENT_REFUND_MAX_RETRY`）后的人工补发。服务端**先向第三方查询该退款单真实状态**，仅在确认第三方不存在该退款时才真正重发（避免重复退款，见 6.6.5）
- 请求体：`{"note": "string"}`（可选，记入 `handle_note` 类字段与审计日志）
- 响应 `200 OK`：返回更新后的退款单

**错误码**：`COMMON-3001`、`PAY-4003`、`PAY-5002`（退款单状态不允许重试，如已 `SUCCEEDED`/`CLOSED`）、`PAY-7002`（第三方仍不可用）。

### 3.14 触发对账

**`POST /api/v1/admin/payments/reconciliations`**

- 鉴权：`FINANCE` / `ADMIN`
- 请求体：

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| `channel` | string | 是 | `STRIPE` / `PAYPAL` | 对账渠道 |
| `reconcile_date` | string | 是 | `YYYY-MM-DD`，不晚于昨日 | 对账日 |
| `force` | bool | 否 | 默认 `false` | 已存在成功批次时是否作废重跑 |

**响应** `202 Accepted`：返回批次摘要（`batch_no`、`status='RUNNING'`），对账在后台异步执行，进度通过 3.15 查询。

```json
{
  "code": "OK",
  "message": "success",
  "data": {
    "batch_no": "RB20260910STRIPE",
    "channel": "STRIPE",
    "reconcile_date": "2026-09-10",
    "status": "RUNNING",
    "started_at": "2026-09-10T02:00:00.000Z"
  },
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "timestamp": "2026-09-10T02:00:00.100Z"

```

**幂等**：同一渠道同一日期已存在 `RUNNING` 或 `SUCCEEDED` 批次时返回 `PAY-5011`（409）；`force=true` 时把既有批次置 `FAILED`（`fail_reason='manual rerun'`）后新建。

**错误码**：`COMMON-1001`、`COMMON-3001`、`PAY-5011`（该日期已对账）、`PAY-7005`（第三方账单拉取失败）、`PAY-5012`（对账日超出可拉取窗口，第三方通常只保留有限天数的账单）。

## 4. 内部接口设计

内部接口置于 `/internal/v1/payments/*`，网关不路由（平台文档 2.1），必须携带 `X-Internal-Token`，校验失败返回 `COMMON-2002`。

### 4.1 查询订单的支付状态（供订单服务）

**`GET /internal/v1/payments/by-order/{order_no}`**

供订单服务在以下场景调用：订单详情展示支付信息、"支付成功但库存扣减失败"进入异常队列时判定是否已收款（FR-ORD-014）、订单关闭前的兜底检查（避免关闭了实际已支付的订单）。

**查询参数**：

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `include_refunds` | bool | 否 | 默认 `false`，`true` 时附带退款列表 |

**响应** `200 OK`：

```json
{
  "code": "OK",
  "message": "success",
  "data": {
    "order_no": "SO20260910000001",
    "has_succeeded_payment": true,
    "total_paid_cents": 19900,
    "total_refunded_cents": 5000,
    "net_paid_cents": 14900,
    "currency": "CNY",
    "latest_payment": {
      "payment_no": "PA20260910000001",
      "channel": "STRIPE",
      "status": "SUCCEEDED",
      "amount_cents": 19900,
      "paid_at": "2026-09-10T08:35:12.000Z"
    },
    "active_payment": null,
    "refunds": []
  },
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "timestamp": "2026-09-10T08:40:00.000Z"
}
```

字段语义：

- `has_succeeded_payment`：该订单是否存在至少一笔 `SUCCEEDED` 的支付单。**这是订单服务判定"是否已收款"的唯一依据**
- `total_paid_cents` / `total_refunded_cents` / `net_paid_cents`：仅统计 `SUCCEEDED` 的支付流水与退款流水
- `latest_payment`：最近一次支付尝试（不限于成功），用于展示
- `active_payment`：当前进行中的支付单（`PENDING`/`PROCESSING`），无则 `null`。订单服务据此判断"用户正在支付中"，避免在支付进行中关闭订单
- 无任何支付记录时：`has_succeeded_payment=false`，`latest_payment=null`，HTTP 仍为 200

**错误码**：`COMMON-2001`（`X-Internal-Token` 无效）、`COMMON-1001`（订单号格式非法）、`PAY-8001`（内部错误）。

### 4.2 查询订单是否存在进行中的支付（供订单服务）

**`GET /internal/v1/payments/by-order/{order_no}/active`**

为订单超时关闭场景提供的轻量接口（响应体小，便于订单服务在批量关闭时高频调用）。

**响应** `200 OK`：

```json
{
  "code": "OK",
  "message": "success",
  "data": {
    "order_no": "SO20260910000001",
    "has_active_payment": true,
    "payment_no": "PA20260910000001",
    "channel": "STRIPE",
    "expires_at": "2026-09-10T09:00:00.000Z"
  },
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "timestamp": "2026-09-10T08:55:00.000Z"
}
```

**错误码**：同 4.1。

> **重要**：本接口返回 `has_active_payment=false` **不代表订单可以安全关闭**。存在"支付刚成功但回调尚未处理"的窗口，订单服务必须仍以 4.1 的 `has_succeeded_payment` 为最终依据，并配合支付服务的 `payment.succeeded` 事件做后置修正（平台文档 1.4 的 `CLOSING → PAID` 逻辑）。本接口只用于降低不必要的关闭尝试，不作为关闭依据。

## 5. 事件设计

事件信封、交换机、路由键、消费队列命名、重试策略均遵循通用约定第 10 章。本节只描述本服务特有内容。

### 5.1 发布事件

发布通过 `outbox_events` 表实现：业务事务内写入 `payments` / `refunds` / `payment_transactions` 与 `outbox_events`，由投递任务（8.5）异步发送至 RabbitMQ（Exchange `ecommerce.events`，Routing Key = `event_type`）。这样保证"支付状态落库成功则事件不丢"。

#### 5.1.1 `payment.succeeded`

**触发时机**：支付单状态由 `PENDING`/`PROCESSING` 变为 `SUCCEEDED` 的同一事务内（来自回调处理 6.3 或补偿查询 6.4）。

```json
{
  "event_id": "9f1c2b3a-4d5e-6f70-8192-a3b4c5d6e7f8",
  "event_type": "payment.succeeded",
  "event_version": "1.0",
  "occurred_at": "2026-09-10T08:35:12.400Z",
  "producer": "payment-service",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "payload": {
    "payment_no": "PA20260910000001",
    "order_no": "SO20260910000001",
    "user_id": "1024",
    "amount_cents": 19900,
    "currency": "CNY",
    "channel": "STRIPE",
    "third_party_payment_id": "pi_3Nx00000000000001",
    "paid_at": "2026-09-10T08:35:12.000Z"
  }
}
```

| payload 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `payment_no` | string | 是 | 支付单号 |
| `order_no` | string | 是 | 订单号，订单服务的处理依据 |
| `user_id` | string | 是 | 用户 ID（字符串，通用约定 7.1） |
| `amount_cents` | int | 是 | 实收金额（分） |
| `currency` | string | 是 | 固定 `CNY` |
| `channel` | string | 是 | `STRIPE` / `PAYPAL` |
| `third_party_payment_id` | string | 否 | 第三方交易号，供财务核对 |
| `paid_at` | string | 是 | ISO 8601 UTC |

**关键约束**：同一支付单**只发布一次** `payment.succeeded`。由状态机保证——只有 `status` 从进行中转为 `SUCCEEDED` 的那次条件更新（影响行数 = 1）才写 outbox；重复回调走幂等分支，不产生第二次事件（见 6.3.4）。

**消费方**：order-service（置订单为已支付）、notification-service（发送支付成功通知）。notification-service 的消费队列 `notification.payment.succeeded`。

#### 5.1.2 `payment.failed`

**触发时机**：支付单状态变为 `FAILED` 时。包括：第三方明确返回失败、用户在第三方页面取消、补偿查询发现第三方已失败/已取消。

```json
{
  "event_id": "1a2b3c4d-5e6f-7a8b-9c0d-1e2f3a4b5c6d",
  "event_type": "payment.failed",
  "event_version": "1.0",
  "occurred_at": "2026-09-10T08:36:00.000Z",
  "producer": "payment-service",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "payload": {
    "payment_no": "PA20260910000001",
    "order_no": "SO20260910000001",
    "user_id": "1024",
    "amount_cents": 19900,
    "channel": "STRIPE",
    "reason": "银行卡被拒绝",
    "fail_code": "card_declined",
    "failed_at": "2026-09-10T08:36:00.000Z"
  }
}
```

> 支付超时关闭（`CLOSED`）**不发布** `payment.failed`。理由：`CLOSED` 是系统行为而非支付失败，订单本身的超时关闭由订单服务自己的定时任务驱动；发布失败事件会让用户收到"支付失败"的误导性通知。差异由订单服务通过 4.1 接口观测。

**消费方**：order-service（记录支付失败次数，用于风控与展示）、notification-service（提示用户重新支付）。

#### 5.1.3 `payment.refunded`

**触发时机**：退款单变为 `SUCCEEDED` 时（来自退款回调 6.6.4 或退款同步任务 8.3）。

```json
{
  "event_id": "2b3c4d5e-6f70-8192-a3b4-c5d6e7f8a9b0",
  "event_type": "payment.refunded",
  "event_version": "1.0",
  "occurred_at": "2026-09-10T09:06:30.500Z",
  "producer": "payment-service",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "payload": {
    "refund_no": "RF20260910000001",
    "payment_no": "PA20260910000001",
    "order_no": "SO20260910000001",
    "user_id": "1024",
    "amount_cents": 5000,
    "currency": "CNY",
    "channel": "STRIPE",
    "refund_type": "PARTIAL",
    "payment_total_amount_cents": 19900,
    "total_refunded_amount_cents": 5000,
    "refunded_at": "2026-09-10T09:06:30.000Z"
  }

```

`payment_total_amount_cents` 与 `total_refunded_amount_cents` 用于让订单服务判断订单是否**全额退完**（据此决定订单进入"已退款"还是"部分退款"状态），避免订单服务为此再回查支付服务。

**消费方**：order-service（更新订单退款状态）、notification-service（发送退款通知）。

### 5.2 订阅事件

#### 5.2.1 `order.created`（可选预创建支付单）

**消费队列**：`payment.order.created`

| 字段 | 说明 |
|---|---|
| `order_no` | 订单号 |
| `user_id` | 用户 ID |
| `total_amount_cents` | 订单应付金额 |
| `currency` | 币种 |
| `expires_at` | 订单过期时间 |
| `items[]` | 商品明细（本服务**不使用**） |

**处理逻辑**（本期为**预留设计，默认不启用**，由配置 `PAYMENT_PRE_CREATE_ON_ORDER_CREATED` 控制）：

```
on_order_created(event):
    if not config.PAYMENT_PRE_CREATE_ON_ORDER_CREATED: return
    if already_processed(event.event_id): return
    # 预创建不落库，仅在 Redis 缓存订单金额与过期时间，
    # 供用户点击"去支付"时省去一次订单服务调用
    set_cache(f"payment:order_ctx:{order_no}",
              {amount_cents, currency, expires_at, user_id},
              ttl=order_ttl)
```

**不预创建支付单记录的理由**：支付单必须绑定渠道，而 `order.created` 事件中用户尚未选择渠道；且预创建的支付单会占用 `uk_payments_order_channel_active` 位置、参与超时关闭任务，增加无谓的状态管理成本。缓存订单上下文已能覆盖"减少一次同步调用"的收益。

**幂等**：按 `event_id` 去重（Redis 已处理集合，TTL 7 天）；缓存写入本身幂等。
**顺序**：按 `order_no` 路由，同一订单事件顺序消费。

#### 5.2.2 `order.cancelled`（关闭支付单）

**消费队列**：`payment.order.cancelled`

| 字段 | 说明 |
|---|---|
| `order_no` | 订单号 |
| `user_id` | 用户 ID |
| `reason` | 取消原因 |
| `items[]` | 商品明细（本服务不使用） |

**处理逻辑**：

```
on_order_cancelled(event):
    if already_processed(event.event_id): return
    lock = redis_lock(f"payment:order:{order_no}")     # 防止与回调并发
    for payment in find_active_payments(order_no):      # status IN (PENDING, PROCESSING)
        # 条件更新保证只有一个执行者生效
        affected = UPDATE payments
                   SET status = 'CLOSED', closed_at = now(), version = version + 1,
                       updated_at = now()
                   WHERE payment_no = :no
                     AND status IN ('PENDING', 'PROCESSING')
                     AND third_party_payment_id IS NULL      # 关键：已有第三方交易号的不关
        if affected == 0: continue
        if payment.status == 'PROCESSING':
            # 已进入第三方处理流程，不能单方面关闭，
            # 转由补偿任务查询真实结果（见 6.4）
            revert_to_active_and_enqueue_sync(payment.payment_no)
            continue
        log_info("payment closed by order.cancelled", payment_no=...)
    remove_idempotency_key(order_no)   # 释放 Redis 幂等键，允许后续重新支付
    mark_processed(event.event_id)
```

**关键判断**：`third_party_payment_id IS NULL` 的条件。如果支付单已经拿到了第三方交易号，说明第三方侧可能已产生真实交易，此时关闭本地支付单会产生"第三方有交易、本地已关闭"的差异。这类支付单**不关闭**，转由补偿任务（8.2）向第三方确认：若第三方确认成功则照常入账并发 `payment.succeeded`（用户确实付了钱，必须认账）；若第三方确认失败/取消才置 `FAILED`。

**幂等**：按 `event_id` 去重；条件更新天然幂等（重复执行影响行数为 0）。
**失败处理**：消费失败按通用约定重试 5 次（1s/5s/30s/2m/10m），仍失败进死信队列并告警。`order.cancelled` 的消费失败不会阻塞订单关闭本身（订单状态由订单服务维护），但会产生"订单已取消、支付单仍是进行中"的悬挂，由 8.1 的支付单超时关闭任务兜底（支付单过期后自行关闭）。

### 5.3 事件顺序保证

- 同一 `payment_no` 的 `payment.succeeded` 与 `payment.refunded` 可能前后到达订单服务。`payment.refunded` 的 payload 中携带 `total_refunded_amount_cents`，**让订单服务可以在乱序到达时以金额字段纠正状态**，而不是依赖事件顺序。
- 本服务投递 outbox 时按 `aggregate_id`（即 `payment_no`）保证发送顺序（`idx_outbox_aggregate_order`），但**不假设下游按序消费**。

## 6. 核心业务流程

### 6.0 支付单状态机

```
                    ┌──────────┐
   发起支付 ───────▶ │ PENDING  │
                    └────┬─────┘
                         │
        ┌────────────────┼────────────────┬─────────────────┐
        │                │                │                 │
   第三方确认成功   第三方返回失败   过期/订单取消     已发起第三方处理
        │                │                │                 │
        ▼                ▼                ▼                 ▼
   ┌──────────┐    ┌──────────┐    ┌──────────┐     ┌────────────┐
   │SUCCEEDED │    │  FAILED  │    │  CLOSED  │     │ PROCESSING │
   └────┬─────┘    └──────────┘    └──────────┘     └─────┬──────┘
        │                                                  │
        │                                          补偿查询第三方结果
        │                                       ┌──────────┼──────────┐
        │                                       ▼          ▼          ▼
        │                                  SUCCEEDED    FAILED    CLOSED
        │
        │ 退款（refunded_amount_cents 累加）
        ▼
   ┌─────────────────────────────────────────────┐
   │ refunded < amount  → 仍为 SUCCEEDED          │
   │ refunded = amount  → 仍为 SUCCEEDED          │
   └─────────────────────────────────────────────┘
   （退款状态记录在 refunds 表，payments.status 不因退款而改变——
    原因见下方说明）
```

**`payments.status` 不引入"已退款"状态的取舍说明**：

支付单的状态表达"这笔钱有没有收到"，退款是另一条独立的事实（记在 `refunds` 表与 `refunded_amount_cents` 字段）。若把 `REFUNDED`/`PARTIALLY_REFUNDED` 塞进 `payments.status`，会出现语义混淆：一个"已退款"的支付单是否还算"支付成功"？订单服务据此判断"订单是否已收款"时会得出错误结论。因此：

- 退款事实 → `refunds` 表（多次退款 = 多行）
- 退款进度 → `payments.refunded_amount_cents`
- 支付事实 → `payments.status = 'SUCCEEDED'`（一旦成功，永不回退）

对外展示"部分退款/已退款"由 `refunded_amount_cents` 与 `amount_cents` 的比较推导，不落成支付单状态。**注意与交易流水表的区别**：流水的"已退款"是记账视角（一条 OUT 流水），两者的 `status` 互不影响。

**状态迁移合法性表**：

| 原状态 | 允许迁移到 | 触发者 | 条件 |
|---|---|---|---|
| `PENDING` | `PROCESSING` | 回调（`payment_intent.processing` 等） | 验签通过 |
| `PENDING` | `SUCCEEDED` | 回调 / 补偿查询 | 验签通过且金额一致 |
| `PENDING` | `FAILED` | 回调 / 补偿查询 | 第三方明确失败 |
| `PENDING` | `CLOSED` | 定时任务 / `order.cancelled` | 已过期或订单取消，且无第三方交易号 |
| `PROCESSING` | `SUCCEEDED` | 回调 / 补偿查询 | 同上 |
| `PROCESSING` | `FAILED` | 回调 / 补偿查询 | 同上 |
| `PROCESSING` | `CLOSED` | **不允许** | 必须由补偿查询得第三方结论后转终态 |
| `SUCCEEDED` | 终态 | — | 不再迁移 |
| `FAILED` / `CLOSED` | 终态 | — | 不再迁移 |

所有状态迁移一律用**条件更新**（`WHERE status IN (...)`）+ `version` 校验实现，禁止"先读后写"。

### 6.1 发起支付（FR-PAY-001）

#### 6.1.1 步骤说明

| 步骤 | 动作 | 失败处理 |
|---|---|---|
| 1 | 校验 `Idempotency-Key` 存在，格式校验 | `PAY-1001` |
| 2 | Redis 幂等键预检 `pay:{order_no}:{channel}` | 命中则直接返回既有支付单（200 + `idempotent_replay`） |
| 3 | **调用订单服务**校验订单状态与金额 | 订单服务 404 → `PAY-4001`；状态非待支付 → `PAY-5001`；不可用 → `PAY-7001` |
| 4 | 校验订单归属（`order.user_id == X-User-Id`） | 不符 → `PAY-3001` |
| 5 | 校验订单未过期（`expires_at > now()`） | 已过期 → `PAY-5003` |
| 6 | 校验渠道可用性（熔断状态） | 熔断中 → `PAY-7004` |
| 7 | 本地事务：创建支付单（`PENDING`）+ 写 outbox（可选，本期不写） | 唯一键冲突 → 转查询返回既有支付单 |
| 8 | 调用第三方创建支付意图（**幂等键透传给第三方**） | 超时/失败 → 见 6.1.3 |
| 9 | 第三方返回后回写 `third_party_intent_id`、`pay_url`、`client_secret`、`channel_payload` | 回写失败 → 不阻塞返回，由补偿任务补 |
| 10 | 写 Redis 幂等键（TTL 7 天） | — |
| 11 | 返回凭据 | — |

#### 6.1.2 伪代码

```python
# app/services/payment_service.py

PAY_IDEM_TTL = 7 * 24 * 3600  # 7 天，通用约定第 6 章

async def create_payment(
    *, order_no: str, channel: str, idempotency_key: str,
    user_id: int, return_url: str | None, cancel_url: str | None,
    trace_id: str,
) -> PaymentResult:
    redis_key = f"payment:idem:pay:{order_no}:{channel}"

    # ── 步骤 1：幂等键格式校验 ────────────────────────────────
    validate_idempotency_key(idempotency_key)   # 长度 8~128，允许字符集校验

    # ── 步骤 2：Redis 幂等预检（快速路径）──────────────────────
    cached = await redis.get(redis_key)
    if cached:
        existing = await payment_repo.get_by_no(json.loads(cached)["payment_no"])
        if existing and existing.status in (PENDING, PROCESSING):
            return PaymentResult.replay(existing)
        # 支付单已进入终态：删除陈旧幂等键，允许重新发起
        await redis.delete(redis_key)

    # ── 步骤 3 & 4 & 5：向订单服务校验（金额以此为准，绝不信任客户端）
    try:
        order = await order_client.payment_check(order_no)   # 见 4.x 约定
    except OrderNotFound:
        raise BusinessError("PAY-4001", "订单不存在", http=404)
    except OrderServiceUnavailable:
        raise BusinessError("PAY-7001", "依赖服务暂不可用，请稍后重试", http=502)

    if order.user_id != user_id:
        raise BusinessError("COMMON-3001", "无权限执行该操作", http=403)
    if order.status != "PENDING_PAYMENT":
        raise BusinessError("PAY-5001", f"订单当前状态（{order.status}）不支持支付", http=409)
    if order.expires_at <= utcnow():
        raise BusinessError("PAY-5003", "支付已超时，请重新下单", http=409)

    # 客户端传入 amount_cents 时忽略并告警（防篡改观测点）
    if client_payload_contains_amount:
        metrics.inc("payments_client_amount_injected_total", channel=channel)
        logger.warning("client injected amount ignored", order_no=order_no, trace_id=trace_id)

    amount_cents = order.total_amount_cents      # ★ 唯一权威金额来源
    currency     = order.currency

    # ── 步骤 6：渠道可用性（熔断检查）─────────────────────────
    if circuit_breaker.is_open(channel):
        raise BusinessError("PAY-7004", "该支付渠道暂不可用，请选择其他渠道", http=502)

    # ── 步骤 7：本地事务创建支付单 ────────────────────────────
    payment_no = generate_payment_no()           # PA + yyyyMMdd + 10 位序列
    try:
        async with db.transaction():
            payment = await payment_repo.insert(
                payment_no=payment_no, order_no=order_no, user_id=user_id,
                channel=channel, status="PENDING",
                amount_cents=amount_cents, currency=currency,
                refunded_amount_cents=0,
                client_idempotency_key=idempotency_key,
                idempotency_key=f"pay:{order_no}:{channel}",
                expires_at=order.expires_at,
            )
    except UniqueViolation as exc:
        # uk_payments_order_channel_active 冲突：并发请求或历史进行中支付单
        if exc.constraint == "uk_payments_order_channel_active":
            existing = await payment_repo.get_active(order_no, channel)
            if existing:
                return PaymentResult.replay(existing)          # 返回既有支付单
        # uk_payments_payment_no 冲突：单号生成碰撞，重试一次
        raise BusinessError("PAY-8001", "服务内部错误", http=500)

    # ── 步骤 8：调用第三方创建支付意图（超时与失败处理见 6.1.3）──
    try:
        intent = await channel_gateway(channel).create_intent(
            payment_no=payment_no,          # 作为渠道侧幂等键（metadata/custom_id）
            order_no=order_no,
            amount_cents=amount_cents,
            currency=currency,
            return_url=return_url,
            cancel_url=cancel_url,
            idempotency_key=f"{payment_no}",   # ★ 第三方幂等键，重试安全
        )
    except ThirdPartyTimeout as exc:
        # 关键：不置失败。第三方可能已创建成功，转由补偿任务查询确认（6.4）
        await payment_repo.update(
            payment_no,
            where_status_in=["PENDING"],
            last_error_note="intent create timeout, awaiting compensation",
        )
        logger.error("third party create_intent timeout", payment_no=payment_no, trace_id=trace_id)
        raise BusinessError("PAY-7002", "支付渠道响应超时，请稍后重试或更换渠道", http=502)

    except ThirdPartyError as exc:
        # 明确失败（参数错误、渠道拒绝等），可直接置 FAILED
        await payment_repo.update(
            payment_no,
            where_status_in=["PENDING"],
            status="FAILED", fail_code=exc.code, fail_reason=exc.message,
            failed_at=utcnow(), version=F("version") + 1,
        )
        await outbox.publish(                       # payment.failed（可选，见 5.1.2 说明）
            event_type="payment.failed", aggregate_id=payment_no,
            payload={"payment_no": payment_no, "order_no": order_no,
                     "user_id": str(user_id), "amount_cents": amount_cents,
                     "channel": channel, "reason": "支付渠道拒绝，请稍后重试",
                     "fail_code": exc.code, "failed_at": iso(utcnow())},
            trace_id=trace_id,
        )
        raise BusinessError("PAY-7002", exc.user_message, http=502)

    # ── 步骤 9：回写第三方返回的凭据 ──────────────────────────
    await payment_repo.update(
        payment_no,
        where_status_in=["PENDING"],
        third_party_intent_id=intent.intent_id,
        third_party_payment_id=intent.payment_id,     # Stripe 可能立即给出 PI id
        pay_url=intent.pay_url,
        client_secret=intent.client_secret,
        channel_payload={"raw_status": intent.status},
        last_synced_at=utcnow(),
        version=F("version") + 1,
    )

    # ── 步骤 10：写幂等键（TTL 7 天）──────────────────────────
    await redis.set(redis_key, json.dumps({"payment_no": payment_no}),
                    nx=True, ex=PAY_IDEM_TTL)

    # ── 步骤 11：返回 ───────────────────────────────────────
    return PaymentResult.created(
        payment_no=payment_no, order_no=order_no, channel=channel,
        amount_cents=amount_cents, currency=currency,
        expires_at=order.expires_at,
        pay_type="CLIENT_SECRET" if channel == "STRIPE" else "REDIRECT",
        pay_payload=intent.client_payload(),
    )
```

#### 6.1.3 第三方超时与失败的处理原则

这是本流程最需要设计判断的地方。三种结果的处理截然不同：

| 第三方结果 | 本地动作 | 理由 |
|---|---|---|
| **明确成功返回** | 回写意图 ID，返回凭据 | 正常路径 |
| **明确失败**（4xx 参数错误、渠道拒绝） | 支付单置 `FAILED`，发布 `payment.failed`，返回 `PAY-7002` | 第三方明确告知未创建，本地无需补偿 |
| **超时 / 5xx / 网络错误**（结果未知） | 支付单**保持 `PENDING`**，不发布事件，返回 `PAY-7002` 但提示用户稍后重试 | **关键**：此时第三方可能已经创建了支付意图。若本地置 `FAILED`，用户可能仍完成支付，造成"第三方有交易、本地认为失败"的漏账 |

对"结果未知"的兜底路径有两条，互为补充：

1. **本地补偿**：补偿任务（8.2）扫描到该支付单超过 `PAYMENT_INTENT_CREATE_GRACE_SECONDS`（默认 120 秒）仍无 `third_party_intent_id`，则调用第三方的"按幂等键/本地订单号查询"能力反查（Stripe 可通过 List PaymentIntents + metadata 过滤，PayPal 可通过 invoice_id/custom_id 查询）。查到则回写意图 ID；查不到则说明创建确实未发生，此时才置 `FAILED`。
2. **第三方幂等键**：给第三方传递以 `payment_no` 为值的幂等键，使"本地重试创建"不会在第三方侧产生两个意图。这就是"支付创建类接口不能盲目重试，要靠幂等键"的落地方式——**重试的安全前提是幂等键存在**，而不是重试次数少。

**因此本服务对第三方创建类调用不配置自动重试**（见 6.10），重试完全由用户的幂等请求或补偿任务驱动。

### 6.2 支付单超时关闭（FR-PAY-009）

由定时任务触发（8.1），逻辑如下：

```python
async def close_expired_payments(batch_size: int = 500) -> int:
    """支付单超时关闭。与订单超时关闭联动，但有独立的兜底职责。"""
    closed = 0
    candidates = await payment_repo.find_expired_active(
        expires_before=utcnow(), limit=batch_size
    )   # WHERE status IN ('PENDING','PROCESSING') AND expires_at < now()

    for p in candidates:
        if p.status == "PROCESSING":
            # 已进入第三方处理，不能单方面关闭，转补偿确认（避免漏账）
            await sync_task.enqueue(p.payment_no, reason="expired_processing")
            continue

        affected = await payment_repo.update_conditional(
            payment_no=p.payment_no,
            set_values={"status": "CLOSED", "closed_at": utcnow()},
            where_status_in=["PENDING"],
            where_extra="third_party_payment_id IS NULL AND third_party_intent_id IS NULL",
            version=F("version") + 1,
        )
        if affected == 0:
            # 状态已变（刚支付成功）或已持有第三方标识 → 跳过
            continue

        mark_idempotency_key_stale(p.order_no, p.channel)   # 刷新 Redis 幂等键，允许重新支付
        closed += 1
        logger.info("payment closed by timeout", payment_no=p.payment_no)
    return closed
```

**与订单超时关闭的联动**：

| 场景 | 订单服务 | 支付服务 | 结果 |
|---|---|---|---|
| 订单先超时关闭 → 发 `order.cancelled` | 订单 `CLOSED` | 收到事件关闭支付单（5.2.2） | 一致 |
| 支付单先超时 → 订单仍待支付 | 订单由自身定时任务关闭 | 支付单 `CLOSED` | 一致（两条独立路径，最终都到关闭） |
| 订单关闭的瞬间用户正在支付 | 订单 `CLOSING`（过渡态） | 支付单**不关**（有第三方交易号或已 `PROCESSING`） | 回调到达 → `payment.succeeded` → 订单由 `CLOSING` 转 `PAID` |

两条路径不共享状态，靠 `CLOSING` 过渡态与"有第三方交易号不关"两个规则避免竞态。这是第 3 章"支付与订单只靠事件驱动"的必然代价：**收益是支付服务与订单服务可独立部署，代价是必须显式处理竞态，且对账是最终兜底。**

### 6.3 回调处理（FR-PAY-003，本文重点）

#### 6.3.1 总体时序

```
第三方 ──POST /webhook──▶ 网关（白名单放行，剥离身份头）
                            │
                            ▼
                        支付服务 Webhook 入口
                            │
                  ① 读原始 body（bytes，不解析）
                  ② 验签（Stripe: HMAC；PayPal: 调用验签 API）
                  ③ 落 payment_callback_logs（RECEIVED）
                            │
                  ④ 幂等校验（渠道 + 事件 ID 唯一索引）
                            │
                  ⑤ 解析业务字段 → 定位支付单
                            │
                  ⑥ 校验金额与币种一致
                            │
                  ⑦ 事务：条件更新支付单 + 写流水 + 写 outbox
                            │
                  ⑧ 返回 2xx（{"received": true}）
```

**为什么不在回调里做重活**：第三方回调有**严格的响应超时**（Stripe 要求 5 秒内响应，PayPal 要求 10 秒内），超时即视为投递失败并进入重试。若在回调里同步执行"更新订单状态"、"发通知"、"重载缓存"等操作，会把这个超时预算全部吃掉，导致：第三方认为失败 → 重试 → 产生重复回调（虽然幂等能挡，但放大了流量并延迟了用户看到支付结果）。因此本服务的设计是：**回调内只做"必须与第三方交互结果一致"的最小工作——验签、落证、幂等、金额校验、本地状态更新、写 outbox；其余由事件异步驱动。** 完成这一组操作只需 2~3 次数据库写，实测可稳定在 100ms 内。

各步骤耗时预算（用于验证设计符合超时要求）：

| 步骤 | 预期耗时 | 说明 |
|---|---|---|
| ① 读 body | < 1ms | 请求体 ≤ 64KB |
| ② 验签 | Stripe 1~5ms（本地 HMAC）；PayPal 200~800ms（远程 API） | PayPal 的验签是远程调用，是主要耗时项 |
| ③ 落日志 | 2~5ms | 单行 INSERT |
| ④ 幂等校验 | 1~3ms | 唯一索引命中 |
| ⑤ 定位支付单 | 1~3ms | 主键/唯一索引 |
| ⑥ 金额校验 | 0ms | 纯内存比较，不调订单服务 |
| ⑦ 事务写 | 5~15ms | 条件更新 + INSERT 流水 + INSERT outbox |
| 合计 | **≤ 50ms**（Stripe）/ **≤ 900ms**（PayPal） | 均远小于第三方超时 |

PayPal 的验签需要调用其 API，为控制耗时：设置 3 秒超时；验签失败或超时不影响落库（先落 `RECEIVED`，验签结果后回填）；对同一 `transmission_id` 的验签结果缓存 10 分钟（Redis），避免重放攻击导致的重复远程验签。

#### 6.3.2 Stripe 验签方式与关键点

Stripe 使用 **HMAC-SHA256 本地验签**，流程：

1. 从 `Stripe-Signature` 请求头解析出 `t`（时间戳）、`v1`（签名值）、`v0`（测试模式签名）等字段
2. 构造待签字符串 `{t}.{raw_body}`（`raw_body` 必须是**原始字节**，任何 JSON 反序列化再序列化都会破坏签名）
3. 用 **Webhook 端点密钥**（`STRIPE_WEBHOOK_SECRET`，注意**不是** API Key，两者用途不同）计算 HMAC-SHA256
4. 与 `v1` 做**常量时间比较**（防时序攻击）
5. 校验时间戳与当前时间差在容差内（默认 ±300 秒，防重放）

**关键点**：

- **必须用原始请求字节验签**。FastAPI 中需通过 `await request.body()` 获取原始 bytes，不能依赖 Pydantic 解析后的对象
- 端点密钥与 API Key 分离，且**每个环境、每个 webhook 端点各一个**（Stripe 支持多端点，如生产与测试分开）
- 时间戳容差既不能太大（削弱防重放）也不能太小（时钟漂移导致误判）。本服务配置为 300 秒，并在告警中区分"验签失败"与"时间戳超差"两类原因
- Stripe 可能一次投递包含**多个事件**（`data.object` 为数组的场景，如批量事件），或同一事件重投多次，都需要正确处理（见 6.3.4、6.3.6）

#### 6.3.3 PayPal 验签方式与关键点

PayPal 使用 **远程验签 API**（`POST /v1/notifications/verify-webhook-signature`），流程：

1. 从请求头取 `transmission_id`、`transmission_time`、`cert_url`、`auth_algo`、`transmission_sig`
2. 连同 `webhook_id`（本服务在 PayPal 后台注册的 webhook 的 ID，配置项 `PAYPAL_WEBHOOK_ID`）与**原始请求体**一起提交给 PayPal 验签接口
3. 验签接口返回 `verification_status = SUCCESS` / `FAILURE`

**关键点**：

- **验签的关键是 `webhook_id` 必须与接收配置严格对应**。同一个 PayPal 账号可能注册多个 webhook 端点，用错 ID 会全部验签失败（这是最常见的踩坑点）
- `cert_url` 由 PayPal 在请求头中提供，**不是本服务自行拼接**；不要自行下载证书做本地验签（PayPal 推荐远程验签，自行实现容易因证书链问题误判）
- 请求体同样必须原样透传，不能解析后重新序列化（PayPal 的签名覆盖原始字节）
- 远程验签是一次外部依赖调用，需要：超时 3 秒、失败不阻塞落库（先落 `RECEIVED` 标记 `verify_result='FAIL'` 并**异步重试验签一次**）、按 `transmission_id` 缓存结果 10 分钟
- **降级策略**：PayPal 验签接口不可用时，**不能放行**（验签是安全要求 NFR-SE-008），回调返回 500 让 PayPal 重试；同时告警。此时支付结果可由补偿任务（8.2）主动查询第三方得到，不依赖回调

**两种方式的对比**：

| 维度 | Stripe | PayPal |
|---|---|---|
| 验签方式 | 本地 HMAC-SHA256 | 远程 API 调用 |
| 依赖网络 | 否 | 是（外部依赖，需超时与降级） |
| 密钥/凭据 | `STRIPE_WEBHOOK_SECRET`（端点密钥） | `PAYPAL_WEBHOOK_ID` |
| 防重放 | 时间戳容差 ±300s | 依赖 PayPal 侧的 `transmission_id` 唯一性 + 本地事件唯一索引 |
| 耗时 | 1~5ms | 200~800ms |
| 失败代价 | 仅告警，无外部影响 | 验签接口不可用会导致回调无法确认 |

> 两种渠道的具体请求头字段名、算法细节以各渠道官方文档为准，本设计仅约定"必须在落库前完成验签，且验签失败的记录必须留存"这一不变量。

#### 6.3.4 回调处理伪代码（详细）

```python
# app/api/v1/webhooks.py → app/services/callback_service.py

@router.post("/payments/stripe/webhook")
async def stripe_webhook(request: Request) -> JSONResponse:
    raw_body: bytes = await request.body()                     # ★ 原始字节
    headers = dict(request.headers)
    client_ip = request.headers.get("X-Client-Ip")
    trace_id = request.headers.get("X-Trace-Id", new_trace_id())
    return await handle_webhook("STRIPE", raw_body, headers, client_ip, trace_id)


async def handle_webhook(
    channel: str, raw_body: bytes, headers: dict[str, str],
    client_ip: str | None, trace_id: str,
) -> JSONResponse:
    started = monotonic()
    log_id: int | None = None

    # ── ① 解析出可用于落库的最小字段（不做业务解析）────────────
    try:
        parsed = parse_raw(channel, raw_body)      # 仅做 json.loads + 取 id/type
    except MalformedPayload:
        logger.error("webhook malformed", channel=channel, trace_id=trace_id)
        metrics.inc("payment_callback_failed_total", reason="malformed", channel=channel)
        return JSONResponse({"error": "malformed payload"}, status_code=400)

    event_id   = parsed.third_party_event_id        # Stripe: event.id
    event_type = parsed.event_type                  # Stripe: event.type

    # ── ② 验签 ────────────────────────────────────────────
    verifier = WEBHOOK_VERIFIERS[channel]           # StripeVerifier / PaypalVerifier
    try:
        verify_result = await verifier.verify(raw_body, headers)
    except VerifierUnavailable as exc:
        # 验签依赖（PayPal API）不可用：不放行，返回 5xx 让第三方重试
        logger.error("verifier unavailable", channel=channel, error=str(exc), trace_id=trace_id)
        metrics.inc("payment_callback_failed_total", reason="verifier_unavailable", channel=channel)
        return JSONResponse({"error": "verification unavailable"}, status_code=500)

    # ── ③ 落原始回调记录（验签结果一并落库）──────────────────
    #     放在验签之后落库：验签失败的记录同样要落，用于攻击溯源
    try:
        log = await callback_log_repo.insert(
            channel=channel,
            third_party_event_id=event_id,
            event_type=event_type,
            payment_no=parsed.hinted_payment_no,     # 从 body 里尽力提取，判不出为 None
            raw_body=raw_body.decode("utf-8", errors="replace"),
            signature_headers=pick_signature_headers(channel, headers),
            client_ip=client_ip,
            verify_result="PASS" if verify_result.ok else "FAIL",
            process_result="RECEIVED",
        )
        log_id = log.id
    except UniqueViolation:
        # uk_callback_logs_channel_event：同一事件已处理过 → 重复回调，直接 200
        await callback_log_repo.update_by_event(
            channel, event_id, process_result="DUPLICATE",
        )
        metrics.inc("payment_callback_total", result="duplicate", channel=channel)
        return JSONResponse({"received": True, "duplicate": True}, status_code=200)

    # ── 验签失败：留证 + 告警 + 返回 400 ───────────────────────
    if not verify_result.ok:
        await callback_log_repo.update(
            log_id, process_result="FAILED",
            process_note=f"verify failed: {verify_result.reason}",
            process_duration_ms=elapsed_ms(started),
        )
        logger.error("webhook signature invalid",
                     channel=channel, event_id=event_id, reason=verify_result.reason,
                     client_ip=client_ip, trace_id=trace_id)
        metrics.inc("payment_callback_failed_total", reason="invalid_signature", channel=channel)
        alert.throttled("PAYMENT_WEBHOOK_SIGNATURE_INVALID", channel=channel, client_ip=client_ip)
        return JSONResponse({"error": "invalid signature"}, status_code=400)

    # ── ④ 事件类型过滤：不关心的事件直接 200 ──────────────────
    if event_type not in CHANNEL_EVENT_MAP[channel]:
        await callback_log_repo.update(log_id, process_result="IGNORED",
                                       process_note=f"unhandled event type: {event_type}")
        return JSONResponse({"received": True, "ignored": True}, status_code=200)

    # ── ⑤ 解析业务字段并定位支付单 ────────────────────────────
    biz = CHANNEL_EVENT_MAP[channel][event_type].parse(parsed)   # 归一化字段
    payment = await resolve_payment(channel, biz)                 # 见 6.3.7

    if payment is None:
        # 找不到支付单：不创建、不修改，留证 + 告警，返回 200（避免无意义重试）
        await callback_log_repo.update(
            log_id, process_result="IGNORED",
            process_note=f"payment not found: {biz.identify_hint()}",
            process_duration_ms=elapsed_ms(started),
        )
        logger.error("webhook payment not found",
                     channel=channel, event_id=event_id, hint=biz.identify_hint(),
                     trace_id=trace_id)
        metrics.inc("payment_callback_failed_total", reason="payment_not_found", channel=channel)
        alert.throttled("PAYMENT_WEBHOOK_PAYMENT_NOT_FOUND", channel=channel, hint=...)
        return JSONResponse({"received": True, "unmatched": True}, status_code=200)

    # ── ⑥ 金额校验（关键防篡改点，纯内存比较）──────────────────
    expected_cents = payment.amount_cents
    actual_cents   = biz.amount_cents          # 已由渠道适配层归一化为"分"

    if actual_cents != expected_cents or biz.currency != payment.currency:
        await callback_log_repo.update(
            log_id, process_result="IGNORED",
            process_note=(f"amount/currency mismatch: local={expected_cents}"
                          f"{payment.currency} third={actual_cents}{biz.currency}"),
            process_duration_ms=elapsed_ms(started),
        )
        logger.error("webhook amount mismatch",
                     payment_no=payment.payment_no, local=expected_cents,
                     third_party=actual_cents, trace_id=trace_id)
        metrics.inc("payment_callback_failed_total", reason="amount_mismatch", channel=channel)
        alert.immediate("PAYMENT_WEBHOOK_AMOUNT_MISMATCH",
                        payment_no=payment.payment_no,
                        local=expected_cents, third=actual_cents)   # P0 告警
        # ★ 不修改支付单状态、不入账、不驱动订单
        return JSONResponse({"received": True, "mismatch": True}, status_code=200)

    # ── ⑦ 事务：条件更新支付单 + 流水 + outbox ─────────────────
    try:
        async with db.transaction():
            result = await apply_payment_outcome(     # 见 6.3.5 决策表
                payment=payment, biz=biz, channel=channel,
                event_id=event_id, trace_id=trace_id,
            )
    except Exception as exc:
        # DB 不可用等内部错误：返回 500，依赖第三方重试
        # 回调日志已落库，重试时将在 ④ 命中 DUPLICATE 或被重新处理（见下方说明）
        await callback_log_repo.update(
            log_id, process_result="FAILED", process_note=f"internal error: {exc}",
        )
        logger.exception("webhook processing failed", payment_no=payment.payment_no,
                         trace_id=trace_id)
        metrics.inc("payment_callback_failed_total", reason="internal_error", channel=channel)
        return JSONResponse({"error": "internal error"}, status_code=500)

    # ── ⑧ 回填回调日志结论并返回 2xx ───────────────────────────
    await callback_log_repo.update(
        log_id,
        process_result="SUCCESS" if result.changed else "DUPLICATE",
        process_note=result.note,
        payment_no=payment.payment_no,
        process_duration_ms=elapsed_ms(started),
    )
    metrics.inc("payment_callback_total", result="success", channel=channel)
    return JSONResponse({"received": True}, status_code=200)
```

**关于③落库与⑦处理之间的失败窗口**：如果回调日志落库成功（`RECEIVED`）但后续处理因 DB 异常未完成，第三方会重试；重试时步骤 ③ 会因 `uk_callback_logs_channel_event` 冲突进入 `DUPLICATE` 分支并直接返回 200——**这会造成漏处理**。为堵住这个洞，重试请求在 `DUPLICATE` 分支中先检查原记录的 `process_result`：

```python
except UniqueViolation:
    original = await callback_log_repo.get_by_event(channel, event_id)
    if original.process_result in ("RECEIVED", "FAILED"):
        # 上次未处理完（如返回 500 后第三方重试）→ 继续走处理流程
        log_id = original.id
        # 落到步骤 ④ 之后的正常处理
    else:
        return JSONResponse({"received": True, "duplicate": True}, status_code=200)
```

即：**唯一索引的冲突判定不是"见过就跳过"，而是"处理完成才跳过"**。

#### 6.3.5 三种异常的处理（分别说明）

**异常一：验签失败**

| 项 | 处理 |
|---|---|
| 判定 | 渠道验签器返回失败（签名不匹配 / 时间戳超差 / 缺少签名头） |
| 落库 | 落 `payment_callback_logs`，`verify_result='FAIL'`，`process_result='FAILED'`，`process_note` 记录失败原因分类 |
| 业务动作 | **不解析业务字段，不触碰任何业务表** |
| HTTP 响应 | `400 {"error": "invalid signature"}` |
| 告警 | `PAYMENT_WEBHOOK_SIGNATURE_INVALID`，节流（同 IP 5 分钟内只告警一次）。第三方回调验签失败率突增往往是攻击或密钥配置错误的信号 |
| 安全 | 对来源 IP 做 60 秒 20 次的滑动窗口限流；连续失败 100 次的 IP 加入网关黑名单 |

**异常二：金额不符**

| 项 | 处理 |
|---|---|
| 判定 | 验签通过，但回调中的 `amount_cents` ≠ `payments.amount_cents`，或 `currency` 不一致 |
| 落库 | `verify_result='PASS'`，`process_result='IGNORED'`，`process_note` 记录两侧金额 |
| 业务动作 | **不修改支付单状态、不写交易流水、不写 outbox、不发事件、不驱动订单**。这一点非常重要：金额不符意味着要么第三方侧出了错（如用户实际付了更少的钱），要么本地金额被篡改。任何一种情况下把支付单置为 `SUCCEEDED` 都会造成资损 |
| HTTP 响应 | `200 {"received": true, "mismatch": true}`。回 200 是刻意的：回 4xx/5xx 会让第三方无限重试同一错误报文，而这个问题**必须由人工介入**（补单或退款），重试不会改善 |
| 告警 | `PAYMENT_WEBHOOK_AMOUNT_MISMATCH`，**P0 立即告警**（不节流），通知财务与值班 |
| 后续 | 人工按渠道后台核对。若确认第三方确为少付，由订单服务侧走"异常订单"流程（FR-ORD-014）；本服务不自动处理。此类差异在次日对账中会以 `AMOUNT_MISMATCH` 再次暴露，形成第二道发现机制 |

**异常三：找不到支付单**

| 情形 | 判定方式 | 处理 |
|---|---|---|
| 回调先于支付单创建到达（极罕见，网络乱序） | 回调查询不到支付单，且创建流程尚未完成 | 记 `IGNORED`，`process_note='payment not found'`，**返回 200**。由补偿任务（8.2）在支付单创建完成后主动查询第三方补状态 |
| 第三方事件属于其他系统（同一 Stripe 账号被其他应用使用） | 回调中 `metadata.payment_no` 为空且 `channel_payload` 匹配不到 | 记 `IGNORED`，返回 200。需在渠道侧配置按 endpoint 过滤，避免无关事件打到本服务 |
| 支付单号存在但渠道不符（同一 `payment_no` 却是另一渠道的回调） | `resolve_payment` 校验 `payment.channel == channel` 失败 | 记 `IGNORED` 并**告警**（这可能意味着配置错误或伪造），返回 200 |
| 伪造回调（验签通过但支付单号瞎编） | 验签通过说明来自真实渠道，但支付单号查不到 | 记 `IGNORED` + 告警，返回 200。这是最可疑的一类，需人工排查 |

**为什么"找不到支付单"也返回 200**：回 4xx 会让第三方重试，而重试无法让支付单出现（除非是第一种乱序情形，而那种情形由补偿任务处理更可靠）。返回 200 并靠补偿任务 + 对账发现差异，是更可控的路径。

`resolve_payment` 的查找顺序（按可靠性从高到低）：

```python
async def resolve_payment(channel: str, biz: NormalizedEvent) -> Payment | None:
    # ① 本地支付单号（最可靠，Stripe metadata.payment_no / PayPal custom_id）
    if biz.payment_no:
        p = await payment_repo.get_by_no(biz.payment_no)
        if p and p.channel == channel:
            return p
    # ② 第三方意图 ID（Stripe PaymentIntent ID / PayPal order id）
    if biz.third_party_intent_id:
        p = await payment_repo.get_by_intent_id(channel, biz.third_party_intent_id)
        if p:
            return p
    # ③ 第三方交易号（可能的二次回调，如 refund 事件）
    if biz.third_party_payment_id:
        p = await payment_repo.get_by_third_party_id(channel, biz.third_party_payment_id)
        if p:
            return p
    # ④ 订单号（PayPal 的 invoice_id 常为订单号）
    if biz.order_no:
        p = await payment_repo.get_latest_by_order(biz.order_no, channel)
        if p:
            return p
    return None      # 四种方式都定位不到 → 异常三
```

#### 6.3.6 幂等实现细节（数据库索引的具体建法）

回调幂等依赖**三层**防护，缺一不可：

| 层 | 机制 | 覆盖的重复场景 | 失效场景 |
|---|---|---|---|
| L1 | `uk_callback_logs_channel_event`（渠道 + 第三方事件 ID 唯一） | 第三方对**同一事件**的重复投递 | 事件 ID 缺失（偶发） |
| L2 | `uk_payment_transactions_third_party`（渠道 + 第三方交易号唯一） | 第三方以**不同事件 ID** 投递同一笔交易（如 Stripe 的 `payment_intent.succeeded` 与 `charge.succeeded` 都带同一 charge id） | 退款场景（交易号不同） |
| L3 | `uk_payments_third_party_payment_id`（渠道 + 第三方支付号唯一） | 上述两层都失效时的最终兜底 | — |

索引建法（已含于 2.11 DDL，此处强调关键点）：

```sql
-- L1：只对能取到事件 ID 的回调生效，NULL 不参与约束
CREATE UNIQUE INDEX uk_callback_logs_channel_event
    ON payment_callback_logs (channel, third_party_event_id)
    WHERE third_party_event_id IS NOT NULL;

-- L2：这是通用约定第 6 章"支付回调 → 第三方交易号 → 支付流水表唯一索引"的直接落地
CREATE UNIQUE INDEX uk_payment_transactions_third_party
    ON payment_transactions (channel, third_party_transaction_id)
    WHERE third_party_transaction_id IS NOT NULL;

-- L3：兜底
CREATE UNIQUE INDEX uk_payments_third_party_payment_id
    ON payments (channel, third_party_payment_id)
    WHERE third_party_payment_id IS NOT NULL;
```

**为什么都加 `WHERE ... IS NOT NULL`**：PostgreSQL 中 `NULL` 之间互不相等，`UNIQUE` 索引允许多行 NULL。既然 NULL 天然不冲突，加不加部分索引条件都能工作；加上是为了**让索引体积更小**（不索引 NULL 项）并**明确表达设计意图**（"只有拿到第三方标识的行才需要防重"）。

**为什么 L2 是主力而不是 L1**：第三方可能对同一笔交易发出多个不同类型的事件（Stripe 的 `payment_intent.succeeded`、`charge.succeeded`、`charge.updated` 都可能到达），它们的事件 ID 不同而交易号相同。L1 挡不住，L2 能挡住——**幂等的正确语义是"同一笔交易不重复入账"，而不是"同一条消息不重复处理"**。这一点是本服务幂等设计中最容易做错的地方。

**处理顺序**：先 L1（进程内快速返回，省一次业务处理），再在事务内靠 L2 兜底，最后 L3 作为数据库约束的兜底（触发意味着前面的逻辑有 bug，必须告警 `PAYMENT_DUPLICATE_SETTLEMENT`）。

`apply_payment_outcome` 的事务实现：

```python
async def apply_payment_outcome(*, payment, biz, channel, event_id, trace_id) -> Outcome:
    """在单一事务内完成支付结果落定。调用方已保证验签通过、金额一致。"""

    if biz.outcome == "SUCCEEDED":
        # 条件更新：仅当仍为进行中时生效（乐观锁，防并发回调）
        affected = await payment_repo.update_conditional(
            payment_no=payment.payment_no,
            set_values={
                "status": "SUCCEEDED",
                "third_party_payment_id": biz.third_party_payment_id,
                "third_party_intent_id": biz.third_party_intent_id or payment.third_party_intent_id,
                "paid_at": biz.occurred_at,
                "last_synced_at": utcnow(),
                "version": F("version") + 1,
            },
            where_status_in=["PENDING", "PROCESSING"],
            version=payment.version,                   # 乐观锁
        )
        if affected == 0:
            # 已被处理过（并发回调或补偿任务先行）→ 幂等返回，不重复入账
            return Outcome(changed=False, note="already settled")

        # 交易流水：L2 唯一索引在此生效
        try:
            await transaction_repo.insert(
                transaction_no=generate_transaction_no(),
                transaction_type="PAYMENT", direction="IN",
                payment_no=payment.payment_no, order_no=payment.order_no,
                user_id=payment.user_id, channel=channel,
                amount_cents=payment.amount_cents, currency=payment.currency,
                status="SUCCEEDED",
                third_party_transaction_id=biz.third_party_payment_id,
                third_party_event_id=event_id,
                transaction_at=biz.occurred_at,
                reconciliation_batch_no=None,
            )
        except UniqueViolation:
            # 同一第三方交易号已记账（不同事件 ID 的同一笔交易）
            # 说明 update_conditional 的幂等已生效但流水已存在 → 视为重复
            raise DuplicateSettlement(payment_no=payment.payment_no)

        # 事务性发件箱：与上面两步同一事务
        await outbox.publish(
            event_type="payment.succeeded",
            event_version="1.0",
            aggregate_type="PAYMENT",
            aggregate_id=payment.payment_no,
            payload={
                "payment_no": payment.payment_no,
                "order_no": payment.order_no,
                "user_id": str(payment.user_id),
                "amount_cents": payment.amount_cents,
                "currency": payment.currency,
                "channel": channel,
                "third_party_payment_id": biz.third_party_payment_id,
                "paid_at": iso(biz.occurred_at),
            },
            trace_id=trace_id,
        )
        return Outcome(changed=True, note="payment settled")

    if biz.outcome == "FAILED":
        affected = await payment_repo.update_conditional(
            payment_no=payment.payment_no,
            set_values={"status": "FAILED", "fail_code": biz.fail_code,
                        "fail_reason": biz.user_message,
                        "failed_at": biz.occurred_at, "version": F("version") + 1},
            where_status_in=["PENDING", "PROCESSING"],
            version=payment.version,
        )
        if affected == 0:
            return Outcome(changed=False, note="already settled")
        await outbox.publish(
            event_type="payment.failed", aggregate_type="PAYMENT",
            aggregate_id=payment.payment_no,
            payload={...}, trace_id=trace_id,
        )
        return Outcome(changed=True, note="payment failed")

    if biz.outcome == "PROCESSING":
        # 中间态：仅推进状态，不写流水、不发事件
        affected = await payment_repo.update_conditional(
            payment_no=payment.payment_no,
            set_values={"status": "PROCESSING", "last_synced_at": utcnow(),
                        "version": F("version") + 1},
            where_status_in=["PENDING"],
        )
        return Outcome(changed=affected == 1, note="processing")

    raise UnsupportedOutcome(biz.outcome)
```

> **`payment.failed` 与事务的取舍**：`FAILED` 分支也走 outbox，但注意：如果未来出现"先收到 failed 回调、随后又收到 succeeded 回调"（第三方状态反复），由于 `failed` 是终态，第二次回调的 `where_status_in=["PENDING","PROCESSING"]` 会失效，导致**漏入账**。这是真实存在的风险（Stripe 的 `payment_intent.payment_failed` 之后可能有重试成功）。因此本服务的处理是：**`FAILED` 不是绝对的终态，允许 `FAILED → SUCCEEDED` 的特殊迁移**，在补偿查询（6.4）中实现：

```python
async def compensate_failed_then_succeeded(payment_no: str, biz) -> None:
    """第三方先报失败、后续又成功（如重试扣款成功）的兜底。
    仅在补偿查询路径启用，且必须能拿到有效的第三方支付号。"""
    affected = await payment_repo.update_conditional(
        payment_no=payment_no,
        set_values={"status": "SUCCEEDED", "third_party_payment_id": biz.third_party_payment_id,
                    "paid_at": biz.occurred_at, "fail_code": None, "fail_reason": None,
                    "version": F("version") + 1},
        where_status_in=["FAILED"],
        where_extra="third_party_payment_id IS NULL",   # 防止覆盖已入账的成功
    )
    if affected == 0:
        return
    await alert.immediate("PAYMENT_FAILED_TO_SUCCEEDED", payment_no=payment_no)
    logger.warning("payment recovered from FAILED to SUCCEEDED", payment_no=payment_no)
    # 补写流水 + outbox（同事务）
```

这一迁移会触发 P1 告警，需人工确认资金确实到账。

#### 6.3.7 快速返回 2xx 的理由（总结）

| 理由 | 说明 |
|---|---|
| 第三方有严格超时 | Stripe 5 秒、PayPal 10 秒。超时即重试，重试放大了幂等压力 |
| 用户感知延迟 | 支付页轮询结果，回调处理越快，用户越早看到"支付成功" |
| 重试风暴 | 处理慢导致的超时重试是"假重复"（同一事件 ID 反复投递），虽然幂等能挡，但浪费资源并污染监控指标 |
| 失败可观测 | 一旦处理超过超时，第三方会重试，而本服务已把原始报文落库（步骤 ③ 在验签后立即执行），即使响应 500，重试也能继续处理（6.3.4 的 `RECEIVED` 复查逻辑） |

**"快速返回"不等于"提前返回"**：本服务**不采用**"收到回调先回 200、业务完全异步处理"的模式。理由是：若异步处理失败，第三方已收到成功响应不会重试，只能靠补偿任务兜底，可靠性下降。本服务选择的是"**同步完成最小必要工作后再返回**"——因为最小必要工作（验签 + 3 次 DB 写 + 内存金额校验）本身就在 100ms 量级，完全在超时预算内，没有理由异步化。真正重的工作（通知、订单状态更新、库存扣减）本来就通过事件交给了下游服务。

### 6.4 回调丢失补偿（FR-PAY-004）

#### 6.4.1 场景与策略

回调丢失的四种可能原因：

| 原因 | 表现 | 补偿手段 |
|---|---|---|
| 第三方回调投递失败（网络/我方 5xx 超过重试上限） | 支付单长期 `PENDING`，第三方侧已成功 | 定时主动查询（8.2） |
| 我方处理成功但响应丢失，第三方停止重试 | 支付单已 `SUCCEEDED`，无影响 | 无需补偿（本地已正确） |
| 用户支付完成但未返回平台（关闭页面） | 支付单 `PENDING` | 定时主动查询 |
| 第三方系统故障延迟回调 | 支付单 `PENDING` 超过正常时长 | 定时主动查询 + 延长补偿窗口 |

#### 6.4.2 补偿查询伪代码

```python
# app/tasks/payment_compensation.py

async def scan_and_compensate() -> None:
    """每 2 分钟执行一次（见 8.2）。扫描需要补偿的支付单。"""
    now = utcnow()

    # 取两类：①已过期望回调时间仍未终态的；②PROCESSING 超过一定时长的
    candidates = await payment_repo.find_for_compensation(
        pending_before   = now - timedelta(seconds=cfg.COMPENSATE_PENDING_AFTER_SECONDS),   # 默认 180s
        processing_before= now - timedelta(seconds=cfg.COMPENSATE_PROCESSING_AFTER_SECONDS),# 默认 300s
        limit=cfg.COMPENSATE_BATCH_SIZE,   # 默认 200
    )

    for p in candidates:
        if p.status == "CLOSED":        # 竞态：刚被关闭
            continue
        if p.expires_at < now - timedelta(hours=cfg.COMPENSATE_MAX_AGE_HOURS):  # 默认 72h
            # 超出补偿窗口：不再无限查询，转人工（对账会持续暴露）
            if not p.compensation_abandoned:      # 由 alert 节流控制，避免重复告警
                alert.immediate("PAYMENT_COMPENSATION_EXHAUSTED", payment_no=p.payment_no)
            continue

        try:
            await sync_one(p.payment_no, reason="compensation")
        except ThirdPartyUnavailable:
            continue          # 本次跳过，下轮再来；不做重试风暴
        except Exception:
            logger.exception("compensation failed", payment_no=p.payment_no)


async def sync_one(payment_no: str, *, reason: str) -> SyncResult:
    """向第三方查询支付单真实状态并落库。被补偿任务、/sync 接口、订单取消事件共用。"""
    payment = await payment_repo.get_by_no(payment_no)
    if payment is None or payment.status in ("SUCCEEDED",):
        return SyncResult.noop()

    # ① 优先按第三方意图 ID 查询；没有则按本地单号/订单号反查
    query_key = (
        QueryKey(intent_id=payment.third_party_intent_id) if payment.third_party_intent_id
        else QueryKey(merchant_ref=payment.payment_no, order_no=payment.order_no)
    )
    remote = await channel_gateway(payment.channel).query_intent(query_key)   # 见 6.10

    if remote is None:
        # 第三方侧查无此单
        if payment.status == "PENDING" and payment.third_party_intent_id is None \
           and utcnow() > payment.expires_at:
            # 从未创建成功且已过期 → 关闭（不是失败）
            await close_payment(payment_no, reason="never_created_and_expired")
        return SyncResult.noop()

    # ② 归一化第三方状态并落库（复用回调处理的事务逻辑，保证一致性）
    biz = normalize(channel=payment.channel, remote=remote, source="compensation")

    if biz.outcome == "SUCCEEDED" and biz.amount_cents != payment.amount_cents:
        # 补偿查询同样必须校验金额，规则与回调一致
        alert.immediate("PAYMENT_SYNC_AMOUNT_MISMATCH",
                        payment_no=payment_no, local=payment.amount_cents,
                        third=biz.amount_cents)
        return SyncResult.mismatch()

    async with db.transaction():
        outcome = await apply_payment_outcome(     # 与回调共用同一函数
            payment=payment, biz=biz, channel=payment.channel,
            event_id=None, trace_id=current_trace_id(),
        )
        # ③ 处理 FAILED → SUCCEEDED 的特殊恢复（6.3.6）
        if biz.outcome == "SUCCEEDED" and payment.status == "FAILED":
            await compensate_failed_then_succeeded(payment_no, biz)

    await payment_repo.touch_synced(payment_no, synced_at=utcnow())
    metrics.inc("payment_compensation_total", result=outcome.note, channel=payment.channel)
    logger.info("payment synced", payment_no=payment_no, reason=reason,
                before=payment.status, after=biz.outcome)
    return SyncResult.of(payment.status, biz.outcome, outcome.changed)
```

#### 6.4.3 与第三方重试的配合

| 我方行为 | 第三方行为 | 配合结果 |
|---|---|---|
| 回调返回 2xx | 停止重试 | 正常收尾 |
| 回调返回 5xx/超时 | 按自带退避策略重试（Stripe 最长约 3 天，PayPal 约 3 天） | 我方补偿任务在 **180 秒** 后就开始主动查询，早于第三方的最后一次重试。因此补偿任务通常**先于**第三方重试拿到结果 |
| 补偿任务先拿到结果并置 `SUCCEEDED` | 第三方重试到达 | 回调处理时 `where_status_in=['PENDING','PROCESSING']` 更新影响行数为 0，且 L2 唯一索引冲突 → 识别为重复，返回 2xx，不发第二次事件 |

**避免"双重入账"的关键**：补偿查询与回调处理**共用 `apply_payment_outcome`**，走同一套条件更新与唯一索引。这与"两条路径各自实现一遍"的方案相比，杜绝了实现漂移导致的重复入账。

**避免"重复告警"**：两条路径都可能触发 `PAYMENT_COMPENSATION_EXHAUSTED` 之类的告警，通过 Redis 键 `payment:alert:{type}:{payment_no}`（TTL 6 小时）节流。

#### 6.5.2 Redis 幂等键的读写规范

```python
# 统一封装，避免各处方言不一致
class IdempotencyStore:
    def key(self, kind: str, *parts) -> str:
        return f"payment:idem:{kind}:" + ":".join(str(p) for p in parts)

    async def get(self, kind, *parts) -> dict | None:
        raw = await redis.get(self.key(kind, *parts))
        return json.loads(raw) if raw else None

    async def acquire(self, kind, *parts, value: dict, ttl: int) -> bool:
        """NX 抢占。返回 False 表示已被占用。"""
        return await redis.set(self.key(kind, *parts), json.dumps(value),
                               nx=True, ex=ttl)

    async def refresh(self, kind, *parts, value: dict, ttl: int) -> None:
        """支付单进入终态后刷新键值，使后续请求能识别到终态并放行重试。"""
        await redis.set(self.key(kind, *parts), json.dumps(value), ex=ttl)
```

**关键设计**：Redis 幂等键的 value **不缓存支付单内容，只缓存 `payment_no`**。命中后回数据库读取支付单真实状态——因为支付单状态会变化，缓存内容会过期失真。这与通用约定"幂等键"的用法略有不同（约定倾向缓存首次结果），本服务选择"键值只做指针"，因为支付单是会被高频更新的实体，缓存其快照只会带来不一致。

### 6.6 退款（FR-PAY-006）

#### 6.6.1 前置校验与真实可退金额

```python
async def prepare_refund(*, payment_no, amount_cents, reason, idempotency_key,
                        operator_id, operator_roles, user_id) -> RefundPlan:
    payment = await payment_repo.get_by_no(payment_no)
    if payment is None:
        raise BusinessError("PAY-4002", "支付单不存在", http=404)

    # ① 归属校验（买家只能退自己的）
    if "BUYER" in operator_roles and payment.user_id != user_id:
        raise BusinessError("COMMON-3001", "无权限执行该操作", http=403)
    # 财务无退款发起权（职责分离）
    if operator_roles == {"FINANCE"}:
        raise BusinessError("COMMON-3001", "无权限执行该操作", http=403)

    # ② 状态校验
    if payment.status != "SUCCEEDED":
        raise BusinessError("PAY-5002", "该支付单当前状态不支持退款", http=409)

    # ③ 金额校验（服务端计算可退金额，绝不信任客户端）
    refundable = payment.amount_cents - payment.refunded_amount_cents
    if amount_cents <= 0:
        raise BusinessError("COMMON-1001", "退款金额必须大于 0", http=400)
    if amount_cents > refundable:
        raise BusinessError("PAY-5007", "退款金额超过可退金额", http=409,
                            details=[{"field": "amount_cents",
                                      "reason": f"当前可退金额 {refundable} 分"}])

    # ④ 退款类型由服务端判定，不信任客户端
    refund_type = "FULL" if amount_cents == payment.amount_cents else "PARTIAL"

    # ⑤ 是否存在未完成的退款（避免并发退款导致超额）
    pending_count = await refund_repo.count_pending(payment_no)
    if pending_count > 0:
        raise BusinessError("PAY-5009", "该支付单存在处理中的退款，请稍后重试", http=409)

    return RefundPlan(payment=payment, amount_cents=amount_cents,
                      refund_type=refund_type, refundable_before=refundable)
```

#### 6.6.3 退款金额校验：条件更新保证累计不超限（重点）

**问题的本质**：单笔退款金额可以在插入时用 `CHECK (amount_cents <= payment_amount_cents)` 约束住，但"**多笔部分退款累计不超过支付金额**"是一个**跨行**约束，`CHECK` 管不了，应用层的"读-算-写"在并发下也不可靠（两个并发退款各自读到 `refunded_amount_cents = 19900` 的旧值，都认为还能退 19900，各退 10000，合计 20000 超出）。

**解决方案：把累计金额的校验与更新合并为一条原子的条件更新语句。**

```python
async def reserve_refund_amount(payment_no: str, amount_cents: int) -> int:
    """在支付单上原子地预占退款额度。
    返回受影响行数：1 表示预占成功，0 表示可退金额不足或状态不允许。
    """
    sql = text("""
        UPDATE payments
           SET refunded_amount_cents = refunded_amount_cents + :amount,
               version = version + 1,
               updated_at = now()
         WHERE payment_no = :payment_no
           AND status = 'SUCCEEDED'
           AND refunded_amount_cents + :amount <= amount_cents    -- ★ 累计上限的原子校验
    """)
    result = await db.execute(sql, {"payment_no": payment_no, "amount": amount_cents})
    return result.rowcount
```

这个语句的四个要点：

1. **`refunded_amount_cents + :amount <= amount_cents` 写在 `WHERE` 里**，由数据库在行锁保护下求值，天然排除了并发读旧值的问题。这是 PostgreSQL 的 `UPDATE ... WHERE` 语义：行被锁定后再求值条件，两个并发事务会串行执行
2. **`status = 'SUCCEEDED'` 也在 `WHERE` 里**，防止对未支付成功的单退款
3. **`version = version + 1`** 使其他基于乐观锁的更新（如回调处理）能感知到变更
4. **返回 `rowcount`**，调用方据此判断成败，不依赖异常

**完整的退款执行流程（含预占与释放）**：

```python
async def execute_refund(refund_no: str, *, trace_id: str, manual_retry: bool = False) -> None:
    refund = await refund_repo.get_by_no(refund_no)
    if refund.status not in ("PENDING", "FAILED"):
        return                                   # 已终态，幂等返回

    # ── ① 原子预占退款额度 ────────────────────────────────────
    affected = await reserve_refund_amount(refund.payment_no, refund.amount_cents)
    if affected == 0:
        # 可退金额不足：可能是并发退款已占用额度
        payment = await payment_repo.get_by_no(refund.payment_no)
        refundable = payment.amount_cents - payment.refunded_amount_cents
        await refund_repo.update_conditional(
            refund_no=refund_no, where_status_in=["PENDING", "FAILED"],
            set_values={"status": "CLOSED", "fail_code": "insufficient_refundable",
                        "fail_reason": f"可退金额不足，当前可退 {refundable} 分"},
        )
        logger.error("refund amount reservation failed", refund_no=refund_no,
                     refundable=refundable, requested=refund.amount_cents)
        metrics.inc("payment_refund_rejected_total", reason="insufficient_refundable")
        # 订单服务侧的退款申请应被标记为失败，通知客服
        await notify_refund_rejected(refund_no, reason="可退金额不足")
        return

    # ── ② 调用第三方退款 ─────────────────────────────────────
    try:
        third = await channel_gateway(refund.channel).create_refund(
            payment_no=refund.payment_no,
            third_party_payment_id=payment.third_party_payment_id,
            amount_cents=refund.amount_cents,
            currency=refund.currency,
            reason=refund.reason,
            idempotency_key=refund.refund_no,     # ★ 第三方幂等键
        )
    except ThirdPartyTimeout:
        # 结果未知：保留预占额度（因为第三方可能已退），转补偿同步（8.3）
        await refund_repo.update(
            refund_no,
            last_synced_at=utcnow(),
            fail_reason="第三方响应超时，等待同步确认",
            retry_count=F("retry_count") + 1,
        )
        logger.error("refund create timeout", refund_no=refund_no, trace_id=trace_id)
        return

    except ThirdPartyError as exc:
        # 明确失败：释放预占额度
        await release_refund_amount(refund.payment_no, refund.amount_cents)
        retry_count = refund.retry_count + 1
        if retry_count >= cfg.REFUND_MAX_RETRY:
            await refund_repo.update(
                refund_no, status="FAILED", fail_code=exc.code,
                fail_reason=f"{exc.message}（已重试 {retry_count} 次，转人工处理）",
                failed_at=utcnow(), retry_count=retry_count,
            )
            alert.immediate("REFUND_NEED_MANUAL", refund_no=refund_no,
                            reason=exc.code, retry_count=retry_count)
        else:
            await refund_repo.update(
                refund_no, fail_code=exc.code, fail_reason=exc.message,
                retry_count=retry_count,      # 保持 PENDING，由 8.3 重试
            )
        return

    # ── ③ 第三方接受请求：记录退款号，等待异步回调 ─────────────
    status = map_refund_status(refund.channel, third.status)
    await refund_repo.update_conditional(
        refund_no=refund_no, where_status_in=["PENDING", "FAILED"],
        set_values={
            "third_party_refund_id": third.refund_id,
            "status": "PENDING",
            "last_synced_at": utcnow(),
            "version": F("version") + 1,
        },
    )
    # 若第三方同步返回成功（部分渠道即时返回），直接落定
    if status == "SUCCEEDED":
        await settle_refund_success(refund_no, third, occurred_at=utcnow(), trace_id=trace_id)


async def release_refund_amount(payment_no: str, amount_cents: int) -> None:
    """退款明确失败时释放预占额度。条件保证不会把已退金额减成负数。"""
    await db.execute(text("""
        UPDATE payments
           SET refunded_amount_cents = refunded_amount_cents - :amount,
               version = version + 1,
               updated_at = now()
         WHERE payment_no = :payment_no
           AND refunded_amount_cents >= :amount
    """), {"payment_no": payment_no, "amount": amount_cents})
```

**额度预占 vs 事后累加**：本设计选择**预占**（在调用第三方之前就增加 `refunded_amount_cents`）而不是**事后累加**。理由是：

- 事后累加的问题是"第三方退款成功到本地累加"之间有窗口，期间另一笔退款可能读到未更新的 `refunded_amount_cents`，导致超额。虽然有并发保护（`status` 检查）但不覆盖多笔并发退款
- 预占的代价是"退款失败后需释放"，但这由 `release_refund_amount` 显式处理，且 `WHERE refunded_amount_cents >= amount` 保证不会减成负数
- 预占后若进程崩溃（既没释放也没落定），会出现"额度被占但第三方未退"的悬挂。这由 8.3 的退款同步任务兜底：查询第三方确认未退款则释放额度

**面试/评审常问点**：为什么不给 `refunds` 表加 `UNIQUE(payment_no, amount_cents)` 之类的约束来防重复退款？因为**合法的重复金额是允许的**（用户确实可以分两次各退 100 元）。防重复必须靠幂等键（`uk_refunds_idempotency_key`），不能靠金额组合。

#### 6.6.4 退款成功落定与回调

```python
async def settle_refund_success(refund_no: str, third, *, occurred_at, trace_id) -> None:
    """退款成功落定。在一个事务内：更新退款单 + 写退款流水 + 写 outbox。"""
    async with db.transaction():
        refund = await refund_repo.get_by_no(refund_no, for_update=True)

        # 幂等：条件更新，重复回调影响行数为 0
        affected = await refund_repo.update_conditional(
            refund_no=refund_no,
            where_status_in=["PENDING"],
            version=refund.version,
            set_values={
                "status": "SUCCEEDED",
                "third_party_refund_id": third.refund_id or refund.third_party_refund_id,
                "refunded_at": occurred_at,
                "last_synced_at": utcnow(),
                "version": F("version") + 1,
            },
        )
        if affected == 0:
            return                      # 已处理过，幂等返回

        # 退款流水（L2 唯一索引兜底：uk_payment_transactions_refund_success）
        await transaction_repo.insert(
            transaction_no=generate_transaction_no(),
            transaction_type="REFUND", direction="OUT",
            payment_no=refund.payment_no, refund_no=refund_no,
            order_no=refund.order_no, user_id=refund.user_id,
            channel=refund.channel,
            amount_cents=refund.amount_cents, currency=refund.currency,
            status="SUCCEEDED",
            third_party_transaction_id=third.refund_id,
            third_party_event_id=getattr(third, "event_id", None),
            transaction_at=occurred_at,
        )

        # 读取最新的累计退款金额，随事件发出（便于订单服务判定是否全额退完）
        payment = await payment_repo.get_by_no(refund.payment_no)

        await outbox.publish(
            event_type="payment.refunded",
            event_version="1.0",
            aggregate_type="PAYMENT",
            aggregate_id=refund.payment_no,
            payload={
                "refund_no": refund_no,
                "payment_no": refund.payment_no,
                "order_no": refund.order_no,
                "user_id": str(refund.user_id),
                "amount_cents": refund.amount_cents,
                "currency": refund.currency,
                "channel": refund.channel,
                "refund_type": refund.refund_type,
                "payment_total_amount_cents": payment.amount_cents,
                "total_refunded_amount_cents": payment.refunded_amount_cents,
                "refunded_at": iso(occurred_at),
            },
            trace_id=trace_id,
        )
```

**注意 `payment.refunded_amount_cents` 已在 6.6.3 的预占中累加**，因此这里发出的事件携带的累计值是正确的（不依赖本次落定时的再次累加）。

`refund_type` 的最终确定：若预占时判定为 `PARTIAL`，但因为后续又有其他退款导致累计达到全额，本服务**不修改已生成退款单的 `refund_type`**（它描述的是"这一笔"的性质）。订单服务要判断"是否全额退完"应以事件中的 `total_refunded_amount_cents == payment_total_amount_cents` 为准。

#### 6.6.5 退款失败的重试与人工介入

| 阶段 | 自动重试 | 上限 | 超限后 |
|---|---|---|---|
| `execute_refund` 第三方明确失败 | 是，由 8.3 按指数退避重试 | `PAYMENT_REFUND_MAX_RETRY`（默认 3 次，间隔 1m / 5m / 30m） | 退款单置 `FAILED`，`REFUND_NEED_MANUAL` P1 告警 |
| `execute_refund` 第三方超时（结果未知） | 不重发，改为**查询确认** | 无上限（但受补偿窗口约束） | 8.3 检查第三方状态；确认未退款后释放额度并转入失败重试 |
| 审核驳回 | 无 | — | 退款单置 `CLOSED`，通知申请人 |
| 人工重试（3.13） | 由 `FINANCE`/`ADMIN` 触发 | 无硬上限（每次记审计日志） | — |

**人工介入的强制前置检查**（3.13 接口内）：

```python
async def manual_retry_refund(refund_no: str, operator_id: int) -> Refund:
    refund = await refund_repo.get_by_no(refund_no)
    if refund.status not in ("FAILED", "PENDING"):
        raise BusinessError("PAY-5002", "退款单当前状态不支持重试", http=409)

    # ★ 重发前必须先向第三方确认：第三方可能已经退过钱但回调丢了
    remote = await channel_gateway(refund.channel).query_refund(
        refund.third_party_refund_id or refund.refund_no
    )
    if remote is not None and remote.status == "SUCCEEDED":
        # 第三方已成功 → 直接落定，绝不重发（否则重复退款）
        await settle_refund_success(refund_no, remote,
                                    occurred_at=remote.occurred_at, trace_id=...)
        await audit_log(operator_id, "refund_manual_retry_settled", refund_no)
        return await refund_repo.get_by_no(refund_no)

    if remote is not None and remote.status in ("PENDING", "PROCESSING"):
        raise BusinessError("PAY-5002", "第三方仍在处理中，请稍后再试", http=409)

    # 确认第三方无此退款 → 允许重发
    await refund_repo.update(refund_no, retry_count=0)   # 重置计数
    await execute_refund(refund_no, trace_id=..., manual_retry=True)
    await audit_log(operator_id, "refund_manual_retry_resubmitted", refund_no)
    return await refund_repo.get_by_no(refund_no)
```

**这段检查就是"退款必须幂等"在人工场景下的落地**：人工重试最大的风险是重复退款，而只要第三方退款接口支持按 `refund_no` 幂等（Stripe 通过 Idempotency-Key，PayPal 通过退款请求唯一性），加上上面的"先查后发"，重复退款在两道防线上都不可能发生。

```python
async def sync_refund(refund_no: str) -> None:
    refund = await refund_repo.get_by_no(refund_no)
    if refund.status != "PENDING":
        return
    remote = await channel_gateway(refund.channel).query_refund(
        refund.third_party_refund_id or refund.refund_no
    )
    if remote is None:
        # 第三方查无此退款：可能是创建超时后确实未创建
        if refund.third_party_refund_id is None and \
           utcnow() - refund.created_at > timedelta(seconds=cfg.REFUND_CREATE_GRACE_SECONDS):
            await release_refund_amount(refund.payment_no, refund.amount_cents)
            await refund_repo.update(refund_no, status="FAILED",
                                     fail_code="create_never_succeeded",
                                     fail_reason="第三方未收到退款请求")
        return

    if remote.status == "SUCCEEDED":
        await settle_refund_success(refund_no, remote,
                                    occurred_at=remote.occurred_at, trace_id=...)
    elif remote.status == "FAILED":
        await release_refund_amount(refund.payment_no, refund.amount_cents)
        await refund_repo.update(refund_no, status="FAILED",
                                 fail_code=remote.fail_code, fail_reason=remote.fail_reason,
                                 failed_at=utcnow())
    # PENDING/PROCESSING：保持，下轮再查
    await refund_repo.touch_synced(refund_no)
```

### 6.7 对账（FR-PAY-008）

#### 6.7.1 对账日的时区口径（先决问题）

对账的第一步是定义"一天"。第三方账单是按**渠道所在时区的自然日**生成的，而不是 UTC 日。例如 Stripe 账户若设置为 `Asia/Shanghai`，其 2026-09-09 的对账单覆盖的是 UTC `2026-09-08T16:00:00Z ~ 2026-09-09T16:00:00Z`。若本地按 UTC 日切分流水去比对，边界上的交易会被分配到不同的"天"，产生大量假差异。

**处理方式**：

- 配置项 `PAYMENT_RECON_TIMEZONE_STRIPE` / `PAYMENT_RECON_TIMEZONE_PAYPAL`，默认 `Asia/Shanghai`（与业务运营时区一致）
- 拉取第三方账单时，**以第三方的日期参数为准**（第三方 API 通常接受其自身时区的日期字符串），不做自行换算
- 本地流水筛选时，把对账日转换为该时区下的 `[day_start_utc, day_end_utc)` 区间，用 UTC 时间过滤
- 若第三方账单接口返回每笔交易的**原始时间戳与所属结算日**（多数渠道会返回），以第三方给出的结算日为准，进一步消除边界歧义
- `reconciliation_batches.timezone` 字段记录本次使用的时区，保证历史批次可复现

#### 6.7.2 对账主流程伪代码

```python
# app/tasks/reconciliation.py

async def run_reconciliation(channel: str, reconcile_date: date, *, force=False) -> str:
    """执行单渠道单日对账。返回 batch_no。"""
    batch_no = f"RB{reconcile_date:%Y%m%d}{channel}"

    # ── ① 创建批次（唯一索引防重跑）──────────────────────────
    if not force:
        if await recon_repo.exists_active(channel, reconcile_date):
            raise BusinessError("PAY-5011", "该日期已完成对账，如需重跑请指定 force", http=409)
    else:
        await recon_repo.invalidate(channel, reconcile_date, reason="manual rerun")
    await recon_repo.insert_batch(
        batch_no=batch_no, channel=channel, reconcile_date=reconcile_date,
        timezone=cfg.RECON_TIMEZONE[channel], status="RUNNING",
    )

    try:
        # ── ② 生成对账时间窗（按渠道时区切分，转换为 UTC）──────
        tz = ZoneInfo(cfg.RECON_TIMEZONE[channel])
        day_start = datetime.combine(reconcile_date, time.min, tzinfo=tz)
        day_end   = day_start + timedelta(days=1)
        start_utc, end_utc = day_start.astimezone(UTC), day_end.astimezone(UTC)

        # ── ③ 拉取第三方账单（全量分页，支持断点续取）──────────
        try:
            third_party_items, file_url, complete = await channel_gateway(channel) \
                .fetch_settlement_report(reconcile_date, tz)
        except ThirdPartyError as exc:
            await recon_repo.fail_batch(batch_no, reason=f"账单拉取失败: {exc}")
            raise BusinessError("PAY-7005", "第三方账单拉取失败，请稍后重试", http=502)

        if not complete:
            # 分页未取完：不能用不完整账单结账
            await recon_repo.mark_partial(batch_no, reason="账单分页未取全",
                                          file_url=file_url)
            alert.immediate("RECON_REPORT_INCOMPLETE", channel=channel,
                            date=str(reconcile_date))
            return batch_no

        # ── ④ 拉取本地流水（含成功与失败，失败单也需比对）──────
        local_items = await transaction_repo.find_for_reconciliation(
            channel=channel, start=start_utc, end=end_utc,
        )

        # ── ⑤ 建立两侧索引，逐条比对 ──────────────────────────
        #     匹配键优先级：第三方交易号 > 商户订单号(payment_no/refund_no)
        local_by_txn = {}
        local_by_ref = {}
        for t in local_items:
            if t.third_party_transaction_id:
                local_by_txn.setdefault(t.third_party_transaction_id, []).append(t)
            local_by_ref.setdefault(t.reference_key(), []).append(t)   # payment_no 或 refund_no

        third_by_txn = {}
        for it in third_party_items:
            third_by_txn.setdefault(it.transaction_id, []).append(it)

        differences: list[Difference] = []
        matched = 0

        # ⑤-a 遍历第三方账单：找出"第三方有本地无""金额不符""状态不符"
        for it in third_party_items:
            candidates = local_by_txn.get(it.transaction_id) \
                      or local_by_ref.get(it.merchant_reference)
            if not candidates:
                differences.append(Difference(
                    difference_type="THIRD_PARTY_ONLY",
                    third_party_transaction_id=it.transaction_id,
                    third_party_amount_cents=it.amount_cents,
                    third_party_status=it.status,
                    order_no=it.order_no,
                    diff_amount_cents=it.amount_cents,
                ))
                continue

            local = pick_best_match(candidates, it)     # 优先金额一致且类型匹配的
            if local is None:
                differences.append(Difference(
                    difference_type="DUPLICATE_LOCAL",
                    third_party_transaction_id=it.transaction_id,
                    local_transaction_no=candidates[0].transaction_no,
                    diff_amount_cents=it.amount_cents,
                ))
                continue

            local.absorb(it)          # 标记已匹配，供 ⑤-b 排除
            local_net = local.signed_amount_cents()      # REFUND 为负
            third_net = it.signed_amount_cents()

            if local_net != third_net or local.currency != it.currency:
                differences.append(Difference(
                    difference_type="AMOUNT_MISMATCH",
                    local_transaction_no=local.transaction_no,
                    third_party_transaction_id=it.transaction_id,
                    payment_no=local.payment_no, refund_no=local.refund_no,
                    order_no=local.order_no,
                    local_amount_cents=local_net,
                    third_party_amount_cents=third_net,
                    diff_amount_cents=third_net - local_net,
                    local_status=local.status, third_party_status=it.status,
                ))
            elif not status_consistent(local, it):
                # 本地失败但第三方成功（漏账），或本地成功但第三方失败（虚假记账）
                differences.append(Difference(
                    difference_type="STATUS_MISMATCH",
                    local_transaction_no=local.transaction_no,
                    third_party_transaction_id=it.transaction_id,
                    payment_no=local.payment_no, refund_no=local.refund_no,
                    order_no=local.order_no,
                    local_amount_cents=local_net, third_party_amount_cents=third_net,
                    diff_amount_cents=0,
                    local_status=local.status, third_party_status=it.status,
                ))
            else:
                matched += 1

        # ⑤-b 遍历本地流水：找出"本地有第三方无"
        for t in local_items:
            if getattr(t, "_absorbed", False):
                continue
            # 未匹配到任何第三方记录
            differences.append(Difference(
                difference_type="LOCAL_ONLY",
                local_transaction_no=t.transaction_no,
                payment_no=t.payment_no, refund_no=t.refund_no, order_no=t.order_no,
                local_amount_cents=t.signed_amount_cents(),
                diff_amount_cents=-t.signed_amount_cents(),
                local_status=t.status,
            ))

        # ── ⑥ 落差异明细（唯一索引保证重跑幂等）───────────────
        async with db.transaction():
            await recon_repo.bulk_insert_differences(batch_no, channel,
                                                     reconcile_date, differences)
            await transaction_repo.mark_batch(batch_no, [t.transaction_no for t in local_items])
            await recon_repo.finish_batch(
                batch_no,
                status="SUCCEEDED",
                local_total_count=len(local_items),
                local_total_cents=sum(t.signed_amount_cents() for t in local_items),
                third_party_total_count=len(third_party_items),
                third_party_total_cents=sum(i.signed_amount_cents() for i in third_party_items),
                matched_count=matched,
                difference_count=len(differences),
                source_file_url=file_url,
            )

        # ── ⑦ 差异告警 ───────────────────────────────────────
        if differences:
            by_type = Counter(d.difference_type for d in differences)
            alert.immediate("RECON_DIFFERENCE_FOUND", channel=channel,
                            date=str(reconcile_date), batch_no=batch_no,
                            total=len(differences), by_type=dict(by_type),
                            amount_net_cents=sum(d.diff_amount_cents or 0 for d in differences))
            metrics.inc("recon_differences_total", channel=channel, n=len(differences))
        return batch_no

    except BusinessError:
        raise
    except Exception as exc:
        await recon_repo.fail_batch(batch_no, reason=str(exc)[:255])
        logger.exception("reconciliation failed", batch_no=batch_no)
        alert.immediate("RECON_TASK_FAILED", channel=channel, date=str(reconcile_date))
        return batch_no
```

#### 6.7.3 差异类型与处理流程

| 差异类型 | 含义 | 典型原因 | 处理方式 |
|---|---|---|---|
| `THIRD_PARTY_ONLY` | 第三方账单有、本地流水无 | 回调丢失且补偿未生效；或第三方事件不属于本系统（配置串号） | 先确认第三方交易号是否属于本平台；若是，手工触发该支付单的 `sync`（3.5）补入账并补流水；若确实不属于本平台，标记 `IGNORED` 并修正渠道配置 |
| `LOCAL_ONLY` | 本地流水有、第三方账单无 | 本地虚假入账（如误判）；或第三方账单延迟出账（跨日边界） | 先排除跨日边界（检查对账日前后的批次）；确认为虚假入账则进入异常订单流程，由订单服务侧处理并回冲 |
| `AMOUNT_MISMATCH` | 两侧交易号匹配但金额不同 | 部分退款在第三方侧单独出账；或本地记账金额错误 | 逐条核对第三方后台；若为退款未入本地流水，补写流水；若为本地录错，走人工更正流程 |
| `STATUS_MISMATCH` | 金额一致但状态不同 | 本地误判失败但第三方已成功（漏账） | 触发该支付单的 `sync`，允许 `FAILED → SUCCEEDED` 恢复（6.3.6），并告警 |
| `DUPLICATE_LOCAL` | 同一第三方交易号在本地有多条流水 | 幂等失效（实现 bug） | **最高优先级**，说明 L2 唯一索引被绕过；立即排查代码路径，清理重复流水并评估资金影响 |

**处理流程（人工）**：

```
差异清单（P1 告警）→ 财务/值班在后台查看（3.16）
  │
  ├─ 可自动修复的（THIRD_PARTY_ONLY / STATUS_MISMATCH）：
  │     运营触发对应支付单的 /sync 接口 → 支付结果补入账 → 差异下轮对账自动消失
  │     （本期不提供"一键批量修复"按钮，避免自动化掩盖问题）
  │
  └─ 需人工判断的：
        财务核对第三方后台 → 在差异记录上写处理说明（3.17）→ 标记 RESOLVED/IGNORED
```

**为什么不做自动修复**：差异意味着"本地认为的资金状态与第三方不一致"，自动修复有把错误数据固化下来的风险。本期选择"**自动发现 + 人工确认 + 手动触发修复**"，把自动化的边界划在"发现"这一步。这也是本服务与对账系统的最大区别：对账系统追求自动平账，本设计追求"差异可见、可追溯、可人工处置"。

#### 6.7.4 导出

差异清单导出（3.18）由本服务直接生成 CSV 流式响应，字段见接口定义。导出时**附带批次摘要行**（放在文件末尾以 `#` 开头的注释行），包含批次号、对账日、两侧条数与金额合计、差异条数，便于财务把文件直接附在结账材料中。

#### 6.7.5 对账记录的保留与复现

- 每个批次记录 `timezone`、`source_file_url`（第三方账单原文）、`local_total_cents`、`third_party_total_cents`，保证**任何历史批次都能复现当时的比对口径**
- 差异明细保留 24 个月，与财务审计周期对齐
- 对账任务**不修改** `payment_transactions` 的业务字段，只回填 `reconciliation_batch_no`，保证流水作为证据的不可变性

### 6.8 敏感信息隔离与 PCI 边界（FR-PAY-010）

#### 6.8.1 PCI DSS 的边界划分

支付卡行业数据安全标准（PCI DSS）把商户分为不同等级，其中 **SAQ A** 是负担最轻的一档，适用于"卡片数据完全由第三方支付页面采集与处理、商户系统不接触"的场景。本平台的设计目标就是**把 PCI 范围收缩到 SAQ A**：

| 数据 | 是否进入本平台 | 存放位置 | 说明 |
|---|---|---|---|
| 卡号（PAN） | **否** | Stripe / PayPal | 由第三方采集表单直接提交至第三方，不经过本平台服务器 |
| CVV / CVC | **否** | Stripe / PayPal | 同上。CVV 在任何情况下不得存储，第三方亦然 |
| 有效期 | **否** | Stripe / PayPal | 同上 |
| 持卡人姓名 | **否** | Stripe / PayPal | 第三方托管 |
| 3DS 验证结果 | 仅结果 | 第三方 | 本平台只接收"验证通过/失败"的最终状态 |
| 支付意图 ID / 交易号 | 是 | `payments` 表 | 非敏感，是第三方对交易的引用 |
| 金额、币种、订单号 | 是 | 本服务各表 | 业务数据，非卡数据 |
| 用户 ID | 是 | `payments.user_id` | 平台自身标识 |

**技术实现上的三个关键点**：

1. **Stripe 使用 Elements / Payment Element**。前端页面嵌入 Stripe 提供的 iframe 组件，用户在 iframe 内输入卡信息；iframe 内的字段由 Stripe 直接接收，**数据流是"浏览器 → Stripe"而非"浏览器 → 本平台 → Stripe"**。本服务只下发 `client_secret` 与 `publishable_key`，不接触卡数据。因此本平台的后端代码中**不存在任何接收卡号的接口**。
2. **PayPal 使用跳转模式**。本服务创建 PayPal Order 后返回 `pay_url`，用户被**重定向到 PayPal 站点**完成登录与支付；支付完成后 PayPal 重定向回 `return_url`。用户的 PayPal 账号密码与卡信息都在 PayPal 域内，本平台全程不接触。
3. **回调报文不含卡数据**。Stripe 的 PaymentIntent 事件与 PayPal 的 Capture 事件中包含的是金额、状态、交易号，**不含 PAN/CVV**。因此 `payment_callback_logs.raw_body` 的留存不构成 PCI 范围扩张。这一点在实际实现中必须验证：若某渠道的事件类型确实携带了卡数据（如 Stripe 的 `charge.succeeded` 事件中 `payment_method_details.card.last4` 与 `brand` 存在），则**只落非敏感字段、不落完整 body**，具体字段以渠道官方文档为准。

#### 6.8.2 系统设计中的落地措施

| 措施 | 实现 |
|---|---|
| 无卡号字段 | 数据库 schema 中**不存在** `card_no`、`cvv`、`expiry` 等字段；代码评审与 CI 静态检查禁止引入 |
| 无卡号接口 | API 契约中不存在接收卡信息的字段；请求体校验（Pydantic）对未知字段的处理策略见下 |
| 日志防护 | 出站第三方调用的请求/响应日志只记录 `intent_id`、`amount`、`status`、`error_code`，**不记录完整请求体**；通用脱敏中间件对 `card`、`cvv`、`pan` 等关键词做兜底遮蔽 |
| 回调报文过滤 | 落 `raw_body` 前执行敏感字段检查；命中则落库前按渠道规则剔除（见 6.8.1 第 3 点） |
| 密钥隔离 | `STRIPE_SECRET_KEY`、`PAYPAL_CLIENT_SECRET`、`STRIPE_WEBHOOK_SECRET` 通过密钥管理注入，不入库不入仓（NFR-SE-007） |
| 最小权限 | Stripe/PayPal 的 API Key 只授予所需能力（创建支付意图、退款、查询），不开启提现、账户管理等高权限 |
| 传输 | 与第三方的一切通信强制 HTTPS，校验证书 |
| 人员 | 密钥访问需审批，操作审计日志记录所有后台资金相关操作（NFR-SE-009） |

**Pydantic 的未知字段策略**：请求模型配置 `model_config = ConfigDict(extra="forbid")`。若客户端意外提交 `card_no` 字段，服务端直接返回 `COMMON-1001` 而非静默忽略——静默忽略会让"客户端以为发了卡数据、平台以为没收到"的状态长期存在，明确拒绝更安全。但注意：这一策略与 3.2 中"客户端传 `amount_cents` 时忽略并告警"看似矛盾。两者的区别是：`amount_cents` 是**本服务已知的业务字段**（客户端可能因历史版本或前端 bug 携带），忽略是兼容性考虑；`card_no` 是**本服务明确不接受的字段**，拒绝是安全考虑。实现上是"显式声明 `amount_cents` 为可选字段但在业务层忽略，其余未知字段一律拒绝"。

#### 6.8.3 PCI 合规声明

本设计使平台处于 **SAQ A** 范围：平台不存储、不处理、不传输持卡人数据（CHD），卡数据采集与处理全部由通过 PCI DSS 认证的第三方（Stripe、PayPal）完成。合规责任边界：

- 平台责任：确保无任何 CHD 进入系统（通过上述措施）、保护 API 密钥、使用 HTTPS、定期自评
- 第三方责任：CHD 的存储、处理、传输安全，以及其自身的 PCI DSS 认证

**这一边界必须在代码层面可验证**：CI 中增加静态检查规则（禁止在代码中出现 `card_number`、`cvv`、`cvc`、`security_code` 等变量名与字面量），使"不接触卡数据"成为可自动验证的约束，而非仅靠文档承诺。

### 6.9 金额处理与单位换算

#### 6.9.1 与第三方的单位换算

| 环节 | 本平台 | Stripe | PayPal |
|---|---|---|---|
| 金额单位 | 分（BIGINT） | 最小货币单位（minor unit，整数） | **字符串小数**（如 `"199.00"`） |
| CNY 最小单位 | 分 | 分（1 CNY = 100 cents，Stripe 的 CNY 为两位小数货币） | 分（字符串 `"199.00"` 表示 199 元 0 分） |
| 币种表示 | `CNY` | 小写 `cny` | 大写 `CNY` |

**换算函数（集中在一处，禁止散落）**：

```python
# app/clients/money.py
"""第三方金额单位换算。所有换算必须经过本模块，禁止在业务代码中自行乘除。"""

ZERO_DECIMAL_CURRENCIES = {"JPY", "KRW", "VND"}     # 无小数位的币种（本期不用，但防御性处理）

def cents_to_stripe(cents: int, currency: str) -> int:
    """本地分 → Stripe 最小单位。CNY 两位小数，1:1。"""
    if cents < 0:
        raise ValueError("amount must be non-negative")
    if currency in ZERO_DECIMAL_CURRENCIES:
        raise UnsupportedCurrency(currency)          # 本期不支持
    return cents                                     # 两位小数货币：分 == 最小单位

def stripe_to_cents(minor_units: int, currency: str) -> int:
    return minor_units

def cents_to_paypal(cents: int, currency: str) -> str:
    """本地分 → PayPal 字符串小数。例如 19900 → '199.00'。
    使用整数运算避免浮点误差（NFR-CP-002）。"""
    if currency in ZERO_DECIMAL_CURRENCIES:
        raise UnsupportedCurrency(currency)
    sign = "-" if cents < 0 else ""
    cents = abs(cents)
    return f"{sign}{cents // 100}.{cents % 100:02d}"

def paypal_to_cents(value: str, currency: str) -> int:
    """PayPal 字符串小数 → 本地分。'199.00' → 19900。
    不经过 float，用字符串解析，避免精度问题。"""
    s = value.strip()
    if s.startswith("-"):
        raise ValueError("amount must be non-negative")
    if "." in s:
        int_part, frac_part = s.split(".", 1)
    else:
        int_part, frac_part = s, ""
    frac_part = (frac_part + "00")[:2]                # 补齐/截断到两位
    if not int_part.isdigit() or not frac_part.isdigit():
        raise MalformedAmount(value)
    return int(int_part) * 100 + int(frac_part)
```

**绝对禁止的写法**：`amount * 100`（当 `amount` 是 float 时，`19.99 * 100 = 1998.9999999999998`）；`float(paypal_value) * 100`（同样的精度陷阱）。所有从第三方解析出的金额必须走字符串解析路径。

**换算后的双向校验**：从第三方回读金额并换算回分后，必须与本地金额**再做一次相等比较**（不仅比较换算结果，也在回调/同步路径中比较）。这一比较是 6.3、6.4 中金额校验的基础。

#### 6.9.2 币种假设与限制

- **本期固定 CNY 单币种**。`payments.currency`、`refunds.currency`、`payment_transactions.currency` 均有 `CHECK (currency = 'CNY')` 约束
- 支持多币种需要变更：①去掉 CHECK 约束；②在 `ZERO_DECIMAL_CURRENCIES` 处理之外引入币种小数位配置表；③对账按币种分别出批次；④订单服务的金额口径同步调整。本设计预留了 `currency` 字段，但**不预留"同一支付单多币种"**这种复杂能力
- **币种不一致的处理**：回调/同步中若发现第三方币种与本地不符，按 6.3.5 异常二处理（金额不符的一类），不入账并告警
- **Stripe 的 CNY 支持有账户准入要求**，需在渠道配置阶段确认账户已开通 CNY 收款；若未开通，本服务在 `create_intent` 阶段会收到渠道错误并置 `FAILED`，运营需在渠道后台开通

### 6.10 第三方调用封装

#### 6.10.1 超时与重试策略

| 调用类型 | 连接超时 | 读取超时 | 自动重试 | 幂等键 | 失败处理 |
|---|---|---|---|---|---|
| 创建支付意图 | 2s | 10s | **不重试** | 传 `payment_no` 作为第三方幂等键 | 超时保持 `PENDING` → 补偿查询（6.1.3） |
| 查询支付意图 | 2s | 5s | **2 次**，退避 1s / 3s | —（只读幂等） | 记录失败，下轮补偿再试 |
| 创建退款 | 2s | 10s | **不重试** | 传 `refund_no` 作为第三方幂等键 | 超时保留额度预占 → 退款同步（6.6.6） |
| 查询退款 | 2s | 5s | **2 次**，退避 1s / 3s | — | 记录失败，下轮再试 |
| 拉取对账账单 | 5s | 30s | **2 次**，退避 5s | — | 批次置 `FAILED`，人工重跑 |
| 回调验签（PayPal） | 2s | 3s | **1 次** | — | 返回 500 让渠道重试（6.3.3） |

**"支付创建类接口不能盲目重试"的具体含义**：

- 自动重试的**前提是幂等键已生效**。本服务向第三方传幂等键（Stripe 用 `Idempotency-Key` 头，PayPal 用请求级唯一标识），理论上重试安全
- 即便如此**仍然不配置自动重试**，原因是：第三方幂等键的语义与窗口由第三方定义（Stripe 的幂等键窗口为 24 小时），在超时且结果未知的情况下，**主动查询比盲目重发更能反映真实状态**，并且避免了"重发 + 查询"两条路径并发产生的不确定性
- 这条规则与通用约定第 11.2 节"写操作默认不重试"完全一致

#### 6.10.2 熔断与降级

```python
class ChannelCircuitBreaker:
    """按渠道维度的熔断器。参数见 11 章配置。"""
    def __init__(self, channel: str):
        self.channel = channel
        self.window = deque(maxlen=cfg.CB_WINDOW_SIZE)      # 默认 50
        self.state = "CLOSED"                                # CLOSED / OPEN / HALF_OPEN
        self.opened_at = None

    def is_open(self) -> bool:
        if self.state == "OPEN":
            if utcnow() - self.opened_at > timedelta(seconds=cfg.CB_HALF_OPEN_AFTER):  # 默认 30s
                self.state = "HALF_OPEN"                     # 放行探测请求
                return False
            return True
        return False

    def record(self, ok: bool) -> None:
        self.window.append(ok)
        if self.state == "HALF_OPEN":
            if ok:
                self.reset()                                 # 探测成功 → 恢复正常
            else:
                self.trip()                                  # 探测失败 → 继续熔断
            return
        if len(self.window) >= cfg.CB_MIN_SAMPLES:           # 默认 20
            error_rate = 1 - sum(self.window) / len(self.window)
            if error_rate > cfg.CB_ERROR_RATE_THRESHOLD:      # 默认 0.5
                self.trip()
```

**降级行为**：

| 场景 | 降级 |
|---|---|
| 某渠道熔断中 | 发起支付时返回 `PAY-7004`，响应中提示可用的其他渠道；不阻断另一渠道 |
| 两渠道同时熔断 | 支付接口整体不可用（返回 `PAY-7004`），但不影响查询、退款、对账等</br>（这些操作走的是已建立的交易，不依赖创建能力） |
| 对账账单拉取失败 | 批次置 `FAILED`，**不影响支付主流程**，由财务人工重跑 |
| 查询类调用失败 | 保持现状，下轮定时任务重试；查询接口返回 `PAY-7002` |

**渠道不可用的用户可见行为**：买家端支付页应在发起支付前向本服务查询渠道健康状态（**建议在支付页加载时调用 `GET /api/v1/payments` 的渠道状态摘要接口**——本期简化为：若创建支付返回 `PAY-7004`，前端直接提示"该渠道暂不可用，请更换渠道"，并允许用户切换到另一渠道）。切换渠道时会创建新的支付单（因为是不同的渠道，不触发 `uk_payments_order_channel_active`），旧支付单由超时任务关闭。

| 环境 | Stripe | PayPal |
|---|---|---|
| `dev` / `test` | `STRIPE_API_BASE=https://api.stripe.com` + 测试模式密钥（`sk_test_*`）+ 测试端点密钥（`whsec_*`） | `PAYPAL_API_BASE=https://api-m.sandbox.paypal.com` + 沙箱 Client ID/Secret + 沙箱 Webhook ID |

## 7. 缓存设计

本服务**不是缓存密集的服务**（与商品目录、购物车不同），缓存仅用于幂等键、限流计数、渠道健康状态与少量查询聚合结果。所有涉及资金状态与金额的读取**一律直查数据库，不走缓存**（通用约定 9.3：强一致的读不走缓存）。

### 7.1 缓存清单

| Key | 类型 | TTL | 内容 | 写入时机 | 失效时机 |
|---|---|---|---|---|---|
| `payment:idem:pay:{order_no}:{channel}` | String(JSON) | 7 天 | `{"payment_no": "..."}` | 发起支付成功后 | ①支付单进入终态后刷新（值不变，但读取时会发现非进行中而放行重试）②TTL 自然到期 ③显式 `DEL`（`order.cancelled` 处理时） |
| `payment:idem:refund:{idempotency_key}` | String(JSON) | 7 天 | `{"payment_no": "...", "refund_no": "..."}` | 退款单创建成功后 | TTL 自然到期；退款单进入终态后不删除（保证重复请求始终返回同一退款单） |
| `payment:order_ctx:{order_no}` | String(JSON) | 同订单 TTL | 订单金额、币种、`expires_at`、`user_id` | 消费 `order.created` 事件（仅在 `PAYMENT_PRE_CREATE_ON_ORDER_CREATED=true` 时） | TTL 自然到期；支付单创建时删除（已不需要） |
| `payment:sync:limit:{payment_no}` | String | 60 秒 | 同步标记 | `/sync` 接口调用时 | TTL 自然到期（即同步频率限制） |
| `payment:cb:state:{channel}` | Hash | 60 秒 | 熔断器状态（窗口计数、状态、开启时间） | 每次第三方调用后更新 | TTL 自然到期（各实例独立维护，不共享窗口，本服务的熔断是实例级的） |
| `payment:alert:{alert_type}:{key}` | String | 6 小时 | 告警节流标记 | 触发告警时 | TTL 自然到期 |
| `payment:tx_summary:{hash(query)}` | String(JSON) | 60 秒 | 交易流水的合计金额与条数 | 后台流水查询接口计算后 | TTL 自然到期；**不主动失效**（后台统计允许 60 秒延迟） |
| `payment:verify_cache:{channel}:{transmission_id}` | String | 10 分钟 | PayPal 验签结果 | 验签成功后 | TTL 自然到期（防重放导致的重复远程验签） |
| `payment:recon:running:{channel}` | String | 30 分钟 | 对账任务运行标记（分布式锁） | 对账任务启动时（`SET NX`） | 任务结束显式删除；异常退出由 TTL 释放 |

### 7.2 幂等键的失效策略（本服务的特殊之处）

通用约定第 9.3 节的"先写库再删缓存"针对的是**数据缓存**。本服务的幂等键是**控制型缓存**，其失效策略不同：

| 场景 | 动作 | 理由 |
|---|---|---|
| 支付单创建成功 | `SET NX EX 7d`，值为 `payment_no` | 拦截重复创建 |
| 支付单进入终态（`SUCCEEDED`/`FAILED`/`CLOSED`） | **不删除**，保持指向该 `payment_no` | 用户重放同一请求时应看到"这个支付单已经成功了"，而不是创建新的支付单 |
| 用户在支付单失败/关闭后重新发起 | 由业务判断：Redis 键存在但支付单非进行中 → 删除键并继续走创建流程 | 允许合法的重新支付（见 6.1.2 步骤 2） |
| 收到 `order.cancelled` | 显式 `DEL` | 订单已取消，该订单不应再有支付行为；删除键可让后续误发的请求快速失败在订单校验环节 |

**为什么不做"命中即返回旧结果"**：如果幂等键只存 `payment_no` 而不缓存支付单内容，命中检查必须回数据库读支付单真实状态。这多了一次数据库读，但**换来的是正确性**——支付单状态是高频变化的，缓存快照极易失真。这个取舍在支付场景是明确的：**正确性优先于一次数据库读的开销**。

### 7.3 缓存一致性与故障处理

| 场景 | 处理 |
|---|---|
| Redis 不可用 | **支付主流程降级为"仅依赖数据库唯一索引"**：跳过 Redis 幂等预检，直接走创建流程，靠 `uk_payments_order_channel_active` 拦截重复。功能性不受影响，仅在极端并发下多几次唯一键冲突 |
| 缓存与数据库不一致 | 幂等键的 value 只有 `payment_no`（不变值），不存在不一致问题；查询聚合缓存允许 60 秒陈旧 |
| 缓存穿透 | 幂等键的 key 由 `order_no` + `channel` 构成，`order_no` 已由订单服务保证有效，不存在恶意构造大量不存在的 key 的场景；但 `/sync` 接口的限流键需校验 `payment_no` 存在性后再写入 |
| 热点 Key | 不存在。幂等键按订单分散，单个订单不会产生超过 20 次/分钟（网关限流）的访问 |

**支付服务可以接受 Redis 完全不可用**，这是一个有意的设计选择：支付是资金操作，**不应把可用性依赖于缓存**。Redis 在本服务只承担"降低数据库压力"与"限流计数"两类非关键职责。

## 8. 定时任务

所有定时任务通过独立的调度器执行（建议使用 `APScheduler` 或独立的 `payment-task` 进程，多实例部署时需通过 Redis 分布式锁或数据库行锁保证单实例执行）。任务清单：

### 8.1 支付单超时关闭

| 项 | 内容 |
|---|---|
| 任务名 | `payment_timeout_close_task` |
| 周期 | 每 1 分钟 |
| 职责 | 扫描 `status IN ('PENDING','PROCESSING') AND expires_at < now()` 的支付单，关闭无第三方标识的，转补偿查询有第三方标识的（逻辑见 6.2） |
| 批量 | 每轮最多 500 条，循环直到无候选（限制单轮总时长 ≤ 30 秒） |
| 幂等要求 | **条件更新**：`WHERE status IN ('PENDING') AND third_party_payment_id IS NULL AND third_party_intent_id IS NULL`。重复执行影响行数为 0。多实例并发执行时，条件更新保证只有一个实例真正关闭 |
| 分布式锁 | 不需要。条件更新已保证幂等；但为避免多实例重复扫描浪费资源，可用 `payment:task:timeout_close` 锁（TTL 50 秒，`SET NX`）做单实例执行 |
| 监控 | `payment_timeout_closed_total` 计数；若单轮关闭数持续 > 100，说明用户支付意愿或渠道有问题，需关注 |
| 前置依赖 | Redis 不可用时任务仍可运行（只影响幂等键刷新，失败不阻塞关闭） |

### 8.2 回调丢失补偿查询

| 项 | 内容 |
|---|---|
| 任务名 | `payment_compensation_sync_task` |
| 周期 | 每 2 分钟 |
| 职责 | 扫描需要补偿的支付单，主动向第三方查询真实状态并落库（逻辑见 6.4） |
| 扫描条件 | ① `status='PENDING'` 且 `created_at < now() - 180s`；② `status='PROCESSING'` 且 `updated_at < now() - 300s`。排除 `expires_at < now() - 72h` 的超期单 |
| 批量 | 每轮最多 200 条；**单轮总第三方调用数上限** `COMPENSATE_MAX_CALLS_PER_ROUND`（默认 100），防止第三方限流 |
| 幂等要求 | 与回调处理**共用 `apply_payment_outcome`**，由条件更新与唯一索引保证。重复执行不会重复入账或重复发事件（见 6.4.3） |
| 频率控制 | 同一支付单两次查询间隔至少 60 秒（`last_synced_at` 判断）；退避策略：连续失败 3 次后，同一支付单的查询间隔按 1m / 5m / 15m / 30m 递增，最长 30 分钟一次 |
| 分布式锁 | `payment:task:compensation`，TTL 110 秒，`SET NX` |
| 监控 | `payment_compensation_total{result}`；`payment_compensation_lag_seconds`（PENDING 支付单从创建到被补偿成功的中位耗时）；告警：`PAYMENT_COMPENSATION_EXHAUSTED`（超 72 小时仍未终态） |

### 8.3 退款状态同步与重试

| 项 | 内容 |
|---|---|
| 任务名 | `refund_sync_task` |
| 周期 | 每 3 分钟 |
| 职责 | ①对 `status='PENDING'` 的退款单主动查询第三方状态并落定（6.6.6）；②对 `status='PENDING'` 且 `retry_count < REFUND_MAX_RETRY` 且距上次尝试超过退避间隔的退款单，重新调用第三方创建退款（6.6.5）；③对超时悬挂的退款单（有额度预占但第三方无记录）释放额度 |
| 退避间隔 | 按 `retry_count`：1 次 → 1 分钟、2 次 → 5 分钟、3 次 → 30 分钟 |
| 批量 | 每轮最多 200 条 |
| 幂等要求 | ①查询落定走 `settle_refund_success`（条件更新 + `uk_payment_transactions_refund_success`）；②重试调用第三方时传 `refund_no` 作为第三方幂等键；③额度释放用 `WHERE refunded_amount_cents >= :amount` 保证不会减成负数。三项均条件更新，重复执行安全 |
| 分布式锁 | `payment:task:refund_sync`，TTL 170 秒，`SET NX` |
| 监控 | `payment_refund_sync_total{result}`；`refund_pending_seconds`（退款从申请到成功的耗时分布）；告警：`REFUND_NEED_MANUAL`（重试超限） |
| 人工介入 | 超限后不再自动重试，由 3.13 接口人工处理。定时任务**不扫描 `FAILED` 状态的退款单**，避免与人工操作竞争 |

### 8.4 每日对账

| 项 | 内容 |
|---|---|
| 任务名 | `daily_reconciliation_task` |
| 周期 | 每日 `PAYMENT_RECON_CRON`（默认 `0 30 2 * * *`，UTC 02:30，即北京时间 10:30，对应渠道前一日账单已出） |
| 职责 | 对**每个渠道**执行前一自然日的对账（6.7.2）；两渠道并行执行 |
| 对账日 | `reconcile_date = 昨天`（按 `PAYMENT_RECON_TIMEZONE_{CHANNEL}` 计算，见 6.7.1） |
| 幂等要求 | `uk_recon_batches_channel_date`（同一渠道同一天只允许一个 `RUNNING`/`SUCCEEDED` 批次）。任务重跑时若已有成功批次，**跳过并记录日志**（不自动 `force`）；人工需要重跑时走 3.14 接口并显式传 `force=true` |
| 分布式锁 | `payment:recon:running:{channel}`，TTL 30 分钟，`SET NX` |
| 容错 | 单渠道失败不影响另一渠道；批次置 `FAILED` 并告警 `RECON_TASK_FAILED` |
| 监控 | `recon_batch_duration_seconds`、`recon_differences_total{channel,type}`；告警：`RECON_DIFFERENCE_FOUND`（差异数 > 0，P1） |

### 8.5 Outbox 事件投递

| 项 | 内容 |
|---|---|
| 任务名 | `outbox_dispatch_task` |
| 周期 | 每 5 秒 |
| 职责 | 扫描 `status IN ('PENDING','FAILED') AND next_retry_at <= now()` 的 outbox 记录，按 `aggregate_id, id` 顺序投递至 RabbitMQ，成功后置 `SENT` 并记录 `sent_at` |
| 顺序保证 | **按 `aggregate_id`（即 `payment_no`）分组投递**，同一 `payment_no` 的事件严格按 `id` 递增顺序发送；不同聚合可并行。若同一聚合的前一条未成功，后续事件**等待**（不跳过），保证同一支付单的事件顺序 |
| 批量 | 每轮最多 200 条 |
| 幂等要求 | 投递失败重试；重复投递由消费端按 `event_id` 去重兜底（通用约定 10.4）。投递成功后置 `SENT` 是条件更新（`WHERE status IN ('PENDING','FAILED')`） |
| 退避 | 按 `retry_count`：1s / 5s / 30s / 2m / 10m，共 5 次（与通用约定 10.4 一致）；超限置 `FAILED` 并告警 `OUTBOX_DISPATCH_FAILED` |
| 分布式锁 | `payment:task:outbox`，TTL 4 秒 |
| 监控 | `outbox_pending_count`（Gauge，积压量）、`outbox_dispatch_lag_seconds`；告警：积压 > 100 且持续 5 分钟 |
| 清理 | 每日清理 `status='SENT' AND sent_at < now() - 7 days` 的记录（可合并到本任务的低频分支） |

### 8.6 数据一致性巡检

| 项 | 内容 |
|---|---|
| 任务名 | `payment_consistency_check_task` |
| 周期 | 每小时 |
| 职责 | 巡检以下不变量，发现不一致即告警（**只告警，不自动修复**，与 6.7.3 的处理原则一致）：<br>① `payments.refunded_amount_cents` 与 `refunds` 表中成功退款金额之和是否一致<br>② 每个 `SUCCEEDED` 的支付单是否有对应的 `PAYMENT` 类型成功流水<br>③ `payment_transactions` 中是否有引用了不存在的 `payments` 的记录<br>④ 是否存在 `status='SUCCEEDED'` 但 `third_party_payment_id IS NULL` 的支付单（不应存在） |
| 幂等要求 | 只读任务，天然幂等 |
| 监控 | `payment_consistency_violation_total{check}`；告警：任一不一致 → P0 告警（资金数据不一致属最高级别） |
| 设计理由 | 这是一道"自我校验"防线，用于发现应用层 bug 造成的累积性数据损坏。它不替代对账（对账比对的是第三方，本任务比对的是本地表之间） |

### 8.7 定时任务汇总

| 任务名 | 周期 | 幂等机制 | 分布式锁 | 优先级 |
|---|---|---|---|---|
| `payment_timeout_close_task` | 1 分钟 | 条件更新 | 可选 | P1 |
| `payment_compensation_sync_task` | 2 分钟 | 条件更新 + 唯一索引 | 是 | P0 |
| `refund_sync_task` | 3 分钟 | 条件更新 + 幂等键 | 是 | P0 |
| `daily_reconciliation_task` | 每日 02:30 UTC | 批次唯一索引 | 是 | P1 |
| `outbox_dispatch_task` | 5 秒 | 条件更新 + 消费端去重 | 是 | P0 |
| `payment_consistency_check_task` | 1 小时 | 只读 | 否 | P1 |

## 10. 安全与权限

### 10.1 鉴权要求

| 接口组 | 鉴权方式 | 说明 |
|---|---|---|
| `/api/v1/payments/*`（买家侧） | 网关 JWT 校验 + 网关注入 `X-User-Id` | 服务内以 `X-User-Id` 做归属校验，禁止信任请求参数中的 `user_id` |
| `/api/v1/payments/stripe/webhook`、`/paypal/webhook` | **免登录**（白名单）+ 验签 | 见 6.3.2 / 6.3.3；不做 JWT 校验（第三方无法携带用户令牌） |
| `/api/v1/admin/payments/*` | 网关 JWT + 服务内角色校验 | 角色不足返回 `COMMON-3001` |
| `/internal/v1/payments/*` | `X-Internal-Token` 校验 | 网关不路由（平台文档 2.1），校验失败返回 `COMMON-2002` |

**Webhook 的特殊安全考量**：Webhook 是唯一免登录的写接口，其安全性完全建立在验签之上。因此：

- 验签失败一律拒绝（`PAY-1004` 之外的失败路径），**不提供"验签失败但放行"的开关**（测试环境的 `SKIPPED` 仅通过配置 `PAYMENT_WEBHOOK_ALLOW_SKIP_VERIFY`（仅 `dev`/`test` 允许）控制，且生产环境启动时若该配置为 true 则**拒绝启动**）
- Webhook 路径在网关单独限流（300 次/分钟/IP），并在服务内对验签失败来源做二级限流（60 秒 20 次）
- 回调处理中不做任何用户身份相关的操作，因此即使被攻破也不会导致越权

### 10.2 数据归属校验

| 资源 | 校验规则 | 失败响应 |
|---|---|---|
| 支付单查询/同步 | `payments.user_id == X-User-Id` | `COMMON-3001`（越权返回 403，不返回 404，避免暴露资源存在性） |
| 按订单查支付单 | 按 `order_no` 查出所有支付单后校验 `user_id`；若支付单为空则直接返回空列表（不校验） | 同上的规则：若存在支付单但非本人，返回 `COMMON-3001` |
| 退款单查询 | `refunds.user_id == X-User-Id` | `COMMON-3001` |
| 发起退款（买家） | `payments.user_id == X-User-Id` | `COMMON-3001` |
| 内部接口 | 无用户身份校验（服务间调用），但**不返回任何用户隐私字段**（仅返回金额与状态） | — |

**"按订单查支付单"的归属校验细节**：由于 `order_no` 由客户端提供，攻击者可能遍历订单号查询他人支付单。因此实现上**必须先按 `order_no` 查出支付单，再用其 `user_id` 与 `X-User-Id` 比对**，不能因为"查不到就返回空列表"而跳过校验——若查到了别人的支付单，必须返回 403。若订单号完全不存在任何支付单，返回空列表（此时不泄露任何信息，因为空列表与"该订单从未支付"无法区分）。

| 触发对账 | — | — | ✓ | — | ✓ |
| 差异处理 | — | — | ✓ | — | ✓ |

**职责分离（SoD）设计**：

- **退款发起与退款重试分离**：发起退款的角色（客服、订单运营）不能执行人工重试（重试是财务/管理员权限）。理由是重试涉及"向第三方重复发起资金流出"，风险等级高于首次发起，需要更谨慎的角色
- **财务不发起退款**：财务只负责对账与资金核查，不参与资金流出的发起，避免"既做账又动钱"
- **审核与发起分离（同角色内）**：客服发起的退款由订单运营审核（通过 `audit_status` 流转）；本期未强制"审核人 ≠ 发起人"，但审计日志中记录两者 ID，可由管理员事后核查

### 10.4 日志脱敏

在通用约定第 12.3 节基础上，本服务的补充规定：

| 字段 | 处理 | 说明 |
|---|---|---|
| 卡号、CVV、有效期 | **不记录**；出现即视为缺陷（P0 缺陷） | 平台本不接触，若日志中出现说明代码路径有问题 |
| `STRIPE_SECRET_KEY`、`PAYPAL_CLIENT_SECRET` | 完全不记录 | 通用约定已规定 |
| `STRIPE_WEBHOOK_SECRET`、`PAYPAL_WEBHOOK_ID` | 完全不记录 | 泄露会导致伪造回调 |
| `client_secret`（Stripe 支付意图凭据） | 日志中只记录前 12 位 + `****` | 泄露可被用于前端冒用，但危险度低于密钥 |
| 回调 `raw_body` | **可以落库**（`payment_callback_logs`），但**不写入应用日志** | 落库是为了验签复现与排查；日志中只记录 `event_id`、`event_type`、`payment_no`、处理结论 |
| 第三方 API 响应体 | 只记录 `status`、`error_code`、`error_message`（截断 255 字符）；**不记录完整响应体** | 响应体可能包含支付方式详情 |
| 用户邮箱/手机号 | 本服务不存储也不返回这些字段（无需脱敏，因为根本没有） | 通知由通知服务负责 |
| `X-Internal-Token` | 完全不记录 | — |
| 支付单的 `pay_url` | 日志中只记录域名部分 | URL 中可能含一次性 token |

**脱敏实现**：在日志中间件中增加一个**关键词黑名单过滤器**，对出站日志的 JSON 字符串做正则替换（`card[_-]?number`、`cvv`、`cvc`、`security[_-]?code`、`pan`、`secret_key`、`webhook_secret` 等），命中后替换为 `***REDACTED***` 并触发 P1 告警（说明某处代码试图记录敏感字段）。这是防止"开发者无意记录了敏感字段"的兜底。

### 10.5 后台操作审计

所有 `/api/v1/admin/payments/*` 的写操作（退款审核、退款重试、触发对账、差异处理标记）必须记录审计日志，字段遵循平台文档 6.3"审计"要求：

| 字段 | 说明 |
|---|---|
| `operator_id` | 操作人（来自 `X-User-Id`） |
| `operator_roles` | 操作人角色 |
| `action` | 动作，如 `refund.audit.approve`、`refund.retry`、`reconciliation.trigger` |
| `target_type` / `target_id` | 对象类型与标识（如 `REFUND` / `RF20260910000001`） |
| `before` / `after` | 变更前后关键字段（如退款单的 `status`、`audit_status`） |
| `ip` | 来源 IP（`X-Client-Ip`） |
| `trace_id` | 链路 ID |
| `note` | 操作人填写的说明 |

审计日志**独立于应用日志**，写入专门的审计表或审计日志流（本服务写入 `payment_callback_logs` 之外独立的审计通道，具体由平台文档 7 章的横切设计统一定义），保留期与订单/支付日志一致（180 天）。

## 12. 测试要点

测试策略遵循平台文档第 10 章。本服务的核心测试目标是**不重复入账、不超额退款、不漏账**。

### 12.1 单元测试（pytest，覆盖率要求：核心逻辑 ≥ 90%）

| 用例 | 验证点 |
|---|---|
| `cents_to_paypal` / `paypal_to_cents` 双向换算 | 19900 ↔ `"199.00"`；`"199.9"` → 19990；`"0.01"` → 1；拒绝负数与非法格式；**不经过 float** |
| `cents_to_stripe` | CNY 下身份映射；零小数位币种抛 `UnsupportedCurrency` |
| 支付单状态机 | 合法迁移全部通过；非法迁移（如 `CLOSED → SUCCEEDED`、`SUCCEEDED → PENDING`）被拒绝 |
| 退款类型判定 | 金额等于支付金额 → `FULL`；小于 → `PARTIAL`；客户端传入的 `refund_type` 被忽略 |
| 可退金额计算 | `amount - refunded`；`refunded = amount` 时可退为 0，再退被拒 |
| Stripe 验签 | 正确签名通过；篡改 body 后被拒；时间戳超差被拒；缺少签名头被拒；签名比较为常量时间 |
| 渠道状态归一化 | Stripe `succeeded` / `processing` / `requires_payment_method` 等映射正确；未知状态抛 `PAY-8004` 并保留原始值 |
| 熔断器 | 窗口内错误率超阈值触发 OPEN；OPEN 后 `is_open()` 为真；半开探测成功恢复、失败继续熔断 |
| 回调事件解析 | 三种结果（SUCCEEDED / FAILED / PROCESSING）解析字段完整；金额字段缺失时报错 |
| 对账差异识别 | 构造 5 种差异类型的数据集，逐类型断言；正常匹配不计入差异 |
| 对账时区换算 | `Asia/Shanghai` 的 2026-09-10 → UTC `[2026-09-09T16:00Z, 2026-09-10T16:00Z)` |
| 敏感字段过滤器 | 含 `card_number`、`cvv` 的日志被替换为 `***REDACTED***` 并触发告警计数 |

### 12.2 集成测试（pytest + testcontainers，真实 PostgreSQL + Redis + RabbitMQ）

**支付主流程**：

| 用例 | 验证点 |
|---|---|
| 发起支付（Stripe，Mock 第三方返回成功） | 支付单落库 `PENDING`；金额等于订单服务返回值；返回 `client_secret`；Redis 幂等键写入 |
| 客户端篡改金额 | 请求体传 `amount_cents=1`，但支付单金额仍为订单服务返回的值；`payments_client_amount_injected_total` 计数 +1 |
| 订单服务的金额与请求不符 | 以订单服务返回值为准（防篡改用例） |
| 订单状态非待支付 | 返回 `PAY-5001`，不创建支付单 |
| 订单不属于当前用户 | 返回 `COMMON-3001`，不创建支付单 |
| 订单服务不可用（停容器） | 返回 `PAY-7001`，不创建支付单 |
| 缺少 `Idempotency-Key` | 返回 `PAY-1001` |
| **同一 `Idempotency-Key` 并发提交 10 次** | 只创建一个支付单，10 次响应同一 `payment_no`，其中 9 次带 `idempotent_replay: true` |
| **同一订单同一渠道并发提交 10 次（不同幂等键）** | 只创建一个支付单（`uk_payments_order_channel_active` 生效），其余返回既有支付单 |
| 支付单失败后换渠道重发 | 允许创建新支付单（不同渠道不冲突） |
| 支付单关闭后同渠道重新发起 | 允许创建新支付单（部分唯一索引只覆盖进行中状态） |
| 第三方创建意图超时 | 支付单保持 `PENDING`，不发 `payment.failed`；补偿任务可查回意图 ID 并推进 |
| 第三方返回明确失败 | 支付单置 `FAILED`，发 `payment.failed`，返回 `PAY-7002` |

**回调处理（重点）**：

| 用例 | 验证点 |
|---|---|
| **同一回调重复投递 5 次** | 只入账一次；`payment_transactions` 只有 1 条；`payment.succeeded` 只发 1 次；5 次均返回 200，第 2~5 次带 `duplicate: true` |
| **不同事件 ID 但同一交易号投递 2 次**（模拟 Stripe 多事件类型） | L2 唯一索引生效，只入账一次；第二次返回 200 |
| **并发投递同一回调 10 次** | 通过 L1/L2/L3 三层防护，只有 1 条流水、1 个事件；无未捕获的 `UniqueViolation` |
| 验签失败（伪造签名） | 返回 400；不触碰业务表；`payment_callback_logs.verify_result='FAIL'`；告警触发 |
| **金额不符**（第三方 18900，本地 19900） | 不修改支付单、不写流水、不发事件；返回 200 + `mismatch: true`；P0 告警触发；`process_note` 记录两侧金额 |
| 币种不符 | 同金额不符处理 |
| **找不到支付单** | 返回 200 + `unmatched: true`；`process_result='IGNORED'`；告警触发；无业务表变更 |
| 支付单号存在但渠道不符 | 记 `IGNORED` + 告警，不修改支付单 |
| 不认识的事件类型 | 记 `IGNORED`，返回 200 |
| 报文格式错误 | 返回 400，记 `FAILED` |
| **回调落库成功但处理时 DB 异常，第三方重试** | 重试时识别原记录为 `RECEIVED`，**继续处理**而非直接返回重复；最终入账一次 |
| 回调处理耗时 | 断言 Stripe 回调处理 < 500ms（PayPal 因远程验签放宽到 3s），验证"快速返回"设计 |
| PayPal 验签接口不可用 | 返回 500，记 `FAILED`；补偿任务可在之后补状态 |
| 回调处理时间戳 | 记录 `process_duration_ms`，验证在预算内 |

**回调丢失补偿**：

| 用例 | 验证点 |
|---|---|
| 支付成功但回调未到达（Mock 回调不投递） | 补偿任务在 180 秒后查询到成功，支付单置 `SUCCEEDED`，发 `payment.succeeded` |
| 补偿先于回调完成，随后回调到达 | 回调识别为重复，返回 2xx，不发第二次事件，无重复流水 |
| 第三方查无此单且已过期 | 支付单置 `CLOSED`（不是 `FAILED`） |
| 补偿超过 72 小时窗口 | 停止查询，触发 `PAYMENT_COMPENSATION_EXHAUSTED` 告警 |
| 第三方先报 `FAILED` 后补偿查到 `SUCCEEDED` | 允许 `FAILED → SUCCEEDED` 恢复，补写流水与事件，触发 P1 告警 |
| 补偿任务与回调任务并发处理同一支付单 | 只有一个入账，另一个走幂等分支 |

**退款**：

| 用例 | 验证点 |
|---|---|
| 全额退款 | `refund_type='FULL'`；支付单 `refunded_amount_cents = amount_cents`；发 `payment.refunded` |
| 部分退款两次（合计 ≤ 支付金额） | 两次均成功；`refunded_amount_cents` 正确累加；两条退款流水 |
| **部分退款两次，合计超过支付金额** | 第二次返回 `PAY-5007`，未调用第三方，`refunded_amount_cents` 未被修改 |
| **并发发起两笔退款，合计超过可退金额** | 只有一笔成功；另一笔因条件更新影响行数为 0 而失败（`PAY-5007` 或退款单置 `CLOSED`）；`refunded_amount_cents` 不超过 `amount_cents` |
| 并发发起两笔退款，合计恰好等于可退金额 | 两笔均成功；`refunded_amount_cents == amount_cents` |
| 同一 `Idempotency-Key` 重复退款请求 5 次 | 返回同一退款单，只调用一次第三方 |
| 同一幂等键用于另一支付单 | 返回 `PAY-5008` |
| 对未支付的支付单退款 | 返回 `PAY-5002` |
| 财务角色发起退款 | 返回 `COMMON-3001` |
| 买家退款超过审核阈值 | 退款单 `audit_status='PENDING'`，不调用第三方 |
| 审核驳回 | 退款单置 `CLOSED`，额度未被预占，通知申请人 |
| 审核通过后第三方调用失败 | 额度已预占，退款单 `FAILED`，`retry_count` +1；8.3 任务重试 |
| 退款第三方超时 | 额度保留，转同步任务查询；查询确认未退款后释放额度 |
| 退款回调重复投递 3 次 | 只落定一次；`uk_payment_transactions_refund_success` 生效；只发一次事件 |
| 退款重试超限 | 退款单置 `FAILED`，`REFUND_NEED_MANUAL` 告警 |
| 人工重试（第三方已退款但回调丢失） | 先查询发现第三方已成功 → 直接落定，**不重发**，无重复退款 |
| 人工重试（第三方确认无记录） | 重发并成功 |
| 额度释放的边界 | `release_refund_amount` 不会把 `refunded_amount_cents` 减成负数（`WHERE >= :amount` 生效） |

**对账**：

| 用例 | 验证点 |
|---|---|
| 构造完全匹配的数据集 | `difference_count = 0`，`status='SUCCEEDED'`，两侧金额合计一致 |
| 构造 `LOCAL_ONLY`（本地多一条） | 差异类型正确；`diff_amount_cents` 为负 |
| 构造 `THIRD_PARTY_ONLY`（第三方多一条） | 差异类型正确；`diff_amount_cents` 为正 |
| 构造 `AMOUNT_MISMATCH` | 差异记录两侧金额与差额正确 |
| 构造 `STATUS_MISMATCH` | 差异类型正确，差额为 0 |
| 构造 `DUPLICATE_LOCAL` | 正确识别 |
| **同一批次重跑** | `uk_recon_diff_batch_type_key` 生效，差异不重复；若无 `force` 则批次被拒（`PAY-5011`） |
| 第三方账单分页不完整 | 批次置 `PARTIAL`，不用于结账，告警触发 |
| 第三方账单拉取失败 | 批次置 `FAILED`，告警触发；不影响其他渠道 |
| 时区边界 | 对账日边界上的交易被正确分配（构造 UTC 15:59 与 16:01 的两笔交易，验证归属日） |
| 差异清单导出 | CSV 行数与差异条数一致；批次摘要行存在 |
| 差异告警 | 差异数 > 0 时触发 `RECON_DIFFERENCE_FOUND` |

**幂等与事务一致性**：

| 用例 | 验证点 |
|---|---|
| **outbox 与业务同事务** | 注入故障使 outbox 写入失败，断言支付单状态也未变更（同事务回滚） |
| outbox 投递失败重试 | 按 1s/5s/30s/2m/10m 退避；超限置 `FAILED` 并告警 |
| 同一 `payment_no` 的多个事件顺序投递 | 按 `id` 递增发送；前一条未成功时后一条等待 |
| 事件消费幂等 | 同一 `event_id` 消费 5 次，只处理一次 |
| 一致性巡检任务 | 手动构造 `refunded_amount_cents` 与退款单不一致的数据，断言巡检告警触发 |

**内部接口与权限**：

| 用例 | 验证点 |
|---|---|
| `X-Internal-Token` 缺失或错误 | 返回 `COMMON-2002` |
| 内部接口不返回用户隐私字段 | 响应中无邮箱、手机号、地址等字段 |
| 买家 A 访问买家 B 的支付单 | 返回 `COMMON-3001`（不是 404） |
| 买家 A 按订单号查买家 B 的支付单 | 返回 `COMMON-3001` |
| 买家 A 用买家 B 的订单号发起支付 | 返回 `COMMON-3001` |
| 后台接口角色不足 | 返回 `COMMON-3001` |
| 未经网关直接访问 admin 接口 | 服务内角色校验仍生效（不依赖网关） |

### 12.3 并发与压力测试

| 用例 | 工具 | 验证点 |
|---|---|---|
| 同一订单并发发起支付 100 次 | locust | 只创建 1 个支付单；无未捕获异常；P95 < 500ms |
| **同一回调并发投递 50 次** | locust / 脚本 | 只入账 1 次；1 条流水；1 个事件；数据库无死锁 |
| **并发退款导致累计超限** | 脚本（10 个并发各退 30%） | 只有 3 个成功（合计 90%），其余被拒；`refunded_amount_cents <= amount_cents` 恒成立 |
| 补偿任务与回调并发处理同一支付单 | 脚本 | 只入账一次 |
| 支付链路端到端压测 | locust | 记录 P50/P95/P99；验证连接池不耗尽；数据库无慢查询累积 |

### 12.4 混沌测试

| 场景 | 注入方式 | 验证点 |
|---|---|---|
| Redis 停机 | 停 `redis` 容器 | 支付主流程仍可用（降级为纯数据库唯一索引）；功能正确性不变 |
| 订单服务停机 | 停 `order-service` 容器 | 发起支付返回 `PAY-7001`；已创建的支付单回调处理不受影响（回调不调订单服务） |
| RabbitMQ 停机 | 停 `rabbitmq` 容器 | 支付状态正常落库；outbox 积压；恢复后自动补投，事件不丢 |
| 第三方超时 | Mock 延迟 30 秒 | 创建支付返回 `PAY-7002` 但支付单不置失败；补偿任务正常 |
| 第三方连续失败 | Mock 返回 500 | 熔断触发；发起支付返回 `PAY-7004`；30 秒后半开探测恢复 |
| PostgreSQL 主库不可用 | 停 `postgres` | 回调返回 500（让第三方重试）；`/ready` 探针返回 503，实例被摘除 |
| 对账任务执行中进程被杀 | kill 任务进程 | 批次停留在 `RUNNING`；锁 TTL 释放后可重跑（`force=true`） |

### 12.5 端到端测试（与订单服务联调）

| 用例 | 验证点 |
|---|---|
| 下单 → 发起支付 → 回调 → 订单置为已支付 | 全链路打通；订单服务收到 `payment.succeeded` 并发出 `order.paid` |
| 下单 → 支付超时 → 订单关闭 | 订单与支付单最终一致（均关闭） |

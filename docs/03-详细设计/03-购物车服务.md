## 1. 服务概览

### 1.1 职责

购物车服务负责"用户把商品暂存起来、准备结算"这一段生命周期内的全部状态管理，是**商品浏览**与**订单创建**之间的缓冲层。

| 职责 | 说明 |
|---|---|
| 购物车增删改查 | 加购（同 SKU 累加）、改数量、单条/批量移除、清空 |
| 选中状态维护 | 部分勾选、全选、取消全选，供结算使用 |
| 失效与价格校验 | 查询时实时校验 SKU 上架状态、可售库存与最新价格，标记失效项与价格变动 |
| 结算预览 | 输出可结算清单、金额汇总、剔除明细与价格变动提示 |
| 游客购物车 | 未登录用户的临时购物车，登录后合并入账号购物车 |
| 跨设备持久化 | 登录态购物车长期保留，任意设备可见 |
| 与订单交接 | 向下单链路提供选中项快照；下单成功后清理已购买条目 |

**明确不属于本服务的职责**：

- **不占用库存**：购物车只做"可售量提示"，不做预占。真正的库存预占、扣减由商品目录服务在订单服务驱动下完成（见概要架构 5.3.1）。
- **不计算订单金额**：购物车只算"商品小计合计"，不含运费、优惠、税费。订单应付金额由订单服务计算（FR-ORD-002）。
- **不做商品检索与详情**：商品标题、规格、图片、价格全部来自商品目录服务，本服务只持有加购瞬间的快照。
- **不保存收货信息**：收货地址由用户服务管理，下单时由订单服务快照。
- **不发布领域事件**：购物车是用户私有状态，不存在多消费方广播语义（见第 5 章）。

### 1.2 服务边界

| 边界对象 | 交互内容 | 方向 | 方式 |
|---|---|---|---|
| API 网关（Traefik） | 转发买家端购物车页、结算页请求 | 入 | 同步 REST |
| 商品目录服务 catalog-service | 批量查询 SKU 状态/可售库存/最新价格/单品限购 | 出 | 同步 REST，有超时与降级 |
| 订单服务 order-service | 1) 提供选中项供下单<br>2) 接收下单成功后的条目清理 | 入 | 同步 REST（`/internal/v1/cart/*`） |
| 用户服务 user-service | 无需调用。登录态由网关注入的 `X-User-Id` 判定 | — | — |
| PostgreSQL `ecommerce_cart` | 持久化权威存储与恢复源 | — | — |
| Redis 7 | 运行时权威存储、落库队列、分布式锁 | — | — |
| RabbitMQ | **不使用**（本服务不发布、不订阅事件） | — | — |

依赖关系与概要架构 8.4 一致：`cart-service → catalog-service`（唯一同步下游）。

### 1.3 上下游依赖与降级

| 依赖 | 用途 | 不可用时行为 |
|---|---|---|
| catalog-service `/internal/v1/skus/batch` | 失效判定、价格比对、库存上限 | 查看购物车：沿用上一次校验结果并标记 `validity_stale=true`，不阻塞展示；结算预览：直接失败返回 `CART-7001`，禁止在无法校验的情况下进入下单 |
| Redis | 全部读写路径 | **服务不可用**。购物车是 Redis 主存储，Redis 故障即服务降级为不可用（Sentinel/主从切换期间返回 `CART-8002`）。不做"穿透到 DB 直读直写"的兜底，因为该路径无法承受购物车量级的写入压力，强行兜底会把故障转移到 PostgreSQL |
| PostgreSQL | 异步落库、恢复 | 落库暂停，Redis 侧继续服务；同步消息堆积在 `cart:sync:stream`，超阈值告警；积压超过 `CART_SYNC_SYNC_MODE_THRESHOLD` 时自动切换为**同步落库模式**（见 7.4） |

## 2. 数据库设计

### 2.1 表清单

| 表名 | 中文名 | 用途 | 预估量级 |
|---|---|---|---|
| `carts` | 购物车主表 | 一个 owner（登录用户或游客）一条活跃记录 | 与用户数同阶 |
| `cart_items` | 购物车明细表 | 购物车中的 SKU 条目，含加购时快照 | 用户数 × 平均 5~15 |
| `cart_guest_mappings` | 游客购物车映射表 | 游客标识 → 购物车，记录合并状态供幂等判断 | 与访客数同阶 |
| `cart_sync_logs` | 落库任务日志表 | Redis → DB 落库任务的持久化兜底与重试队列 | 低（仅异常任务落此表） |
| `cart_purge_records` | 下单清理记录表 | 下单成功后的条目清理幂等凭据 | 与订单数同阶 |

> **不建"失效商品表"**：失效是**派生状态**（下架、库存为 0 是商品目录服务的事实），不是购物车的事实。把它落库会引入"商品重新上架后购物车仍标失效"的一致性问题，且需要商品变更事件来驱动——而标准事件目录中不存在商品变更事件（见第 5 章）。因此失效状态一律实时推导，不落库。

### 2.2 `carts` 购物车主表

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | PK | — | 雪花 ID |
| `owner_type` | VARCHAR(16) | NOT NULL, CHECK | — | 归属类型：`USER` / `GUEST` |
| `user_id` | BIGINT | NULL | NULL | 登录用户 ID；`owner_type=USER` 时必填 |
| `guest_id` | VARCHAR(64) | NULL | NULL | 游客标识（UUID v4 字符串）；`owner_type=GUEST` 时必填 |
| `status` | VARCHAR(16) | NOT NULL, CHECK | `ACTIVE` | 购物车状态：`ACTIVE` / `MERGED` / `EXPIRED` |
| `item_count` | INTEGER | NOT NULL | 0 | 条目数（不同 SKU 数） |
| `selected_item_count` | INTEGER | NOT NULL | 0 | 选中条目数 |
| `selected_amount_cents` | BIGINT | NOT NULL | 0 | 选中项按**快照价**计算的商品小计合计（分） |
| `currency` | CHAR(3) | NOT NULL | `CNY` | ISO 4217 币种 |
| `op_seq` | BIGINT | NOT NULL | 0 | 购物车操作序号，单调递增。**用于判定 Redis 与 DB 哪一侧更新**（见 6.8） |
| `last_active_at` | TIMESTAMPTZ | NOT NULL | `now()` | 最后一次写操作时间，用于游客车清理 |
| `merged_into_cart_id` | BIGINT | NULL | NULL | 被合并到的目标购物车 ID（仅游客车） |
| `created_at` | TIMESTAMPTZ | NOT NULL | `now()` | 创建时间 |
| `updated_at` | TIMESTAMPTZ | NOT NULL | `now()` | 更新时间，应用层维护 |

> `item_count` / `selected_item_count` / `selected_amount_cents` 是**冗余汇总字段**，由落库任务在同一事务内与明细一起更新，用于内部接口和运营侧免聚合查询。Redis 侧的 `cart:meta` 才是服务运行时读取的汇总来源。

### 2.3 `cart_items` 购物车明细表

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | PK | — | 雪花 ID，即 API 中的 `item_id`，**在主键生成后立即用于 Redis 写入** |
| `cart_id` | BIGINT | NOT NULL | — | 所属购物车 ID（逻辑引用 `carts.id`，无物理外键） |
| `sku_id` | BIGINT | NOT NULL | — | SKU ID（逻辑引用 catalog 服务，本服务不存可变字段） |
| `quantity` | INTEGER | NOT NULL, CHECK > 0 | — | 数量。**0 在业务层即移除，不会落库** |
| `is_selected` | BOOLEAN | NOT NULL | TRUE | 是否选中结算 |
| `snapshot_title` | VARCHAR(256) | NOT NULL | `''` | 加购时商品标题快照 |
| `snapshot_spec_name` | VARCHAR(256) | NOT NULL | `''` | 加购时规格快照，如 `M / 黑色` |
| `snapshot_image_url` | VARCHAR(512) | NOT NULL | `''` | 加购时主图快照 |
| `snapshot_unit_price_cents` | BIGINT | NOT NULL | — | 加购时单价快照（分） |
| `snapshot_at` | TIMESTAMPTZ | NOT NULL | — | 快照生成时刻，合并冲突时取较新者 |
| `currency` | CHAR(3) | NOT NULL | `CNY` | 币种 |
| `version` | BIGINT | NOT NULL | 0 | 条目级写入序号，**落库时 last-write-wins 的依据** |
| `added_at` | TIMESTAMPTZ | NOT NULL | `now()` | 加入时间（合并时保留原值） |
| `created_at` | TIMESTAMPTZ | NOT NULL | `now()` | 创建时间 |
| `updated_at` | TIMESTAMPTZ | NOT NULL | `now()` | 更新时间 |

**为什么快照价格也存在这里**：快照是"用户加购时看到的价格"，是给用户的价格变动提示的比对基准，必须持久化，否则 Redis 回源重建后无法再判断"价格是否变动过"。它与订单明细快照（FR-ORD-001）语义不同：购物车快照**可变**（用户确认接受新价后允许覆盖），订单快照**不可变**。

### 2.4 `cart_guest_mappings` 游客购物车映射表

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | PK | — | 雪花 ID |
| `guest_id` | VARCHAR(64) | NOT NULL | — | 游客标识（UUID v4） |
| `cart_id` | BIGINT | NOT NULL | — | 该游客标识对应的购物车 ID |
| `is_merged` | BOOLEAN | NOT NULL | FALSE | 是否已合并到登录账号 |
| `merged_into_cart_id` | BIGINT | NULL | NULL | 合并目标购物车 ID |
| `merged_into_user_id` | BIGINT | NULL | NULL | 合并目标用户 ID |
| `merged_at` | TIMESTAMPTZ | NULL | NULL | 合并时刻 |
| `first_seen_at` | TIMESTAMPTZ | NOT NULL | `now()` | 首次出现时间 |
| `last_seen_at` | TIMESTAMPTZ | NOT NULL | `now()` | 最近一次携带该标识请求的时间 |
| `created_at` | TIMESTAMPTZ | NOT NULL | `now()` | 创建时间 |
| `updated_at` | TIMESTAMPTZ | NOT NULL | `now()` | 更新时间 |

该表是**合并幂等性的唯一权威**：`POST /api/v1/cart/merge` 重复调用时，以 `guest_id` 查得 `is_merged=true` 即直接返回既有结果，不重复累加数量。

### 2.5 `cart_sync_logs` 落库任务日志表

| 字段名 | 类型 | 约束 | 默认值 | 说明 |
|---|---|---|---|---|
| `id` | BIGINT | PK | — | 雪花 ID |
| `owner_key` | VARCHAR(96) | NOT NULL | — | 购物车 owner key，如 `u:1024` / `g:550e8400...` |
| `op_seq` | BIGINT | NOT NULL | — | 对应 Redis 侧操作序号 |
| `cart_id` | BIGINT | NULL | NULL | 购物车 ID |
| `op_type` | VARCHAR(32) | NOT NULL | — | `UPSERT_ITEM` / `DELETE_ITEM` / `SELECT_ITEM` / `REPLACE_ALL` / `PURGE_ITEMS` |
| `item_id` | BIGINT | NULL | NULL | 单条操作时的条目 ID |
| `payload` | JSONB | NOT NULL | `'{}'` | 落库所需的最小数据（明细快照或条目 ID 列表） |
| `status` | VARCHAR(16) | NOT NULL | `PENDING` | `PENDING` / `DONE` / `FAILED` / `DEAD` |
| `retry_count` | INTEGER | NOT NULL | 0 | 已重试次数 |
| `next_retry_at` | TIMESTAMPTZ | NULL | NULL | 下次重试时间（指数退避） |
| `last_error` | TEXT | NULL | NULL | 最近一次失败原因（截断至 2000 字符） |
| `stream_id` | VARCHAR(64) | NULL | NULL | 来源 Redis Stream 消息 ID |
| `created_at` | TIMESTAMPTZ | NOT NULL | `now()` | 创建时间 |
| `updated_at` | TIMESTAMPTZ | NOT NULL | `now()` | 更新时间 |

**仅在异常路径写入**：正常落库走 Redis Stream 内存队列，不落此表；只有 Stream 消费失败达到重试上限时，才把任务持久化到这里做持久重试。这样正常路径零额外 DB 写入。

### 2.7 索引设计

| 索引名 | 表 | 字段 | 类型 | 用途 |
|---|---|---|---|---|
| `pk_carts` | carts | `id` | PK | — |
| `uk_carts_user_id` | carts | `user_id` WHERE `owner_type='USER'` | UNIQUE 部分索引 | 一个用户只有一个购物车；登录合并时按用户定位目标车 |
| `uk_carts_guest_id` | carts | `guest_id` WHERE `owner_type='GUEST'` | UNIQUE 部分索引 | 一个游客标识只有一个购物车 |
| `pk_cart_items` | cart_items | `id` | PK | 条目定位 |
| `uk_cart_items_cart_id_sku_id` | cart_items | `cart_id`, `sku_id` | UNIQUE | 同车同 SKU 唯一，是落库 upsert 的冲突键 |
| `idx_cart_items_cart_id_added_at` | cart_items | `cart_id`, `added_at` | 普通 | 按加入时间输出购物车列表 |
| `idx_cart_items_sku_id` | cart_items | `sku_id` | 普通 | 反向排查（某 SKU 下架/召回时定位受影响购物车） |
| `pk_cart_guest_mappings` | cart_guest_mappings | `id` | PK | — |
| `uk_cart_guest_mappings_guest_id` | cart_guest_mappings | `guest_id` | UNIQUE | 合并幂等判断的唯一入口 |
| `idx_cart_guest_mappings_is_merged_last_seen_at` | cart_guest_mappings | `is_merged`, `last_seen_at` | 普通 | 定时清理未合并的过期游客车 |
| `pk_cart_sync_logs` | cart_sync_logs | `id` | PK | — |
| `uk_cart_sync_logs_owner_key_op_seq` | cart_sync_logs | `owner_key`, `op_seq` | UNIQUE | 重投去重，防止同一操作重复落库 |
| `idx_cart_sync_logs_status_next_retry_at` | cart_sync_logs | `status`, `next_retry_at` | 普通 | 定时任务扫描待重试任务 |
| `pk_cart_purge_records` | cart_purge_records | `id` | PK | — |
| `uk_cart_purge_records_order_no` | cart_purge_records | `order_no` | UNIQUE | 清理幂等，重复请求直接返回首次结果 |
| `idx_cart_purge_records_user_id_created_at` | cart_purge_records | `user_id`, `created_at DESC` | 普通 | 用户清理历史查询 |

单表索引数：carts 3 个、cart_items 4 个、cart_guest_mappings 3 个、cart_sync_logs 3 个、cart_purge_records 3 个，均未超过约定上限 6 个。

### 2.8 枚举字典

| 枚举 | 取值 | 说明 |
|---|---|---|
| `carts.owner_type` | `USER` / `GUEST` | 登录用户车 / 游客车 |
| `carts.status` | `ACTIVE` / `MERGED` / `EXPIRED` | 活跃 / 已合并入账号 / 已过期（游客车超期未合并） |
| `cart_sync_logs.op_type` | `UPSERT_ITEM` / `DELETE_ITEM` / `SELECT_ITEM` / `REPLACE_ALL` / `PURGE_ITEMS` | 条目新增或更新 / 条目删除 / 选中状态变更 / 整车覆盖 / 下单后批量清理 |
| `cart_sync_logs.status` | `PENDING` / `DONE` / `FAILED` / `DEAD` | 待处理 / 已完成 / 待重试 / 已死信 |
| API 层 `invalid_reason`（不落库） | `OFF_SHELF` / `SOLD_OUT` / `SKU_NOT_FOUND` / `PURCHASE_LIMIT_EXCEEDED` | 已下架 / 可售库存为 0 / SKU 已删除 / 加购数超过单品限购 |
| API 层 `price_state`（不落库） | `NORMAL` / `INCREASED` / `DECREASED` | 价格未变 / 涨价 / 降价 |

### 2.9 完整可执行 DDL

```sql
-- =============================================================================
-- 购物车服务（cart-service）数据库初始化脚本
-- 目标库：ecommerce_cart        目标版本：PostgreSQL 16
-- 字符集/时区：UTF8 / UTC（连接串需带 TimeZone=UTC）
--
-- 设计说明：
--   1. 本服务以 Redis 为「运行时权威」，PostgreSQL 为「持久化权威与恢复源」。
--      Redis 写入后由后台 worker 异步落库，落库任务经 Redis Stream 传递。
--   2. carts.op_seq 为购物车级单调操作序号，用于判定 Redis 与 DB 哪一侧更新：
--      对账/恢复时以 op_seq 较大的一侧为准（见详细设计 6.8）。
--   3. cart_items.version 为条目级写入序号，落库时以
--      「excluded.version > cart_items.version」作为 last-write-wins 条件，
--      保证乱序消费不会用旧值覆盖新值。
```

## 3. API 设计

### 3.1 通用说明

**身份识别（本服务特有）**

| 请求头 | 场景 | 说明 |
|---|---|---|
| `X-User-Id` | 登录用户 | 由网关校验 JWT 后注入，**服务端只信任该头**，不解析令牌。存在时操作登录用户购物车 |
| `X-Guest-Id` | 游客 | 由客户端生成 UUID v4 并经此头传递。网关**保留**该头（客户端产物的正常透传），服务端做格式校验 |
| `Idempotency-Key` | 写接口可选 | 见 3.11 |

**身份判定优先级**：`X-User-Id` 存在 → 登录态，忽略 `X-Guest-Id`；否则 `X-Guest-Id` 存在且合法 → 游客态；两者都无 → `CART-2001`（401）。

**响应约定**：所有接口遵循通用约定第 2 章信封格式；`id` / `item_id` / `sku_id` / `cart_id` 等 64 位整型在 JSON 中序列化为**字符串**；金额字段以 `_cents` 结尾、整型分值。

**购物车资源统一视图（`CartView`）**，多个接口复用：

| 字段 | 类型 | 说明 |
|---|---|---|
| `cart_id` | string | 购物车 ID |
| `cart_version` | string | 购物车操作序号（`op_seq`），客户端可用于乐观校验 |
| `owner_type` | string | `USER` / `GUEST` |
| `items` | array | 有效条目列表，结构见 `CartItemView`，按 `added_at` 升序 |
| `invalid_items` | array | 失效条目列表，结构见 `CartItemView`，含 `invalid_reason` / `invalid_message` |
| `summary` | object | 汇总，结构见 `CartSummary` |
| `validity_stale` | boolean | 本次失效校验是否降级（catalog 不可用时为 `true`，客户端展示"价格与库存状态可能不是最新"） |
| `validity_expires_at` | string\|null | 本次校验结果的有效期截止时间（ISO 8601） |
| `currency` | string | 币种，`CNY` |

**`CartItemView`**

| 字段 | 类型 | 说明 |
|---|---|---|
| `item_id` | string | 条目 ID |
| `sku_id` | string | SKU ID |
| `spu_id` | string\|null | SPU ID，便于前端跳详情页 |
| `title` | string | 商品标题（快照） |
| `spec_name` | string | 规格（快照） |
| `image_url` | string | 主图（快照） |
| `quantity` | integer | 数量 |
| `is_selected` | boolean | 是否选中（失效项恒为 `false`） |
| `snapshot_unit_price_cents` | integer | 加购时单价快照 |
| `current_unit_price_cents` | integer\|null | 当前单价；`validity_stale=true` 时为 `null` |
| `price_state` | string | `NORMAL` / `INCREASED` / `DECREASED` |
| `price_delta_cents` | integer | 当前价 − 快照价（可为负） |
| `subtotal_cents` | integer | 按**当前价** × 数量计算的小计；当前价不可得时按快照价 |
| `available` | integer\|null | 当前可售库存；不可得时为 `null` |
| `max_purchase_quantity` | integer\|null | 单品限购上限（catalog 提供）；无限制为 `null` |

| `invalid_message` | string\|null | 可直接展示的中文原因 |
| `added_at` | string | 加入时间（ISO 8601） |

**`CartSummary`**

| 字段 | 类型 | 说明 |
|---|---|---|
| `item_count` | integer | 有效条目数 |
| `invalid_item_count` | integer | 失效条目数 |
| `total_quantity` | integer | 有效条目数量合计 |
| `selected_item_count` | integer | 有效且选中的条目数 |
| `selected_quantity` | integer | 有效且选中的数量合计 |
| `selected_amount_cents` | integer | 有效且选中项按**当前价**计算的商品小计合计 |
| `selected_amount_snapshot_cents` | integer | 同上，但按快照价计算（用于判断金额是否变动） |
| `price_changed_count` | integer | 价格发生变动的选中条目数 |
| `all_selected` | boolean | 有效条目是否全选 |

### 3.4 `POST /api/v1/cart/items` 加入购物车

**鉴权**：登录用户或游客。

**请求头**：`Idempotency-Key`（可选，强烈建议前端必传以防重复提交）。

**请求体**

| 字段 | 类型 | 必填 | 约束 | 说明 |
|---|---|---|---|---|
| `sku_id` | string | 是 | 正整数，≤ 20 位 | SKU ID |
| `quantity` | integer | 是 | 1 ~ 999 | 本次新增数量，非最终数量 |

```json
{
  "sku_id": "3001",
  "quantity": 2
}
```

**处理流程**

1. 校验 `sku_id` 与 `quantity` 格式，`quantity` 不在 `1~999` 返回 `CART-1002`。
2. 幂等键存在 → 尝试 `SET cart:idem:{owner}:{key} ... NX EX 600`；抢占失败直接返回首次结果。
3. 调用 catalog-service `POST /internal/v1/skus/batch` 获取该 SKU 的 `status` / `available` / `price_cents` / `spu_id` / `title` / `spec_name` / `image_url` / `max_purchase_quantity`。
4. SKU 不存在 → `CART-5003`；`status != ON_SALE` → `CART-5003`；`available == 0` → `CART-5003`。
5. 计算允许上限 `limit = min(available, max_purchase_quantity or 999, CART_MAX_ITEM_QUANTITY)`。
6. 执行 Lua 脚本（见 6.1）：条目不存在则新增，存在则在原数量上累加；累加结果超过 `limit` 时**截断至 `limit`** 并在响应中返回提示，不报错。
7. 条目数已达 `CART_MAX_ITEMS_PER_CART` 且为新 SKU → `CART-5002`。
8. 返回最新购物车计数与提示。

**响应 200**

```json

  "code": "OK",
```

### 3.12 幂等键约定（本服务）

| 接口 | 幂等键 | 存储 | TTL | 重复请求行为 |
|---|---|---|---|---|
| `POST /cart/items` | 客户端 `Idempotency-Key` | `cart:idem:{owner_key}:{key}` | 10 分钟 | 返回首次加购的响应快照 |
| `POST /cart/items/batch-delete` | 客户端 `Idempotency-Key` | 同上 | 10 分钟 | 返回首次结果 |
| `POST /cart/checkout-preview` | 无（`accept_price_changes` 回写本身幂等） | — | — | 幂等 |
| `POST /cart/merge` | `guest_id`（服务端固定） | `cart_guest_mappings.is_merged` + `cart:merged:g:{guest_id}` 墓碑 | 永久 / 300 秒 | 返回首次合并结果 |
| `POST /internal/v1/cart/{user_id}/purge` | `order_no` | `cart_purge_records` 唯一索引 | 永久 | 返回首次清理结果 |

TTL 取 10 分钟（短于通用约定中"创建订单 24 小时"）：购物车加购是高频、低风险、用户可立即感知的操作，用户手动重试的意愿强，10 分钟足以覆盖网络重试窗口，同时避免幂等键堆积占用 Redis 内存。

## 4. 内部接口设计

所有内部接口位于 `/internal/` 命名空间，**网关不对外暴露**；调用方必须携带 `X-Internal-Token`，校验失败返回 `COMMON-2002`。统一设置连接超时 1s、读取超时 3s（通用约定 11.1）。

### 4.1 `GET /internal/v1/cart/{user_id}/selected-items` 读取选中项

**调用方**：订单服务（创建订单时，FR-ORD-001）。

**路径参数**：`user_id`（BIGINT）。

**Query 参数**

| 参数 | 类型 | 必填 | 默认 | 说明 |
|---|---|---|---|---|
| `item_ids` | string | 否 | — | 逗号分隔的条目 ID，用于"立即购买"式局部下单。缺省时返回全部选中项 |
| `validate` | boolean | 否 | `true` | 是否在返回前实时校验价格与库存。订单服务下单时**必须传 `true`**（下单前最后一道用户侧提示），除非订单服务将自行完成权威校验 |
| `min_cart_version` | string | 否 | — | 客户端下单时携带的 `cart_version`。若当前 `op_seq` 大于该值，说明购物车在用户确认后被其他端修改过，返回 `stale=true` 提示订单服务重新确认 |

**处理**

1. 读 Redis 购物车（未命中回源 DB）。
2. 取选中项（有效项才参与；失效项一律排除）。
3. `validate=true` 时**强制穿透** catalog-service `POST /internal/v1/skus/batch`（不使用 60 秒缓存），保证下单前的价格与库存是当下最新值。
4. 组装返回；**不修改购物车状态**（只读）。

**关键约定**

- 返回的 `unit_price_cents` 是**实时价**（`validate=true` 时）。订单服务以该值作为订单明细的价格快照，**而不是**购物车的 `snapshot_unit_price_cents`——购物车快照只用于"提示价格变动"，订单快照必须是下单当刻的权威价。
- 库存校验仅作前置提示，**权威校验仍在订单服务 → catalog 的库存预占环节**（概要架构 5.3.1）。购物车不做预占，因此存在"预览通过但预占失败"的窗口，这是有意的分层：购物车校验追求"用户友好"，订单预占追求"不超卖"。
- `stale=true` 时订单服务应重新拉取或提示用户刷新，避免用已变更的购物车内容下单。

**错误码**：`COMMON-2002`、`CART-4001`（购物车不存在/为空）、`CART-7001`、`CART-8002`。

### 4.2 `POST /internal/v1/cart/{user_id}/purge` 下单后清理已购买项

**调用方**：订单服务（下单成功后）。

**为什么是同步接口而非事件**：标准事件目录（通用约定 10.3）中没有购物车相关事件。购物车状态是**用户私有状态**，不具备"一对多广播"的语义；新增事件需同步修改通用约定文档，收益不足以抵消契约扩张成本。因此采用同步调用，并明确其失败语义（见下）。

**请求体**

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `order_no` | string | 是 | 订单号，**幂等键** |
| `item_ids` | array[string] | 是 | 本次下单占用、需要清理的购物车条目 ID，1 ~ 100 个 |
| `purge_mode` | string | 否 | 固定 `BY_ITEM`（按条目清理）。预留 `CLEAR_SELECTED`（清空所有选中项） |

```json
{
  "order_no": "SO20260910000001",
  "item_ids": ["1813456789012345678"],
  "purge_mode": "BY_ITEM"
}
```

**处理**

1. 以 `order_no` 查 `cart_purge_records`，命中则直接返回首次结果（**不重复清理**）。
2. 未命中 → 插入 `cart_purge_records`（`order_no` 唯一索引抢占，冲突则转查询返回）。
3. Lua 内批量 `HDEL` 对应条目，投递 `PURGE_ITEMS` 落库任务。
4. 条目可能已被用户手动删除 → `purged_count` 小于请求数，属正常，不报错。

**响应 200**

```json
{
  "code": "OK",
  "message": "success",
  "data": {
    "order_no": "SO20260910000001",
    "purged_count": 1,
    "not_found_ids": [],
    "cart_item_count": 3,
    "cart_version": "50"
  },
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "timestamp": "2026-09-10T08:30:00.123Z"
}
```

**失败语义（明确取舍）**

订单服务调用本接口失败（超时、网络异常）时，**不得回滚订单**——订单是资金事实，购物车是便利性状态，二者不具有对等重要性。处理策略：

1. 订单服务按只读重试规则最多重试 2 次（该接口以 `order_no` 幂等，重试安全）；
2. 仍失败 → 记录日志与告警，**放弃清理**；
3. 遗留的购物车条目由用户在购物车页手动删除，或在下一次结算预览时被再次校验（若库存已被本次订单占用，会因库存不足被标记失效或截断）。

这个残留是**最终一致**的、可自愈的、且不影响订单与库存正确性，因此可接受。

**错误码**：`COMMON-2002`、`CART-1001`、`CART-4001`、`CART-8002`。

## 5. 事件设计

### 5.1 发布事件

**无。**

购物车变更属于用户私有状态：一次加购只对当前用户有意义，不存在需要广播给其他服务的消费方。通知服务不关心购物车、订单服务通过 `GET /internal/v1/cart/{user_id}/selected-items` 按需拉取而非被动接收。因此本服务**不声明任何 `outbox_events` 表、不接入 RabbitMQ**，也无需承担事务性发件箱的实现成本。

> 这一取舍的代价：订单服务无法通过事件感知购物车变化，只能同步拉取。因为下单是一条必须实时获取结果的同步链路（概要架构 4.3），这个代价为零。

### 5.2 订阅事件

**无。**

**关于"订阅商品变更事件用于失效标记"的取舍说明**

初衷是：商品下架时主动把购物车中的对应条目标记为失效。评估后**不做**，理由如下：

1. **通用约定 10.3 的标准事件目录中没有商品变更事件**（只有 `stock.low`，且其语义是"低库存预警给运营"，不是"SKU 下架"）。按约定"各服务不得擅自更名或改变语义，新增事件需同步更新本文档"，凭空发明 `product.off_shelf` 这类事件会破坏契约基线。
2. **失效是派生状态，不是购物车的事实**。即使收到了下架事件，也需要处理"商品重新上架"的反向场景，届时还要再引入 `product.on_shelf` 事件，事件面会持续膨胀。
3. **实时校验的代价可接受**。购物车页面的访问频率远低于商品列表页，且校验结果按 SKU 维度做 60 秒缓存（`cart:skusnap:*` 全用户共享），一次批量接口可覆盖用户购物车内的全部 SKU。一次 `POST /internal/v1/skus/batch` 即可完成当前用户全车校验。
4. **实时校验永远是正确的**。事件驱动失效存在"事件丢失 → 购物车永远显示失效（或永远显示有效）"的长期不一致风险；实时查询不存在这个问题，因为答案直接来自权威方。

**结论**：失效判定 100% 在**读取时**由商品目录服务的实时数据推导，本服务不存失效状态、不订阅任何事件。详见 6.3。

### 5.3 未来演进

若后续需要"商品下架时主动通知已加购用户"这类主动触达能力，正确做法是：

1. 由商品目录服务新增 `product.off_shelf` / `product.on_shelf` 事件并更新通用约定 10.3 目录；
2. 本服务订阅该事件，但**只用于预热 `cart:skusnap:{sku_id}` 缓存**（写入失效标记并设置较短 TTL），**不落库**、不改变"读取时实时校验"的主路径。

这样事件只是一个缓存优化，事件丢失不影响正确性，保持系统对事件可靠性的低耦合。

## 6. 核心业务流程

### 6.1 加入购物车（FR-CART-001）

**设计要点**：整个"读旧值 → 计算 → 写新值 → 投递落库任务"在**单个 Lua 脚本**内完成。Redis 单线程执行脚本，因此同一用户多端并发加购同一 SKU 不会丢失累加，且不需要分布式锁。

```
def add_to_cart(owner, sku_id, add_quantity, idempotency_key=None):
    # ---- 1. 幂等抢占（脚本之外，避免在 Lua 中做网络判断）----
    if idempotency_key:
        first_time, cached = redis.set_idem(f"cart:idem:{owner.key}:{idempotency_key}", ttl=600)
        if not first_time:
            return cached          # 返回首次结果，不重复加购

    # ---- 2. 查询商品目录，拿到权威的价格/库存/限购 ----
    sku = catalog_client.batch_get([sku_id]).get(sku_id)
    if sku is None:
        raise BizError("CART-5003", 409, "商品不存在或已被删除")
    if sku.status != "ON_SALE":
        raise BizError("CART-5003", 409, "商品已下架，无法加入购物车")
    if sku.available <= 0:
        raise BizError("CART-5003", 409, "商品已售罄，无法加入购物车")

    limit = min(
        sku.available,
        sku.max_purchase_quantity or cfg.CART_MAX_ITEM_QUANTITY,
        cfg.CART_MAX_ITEM_QUANTITY,
    )

    # ---- 3. 原子写入（Lua，见下方脚本逻辑）----
    item_snapshot = {
        "title": sku.title, "spec_name": sku.spec_name,
        "image_url": sku.image_url, "price_cents": sku.price_cents,
        "spu_id": sku.spu_id, "currency": "CNY",
        "snapshot_at": now_iso(),
    }
    result = redis.eval_script(
        ADD_ITEM_LUA,
        keys=[items_key, meta_key, seq_key, SYNC_STREAM],
        args=[item_id_or_empty, sku_id, add_quantity, item_snapshot_json,
              limit, cfg.CART_MAX_ITEMS_PER_CART, ttl, owner_key, now_ms()],
    )
    # result.code:
    #   OK             正常写入
    #   CART_MAX_ITEMS 新 SKU 但条目数已达上限
    #   ADJUSTED       累加后超过上限，已截断至 limit

    # ---- 4. 缓存幂等结果 ----
    if idempotency_key:
        redis.set_idem_result(..., ttl=600, value=response)
    return response
```

**Lua 脚本逻辑（伪代码，实际为 `EVAL` 的 Lua 实现）**

```lua
-- KEYS[1] cart:items:{owner}   KEYS[2] cart:meta:{owner}
-- KEYS[3] cart:seq:{owner}     KEYS[4] cart:sync:stream
-- ARGV[1] item_id(可空，空则由服务端预生成)  ARGV[2] sku_id
-- ARGV[3] add_quantity  ARGV[4] item_snapshot_json  ARGV[5] limit
-- ARGV[6] max_items     ARGV[7] ttl_seconds        ARGV[8] owner_key
-- ARGV[9] now_ms

-- 第 1 步：读取与决策（无副作用）
local item_id = ARGV[1]
local raw     = redis.call('HGET', KEYS[1], item_id)
local decision, new_qty, meta_op

if raw == false then
    -- 新增条目
    if redis.call('HLEN', KEYS[1]) >= tonumber(ARGV[6]) then
        return { 'CART_MAX_ITEMS', 0 }
    end
    new_qty   = math.min(tonumber(ARGV[3]), tonumber(ARGV[5]))
    decision  = (new_qty < tonumber(ARGV[3])) and 'ADJUSTED' or 'OK'
    meta_op   = 'NEW'
else
    local item = cjson.decode(raw)
    local target = item.quantity + tonumber(ARGV[3])
    new_qty  = math.min(target, tonumber(ARGV[5]))
    decision = (new_qty < target) and 'ADJUSTED' or 'OK'
    meta_op  = 'UPDATE'
end

-- 第 2 步：先投递落库任务，再写数据
--   Redis Lua 无回滚能力，此顺序保证最坏情况是「多一条冗余同步消息」（落库幂等可消化），
--   而不是「数据变了但没有同步记录」（会导致数据永久丢失）。
local op_seq = redis.call('INCR', KEYS[3])
local item_json = build_item_json(ARGV[4], new_qty, item_raw_or_default(raw), op_seq, ARGV[9])
redis.call('XADD', KEYS[4], 'MAXLEN', '~', 1000000, '*',
           'owner_key', ARGV[8], 'op_seq', op_seq, 'op_type', 'UPSERT_ITEM',
           'item_id', item_id, 'sku_id', ARGV[2], 'payload', item_json)

-- 第 3 步：写明细
redis.call('HSET', KEYS[1], item_id, item_json)

-- 第 4 步：更新汇总（item_count / selected_count / selected_amount_cents / op_seq）
recompute_meta(KEYS[2], KEYS[1], ARGV[8], op_seq, ARGV[9])

-- 第 5 步：续期 TTL
redis.call('EXPIRE', KEYS[1], ARGV[7])
redis.call('EXPIRE', KEYS[2], ARGV[7])
redis.call('EXPIRE', KEYS[3], ARGV[7])

return { decision, new_qty, op_seq }
```

**上限策略对照**

| 场景 | 行为 | 理由 |
|---|---|---|
| 加购累加后超过上限 | **截断至上限** + 返回 `adjusted=true` 提示 | 用户意图是"加 N 件"，尽量满足；FR-CART 异常流明确要求"限制为最大可售量并提示" |
| 修改数量指定值超过上限 | **报错 `CART-5001`** | 用户明确指定目标值，静默改值会造成"我设了 5 件怎么变成 3 件"的困惑 |
| 新 SKU 且条目数已满 | **报错 `CART-5002`** | 必须让用户先清理，不能静默丢弃 |

### 6.2 修改数量与移除（FR-CART-003、004）

```
def update_quantity(owner, item_id, quantity):
    if quantity < 0 or quantity > cfg.CART_MAX_ITEM_QUANTITY:
        raise BizError("CART-1002", 400, "商品数量必须在 0 到 999 之间")

    if quantity == 0:
        return remove_items(owner, [item_id])          # 0 视为移除

    if not redis.hexists(items_key(owner), item_id):
        raise BizError("CART-4002", 404, "购物车条目不存在")

    sku = catalog_client.batch_get([item.sku_id]).get(item.sku_id)
    limit = min(sku.available, sku.max_purchase_quantity or MAX, cfg.CART_MAX_ITEM_QUANTITY)
    if quantity > limit:
        # 明确指定值超限 → 报错而非截断
        raise BizError("CART-5001", 409,
                       f"该商品最多可购买 {limit} 件",
                       details=[{"field": "quantity", "reason": f"可售库存/限购上限为 {limit}"}])

    return redis.eval_script(UPDATE_QTY_LUA, ...)      # 原子 HEXISTS + HSET + XADD
```

```
def remove_items(owner, item_ids):
    # 单条与批量共用同一路径；批量上限 50（CART-1003）
    return redis.eval_script(BATCH_DELETE_LUA, ...)
    # 脚本内：HEAD 过滤出真实存在的 ID → XADD(DELETE_ITEM, payload=id数组)
    #        → HDEL → 重算 meta → EXPIRE
```

**并发与幂等**：`PUT` 为绝对值覆盖语义，天然幂等；`DELETE` 对不存在的条目返回 204。二者都在 Lua 内原子完成，多端并发执行"设置数量为 3"最终结果一致。

### 6.3 查看购物车：失效标记与价格提示（FR-CART-002、006、008）

```
def get_cart(owner, validate=True, include_invalid=True):
    cart = load_cart(owner)              # Redis 命中直接返回；未命中 → 从 DB 回源重建（见 6.8）
    if not validate:
        return build_view(cart, validity_stale=True, current_price=None)

    sku_ids = [item.sku_id for item in cart.items]
    sku_map, stale = fetch_sku_snapshots(sku_ids)   # 批量 + 60s 缓存，见 7.2

    valid, invalid = [], []
    for item in cart.items:
        sku = sku_map.get(item.sku_id)
        reason = judge_invalid(sku, item)
        if reason is None:
            valid.append(enrich(item, sku))
        else:
            invalid.append(mark_invalid(item, reason))   # 不改 Redis 中的 is_selected

    return build_view(valid, invalid, summary_of(valid), validity_stale=stale)


def judge_invalid(sku, item):
    if sku is None:                       return "SKU_NOT_FOUND"
    if sku.status == "DELETED":           return "SKU_NOT_FOUND"
    if sku.status == "OFF_SHELF":         return "OFF_SHELF"
    if sku.available <= 0:                return "SOLD_OUT"
    if item.quantity > sku.available:     return "SOLD_OUT"        # 库存被他人买走，不再满足
    if sku.max_purchase_quantity and item.quantity > sku.max_purchase_quantity:
        return "PURCHASE_LIMIT_EXCEEDED"
    return None
```

**失效处理的核心决策**

| 决策 | 选择 | 理由 |
|---|---|---|
| 何时标记失效 | **查询时实时推导**，不落库、不定时扫描 | 见 5.2 的取舍分析。定时扫描存在"扫描间隔内失效项仍显示为有效"的窗口，且扫描全量用户的购物车需要遍历所有 Redis key，成本远高于按需校验 |
| 失效项是否自动删除 | **不删除**，置灰展示在"失效商品"分组 | 用户加购是有意图的，静默删除会造成"我的东西怎么没了"的投诉；FR-CART-002 明确要求"含失效商品标记" |
| 失效项的选中状态 | **保留 Redis 中的真实值**，接口层恒返回 `is_selected=false` | 商品重新上架后自动恢复有效并沿用原选中状态，用户无感知 |
| 结算时如何处理 | **自动剔除**（见 6.5），并在预览结果中明示 | FR-CART-006 明确要求"结算时自动剔除" |
| 失效判定失败（catalog 不可用） | **视为有效**，响应标记 `validity_stale=true` | 面向用户的展示不应因下游故障而"误伤"商品；真正的把关在下单环节 |

**性能设计**：`cart:skusnap:{sku_id}` 为**全用户共享**的 SKU 快照缓存（TTL 60 秒），使"每个用户每次打开购物车都调一次 catalog"降为"每个 SKU 每 60 秒最多调一次"，命中率随用户规模提升而提升。购物车条目上限 100，单次批量查询即可覆盖。

### 6.4 游客购物车与合并（FR-CART-007）

**6.4.1 游客标识的生成与传递**

| 环节 | 设计 |
|---|---|
| 生成 | 前端首次访问时生成 UUID v4（122 位随机），写入 `localStorage` 与 Cookie `guest_id`（`SameSite=Lax; Secure; Max-Age=34560000`，约 400 天） |
| 传递 | 每次请求携带请求头 `X-Guest-Id: <uuid>` |
| 服务端校验 | 正则 `^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`（严格 UUID v4），不合法返回 `CART-1004` |
| 网关行为 | 网关**保留** `X-Guest-Id`（它是客户端合法产物），但**必须剥离**外部传入的 `X-User-Id` / `X-User-Roles` / `X-Internal-Token`（通用约定 4.3） |
| 安全边界 | `guest_id` 不可枚举（UUID v4）；游客车内无敏感信息；游客 key 前缀 `g:` 与登录 key 前缀 `u:` 物理隔离，无法通过构造 `guest_id` 读取他人登录态购物车 |

Guest 购物车在 Redis 中使用与登录用户**完全相同的数据结构与脚本**，仅 owner key 前缀不同（`cart:items:g:{guest_id}` vs `cart:items:u:{user_id}`），因此所有增删改查逻辑零分叉。

**6.4.2 合并规则**

```
def merge_guest_cart(user_id, guest_id):
    # 1. guest_id 幂等检查（DB 唯一索引为最终权威）
    mapping = repo.find_guest_mapping(guest_id)
    if mapping and mapping.is_merged:
        return build_merged_response(mapping, already_merged=True)   # 不重复累加

    # 2. 加锁：按字典序加锁，避免与「反向合并」并发时死锁
    with acquire_locks_sorted(f"cart:lock:g:{guest_id}", f"cart:lock:u:{user_id}", ttl_ms=3000):
        user_cart = load_or_create_user_cart(user_id)
        guest_cart = load_guest_cart(guest_id)

        if guest_cart is None or guest_cart.is_empty():
            return finish_merge(guest_cart, user_cart, moved=0, merged=0)

        # 3. 若用户车不存在/为空 → 直接过户（最小代价，无数量冲突）
        if user_cart.is_empty():
            return transfer_ownership(guest_cart, user_id)   # owner_type: GUEST → USER

        # 4. 逐项合并
        sku_ids = [i.sku_id for i in guest_cart.items]
        sku_map, stale = fetch_sku_snapshots(sku_ids, force_refresh=True)
        truncated, dropped = [], []

        for g_item in guest_cart.items:
            u_item = user_cart.find_by_sku(g_item.sku_id)
            sku = sku_map.get(g_item.sku_id)

            limit = min(sku.available if sku else INF,
                        (sku.max_purchase_quantity if sku else None) or MAX,
                        cfg.CART_MAX_ITEM_QUANTITY)

            if u_item is None:
                # 用户车没有该 SKU：整条迁入并受上限约束
                if user_cart.item_count >= cfg.CART_MAX_ITEMS_PER_CART:
                    dropped.append(g_item)          # 条目数已满，丢弃并提示
                    continue
                qty = min(g_item.quantity, limit)
                move_item(g_item, user_id, qty)
                if qty < g_item.quantity:
                    truncated.append((g_item.sku_id, g_item.quantity, qty, "LIMITED_BY_STOCK"))
            else:
                # 同 SKU 冲突：数量相加，受库存与限购上限约束
                target = u_item.quantity + g_item.quantity
                final  = min(target, limit)
                # 选中状态取「或」：任一侧选中则合并后仍选中
                update_user_item(u_item, quantity=final,
                                 is_selected=u_item.is_selected or g_item.is_selected)
                if final < target:
                    truncated.append((g_item.sku_id, target, final, "LIMITED_BY_PURCHASE_LIMIT"))

        # 5. 标记与清理
        repo.mark_guest_merged(guest_id, user_cart.id, user_id)   # DB，事务提交
        redis.set(f"cart:merged:g:{guest_id}", user_id, ex=300)   # 300 秒墓碑，吸收并发重复请求
        redis.delete(items_key_guest, meta_key_guest, seq_key_guest)
        enqueue_sync_task(user_cart, op_type="REPLACE_ALL")

    return build_merged_response(..., truncated=truncated, dropped=dropped)
```

**合并规则汇总**

| 规则项 | 处理 |
|---|---|
| 目标购物车不存在 | 游客车**直接过户**（`owner_type: GUEST → USER`），零冲突路径 |
| 同 SKU 数量冲突 | **数量相加**，结果受 `min(可售库存, 单品限购, 配置上限)` 约束；超限则截断并在 `truncated_items` 中明示 |
| 条目数超过 100 | 按**游客车 `added_at` 升序**尽量迁入，装不下的记入 `dropped_items` 提示用户 |
| 选中状态冲突 | **逻辑或**：任一侧选中则合并后选中（符合"游客勾选后登录结算"的用户预期） |
| 价格快照冲突 | 同 SKU 取 `snapshot_at` **较新**者（服务端逐项比较，不额外回源） |
| 合并后游客车 | Redis 删除 + 写入 300 秒墓碑；DB 中 `carts.status='MERGED'` 与 `cart_guest_mappings` 永久保留 |
| 幂等 | `guest_id` 为幂等键；重复调用返回 `already_merged=true` 与当前状态，**绝不重复累加** |
| 并发 | 对两个 owner key 按字典序加锁（`SET NX PX 3000`），避免"同一容器多端同时登录"造成双重合并 |
| 商品已失效 | 按 6.3 逻辑迁入后仍会被标记失效，不在合并时丢弃（保留用户的加购意图） |
| catalog 不可用 | 合并**不阻塞**：以 `INF` 为上限完成合并（不做截断），后续查看购物车时实时校验会自然修正；标记 `validity_stale=true` |

### 6.5 结算预览：价格与库存实时校验（FR-CART-008、006）

```
def checkout_preview(owner, accept_price_changes=False, item_ids=None):
    cart = load_cart(owner)
    targets = pick_selected(cart, item_ids)      # 未指定则取全部 is_selected=true 的条目
    if not targets:
        raise BizError("CART-5005", 409, "请先选择要结算的商品")

    # 结算校验强制穿透缓存，直查商品目录服务：结算对准确性的要求高于对 QPS 的要求
    sku_map, _ = catalog_client.batch_get([i.sku_id for i in targets], bypass_cache=True)

    valid, invalid, price_changed = [], [], []
    for item in targets:
        sku = sku_map.get(item.sku_id)
        reason = judge_invalid(sku, item)
        if reason:
            invalid.append(build_invalid(item, reason))
            continue
        state = compare_price(item.snapshot_unit_price_cents, sku.price_cents)
        if state != "NORMAL":
            price_changed.append(item.item_id)
        valid.append(build_preview_item(item, sku))

    requires_confirm = len(price_changed) > 0 and not accept_price_changes

    if accept_price_changes and price_changed:
        # 用户已确认接受新价 → 回写快照价，使购物车价格与当前价对齐
        redis.eval_script(ACCEPT_PRICE_LUA, ...)   # 仅更新真正变动过的条目，幂等
        enqueue_sync_task(op_type="UPSERT_ITEM", item_ids=price_changed)

    return {
        "items": valid,
        "invalid_items": invalid,
        "summary": {
            "goods_amount_cents": sum(i.subtotal_current for i in valid),
            "price_changed": len(price_changed) > 0,
            "has_invalid_items": len(invalid) > 0,
            "requires_price_confirmation": requires_confirm,
            "can_checkout": len(valid) > 0 and not requires_confirm,
        },
    }
```

**关键设计决策**

| 决策 | 选择 | 理由 |
|---|---|---|
| 价格变动如何处理 | **返回提示，绝不静默改价** | FR-CART-008 明确"价格变动时提示用户"。静默改价会让用户在下单页看到与购物车页不同的金额，是最典型的电商信任事故 |
| 用户确认后 | 通过 `accept_price_changes=true` **显式回写快照价** | 把"接受新价"变成一次用户可见的动作，写路径清晰、可审计、幂等 |
| 是否使用 60 秒缓存 | **不使用，强制穿透** | 结算是低频动作，准确性优先；查看购物车（高频）使用缓存 |
| 库存不足的条目 | 标记失效并**自动剔除**，不计入金额 | FR-CART-006 |
| 部分失效 | 有效项照常可结算，`can_checkout=true` | 不能因为一件商品售罄就阻断整单结算 |
| 全部失效 | 返回 200 + `can_checkout=false` + 提示 | 用业务状态而非 HTTP 错误表达，前端体验更顺 |
| 与订单的关系 | 购物车校验是**提示层**，权威校验在订单服务的库存预占 | 概要架构 5.3.1 的预占是不可绕过的最终防线，购物车不重复实现并发控制 |

**交接契约**

| 事项 | 约定 |
|---|---|
| 订单取数 | `GET /internal/v1/cart/{user_id}/selected-items?validate=true&min_cart_version={客户端携带的版本}` |
| 价格来源 | 以该接口返回的 **`unit_price_cents`（实时价）** 作为订单明细快照，而非购物车快照价 |

### 6.7 Redis 写入与异步落库（本服务最大设计难点之一）

**6.7.1 权威性定义（必须先说清楚）**

| 角色 | 存储 | 含义 |
|---|---|---|
| **运行时权威** | Redis | 服务的**所有读写都走 Redis**，它反映的是购物车的最新状态。任何时刻读到的购物车内容以 Redis 为准 |
| **持久化权威** | PostgreSQL | Redis 数据的最终归集地。承担三个职责：① Redis 故障/过期后的恢复源；② 跨设备长期可见（FR-CART-009）；③ 运营侧只读查询 |

二者**不追求实时强一致**，而是**有界滞后的最终一致**：正常负载下滞后目标 ≤ 1s（P99 ≤ 5s），滞后量由 `cart:sync:stream` 的 pending 长度直接度量并可告警。

> **与通用约定 9.3 的关系**：通用约定要求"先写数据库，再删除缓存"的 Cache-Aside 失效模式。购物车是本服务**唯一以 Redis 为主存储**的场景（通用约定 9.2 明确给出"购物车 30 天 TTL 并异步落库持久化"），Cache-Aside 在此不适用：购物车不存在"数据库是权威、缓存是副本"的关系，而是"Redis 服务在线流量、DB 服务持久化"。本服务**严格遵循 Cache-Aside 的场景**是 `cart:skusnap:*`（catalog 数据的缓存），该处一律先查权威再回填。

**6.7.2 写路径（三段式）**

```
第 1 段：请求内（同步，Lua 原子）
  ① 校验身份与参数
  ② （必要时）调用 catalog 获取权威数据
  ③ 执行 Lua 脚本：
       XADD cart:sync:stream   ← 先投递落库任务
       HSET cart:items:{owner} ← 再改数据
       HSET cart:meta:{owner}  ← 更新汇总
       EXPIRE 三个 key
     返回给用户

第 2 段：后台消费（异步）
  cart-persist-worker（每个服务实例内置，消费组 cart-persist）
  ① XREADGROUP 批量拉取（默认 200 条 / 500ms）
  ② 按 owner_key 分组，同 owner 内按 op_seq 升序处理
  ③ 单事务内 upsert carts + cart_items + 更新汇总字段
  ④ 成功 → XACK
     失败 → 不 XACK，留在 pending 由 XAUTOCLAIM 回收重试

第 3 段：兜底（异步 + 持久化）
  pending 消息投递次数 > CART_SYNC_MAX_RETRY(5)
  → 写入 cart_sync_logs (status=PENDING, retry_count=n, next_retry_at=退避时间)
  → XACK 原消息（避免阻塞 Stream）
  → 由 cart-sync-retry 定时任务按 next_retry_at 重试
  → 重试 8 次仍失败 → status=DEAD + 告警，人工介入
```

**为什么"先 XADD 再改数据"**：Redis Lua 脚本是原子的，但**出错时不会回滚已执行的写命令**。若顺序颠倒（先 HSET 后 XADD），一旦 XADD 因内存上限等原因失败，就会出现"数据改了但没有同步记录"，这条变更是**永久丢失**的。反过来（先 XADD 后 HSET），最坏情况是"多了一条冗余同步消息"，落库是幂等 upsert（`excluded.version > cart_items.version` 条件 + `uk_cart_items_cart_id_sku_id` 冲突键），可以安全消化。**把可能的错误偏向"重复"而非"丢失"**，是本服务写路径的核心原则。

**6.7.3 落库 SQL（幂等 + last-write-wins）**

```sql
-- 购物车主表：确保存在并推进版本号
INSERT INTO carts (id, owner_type, user_id, guest_id, status, currency, op_seq,
                   last_active_at, created_at, updated_at)
VALUES (:cart_id, :owner_type, :user_id, :guest_id, 'ACTIVE', 'CNY', :op_seq,
        :updated_at, now(), now())
ON CONFLICT (id) DO UPDATE
SET item_count            = EXCLUDED.item_count,
    selected_item_count   = EXCLUDED.selected_item_count,
    selected_amount_cents = EXCLUDED.selected_amount_cents,
    op_seq                = EXCLUDED.op_seq,
    last_active_at        = GREATEST(carts.last_active_at, EXCLUDED.last_active_at),
    updated_at            = now();

-- 明细 upsert：version 更大才覆盖，天然消解乱序消费与重复消费
INSERT INTO cart_items (id, cart_id, sku_id, quantity, is_selected,
                        snapshot_title, snapshot_spec_name, snapshot_image_url,
                        snapshot_unit_price_cents, snapshot_at, currency, version,

ON CONFLICT (cart_id, sku_id) DO UPDATE

    is_selected               = EXCLUDED.is_selected,
    snapshot_title            = EXCLUDED.snapshot_title,
    snapshot_spec_name        = EXCLUDED.snapshot_spec_name,
    snapshot_image_url        = EXCLUDED.snapshot_image_url,
    snapshot_unit_price_cents = EXCLUDED.snapshot_unit_price_cents,
    snapshot_at               = EXCLUDED.snapshot_at,

-- 条目删除（物理删除：购物车条目无追溯价值）
DELETE FROM cart_items WHERE cart_id = :cart_id AND id = ANY(:item_ids);
```

**6.7.4 落库失败的兜底层级**

| 层级 | 机制 | 覆盖的故障 |
|---|---|---|
| L1 | Lua 内 XADD 与数据写入同脚本原子执行 | 进程崩溃导致"数据变了但没投递任务" |
| L2 | Redis Stream + 消费组 + `XACK` 成功后移出 pending | worker 崩溃、消费中途异常 |
| L3 | `XAUTOCLAIM` 回收 pending 超过 60 秒的消息 | worker 长时间宕机、消息被遗忘 |
| L4 | 投递次数超限写入 `cart_sync_logs`（持久化） | Redis Stream 被裁剪（MAXLEN 溢出）前的抢救 |
| L5 | `cart-sync-retry` 定时任务按退避重试，最终 DEAD + 告警 | DB 长时间不可用、数据约束冲突 |
| L6 | `cart-reconcile` 每日对账，比对 Redis 与 DB 差异并修复（见 6.8） | 以上全部失效的极端情况 |

**6.7.5 降级为同步落库（重要兜底）**

当满足以下任一条件时，服务自动切换为**同步落库模式**（`CART_SYNC_MODE=auto` 时的自动行为）：

- `XLEN cart:sync:stream` 超过 `CART_SYNC_LAG_THRESHOLD`（默认 100000）；
- 消费组 pending 数量超过 `CART_SYNC_PENDING_THRESHOLD`（默认 5000）且持续 1 分钟；
- 落库 worker 心跳丢失超过 30 秒。

同步落库模式下，写请求在返回前**额外同步执行一次 DB 落库**（仍然写 Redis，Redis 仍是读路径的权威）。代价是写延迟从 P99 < 20ms 升至 P99 < 80ms、DB 写入压力上升，但**数据不再有丢失窗口**。切换与恢复均记录 ERROR 级日志并触发告警，切换状态通过 `/ready` 端点暴露。

### 6.8 Redis 数据恢复（本服务最大设计难点之二）

**核心洞察：Redis 的数据"消失"有三类，它们的恢复路径是同一条。**

| 类型 | 触发场景 | 频率 | 数据是否真的丢失 |
|---|---|---|---|
| A. TTL 自然过期 | 用户 30 天未访问购物车 | 常态，天天发生 | 否——DB 中有完整数据 |
| B. Redis 实例故障/重启 | 进程崩溃、主从切换、扩容重建 | 偶发 | 否（有 AOF 时），AOF 关闭时可能丢 ≤ 1 秒 |
| C. 误操作/全新实例 | `FLUSHALL`、配置错误连到空实例 | 极少 | Redis 侧全部丢失，但 DB 完整 |

因此"恢复路径"不需要为三类分别设计：**统一走"惰性回源"**。A 类天天发生，意味着这条路径**每天都被真实流量验证**，风险远低于一条"只在灾难时启用"的冷路径。这是本设计最重要的健壮性保证。

**6.8.1 惰性回源（A / B / C 共用路径）**

```
def load_cart(owner):
    meta = redis.hgetall(meta_key(owner))
    if meta and redis.exists(items_key(owner)):
        return build_cart_from_redis(meta, redis.hgetall(items_key(owner)))   # 快路径

    # ---- 慢路径：从 PostgreSQL 回源重建 ----
    with acquire_lock(f"cart:lock:rebuild:{owner.key}", ttl_ms=5000):
        # 双检，避免并发重建
        if redis.exists(items_key(owner)):
            return build_cart_from_redis(...)

        rows = repo.list_items_with_cart(owner)      # 单次 JOIN 查询，同一库内
        if not rows:
            return None

        pipe = redis.pipeline(transaction=False)
        items = {str(r.id): serialize_item(r) for r in rows}
        pipe.hset(items_key(owner), mapping=items)               # 一次性 HSET 全量
        pipe.hset(meta_key(owner), mapping=build_meta(rows))     # 含 op_seq = carts.op_seq
        pipe.set(seq_key(owner), rows[0].cart_op_seq, ex=ttl)    # 序号从 DB 值续接
        pipe.expire(items_key(owner), ttl)
        pipe.expire(meta_key(owner), ttl)
        pipe.execute()

        log.info("cart rebuilt from postgres", extra={"owner_key": owner.key, "items": len(rows)})
        return build_cart_from_redis(...)
```

**关键点**：重建时 `cart:seq:{owner}` 从 `carts.op_seq` **续接**，而不是从 0 开始。这样重建后新产生的 `op_seq` 仍然单调大于 DB 中的值，6.8.2 的权威性判定规则继续成立。

**6.8.2 权威性判定规则（op_seq 比较）**

正常运行时 Redis 领先于 DB（落库异步滞后）；Redis 被重建后 Redis 与 DB 相等。因此可以定义一条统一规则：

```
权威方向判定：
   redis_op_seq >= db_op_seq  →  Redis 权威（正常态），差异数据由落库任务补偿
   redis_op_seq <  db_op_seq  →  DB 权威（Redis 是陈旧副本），以 DB 覆盖 Redis 重建
```

`redis_op_seq` 取自 `cart:meta:{owner}` 的 `op_seq` 字段，`db_op_seq` 取自 `carts.op_seq`。由于 Redis 的 `op_seq` 只在重建时从 DB 续接、之后只增不减，**这个比较在数学上永远不会退化**（不会出现两侧交替领先导致反复翻转）。

**6.8.3 有界丢失窗口（诚实说明）**

必须承认：在 **C 类故障**（Redis 数据全部丢失且不可恢复）中，存在一个真实的数据丢失窗口：

```
窗口 = Redis 中已写入但尚未落库的变更
     ≈ cart:sync:stream 中 pending 的消息所对应的变更
```

压缩手段：

| 手段 | 效果 |
|---|---|
| 消费组批量消费 + 并发处理（按 owner_key 哈希到 8 个并发槽） | 正常负载下单条消息端到端落库 < 1s |
| Stream lag 与 pending 长度实时监控 + 阈值告警 | 窗口变大时可被立即发现 |
| 降级为同步落库（6.7.5） | 窗口直接归零，代价是写延迟与 DB 压力上升 |
| Redis AOF `appendfsync everysec` + Sentinel 主从 | 实例级故障的窗口压缩到 ≤ 1 秒 |

**业务层面的取舍结论**：购物车是**非资金数据**——它不占用库存、不产生订单、不涉及金额结算。丢失"用户最近几秒加的几件商品"的最坏后果是用户重新加一次，**不产生任何资损或超卖**。因此本服务**有意不做**"购物车写操作同步双写 DB"这种为换取强持久性而牺牲全部写性能的设计。这是一个显式的、被记录的取舍，而非疏漏。

若未来业务要求购物车达到与订单同级的持久性，改造路径是明确的：开启 6.7.5 的同步落库模式并常驻启用。

**6.8.4 每日对账（兜底校验）**

`cart-reconcile` 任务（见第 8 章）抽样比对 Redis 与 DB：

1. 按 `carts.last_active_at` 取最近 7 天活跃的购物车（默认抽样 5000 个，全量可配置）；
2. 逐车比较 `redis_op_seq` 与 `db_op_seq`：
   - `redis > db`：正常滞后，跳过（除非差值 > `CART_RECONCILE_LAG_ALERT`，说明落库严重滞后，告警）；
   - `redis == db`：逐条比对明细（`sku_id` / `quantity` / `is_selected` / `version`），不一致则以 **Redis 为准**修复 DB（Redis 是运行时权威）；
   - `redis < db`：Redis 是陈旧副本（应为重建后的边界情况，正常不应出现），以 **DB 为准**覆盖 Redis，并告警；
3. 差异统计写入日志与指标，超过阈值触发告警。

### 6.9 并发场景处理

| 场景 | 处理方式 | 保证 |
|---|---|---|
| 同一用户多端同时加购同一 SKU | Lua 脚本内 `HGET` → 计算 → `HSET`，Redis 单线程执行，天然原子 | 数量**不丢失**，最终为两次加购之和（受上限约束） |
| 同一用户多端同时改同一 SKU 数量 | 绝对值覆盖语义，后写者胜（按 Lua 实际执行顺序） | 最终值为最后一次操作的值，语义明确 |
| 同一用户同时"查看"与"加购" | 读不加锁，写走原子脚本。读可能读到加购前或加购后的状态 | 弱一致读，可接受（用户刷新即可） |
| 同一游客在多端同时发起合并 | 对 `cart:lock:g:{guest_id}` + `cart:lock:u:{user_id}` 按字典序加锁；DB 侧 `is_merged` 唯一权威 | **不重复累加**。并发第二个请求拿到锁后读到 `is_merged=true`，返回首次结果 |
| 合并与加购并发 | 合并持有 owner 锁；同一 owner 的加购走 Lua 但不检查锁 | 加购可能落在被删除的游客车 key 上（重新创建一个空车）。极端情况下这条加购会丢失，但概率极低且用户可感知后重试。**不做强保证**，因为合并是用户主动触发的显式动作，不会与自身加购并发 |
| 下单清理与用户改数量并发 | `purge` 在 Lua 内 `HDEL`；并发 `PUT` 若先执行则条目被删除（`purged_count` 少 1），若后执行则条目已不存在返回 `CART-4002` | 无脏数据。订单已按购物车当时的状态生成，购物车的后续变化不影响订单 |
| 购物车内同 SKU 被并发加入导致重复条目 | `cart:items` 为 Hash，field 为 `item_id`。若两端都判定"不存在"并各自生成新 item_id，会产生两条同 SKU 条目 | **落到 DB 时由 `uk_cart_items_cart_id_sku_id` 唯一索引拦截**：第二条 upsert 会命中冲突转为 UPDATE 而非 INSERT。Redis 侧则在 `cart:reconcile` 与下次读取时按 `sku_id` 去重（保留 `added_at` 较早者，数量取两者之和并受上限约束），修复 Redis |
| 分布式锁不可用 | 锁仅用于"重建"与"合并"，不加锁的操作（增删改查）全部依赖 Lua 原子性 | 锁故障不影响主流程可用性 |

**去重修复伪代码（合并重复 SKU 条目）**

```
def dedupe_by_sku(owner):
    items = redis.hgetall(items_key(owner))
    grouped = group_by(items, key=lambda i: i.sku_id)
    for sku_id, group in grouped.items():
        if len(group) == 1:
            continue
        keep = min(group, key=lambda i: i.added_at)          # 保留最早加入的条目
        total = sum(i.quantity for i in group)
        limit = min(catalog.available(sku_id), catalog.max_purchase(sku_id) or MAX, MAX)
        redis.eval_script(MERGE_DUP_LUA, keep.item_id, [i.item_id for i in group],
                          quantity=min(total, limit))
    # 该修复在 GET /api/v1/cart 的读路径上顺带触发，代价 O(n log n)，n ≤ 100
```

### 7.2 数据结构选型（为什么是 Hash，而不是 Hash + Sorted Set）

**决策：明细使用单个 Hash，不引入 Sorted Set；排序在应用层完成。**

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **单 Hash（选定）** | 一次 `HGETALL` 拿到全部条目与顺序所需字段；单一数据源，无跨结构一致性问题；Lua 脚本简单（一个 key 的读写） | 排序需应用层完成（O(n log n)） | **采纳** |
| Hash + Sorted Set | 服务端有序，`ZRANGE` 可做分页与截断 | 需要在 Lua 内同时维护两个结构，任何一处失败都会造成结构漂移（成员在 ZSet 但不在 Hash，或反之），需要额外的自愈逻辑；购物车条目上限 100，`HGETALL` 的开销完全可接受 | 不采纳 |
| 单 Hash + 独立 Key 存排序数组 | 排序 O(1) 读取 | 维护成本同 ZSet，且数组与 Hash 的一致性更难保证 | 不采纳 |

**关键量化依据**：`CART_MAX_ITEMS_PER_CART = 100`，单次 `HGETALL` 返回的 volume 约 16KB，Redis 处理耗时 < 1ms。当 n 小到可以一次性全量取出时，有序结构的价值仅剩"服务端分页"，而购物车页面**从不分页**（用户要看全部）。

**演进路径**：若将来把条目上限提升到千级（例如支持 B 端批量采购车），则引入 `cart:zorder:{owner}` Sorted Set（`score = added_at_ms`，`member = item_id`），并在同一个 Lua 脚本内做双写 + 幂等自愈（以 Hash 为准，ZSet 缺失的成员在读取时补建）。届时需要评估的正是这里列出的"结构漂移"成本。

**选中状态为什么不单独用 Set**

候选方案是 `cart:selected:{owner}` SET（`SMEMBERS` 直接得到选中项，全选 O(1)）。未采纳，原因是：**引入第二处状态就引入了不一致的可能**，而收益仅仅是节省一次 `HGETALL`（在 100 条上限下可忽略）。全选场景在单 Hash 方案下退化为"遍历 Hash 更新 `sel` 字段"，在 Lua 内一次完成，耗时同样在 1ms 量级。**优先选择单一数据源**，是本服务在数据结构选型上的一贯原则。

**商品快照为什么不单独建缓存 Key**

候选方案是 `cart:itemsnap:{item_id}` 存放商品快照。未采纳：快照的生命周期**严格等同于条目生命周期**（条目删除，快照即无意义），拆开后需要管理两套 TTL 并保证"条目活着而快照过期"时不出现空窗，复杂度上升而内存节省为零。因此快照**内嵌在条目 JSON 中**。

### 7.3 读路径与缓存命中

| 读取场景 | 路径 | 期望 |
|---|---|---|
| `GET /api/v1/cart` | `cart:items` + `cart:meta`（HGETALL × 2） + `cart:skusnap:*`（批量 HGETALL） | 命中率 > 99%（30 天 TTL 且每次写续期） |
| `GET /api/v1/cart/count` | `cart:meta`（HMGET ic/iq/sc） | 命中率 > 99%，单次 RTT |
| `POST /api/v1/cart/checkout-preview` | 读 Redis + **穿透** catalog（不使用 `cart:skusnap`） | 无缓存依赖，保证准确 |
| `GET /internal/.../selected-items` | 读 Redis + **穿透** catalog（`validate=true` 时） | 同上 |
| `cart:skusnap:*` | 批量读 → 未命中批量回源 → 回填 | 稳态命中率随用户规模上升，60 秒窗口 |

**缓存穿透防护**：`cart:skusnap:{sku_id}` 对"不存在的 SKU"同样写入（`status=DELETED`），TTL 缩短为 60 秒，避免不存在的 SKU 反复打穿到 catalog（通用约定 9.3）。

**缓存击穿防护**：SKU 快照缓存过期时可能被大量用户同时读。采用**逻辑过期 + 单飞回源**：读到的快照若 `fetched_at` 超过 60 秒，先返回旧值（标记 `validity_stale=true`），同时异步触发一次回源刷新，同一 SKU 的刷新请求由 `SET NX` 互斥，只有一个请求真正调用 catalog。热销 SKU 的过期不会造成 catalog 流量尖峰。

### 7.4 `cart:sync:stream` 设计

| 项 | 取值 | 说明 |
|---|---|---|
| Key | `cart:sync:stream` | 全局单一 Stream（非按用户分片） |
| 消息字段 | `owner_key` / `op_seq` / `op_type` / `item_id` / `sku_id` / `payload` | `payload` 为条目 JSON 或条目 ID 数组，使重试时**无需回查 Redis** |
| 生产 | Lua 脚本内 `XADD`（与数据变更同一原子操作） | 见 6.7.2 |
| 消费组 | `cart-persist` | 每个服务实例为一个 consumer（实例名） |
| 批量 | `COUNT 200` + `BLOCK 500ms` | 批量落库摊薄 DB 开销 |
| 并发 | 按 `owner_key` 哈希到 8 个并发槽，**同 owner 内串行** | 保证同车的 `op_seq` 顺序处理 |
| 上限 | `MAXLEN ~ 1000000` | 约 7 天量。`~` 近似裁剪，性能优于精确裁剪 |
| ACK | 落库成功后才 `XACK` | 失败留 pending，由 `XAUTOCLAIM`（60 秒空闲）回收 |
| 监控 | `XLEN` 与 `XINFO GROUPS` 的 pending 长度 | 超阈值告警 + 触发同步落库降级 |

### 7.5 缓存失效时机

| Key | 失效触发 | 方式 |
|---|---|---|
| `cart:items:*` / `cart:meta:*` / `cart:seq:*` | 任何写操作 | **续期**（`EXPIRE 30d`），不失效。30 天不活跃则自然过期，DB 仍是恢复源 |
| 同上 | 合并完成后删除游客侧 | `DEL`（原子删除 #2 #4 #6） |
| 同上 | 用户主动清空购物车 | `DEL` 明细与汇总，保留 `cart:seq`（序号需保持单调） |
| `cart:skusnap:{sku_id}` | 超过 60 秒 | 自然过期。**不使用主动失效**——本服务不订阅商品变更事件（见 5.2），60 秒是"准确性 vs 下游压力"的折中 |
| `cart:skusnap:{sku_id}` | 结算预览时的最高要求 | 预览接口**穿透**（`bypass_cache=True`），不依赖该缓存 |
| `cart:merged:g:*` | 300 秒 | 自然过期，仅需覆盖并发重复合并的窗口 |
| `cart:idem:*` | 600 秒 | 自然过期 |
| `cart:rate:*` | 60 秒 | 滑动窗口计数 |
| `cart:lock:*` | 3 秒或显式释放 | 短锁 + TTL 兜底，避免持锁进程崩溃导致死锁 |

## 8. 定时任务

所有任务通过分布式调度（每个任务在执行前用 `SET NX` 抢占 `cart:job:{task_name}:{period}` 锁，TTL = 任务周期）保证**多实例部署时只有一个实例执行**。

| # | 任务名 | 周期 | 职责 | 幂等要求 |
|---|---|---|---|---|
| 1 | `cart-sync-retry` | 每 2 分钟 | 扫描 `cart_sync_logs` 中 `status IN ('PENDING','FAILED')` 且 `next_retry_at <= now()` 的记录，按指数退避（1m/2m/5m/15m/1h/3h/6h/12h）重试落库；连续失败 8 次转 `DEAD` 并告警 | **必须幂等**：落库为 upsert + `version` 条件更新；`uk_cart_sync_logs_owner_key_op_seq` 唯一索引拦截重复投递；`op_seq` 单调保证同一记录多次重试结果一致 |
| 2 | `cart-reconcile` | 每日 04:00（低峰） | 抽样比对 Redis 与 PostgreSQL（见 6.8.4）：按 `op_seq` 判定权威方向；`redis == db` 时逐条比对明细并修复 DB 差异；统计差异数量、落库滞后分布并输出指标与告警 | **幂等**：只做"以权威方覆盖落后方"的收敛操作；修复动作本身可重复执行且结果不变。样本按 `last_active_at` 稳定抽样，不使用随机数以免重复修复同一批车 |
| 3 | `cart-guest-cleanup` | 每日 03:00（低峰） | 清理 `cart_guest_mappings` 中 `is_merged=false` 且 `last_seen_at` 早于 `CART_GUEST_IDLE_DAYS`（默认 90）天的记录：DB 侧置 `carts.status='EXPIRED'` 并删除明细，Redis 侧删除游客车 key（若已自然过期则跳过） | **幂等**：以 `last_seen_at` 为界，清理后记录不再满足条件；Redis `DEL` 天然幂等 |
| 4 | `cart-purge-record-cleanup` | 每月 1 日 05:00 | 删除 `cart_purge_records` 中 `created_at` 早于 180 天的记录，控制表体积 | **幂等**：按时间范围物理删除，重复执行结果一致。保留 180 天足以覆盖订单侧的任何对账回溯需求 |
| 5 | `cart-metrics-report` | 每 1 分钟 | 采集并上报：`cart:sync:stream` 的 XLEN 与 pending 长度、落库成功率、`cart:skusnap` 命中率、购物车平均条目数、失效项占比、合并成功率、当前落库模式（async/sync） | **只读**，无幂等要求 |
| 6 | `cart-ttl-refresh` | 每日 02:00 | 对 `last_active_at` 在最近 7 天内的购物车，将其 Redis key 的 TTL 重置为 30 天 | **幂等**：`EXPIRE` 重复执行结果一致。**注意**：该任务只覆盖"DB 显示近期活跃但 Redis 即将过期"的边界情况（如落库时间与 Redis 写入时间错位），不是主路径——主路径是每次写操作在 Lua 内续期 |

**任务与 `cart-persist-worker` 的区别**：`cart-persist-worker` 是**常驻消费者进程**（随服务实例启动，不属于定时任务，见 6.7.2），上表 1~6 才是定时任务。

## 9. 错误码表

前缀 `CART`，号段遵循通用约定 3.2。所有错误码的 `message` 均为可直接展示给用户的中文文案。

| 错误码 | HTTP | 含义 | 触发场景 | message 示例 |
|---|---|---|---|---|
| `CART-1001` | 400 | 请求参数校验失败 | 请求体字段缺失、类型错误、`select_all` 与 `item_ids` 同时缺失 | 请求参数有误，请检查后重试 |
| `CART-1002` | 400 | 商品数量取值非法 | `quantity` 不在 `0~999` 整数范围 | 商品数量必须在 0 到 999 之间 |
| `CART-1003` | 400 | 批量操作条目数超过上限 | `batch-delete` 的 `item_ids` 超过 50 个 | 单次最多操作 50 个商品 |
| `CART-1004` | 400 | 游客标识格式非法 | `X-Guest-Id` 不是合法的 UUID v4 | 客户端标识无效，请刷新页面后重试 |
| `CART-2001` | 401 | 缺少身份标识 | 既无 `X-User-Id` 也无 `X-Guest-Id` | 请先登录后再操作购物车 |
| `CART-3001` | 403 | 无权操作该购物车 | 内部接口传入了与内部令牌不匹配的 user_id 范围 | 无权执行该操作 |
| `CART-4001` | 404 | 购物车不存在或为空 | 访问不存在的 `user_id` 的购物车 | 购物车不存在 |

| `CART-6001` | 429 | 购物车操作过于频繁 | 单 owner 加购频率超过 `CART_RATE_LIMIT_PER_MINUTE` | 操作过于频繁，请稍后重试 |

| `CART-7001` | 502 | 依赖服务暂不可用 | 调用 catalog `/internal/v1/skus/batch` 超时、熔断或返回 5xx | 商品信息暂时无法获取，请稍后重试 |
| `CART-8001` | 500 | 购物车数据同步失败 | 同步落库模式下 DB 写入失败 | 保存购物车失败，请稍后重试 |
| `CART-8002` | 500 | 服务内部错误 | 未捕获异常、Redis 不可用 | 服务暂时不可用，请稍后重试 |

**通用错误码的使用**（由本服务直接返回，不重复定义）：

| 错误码 | 场景 |
|---|---|
| `COMMON-1001` | Pydantic 模型校验失败（在 `CART-1001` 之前由框架抛出，统一映射） |
| `COMMON-1002` | 请求体不是合法 JSON |
| `COMMON-2001` | 网关判定为需登录接口但未携带令牌（购物车接口本身允许游客，此码用于 `POST /cart/merge`） |
| `COMMON-2002` | 内部接口 `X-Internal-Token` 校验失败；访问令牌无效，由网关返回 |
| `COMMON-3001` | 越权访问内部接口的他人购物车 |
| `COMMON-6001` | 网关层限流命中（服务层限流为 `CART-6001`） |
| `COMMON-7001` | 保留（本服务使用 `CART-7001` 以携带更明确的语义） |
| `COMMON-8001` | 未捕获异常的兜底（本服务使用 `CART-8002`） |

**错误码与 HTTP 状态的映射实现**：统一在 `app/core/exceptions.py` 中定义 `CartError(code, http_status, message, details)`，由全局异常处理器转换为通用约定 2.2 的失败响应结构，禁止在业务代码中直接返回 HTTP 状态码。

## 10. 安全与权限

### 10.1 鉴权要求

| 接口组 | 鉴权方式 | 说明 |
|---|---|---|
| `/api/v1/cart/*`（除 `merge`） | 登录用户（`X-User-Id`）或游客（`X-Guest-Id`） | 二者至少其一，否则 `CART-2001` |
| `POST /api/v1/cart/merge` | **必须登录** | 未登录由网关返回 `COMMON-2001` |
| `/internal/v1/cart/*` | `X-Internal-Token` | 校验失败 `COMMON-2002`；已验证 `/internal/` 前缀不被网关对外暴露 |

**服务端不解析 JWT**：本服务只信任网关注入的 `X-User-Id`，不自行验签（通用约定 4.3）。网关必须剥离外部伪造的 `X-User-Id` / `X-User-Roles` / `X-Internal-Token`。

### 10.2 数据归属校验（NFR-SE-006）

**核心原则：所有查询与写入都在"属于当前 owner 的 Redis Key 内"完成，服务端从不跨用户查找。**

| 校验点 | 实现 |
|---|---|
| 购物车定位 | `userId` 只取自 `X-User-Id`；**任何请求参数或请求体中的 `user_id` 一律忽略**（内部接口除外，其 user_id 来自路径且由内部令牌保护） |
| 条目归属 | 所有 `item_id` 操作在 Lua 内先 `HEXISTS cart:items:{当前 owner 的 key} item_id`；不存在即返回 `CART-4002`（404） |
| 为什么用 404 而非 403 | 通用约定 4.4 要求"越权访问他人资源返回 403，避免暴露资源是否存在"。本服务的实现方式是**从根本上不进行跨用户查询**：条目不在当前 owner 的 Hash 中，对本用户而言就是"不存在"，因此返回 404 在语义上与"不暴露他人资源存在性"一致。由于 `item_id` 是雪花 ID（不可枚举、不可预测），攻击者无法通过枚举区分"不存在"与"他人的"。该处理方式记录在此，供安全评审确认 |
| 内部接口 | `GET /internal/v1/cart/{user_id}/selected-items` 与 `POST .../purge` 接受路径中的 `user_id`，由 `X-Internal-Token` 保证调用方是可信服务；网关不暴露该命名空间 |
| 游客越权 | `guest_id` 为 UUID v4（122 位随机），不可枚举；游客车 key 前缀 `g:` 与登录车 `u:` 隔离，无法通过构造 `guest_id` 访问登录态购物车 |

### 10.3 输入校验

| 输入 | 校验 |
|---|---|
| `X-Guest-Id` | 严格 UUID v4 正则（版本位 `4`、变体位 `[89ab]`），不合法 `CART-1004`。防止用超长字符串或特殊字符污染 Redis Key |
| `sku_id` / `item_id` | 字符串形式正整数，≤ 20 位，`int()` 解析失败即 `CART-1001`。防 Redis Key 注入（严禁把原始字符串直接拼进 Key，必须先解析为整数再拼接） |
| `quantity` | 整数范围校验 `0~999` |
| `item_ids` | 数组长度 ≤ 50（批量删除）/ ≤ 100（选中），元素数量级校验 |
| `page` / `page_size` | `page ≥ 1`，`1 ≤ page_size ≤ 100` |
| 所有 SQL | 通过 SQLAlchemy 参数化查询，禁止字符串拼接（防注入） |
| 商品标题回显 | 服务端**不做任何 HTML 渲染或转义**，原样返回 JSON；XSS 防护由前端渲染层负责（React 默认转义）。服务端在写入快照时对 `title` / `spec_name` 做长度截断（256 字符），防超长内容撑爆 Redis |

### 10.4 频率限制

| 接口 | 限制 | 实现 |
|---|---|---|
| `POST /api/v1/cart/items` | 单 owner 每分钟 60 次 | `cart:rate:{owner_key}:{分钟窗口}` `INCR` + `EXPIRE 60`，超限 `CART-6001` |
| `POST /api/v1/cart/items/batch-delete` | 单 owner 每分钟 20 次 | 同上 |
| `POST /api/v1/cart/merge` | 单 user 每分钟 5 次 | 同上 |
| 其他读接口 | 由网关按用户/IP 维度限流 | 网关令牌桶 |

服务层限流是网关限流的**补充**（网关限流按"账号 + 接口"粒度，服务层限流可覆盖"购物车操作频次"这类业务语义），两者不冲突。

### 10.5 日志脱敏

购物车数据本身不含支付敏感信息、密码、收货地址。脱敏要求：

| 字段 | 处理 |
|---|---|
| `X-Internal-Token` | **完全不记录** |
| `X-User-Id` / `user_id` | 可记录（用于排障），属于内部标识 |
| `guest_id` | 记录时保留前 8 位 + 后 4 位，中间掩码（避免日志泄露可用于冒充游客的完整标识） |
| `X-Guest-Id` 请求头 | 同 `guest_id` 处理 |
| 商品标题 / 规格 | 可记录（非敏感），但批量日志中截断至 64 字符 |
| 请求体 | 购物车请求体不含敏感字段，可全量记录；但统一使用结构化日志的 `extra` 字段，不拼接字符串 |

### 10.6 其他安全措施

| 项 | 措施 |
|---|---|
| 内部接口暴露 | `/internal/` 前缀在网关路由层**无对应规则**，外部请求 404 |
| 越权横向移动 | 本服务无管理员角色接口，不涉及后台权限 |
| 服务间通信 | 携带 `X-Internal-Token`；内网 mTLS（平台层能力） |
| 依赖调用 | 对 catalog 的调用设置连接 1s / 读取 3s 超时 + 熔断 30 秒，防止下游慢导致本服务线程池耗尽（雪崩） |
| 反序列化 | `cart:items` 的 JSON value 反序列化时捕获异常，单条损坏则跳过该条并记 ERROR 日志（不因单条脏数据导致整个购物车不可用） |

| `CART_IDEMPOTENCY_TTL_SECONDS` | int | `600` | 幂等键 TTL |

**配置来源优先级**：环境变量 > Consul KV（`cart/{env}/...`）> 代码默认值（通用约定 13）。

**关键配置的风险提示**：

- `CART_SYNC_MODE` 生产默认 `auto`。若误设为 `sync`，写延迟上升约 4 倍，需评估 DB 连接池容量（建议 `sync` 模式下 `DB_POOL_SIZE` ≥ 20）。
- `CART_SKU_SNAPSHOT_TTL_SECONDS` 调大（如 300 秒）会显著降低 catalog 压力，但用户看到的"库存不足"提示会滞后最多 300 秒；上线初期建议保持 60 秒。

| `batch-delete` 含不存在的 ID | `not_found_ids` 正确，Stream 只投递实际删除的 ID |
| `select_all=true` 且含失效项 | 失效项 `sel` **未被修改**，返回 `skipped_invalid_ids` |
| `meta` 汇总字段原子性 | 任意单条操作后，`ic` / `iq` / `sc` / `sq` / `sa` 与明细重算结果**完全一致** |
| 脚本执行前 XADD 后 HSET 的顺序 | 通过注入 `XADD` 失败（mock）验证：失败时数据**未被修改**（验证"错误偏向重复而非丢失"） |

**12.2.3 Redis 恢复与数据一致性（本服务最关键的一组）**

| 用例 | 方法 | 预期 |
|---|---|---|
| TTL 过期后回源（类型 A） | 手动 `DEL` 购物车 key 后 `GET /cart` | 从 DB 重建，内容与删除前一致，`cart:seq` 从 DB `op_seq` 续接而非从 0 |
| Redis 实例重启（类型 B） | 重启 Redis 容器后 `GET /cart` | 从 DB 自动重建，用户无感知 |
| 全库清空（类型 C） | `FLUSHALL` 后连续操作 | 各用户按需重建；重建后 `op_seq` 单调，后续落库正常 |
| 重建后序号不倒退 | 重建后加购，检查 DB `op_seq` | 新 `op_seq` > DB 原值，`redis_op_seq >= db_op_seq` 成立 |
| 落库 worker 停掉后写入 | 停 worker → 加购 100 次 → 启动 worker | 100 条变更全部落库，DB 与 Redis 一致 |
| 落库失败重试 | 注入 DB 写入异常 3 次后恢复 | `cart_sync_logs` 出现 PENDING 记录，重试后转 DONE，数据最终一致 |
| 落库持续失败转 DEAD | 持续注入异常 | 达到重试上限后转 DEAD 并告警，**不无限重试** |
| 降级为同步落库 | 向 Stream 灌入超过阈值的消息 | 服务自动切换 `CART_SYNC_MODE=sync`，告警触发，写请求延迟上升但数据零丢失 |
| 每日对账修复差异 | 手动构造 Redis 与 DB 不一致（`redis > db`） | 对账任务以 Redis 为准修复 DB；构造 `redis < db` 则反向修复并告警 |
| 重复消费 | 对同一 `op_seq` 的消息重复投递 | DB 结果不变（`version` 条件 + 唯一索引） |
| 乱序消费 | 故意乱序投递 `op_seq` 1 和 2 | 最终 DB 为 `op_seq=2` 的状态（`version` last-write-wins） |

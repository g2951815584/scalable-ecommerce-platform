## 1. 命名规范

| 对象 | 规范 | 示例 |
|---|---|---|
| URL 路径 | 小写 kebab-case，资源用复数名词 | `/api/v1/products`、`/api/v1/order-items` |
| 路径参数 | 小写 snake_case | `/api/v1/orders/{order_no}` |
| JSON 字段 | 小写 snake_case | `total_amount_cents` |
| 枚举值 | 全大写 snake_case 字符串 | `PENDING_PAYMENT` |
| 数据库库名 | 小写 snake_case | `ecommerce_order` |
| 数据库表名 | 小写 snake_case，复数名词 | `order_items` |
| 数据库字段 | 小写 snake_case | `created_at` |
| 主键索引 | `pk_表名` | `pk_orders` |
| 唯一索引 | `uk_表名_字段` | `uk_orders_order_no` |
| 普通索引 | `idx_表名_字段` | `idx_orders_user_id_status` |
| Redis Key | `{服务名}:{实体}:{标识}` | `catalog:product:1234` |
| 事件类型 | `{领域}.{动作}` 过去式 | `order.created` |
| 消息队列 | `{消费服务}.{事件类型}` | `notification.order.created` |
| 环境变量 | 全大写 snake_case | `DATABASE_URL` |

## 2. 通用响应格式

### 2.1 成功响应

HTTP 状态码 `200` / `201`：

```json
{
  "code": "OK",
  "message": "success",
  "data": {
    "order_no": "SO20260910000001",
    "status": "PENDING_PAYMENT"
  },
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "timestamp": "2026-09-10T08:30:00.123Z"
}
```

- `204 No Content` 场景（如登出、删除）不返回 body
- `data` 为对象或数组；无返回内容时给 `null`

### 2.2 失败响应

```json
{
  "code": "ORD-5001",
  "message": "库存不足",
  "details": [
    {
      "field": "items[0].sku_id",
      "reason": "可售库存不足，当前可售 2 件"
    }
  ],
  "data": null,
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "timestamp": "2026-09-10T08:30:00.123Z"
}
```

- `message` 必须是可直接展示给用户的中文文案
- `details` 可选，用于字段级校验错误或批量失败明细
- 所有 HTTP 非 2xx 响应必须使用此结构

### 2.3 分页响应

请求参数固定为 `page`（从 1 开始，默认 1）与 `page_size`（默认 20，最大 100）。

```json
{
  "code": "OK",
  "message": "success",
  "data": {
    "items": [],
    "pagination": {
      "page": 1,
      "page_size": 20,
      "total": 135,
      "total_pages": 7
    }
  },
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "timestamp": "2026-09-10T08:30:00.123Z"
}
```

数据量可能极大的列表（订单流水、支付流水、通知记录）必须额外支持游标分页：请求 `cursor` + `limit`，响应 `next_cursor` + `has_more`。偏移分页与游标分页二选一，同一接口不得混用。

## 3. 错误码规范

### 3.1 格式

```
{服务前缀}-{四位数字}
```

服务前缀分配（**各服务不得越界使用**）：

| 前缀 | 归属服务 |
|---|---|
| `COMMON` | 通用（网关与所有服务共用） |
| `USER` | 用户服务 |
| `CAT` | 商品目录服务 |
| `CART` | 购物车服务 |
| `ORD` | 订单服务 |
| `PAY` | 支付服务 |
| `NOT` | 通知服务 |

### 3.2 号段划分

| 号段 | 含义 | HTTP 状态码 |
|---|---|---|
| 1000-1999 | 请求参数缺失、格式错误、校验失败 | 400 |
| 2000-2999 | 未认证（令牌缺失、过期、签名无效） | 401 |
| 3000-3999 | 无权限（角色不足、越权访问他人资源） | 403 |
| 4000-4999 | 资源不存在 | 404 |
| 5000-5999 | 业务规则冲突（状态不允许、重复提交、库存不足、余额不符） | 409 |
| 6000-6999 | 请求过频、并发冲突、乐观锁失败 | 429 |
| 7000-7999 | 下游依赖不可用（第三方超时、内部服务调用失败） | 502 |
| 8000-8999 | 服务内部错误（未捕获异常、数据库故障） | 500 |
| 9000-9999 | 预留 | — |

### 3.3 通用错误码

所有服务都必须支持以下通用码：

| 错误码 | 含义 | HTTP |
|---|---|---|
| `COMMON-1001` | 请求参数校验失败 | 400 |
| `COMMON-1002` | 请求体格式错误 | 400 |
| `COMMON-2001` | 缺少访问令牌 | 401 |
| `COMMON-2002` | 访问令牌无效或已过期 | 401 |
| `COMMON-2003` | 刷新令牌无效或已过期 | 401 |
| `COMMON-3001` | 无权限执行该操作 | 403 |
| `COMMON-4001` | 请求的资源不存在 | 404 |
| `COMMON-6001` | 请求过于频繁，请稍后重试 | 429 |
| `COMMON-7001` | 依赖服务暂不可用，请稍后重试 | 502 |
| `COMMON-8001` | 服务内部错误 | 500 |

## 4. 认证与授权约定

### 4.1 用户认证

- 采用 JWT：**访问令牌** 有效期 30 分钟，**刷新令牌** 有效期 14 天
- 访问令牌载荷必须包含：`sub`（user_id）、`roles`（角色数组）、`iat`、`exp`、`jti`
- 刷新令牌持久化存储（用户服务），登出时吊销；改用 Redis 黑名单记录已吊销的 `jti`
- 密码使用 **argon2id** 哈希，禁止 MD5/SHA1/可逆加密

### 4.2 令牌传递

客户端仅需携带访问令牌：

```
Authorization: Bearer <access_token>
```

### 4.3 网关注入的请求头

网关校验令牌通过后，向下游注入以下头部。**下游服务只信任这些头部，不自行解析令牌**：

| 请求头 | 说明 |
|---|---|
| `X-User-Id` | 已认证用户 ID（字符串形式的整型 ID）；未登录时不注入 |
| `X-User-Roles` | 角色列表，逗号分隔，如 `BUYER,ADMIN` |
| `X-Request-Id` | 客户端请求 ID，客户端未传则由网关生成 |
| `X-Trace-Id` | 链路追踪 ID |
| `X-Client-Ip` | 客户端真实 IP |
| `X-Internal-Token` | 服务间调用凭证 |

**安全强制要求**：网关必须**剥离**外部请求传入的 `X-User-Id`、`X-User-Roles`、`X-Internal-Token`，防止伪造身份。服务间调用必须携带有效 `X-Internal-Token`，服务端校验失败返回 `COMMON-2002`。

### 4.4 权限校验

- 网关只做"是否登录"的粗粒度校验与白名单放行
- **资源归属校验必须在业务服务内完成**：涉及 `user_id` 的查询与写入，一律以 `X-User-Id` 为准，禁止信任请求参数中的 user_id
- 后台接口需在服务内校验角色，角色不足返回 `COMMON-3001`
- 越权访问他人资源返回 `COMMON-3001`（而非 404），避免暴露资源是否存在

### 4.5 免登录白名单

注册、登录、找回密码、商品浏览与搜索、商品详情、支付回调、健康检查、指标端点无需登录。

## 5. 通用请求头

| 请求头 | 必填 | 说明 |
|---|---|---|
| `Authorization` | 视接口 | `Bearer <access_token>` |
| `X-Request-Id` | 否 | 客户端生成的请求唯一标识，用于排障 |
| `Idempotency-Key` | 写接口视情况 | 幂等键，见第 7 章 |
| `Content-Type` | 是（有请求体时） | 固定 `application/json` |
| `Accept-Language` | 否 | 语言偏好，默认 `zh-CN` |

## 6. 幂等设计约定

| 场景 | 幂等键来源 | 存储 | TTL | 重复请求行为 |
|---|---|---|---|---|
| 创建订单 | 客户端生成 `Idempotency-Key` | Redis + 订单表唯一索引 | 24 小时 | 返回首次创建的订单，不重复下单 |
| 发起支付 | 订单号 + 渠道 | Redis + 支付单表唯一索引 | 7 天 | 返回已有支付单 |
| 支付回调 | 第三方交易号 | 支付流水表唯一索引 | 永久 | 直接返回成功，不重复入账 |
| 退款申请 | 客户端生成 `Idempotency-Key` | Redis + 退款单表唯一索引 | 7 天 | 返回已有退款单 |
| 事件消费 | `event_id` | Redis 已处理集合 | 7 天 | 跳过，记录 debug 日志 |

实现要求：Redis `SET key value NX EX ttl` 抢占成功才执行业务，失败则返回首次结果。数据库唯一索引为最终兜底，捕获唯一键冲突异常后转查询返回。

## 7. 数据表示约定

### 7.1 标识符

| 类型 | 规则 |
|---|---|
| 主键 `id` | 雪花算法生成的 64 位整数，数据库中为 `BIGINT`，**JSON 中序列化为字符串**（避免前端精度丢失） |
| 业务单号 | 有业务含义的字符串，如订单号 `SO20260910000001`、支付单号 `PA20260910000001`、退款单号 `RF20260910000001` |
| 事件 ID `event_id` | UUID v4 字符串 |

### 7.2 金额

- 统一使用 **BIGINT 存储最小货币单位（分）**，字段名以 `_cents` 结尾，如 `total_amount_cents`
- 禁止使用浮点类型
- 涉及金额的表必须含 `currency` 字段（`CHAR(3)`，ISO 4217，本期固定 `CNY`）
- JSON 中金额同时给出整数分值，如 `"total_amount_cents": 19900`

### 7.3 时间

- 数据库统一使用 `TIMESTAMPTZ`，以 **UTC** 存储
- JSON 序列化为 ISO 8601 带毫秒与 `Z`，如 `2026-09-10T08:30:00.123Z`
- 面向用户的展示时间由前端按本地时区转换
- 需要过期语义的字段显式命名，如 `expires_at`、`paid_at`

### 7.4 布尔与枚举

- 布尔字段以 `is_` 前缀命名，如 `is_default`
- 枚举一律使用**全大写字符串**，禁止用数字编码；数据库中用 `VARCHAR(32)` + `CHECK` 约束

## 8. 数据库通用约定

### 8.1 公共字段

每张业务表必须包含：

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| `id` | BIGINT | PK | 雪花 ID |
| `created_at` | TIMESTAMPTZ | NOT NULL DEFAULT now() | 创建时间 |
| `updated_at` | TIMESTAMPTZ | NOT NULL DEFAULT now() | 更新时间，由应用层或触发器维护 |

按需追加：

| 字段 | 用途 |
|---|---|
| `deleted_at` | 软删除标记，仅用户、地址、商品等需要"删除后仍可追溯"的表使用 |
| `version` | 乐观锁版本号，库存、订单状态等并发敏感表必须携带 |

### 8.2 约束与索引

- **不使用物理外键**，跨表引用由应用层保证，避免服务间与表间强耦合
- 唯一约束用 `UNIQUE` 索引显式声明
- 查询条件与排序字段必须建索引；复合索引遵循最左前缀，区分度高的字段在前
- 单表索引数量建议不超过 6 个

### 8.3 隔离要求

- 一服务一库，数据库账号仅授权本库，禁止跨库查询
- 跨服务引用只存对方 ID（如订单表存 `user_id`、`sku_id`），不存对方可变字段；必须展示的信息采用**下单时快照**

## 9. 缓存约定

### 9.1 Key 规范

```
{服务名}:{实体}:{标识}[:{子标识}]
```

示例：`user:profile:1024`、`catalog:spu:2001`、`cart:items:1024`、`order:detail:SO20260910000001`

### 9.2 TTL 基线

| 数据类型 | TTL |
|---|---|
| 商品详情、分类树 | 30 分钟（变更时主动失效） |
| 用户资料 | 15 分钟 |
| 购物车 | 30 天（并异步落库持久化） |
| 幂等键 | 见第 6 章 |
| 库存可售量 | 不设 TTL，以数据库为准定期校准 |

### 9.3 一致性策略

- 写操作：**先写数据库，再删除缓存**（Cache-Aside 失效模式），禁止先删缓存后写库
- 缓存未命中：回源数据库并回填，回填需设置 TTL
- 强一致的读（库存、订单状态）**不走缓存**，直接读数据库
- 缓存穿透防护：不存在的键缓存空值并设置短 TTL（60 秒）；热点 Key 采用逻辑过期避免击穿

## 10. 事件与消息约定

### 10.1 交换机与队列

- Exchange：`ecommerce.events`，类型 `topic`，持久化
- Routing Key = `event_type`
- 消费队列命名：`{消费服务名}.{event_type}`，如 `notification.order.created`
- 死信：每个队列配置 DLX `ecommerce.events.dlx`，死信队列命名 `{队列名}.dlq`

### 10.2 事件信封

所有事件必须使用统一信封：

```json
{
  "event_id": "9f1c2b3a-4d5e-6f70-8192-a3b4c5d6e7f8",
  "event_type": "order.created",
  "event_version": "1.0",
  "occurred_at": "2026-09-10T08:30:00.123Z",
  "producer": "order-service",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "payload": {}
}
```

### 10.3 标准事件目录

跨服务事件以此目录为准。各服务不得擅自更名或改变语义；新增事件需同步更新本文档。

| event_type | 生产者 | 消费者 | payload 核心字段 |
|---|---|---|---|
| `user.registered` | 用户服务 | 通知服务 | `user_id`、`account`、`email`、`phone`、`nickname` |
| `order.created` | 订单服务 | 支付服务、通知服务 | `order_no`、`user_id`、`total_amount_cents`、`currency`、`expires_at`、`items[]`（`sku_id`、`quantity`） |
| `order.paid` | 订单服务 | 商品目录服务、通知服务 | `order_no`、`user_id`、`paid_at`、`items[]`（`sku_id`、`quantity`） |
| `order.cancelled` | 订单服务 | 商品目录服务、支付服务、通知服务 | `order_no`、`user_id`、`reason`、`items[]`（`sku_id`、`quantity`） |
| `order.shipped` | 订单服务 | 通知服务 | `order_no`、`user_id`、`carrier`、`tracking_no`、`shipped_at` |
| `payment.succeeded` | 支付服务 | 订单服务 | `payment_no`、`order_no`、`amount_cents`、`currency`、`channel`、`paid_at` |
| `payment.failed` | 支付服务 | 订单服务、通知服务 | `payment_no`、`order_no`、`reason`、`failed_at` |
| `payment.refunded` | 支付服务 | 订单服务、通知服务 | `refund_no`、`payment_no`、`order_no`、`amount_cents`、`refunded_at` |
| `stock.low` | 商品目录服务 | 通知服务 | `sku_id`、`spu_title`、`spec_name`、`available`、`threshold` |

**关键链路**：`payment.succeeded` → 订单服务置为已支付 → 订单服务发出 `order.paid` → 商品目录服务正式扣减库存。两步不可合并，订单状态与库存扣减分别由各自服务负责。

### 10.4 发布与消费要求

- **事务性发件箱**：业务数据与待发事件写入同一本地事务（`outbox_events` 表），由后台任务投递至 MQ，保证"业务成功则事件不丢"
- **消费幂等**：按 `event_id` 去重（见第 6 章）
- **重试策略**：消费失败按指数退避重试，间隔 `1s / 5s / 30s / 2m / 10m`，共 5 次；仍失败则进入死信队列并触发告警
- **顺序性**：同一订单的事件需保证顺序。按 `order_no` 作为分区键路由到同一队列（或消费端按序处理），跨聚合不保证全局顺序
- 消费端只依赖 `event_id`、`event_type`、`payload` 三个字段，新增字段必须可选

## 11. 服务间调用约定

### 11.1 调用规范

- 协议：HTTP/JSON，路径前缀 `/api/v1`
- 内部接口统一置于 `/internal/` 命名空间，**网关不对外暴露**，如 `/internal/v1/inventory/reserve`
- 必须设置超时：连接 1s，读取 3s
- 必须携带 `X-Internal-Token`、`X-Request-Id`、`X-Trace-Id`

### 11.2 重试与熔断

| 场景 | 重试 | 说明 |
|---|---|---|
| 只读查询 | 最多 2 次，指数退避 | 幂等安全 |
| 写操作 | **默认不重试** | 由业务层幂等键控制，避免重复扣减 |
| 下游连续失败 | 熔断 30 秒 | 熔断期间快速失败并走降级 |

### 11.3 降级策略

| 场景 | 降级行为 |
|---|---|
| 商品服务不可用（列表页） | 返回缓存快照 |
| 通知服务不可用 | 主流程继续，事件进队列待重试 |
| 评价数查询失败 | 展示为 0，不影响主流程 |

## 12. 日志与链路追踪

### 12.1 日志格式

所有服务输出结构化 JSON 到 stdout：

```json
{
  "ts": "2026-09-10T08:30:00.123Z",
  "level": "INFO",
  "service": "order-service",
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736",
  "span_id": "b7ad6b7169203331",
  "user_id": "1024",
  "method": "POST",
  "path": "/api/v1/orders",
  "status": 201,
  "duration_ms": 142,
  "msg": "order created"
}
```

### 12.2 埋点要求

- 每个入站请求生成或继承 `trace_id`，通过请求头向下游与 MQ 事件传递
- 出站调用、数据库慢查询（>500ms）、MQ 发布/消费均需记录日志
- 异常必须记录堆栈，但**不得记录敏感字段**

### 12.3 脱敏清单

| 字段 | 处理 |
|---|---|
| 密码、令牌、`X-Internal-Token` | 完全不记录 |
| 手机号 | 保留前 3 后 4，中间掩码 |
| 邮箱 | 保留首字符与域名，中间掩码 |
| 银行卡号、CVV | 平台不存储，日志中出现即视为缺陷 |
| 收货地址 | 日志中只记录地址 ID，不记录明细 |

## 13. 配置管理

- 环境变量优先，通过 `.env` 注入；`.env` 不入版本库，仅提交 `.env.example`
- 非敏感配置存 Consul KV，按 `dev` / `test` / `prod` 前缀隔离
- 密钥类（数据库口令、JWT 密钥、第三方 API Key）通过密钥管理服务注入，禁止硬编码

各服务必须声明的配置项（补充各服务特有项）：

| 环境变量 | 说明 |
|---|---|
| `APP_ENV` | 运行环境：`dev` / `test` / `prod` |
| `APP_PORT` | 服务监听端口 |
| `DATABASE_URL` | PostgreSQL 连接串 |
| `REDIS_URL` | Redis 连接串 |
| `RABBITMQ_URL` | RabbitMQ 连接串 |
| `JWT_PUBLIC_KEY` | 令牌验签公钥 |
| `INTERNAL_TOKEN` | 服务间调用令牌 |
| `CONSUL_HOST` | Consul 地址 |
| `LOG_LEVEL` | 日志级别，默认 `INFO` |

## 14. 服务代码目录结构

各服务统一采用如下结构，详细设计中引用代码位置时以此为准：

```
service-name/
├── app/
│   ├── main.py                  # 应用入口、路由挂载、生命周期
│   ├── api/
│   │   └── v1/                  # 对外路由
│   │   └── internal/            # 内部接口路由
│   ├── core/                    # 配置、日志、异常、安全、依赖注入
│   ├── models/                  # SQLAlchemy ORM 实体
│   ├── schemas/                 # Pydantic 请求/响应模型
│   ├── services/                # 业务逻辑
│   ├── repositories/            # 数据访问
│   ├── events/                  # 事件发布（outbox）与订阅消费者
│   ├── clients/                 # 其他服务的调用客户端
│   └── tasks/                   # 定时任务
├── alembic/                     # 数据库迁移
├── tests/
│   ├── unit/
│   └── integration/
├── Dockerfile
├── pyproject.toml
└── .env.example
```

分层依赖方向：`api → services → repositories → models`，禁止跨层反向调用；跨服务调用只允许出现在 `services` 层，通过 `clients` 封装。

## 16. 详细设计文档模板

各服务详细设计文档必须包含以下章节：

1. **服务概览** — 职责、边界、上下游依赖、对应需求编号（FR-xxx）
2. **数据库设计** — 表清单、逐表字段定义、索引设计、枚举字典、完整 DDL
3. **API 设计** — 接口清单、逐接口明细（路径、方法、鉴权、参数、请求体、响应体、错误码、示例）
4. **内部接口设计** — 服务间调用接口（如有）
5. **事件设计** — 发布事件 Schema、订阅事件与处理逻辑
6. **核心业务流程** — 关键场景的步骤说明与伪代码（状态机、并发控制、补偿逻辑）
7. **缓存设计** — Key、TTL、失效时机
8. **定时任务** — 任务名、周期、职责、幂等要求
9. **错误码表** — 本服务完整错误码清单
10. **安全与权限** — 鉴权要求、数据归属校验、脱敏
11. **配置项** — 本服务特有配置
12. **测试要点** — 单元测试与集成测试关键用例
